# 集群接入

> 💡 管理平台纳管的 TiDB 集群：一个平台可以同时管理多个集群（测试 / 预发 / 生产各一套都行），在这里接入、查看、测试、编辑、移除集群；日常在页面顶栏的集群下拉里切换。**接入、编辑、测试、移除集群需要「修改平台设置」能力（settings.edit，默认只有内置「管理员」角色）**；切换集群所有登录用户都能用（只能切换到自己可见的集群）。**只有运维模式（后端带 `--data-dir`）才有集群注册表；只读 / 回放模式（没有登录）仍是单集群，本页只有一张说明卡片。**

> ⚠️ 本平台至今只在「回放数据 + 模拟执行器」下测试过，**没有连过真实的 TiDB / tiup 集群**。本篇里「live 实时集群」的连通性测试、自动探测、sudo 策略文件的配合，都是按代码与官方文档写的，以真实集群联调结果为准（联调清单见 `docs/运维部署手册.md` 12.7）。

> 🧭 **中控机模式（`install.sh --local-tiup`）**：平台装在 tiup 中控机上、不预设集群。点右上角 **「从本机 tiup 导入」**，列表里列出本机 tiup 管理的全部集群，勾选、选环境（可选填一个只读 SQL 账号）后导入——导入的集群标「**本机 tiup · 可运维**」，可做全部运维操作（写操作仍需两名管理员开启写开关，高风险变更仍需审批）。导入只运行只读的 `tiup cluster list / display` 读出各组件地址，**不改动集群，也不读取或传输 SSH 私钥**（tiup 用部署用户自己的密钥连各节点）。**「＋ 手工接入远程集群（只读）」** 添加的集群标「**远程接入 · 只读**」，平台碰不到它的 tiup / SSH，即使打开写开关也不能执行变更；要运维它，先删除（只是移除纳管），再从本机 tiup 导入。
>
> 🧭 **独立部署（`install.sh --standalone`）**：平台不在任何集群的中控机上，本身不代表任何集群，所以刚装好时这里是空的，其他集群数据页会显示「尚未接入集群」。管理员在这里「＋ 接入集群」添加已有集群：**PD 地址必填**（本机没有 tiup 可自动探测），建议同时填 Prometheus、Alertmanager、TiDB status 和只读 SQL 账号（没填的项在页面里显示「数据缺失」）。独立部署下接入的集群是**只读接入**——总览、拓扑、慢 SQL、热点、告警、诊断可用，扩缩容 / 配置变更 / 重启 / 维护 / 备份等写操作不可用，需要在集群的中控机上执行；「tiup 集群名」只是标识，高级里没有 tiup 相关字段；测试也不再探测 tiup。独立部署的平台实例不计入 20 个集群的上限。

## 这个页面做什么

- 列出平台纳管的全部集群：显示名、环境、模式（live / replay）、状态（版本 / 节点数 / 上次快照 / 是否可达）、写操作开关状态。
- 「＋ 接入集群」：登记一个新集群，登记后**立即生效，不需要重启平台**。
- 对每个集群：「测试」（只读连通性探测）、「编辑」、「删除」（只是移除纳管）、「切换到该集群」。
- 最多纳管 **20 个**集群（含主集群）。

## 先搞清几个概念

### 一个平台，多个「集群实例」

平台启动时由启动参数（`--cluster`、`--env`、`--pd` 等）定义的那个集群叫**主集群**；在本页接入的叫**其他集群**。每个集群在平台里是一个独立的「实例」。下表说清哪些东西**每个集群各管各的**，哪些是**全平台共用一份**：

| 范围 | 内容 | 对你意味着什么 |
|---|---|---|
| 每个集群独立 | 数据采集（总览 / 架构 / 慢 SQL / 热点 / 诊断都是当前集群的） | 切换集群后所有看数据的页面都换成该集群的 |
| 每个集群独立 | 变更与审批队列（变更编号、待审批、排队、定时、任务中心） | 在 A 集群提交的变更，在 B 集群看不到；编号 `CHG-0001` 各集群各自从头编，会重复 |
| 每个集群独立 | 写操作开关（含两名管理员确认） | 在生产集群开了写开关，不影响预发集群；新接入的集群写开关默认关闭 |
| 每个集群独立 | 变更窗口规则、变更冻结期、「集群前有负载均衡」标志 | 每个集群各配各的 |
| 每个集群独立 | 通知渠道（企业微信 / 钉钉 / 飞书 / Lark / Slack / 其他） | 每个集群各自添加渠道；消息里带「环境」与「集群」 |
| 每个集群独立 | 候选主机池、巡检结果 | 主机池登记在当前集群下；巡检保存的是该集群最近一次结果 |
| 每个集群独立 | 环境（测试 / 预发 / 生产） | 决定该集群里每个人是什么角色（见下） |
| 全平台共用 | 用户、自定义角色、登录会话 | 登录一次，所有可见集群通用；退出登录 / 被禁用 / 被重置口令，对所有集群同时生效 |
| 全平台共用 | 审批策略（风险 × 环境）、双人复核提案（授予管理员、修改审批策略） | 审批策略按环境取列：预发集群用「预发」那一列，生产集群用「生产」那一列 |
| 全平台共用 | 审计日志（同一条哈希链）、READONLY 熔断文件 | 审计里用「集群」列区分；中控机上放一个 READONLY 文件，**所有集群**都变成强制只读 |

### 环境决定「这个集群里你是谁」

- 每个集群有一个**环境**：测试 / 预发 / 生产。角色是**按环境**分配给用户的（见 [用户管理](help:users) 的「角色按环境分配」）。所以：你在某个集群里有什么角色、能做什么，由**该集群的环境**决定，与你在别的环境的角色无关。
- **可见性**：你至少要在该集群的环境里有「查看总览」能力（所有内置角色都有），才能看到这个集群。看不到的集群，在顶栏下拉里没有，直接访问它的数据接口得到的是「集群不存在或无权访问」（HTTP 404），**与集群真的不存在时的表现完全一样**，平台不会泄露某个集群是否存在。
- 举例：平台里有「生产」集群 prod-a 和「测试」集群 dev-a。用户 bob 的角色设置是「所有环境 = 访客；测试单独设置 = DBA」，则 bob 在 dev-a 里是 DBA、在 prod-a 里是访客，两个集群他都看得到。用户 carol 只在「测试」单独设置了角色，「所有环境」没设，则她**只看得到** dev-a，prod-a 对她等于不存在。

### id、name、显示名是三个不同的东西

| 叫法 | 界面字段 | 作用 | 例子 |
|---|---|---|---|
| 集群 id | 「集群 id」 | 平台内部的唯一短名，创建后**不能修改**；用在请求头、数据目录名里 | `stg` |
| tiup 集群名 | 「tiup 集群名 name」 | 中控机上 `tiup cluster list` 的 Name 列里的名字；平台所有 tiup 命令、审计的「集群」列、通知消息里的「集群：」都用它 | `stg-tidb-01` |
| 显示名 | 「显示名」 | 顶栏下拉与列表里显示的名字，可随时改 | `预发集群` |

id 与 tiup 集群名**在整个平台（含主集群）里不能互相冲突**：不能有两个集群用同一个 id 或同一个 tiup 集群名，也不能让一个集群的 id 等于另一个集群的 tiup 集群名。主集群的 id 由启动参数 `--cluster` 的值转换而来（小写，非字母数字的字符变成 `-`），例如 `--cluster prod-tidb-01` 对应 id `prod-tidb-01`。

### 两种模式：live 与 replay

| 模式 | 数据从哪来 | 变更执行 | 适用 |
|---|---|---|---|
| live 实时 | 平台直接访问这个集群的 PD / TiDB 状态端口 / Prometheus / Alertmanager / SQL / tiup（只读） | 沿用平台的执行器（`direct` / `sudo`，见 [快速入门](help:quickstart) 的「执行器」） | 管理真实集群 |
| replay 回放 | 读取一份 fixtures 数据包（样例数据），不连接任何真实组件 | **恒用模拟执行器**：流程完整，但不会作用于任何真实集群 | 演示、培训、联调前演练 |

## 怎么用（按步骤）

### 第 0 步：确认你在运维模式、有没有权限

1. 登录平台。顶栏右侧能看到环境标签、你的角色和用户名，说明是运维模式（没有的话见 [快速入门](help:quickstart)）。
2. 看顶栏页面标题右边的集群下拉框。
   - 你会看到：一个下拉框，每个选项形如「预发集群（预发）」。**能点开且有多个选项**，说明你能看到多个集群。
   - 下拉框是灰色的，悬停提示「当前账号只能看到这一个集群」：你只能看到一个集群（可能只纳管了一个，也可能你在其他集群的环境里没有角色），无需也无法切换。
3. 看侧栏「平台配置」分组。**「集群接入」只对管理员显示**（需要 settings.edit）；没有这个菜单说明你没有管理权限，可以切换集群，但不能接入 / 编辑 / 删除。手工打开 `#clusters` 地址也只会看到说明「只有集群管理员（拥有 settings.edit 能力）可以管理集群接入。你可以用顶栏的集群下拉在自己可见的集群之间切换。」

> 💡 「集群接入」的授权按**主集群的环境**判断：你要在主集群的环境里有 settings.edit。内置管理员通常设置在「所有环境」，没有问题；如果某个管理员只在某个非主集群的环境里有角色，他管不了集群接入，也管不了用户和角色（见本篇末尾「已知限制与易混淆点」）。注意：「集群接入」菜单的显示就是按这个主集群授权判断的；而「用户管理」「角色权限」菜单按你**当前所选集群**的环境判断是否显示，所以这种管理员切到那个非主集群后可能看到这两个菜单，但打开页面会被拒绝。

### 一、在顶栏切换集群

**前置条件**：运维模式、已登录，且你能看到至少两个集群。

1. 看页面标题右边的集群下拉框。你会看到：
   - 每个选项是「显示名（环境）」，如「开发集群（测试）」；集群启动失败时选项末尾会多一个「 · 异常」。
   - 下拉框的**颜色按当前集群的环境着色**：测试是绿色、预发是橙色、生产是红色。**当前集群是生产环境时**，下拉框右边还会多一个红底白字的「生产环境」标签，悬停提示「当前集群是生产环境：操作需更严格审批，请谨慎」。
2. 点开下拉框，选另一个集群。
   - 如果这时你开着右侧抽屉、或页面上有未保存的内容，浏览器会先弹出确认框「当前有打开的抽屉或未保存的内容，切换到集群「X」会刷新页面并丢弃它们。确定切换吗？」。点「确定」继续切换；点「取消」留在原集群，下拉框回到当前集群，什么都没丢。
3. 页面会**整页刷新**，并停留在你当前所在的页面（例如还在「节点管理」）。刷新后你会看到：
   - 下拉框选中了新集群，浏览器标签页标题变成「页面名 · 新集群显示名 · TiDB 运维平台原型」；
   - 顶栏右侧的环境标签（悬停显示「集群 X 的环境」）、「写操作已开启 / 只读」、你的角色，**全部变成新集群的**；
   - 总览顶部横幅里的「集群 xxx」（回放时写「回放数据 · 集群 xxx」）是该集群自己的集群名（来自采集到的拓扑 / 数据包）；
   - 节点、变更、告警、慢 SQL 等所有数据都是新集群的。
4. 你的选择**记在这个浏览器的 localStorage 里**（键名 `opCluster`）：下次打开平台自动回到你上次选的集群。换浏览器、用隐私窗口、清理站点数据后，会回到「默认集群」——主集群（如果你对它可见），否则是你可见的第一个集群。

**后果**：切换只是换一个「看哪个集群」，不会改动服务器上的任何东西，也不用重新登录（登录会话是全平台共用的）。

> ⚠️ **每次动手前先看顶栏**：集群下拉框的颜色与「生产环境」红色标签，以及变更提交面板顶部的「集群 X」标签（见 [节点管理](help:nodes)）。同一个浏览器同时开两个标签页时，每个标签页各用自己页面里的集群，但**刷新后都会回到最后一次选择的那个集群**，容易搞混——建议一个浏览器只开一个集群。

**集群不可用时的自动处理**：如果你正在使用的集群被管理员删除了、你在它的环境里的角色被拿掉了、或者它的环境被改成你没有角色的环境，你的下一个请求会得到「集群不存在或无权访问」。页面会自动清除保存的选择并刷新，回到默认集群，底部提示「当前集群已不可用，已切换到默认集群」。为防止反复刷新，连续自动处理最多 3 次；超过后请手工清除本站点的浏览器存储（localStorage 的 `opCluster`）再刷新，或联系管理员确认你的权限。排查步骤见 [常见问题](help:faq) 的「集群相关」。

### 二、查看集群列表与状态（管理员）

**前置条件**：settings.edit。

1. 点侧栏「平台配置」→「集群接入」。你会看到标题「集群接入」，旁边写「N / 20 个集群」，右边有「刷新」和「＋ 接入集群」。表格列：集群、环境、模式、状态、写开关、操作。
2. 逐列读（含义见下文「列表每一列」）。页面每隔约 9 秒自动刷新状态（打开了抽屉或正在输入时不刷新）；也可点「刷新」，提示「已刷新」。
3. 刚接入的集群，状态列可能暂时没有「可达 / 不可达」标签，「上次快照」显示「—」：平台接入后会在后台做第一次采集（最长约 60 秒），稍后自动出现。

### 三、接入一个回放（replay）集群

**前置条件**：settings.edit；有一份 fixtures 数据包目录（里面有 `manifest.json`），并且它位于**允许的根目录**之下。允许的根目录由平台启动参数 `--fixtures-root` 指定（可写多个，逗号分隔）；没指定时，只允许与启动参数 `--fixtures` 同级的目录（没有 `--fixtures` 就不能添加回放集群）。具体根目录会显示在接入抽屉的「fixtures 目录」输入框下方，形如「可用根目录：D:\tidb\fixtures」。数据包用 `tidbops-fixtures` 工具生成（演示数据用 `tidbops-fixtures demo --profile stg --out fixtures/stg`；从真实集群导出用 `tidbops-fixtures -h` 查看用法）。

1. 在「集群接入」页点「＋ 接入集群」。你会看到右侧抽屉「接入集群」。
2. 在「集群 id」里填一个 id，例如 `dev`。输入时下方实时提示：灰字是规则（2 到 32 位，小写字母开头，只含小写字母 / 数字 / 连字符；创建后不可修改）；红字「✖ 格式不符…」或「✖ 该 id 已存在」要先改掉；绿字「✔ 可用」可以继续。
3. 「显示名」填顶栏里想看到的名字（最多 40 字），例如 `开发集群`；留空 = 用 id。
4. 「tiup 集群名 name」：回放集群没有真实的 tiup 集群，可以留空（默认等于 id）；但它会出现在审计与通知里，建议填成有意义的名字，例如 `dev-tidb-01`，且不能与其他集群的 id / 名字冲突。
5. 「描述」可选，最多 200 字。
6. 「环境」选「测试环境」/「预发环境」/「生产环境」。**这一步决定谁在这个集群里有什么角色**，选错会让不该看到的人看到它，请对照「环境决定『这个集群里你是谁』」。选「生产环境」时抽屉里会出现黄色提示「生产环境：更严格审批。高风险变更需要更多级审批 / MFA，写操作默认关闭并需两名管理员确认开启（具体以「审批策略」为准）。」
7. 「模式」选「replay 回放」。抽屉下半部分变成「数据包（replay）」。
8. 「fixtures 目录」填数据包的**绝对路径**，例如 `/opt/tidbops/fixtures/dev`（必须在上面「可用根目录」之下；符号链接会先解析成真实路径再比较）。
9. 点「接入集群」。你会看到：抽屉标题变成「已接入集群：开发集群」，绿色提示「集群 开发集群（dev）已接入，环境 测试，模式 replay。」，下面有「切换到该集群」「关闭」按钮。列表里出现新的一行。
10. 与预期不符：抽屉里红字提示失败原因，对照下文「错误提示对照」处理，修正后再点「接入集群」。

**后果**：新集群立即可用，写开关默认**关闭**；回放集群恒用模拟执行器，之后在这个集群里提交的变更只在平台里走流程，**不会改动任何真实集群**。审计里多一条 `cluster.add`（风险：中）。

### 四、接入一个实时（live）集群

**前置条件**：settings.edit；运维模式；平台所在的中控机能访问这个集群的各组件；你已经按下表准备好信息。

**接入前准备清单**（占位符都在表里解释）：

| 要准备什么 | 从哪里取 | 示例 | 说明 |
|---|---|---|---|
| tiup 集群名 | 在中控机上执行 `tiup cluster list`，看 Name 列 | `stg-tidb-01` | 必须与 tiup 里的名字**完全一致**；平台所有 tiup 命令都带它。注意 `tiup cluster list` 只列出**当前系统用户**部署的集群（官方说明），要在部署集群的那个用户（通常是 `tidb`）下执行。它**不是**平台 id |
| PD 地址 | `tiup cluster display <集群名>` 输出里任一 PD 行的 Host 与客户端端口（默认 2379），写成 `http://主机:端口` | `http://10.20.1.21:2379` | `<集群名>` 就是上一行的 tiup 集群名。只允许 http / https |
| TiDB 状态地址 | 任一 TiDB 实例的 Host 加状态端口（默认 10080） | `http://10.20.1.11:10080` | 平台用它的 `/status` 探测 |
| Prometheus 地址 | 监控节点 Host 加 9090 | `http://10.20.1.31:9090` | 趋势、容量预测、CPU / 内存都靠它；智能诊断的 PD 副本、TiKV 写入链路、主机层（inode / 只读 / 磁盘延迟 / 负载）规则也读它，缺哪项指标，对应规则就不触发（不报错） |
| Alertmanager 地址 | 告警节点 Host 加 9093 | `http://10.20.1.31:9093` | 活跃告警与告警静默 |
| SQL 连接：host / 端口 / 用户 / 密码 | 任一 TiDB 实例的 Host 与服务端口（默认 4000）；一个**只读专用账号** | `10.20.1.11`、`4000`、`readonly` | 见下文「只读账号怎么建」。**这里的账号是采集用的只读账号**，与执行器的「运维账号」（SET GLOBAL / SET CONFIG）是两个账号 |
| mysql 可执行文件 | 中控机上 `which mysql` | `/usr/bin/mysql` | 绝对路径，文件名必须是 `mysql` 或 `mariadb`；留空 = 用平台启动参数 `--mysql-bin` |
| tiup 可执行文件 | 部署用户下 `which tiup` | `/home/tidb/.tiup/bin/tiup` | 绝对路径，文件名必须是 `tiup`；留空 = 用启动参数 `--tiup` |
| tiup 用户的 HOME 目录 | 部署集群的系统用户的家目录 | `/home/tidb` | 用来定位 `~/.tiup/storage/cluster/clusters/<tiup 集群名>/meta.yaml`（配置变更要读它）；留空 = 用平台启动参数 `--home` |

端口的默认值见官方 [TiDB 软件和硬件环境需求 → 网络要求](https://docs.pingcap.com/zh/tidb/stable/hardware-and-software-requirements/)（Prometheus 9090、Alertmanager 9093、PD 2379、TiDB 状态端口 10080、TiDB 服务端口 4000），**以你集群的实际拓扑为准**。**地址留空时**，平台在创建该集群的实例时（接入、编辑后重建、平台重启）会执行一次 `tiup cluster display <tiup 集群名>` 自动探测并补全留空的项（探测最多约 20 秒；平台以 `--no-auto` 启动时不探测）；探测失败不会报错，只是留空的地址没有值，对应数据会缺失。**强烈建议自己填全**，不要依赖自动探测。

**只读账号怎么建**：

- 平台用这个账号只执行**固定的只读查询**：`SELECT tidb_version()`，以及对 `information_schema` 里 `cluster_info`、`cluster_slow_query`（含一条最近 2 小时的聚合统计，不取 SQL 文本）、`cluster_statements_summary`、`session_variables`、`cluster_config`、`tidb_hot_regions` 的 SELECT（平台代码只允许访问 `information_schema` / `performance_schema`）。**它不读业务表**。密码只经环境变量 `MYSQL_PWD` 交给 mysql 客户端，不进命令行与日志。
- 建议用**专用账号**，不授予任何写权限和业务库权限。创建账号的语法见官方 [CREATE USER](https://docs.pingcap.com/zh/tidb/stable/sql-statement-create-user/)，授权见 [GRANT <privileges>](https://docs.pingcap.com/zh/tidb/stable/sql-statement-grant-privileges/)。例如：

```sql
CREATE USER 'readonly'@'10.20.1.%' IDENTIFIED BY '<你设置的强口令>';
```

- 占位符说明：`'readonly'` 是账号名（与接入页「用户」一致）；`'10.20.1.%'` 是允许连接的来源主机（改成平台所在中控机的 IP 或网段）；`<你设置的强口令>` 自己定，之后填进接入页的「密码」。
- **所需的最小权限以真实集群联调为准**：官方文档里上述几张表的页面（[CLUSTER_INFO](https://docs.pingcap.com/zh/tidb/stable/information-schema-cluster-info/)、[SLOW_QUERY / CLUSTER_SLOW_QUERY](https://docs.pingcap.com/zh/tidb/stable/information-schema-slow-query/)、[Statement Summary Tables](https://docs.pingcap.com/zh/tidb/stable/statement-summary-tables/)、[CLUSTER_CONFIG](https://docs.pingcap.com/zh/tidb/stable/information-schema-cluster-config/)、[TIDB_HOT_REGIONS](https://docs.pingcap.com/zh/tidb/stable/information-schema-tidb-hot-regions/)）都没有写明访问需要什么权限；官方 [权限管理](https://docs.pingcap.com/zh/tidb/stable/privilege-management/) 的权限列表里有全局权限 `PROCESS` 和 `CONFIG`，但没有说明它们对这些表是否生效。项目的联调清单给的起步做法是 `GRANT SELECT ON *.* TO 'readonly'@'10.20.1.%'`（比最小权限宽，会允许读业务表，请先确认符合公司安全规范）。接入后如果「测试」里 SQL 项通过、但总览 / SQL 优化页顶部提示「N 项数据缺失」且原因里有慢查询或配置值，就是权限不够，请逐项补授权后再看。

> ⚠️ **多个集群共用 sudo 执行器策略文件时，务必给每个集群配置 `perCluster`，否则非主集群的 SET CONFIG / SET GLOBAL 与告警静默可能打到主集群。** `sudo` 执行器模式下，平台只是把命令交给特权端，特权端读的是**全局唯一的一份**策略文件（`--exec-policy`，安装包默认 `/etc/tidb-ops/exec.json`），其中顶层的 `mysqlHost` / `mysqlPort` 与 `alertURL` 是一套全局值，**没有 `perCluster` 项的集群一律沿用这套全局值**。平台（Web 进程）读不到这份文件的内容，**无法发现你漏配**，界面也不会有任何警告。漏配的后果：在非主集群提交的配置变更（SET CONFIG / SET GLOBAL）会连到全局 `mysqlHost` 所属的那个集群（通常是主集群）去修改配置；在非主集群做的告警静默会创建到全局 `alertURL` 所属的 Alertmanager 上。

**正确做法**（在中控机上，用有权限的账号编辑策略文件）：

1. 把每个要执行变更的 tiup 集群名加进 `clusters` 列表；
2. 为**包括主集群在内的每个集群**在 `perCluster` 里写一项（键是 tiup 集群名），含它自己的 `mysqlHost`、`mysqlPort`、`alertURL`；
3. 把顶层的 `mysqlHost`、`alertURL` 清空（否则漏配的集群会静默沿用它们）。运维账号的名字与口令（`mysqlUser`、`mysqlPwdEnv`）是全局一份，各集群都用它：请在每个集群里创建同名同口令的运维账号，只授予 SET GLOBAL / SET CONFIG 所需权限。

```
{
  "clusters": ["prod-tidb-01", "stg-tidb-01"],
  "tiupBin": "/home/tidb/.tiup/bin/tiup",
  "mysqlHost": "",
  "alertURL": "",
  "perCluster": {
    "prod-tidb-01": {"mysqlHost": "10.0.1.11", "mysqlPort": 4000, "alertURL": "http://10.0.1.31:9093"},
    "stg-tidb-01":  {"mysqlHost": "10.20.1.11", "mysqlPort": 4000, "alertURL": "http://10.20.1.31:9093"}
  }
}
```

上面是只列出与多集群相关的字段的**片段**（其余字段如 `mysqlBin`、`mysqlUser`、`mysqlPwdEnv`、`backupRoots` 保持你原有的值；完整字段见安装包里的 `exec.json.example`）。`prod-tidb-01` / `stg-tidb-01` 是各集群的 tiup 集群名，IP 换成你自己的。特权端每次执行命令都会重新读取策略文件，编辑后对**之后的**命令立即生效（以真实集群联调为准）。`direct` 模式不使用特权端：平台按集群直接构造策略，SQL 地址与告警地址取自各集群自己的接入配置，没有这个问题；但 `direct` 模式下如果策略文件里显式列了 `clusters`，则取交集（不在其中的集群命令会被拒绝），该文件在平台启动时读取，改了要重启平台。

**接入步骤**：

1. 在「集群接入」页点「＋ 接入集群」。你会看到抽屉「接入集群」，「模式」默认就是「live 实时」。
2. 「基本信息」：依次填「集群 id」（如 `stg`）、「显示名」、「tiup 集群名 name」（如 `stg-tidb-01`，**必须与 `tiup cluster list` 里一致**；留空 = 用 id）、「描述」。
3. 「环境」选对应环境（**决定谁在这个集群里有什么角色，也决定审批强度**）。
4. 「连接信息（live）」：填「PD 地址」「TiDB status 地址」「Prometheus 地址」「Alertmanager 地址」。格式必须是 `http://主机:端口` 或 `https://…`，**不能**在地址里写用户名 / 口令，不能带 `?` `#` 查询串、空格、反斜杠，最长 256 字符。
5. 「MySQL host（TiDB SQL）」「端口（留空 = 4000）」「用户」填只读账号信息；「密码」填该账号口令（见下文「密码怎么保存」）。填了 MySQL host 就必须填「用户」。
6. 需要时展开「高级：可执行文件 / 目录（绝对路径，留空用默认）」，填「mysql 可执行文件」「tiup 可执行文件」「tiup 用户的 HOME 目录」。
7. 点「接入集群」。预期结果：抽屉标题变成「已接入集群：…」，绿色提示「集群 …（stg）已接入，环境 预发，模式 live。」；如果有执行器相关的警告，会以橙色 ⚠ 提示框显示在下面（见下一条）；下面还有一行灰字「新集群的写操作开关默认关闭；需要执行变更时，请先切换到该集群，在「权限与审计 → 写操作开关」由两名管理员确认开启。如果提示了 sudo 策略，请在中控机上完成后再提交变更。」
8. **读橙色警告**。`sudo` / `direct` 执行器模式下，平台接入时会经执行器做一次只读预检（`tiup cluster display <tiup 集群名>`）。预检失败会给出形如「执行器预检未通过（…）：该集群的变更 / 巡检命令可能无法执行。sudo 模式下特权端的策略文件（--exec-policy）必须允许集群名 "stg-tidb-01"：请把它加入策略文件的 clusters 列表，并确认 tiup 路径与账号」的提示，同样的警告会一直显示在该集群「状态」列里。处理：按上一节在中控机上修好策略文件，然后**重启平台，或在「编辑」里改动任一连接信息字段并保存**（会重建实例并重新预检）；警告不会自动消失。
9. 点「关闭」关掉抽屉，在列表里找到该集群，按「五、测试连通性」逐项确认。**接入本身不校验连通性**：地址写错、集群连不上也能接入成功，只是之后数据缺失。

**后果**：平台开始用只读账号**周期性查询这个集群**（与主集群一样，采集有缓存）；新集群的写操作开关**默认关闭**，不能提交变更，直到两名管理员在该集群下确认开启。审计里多一条 `cluster.add`（风险：中，摘要只含环境 / 模式 / 地址，**不含任何密码**，只写「已保存数据库密码」）。启动失败（见「错误提示对照」里的 `start`）时整体回滚，不影响其他集群。

#### 密码怎么保存

- 「密码」填的是 live 集群的 **SQL 只读账号口令**。保存时平台用数据目录里的 `master.key` 加密（AES-256-GCM）后写入 `clusters.json` 的 `mysqlPasswordEnc`，**文件里没有明文**，接口、审计、日志里也都没有。
- 界面**永远不回显**密码：「编辑」时密码框是空的，旁边的标签只显示「已保存密码」或「未保存密码」。
- 编辑时：密码框**留空 = 不修改**；填了新值 = 替换；勾选「清除已保存的密码」= 清除（勾选后密码框被禁用）。
- 没有主密钥（`master.key`）时平台拒绝保存密码。备份数据目录时**必须连同 `master.key` 一起备份**：丢了它，已保存的密码无法解密，该集群会变成「异常」，需要在「编辑」里重新填密码（提示「数据库密码无法解密（master.key 是否变更？）：请在集群接入页重新填写密码」）。

### 五、测试连通性

**前置条件**：settings.edit。测试是**只读**的，不会改动集群；它用的是**已保存**的配置（改了配置要先「保存」再测试）；它从**平台所在主机**发起（网络是否通，以平台主机的视角为准）。

1. 在列表里找到集群，点该行的「测试」。你会看到抽屉「测试：集群名」，先显示「正在只读探测…」。
2. 等待结果（逐项执行，每一项最长 10 秒超时，整体最长约 1 分钟）。你会看到一条汇总提示和一张表（列：检查项、结果、耗时、详情）：绿色「全部通过。」、橙色「可用，N 项警告。」或红色「N 项失败」，后面总跟着「只读探测，不会改动集群。」。
3. 逐行读「结果」「详情」，对照下文「测试各项含义与失败怎么办」处理；改完配置再点「重新测试」。

**后果**：测试会写一条审计 `cluster.test`（风险：中；摘要形如「连通性测试：通过 N / 警告 N / 异常 N」，有失败项时结果记为「失败」）。

### 六、编辑集群

**前置条件**：settings.edit。

1. 点该行的「编辑」。抽屉标题「编辑集群：显示名」，「集群 id」显示为「（不可修改）」。
2. 修改需要的字段（规则与「接入」时相同；密码框留空 = 不修改）。
3. 点「保存」。预期结果：抽屉标题变成「已保存：显示名」，绿色提示「集群 … 的配置已保存，修改了：pd、desc」（列出改了哪些字段）；没有任何改动时写「（没有任何改动）」。
4. 如果你正在使用的就是这个集群，提示「你正在使用的就是这个集群：环境 / 权限变化会在几秒内同步到页面。」

规则：

- **只改「显示名」「描述」**：立即生效，不重建实例，不影响采集与变更。
- **改了连接信息（地址 / SQL 账号 / 密码 / 可执行文件 / 模式）**：平台会**重建该集群的实例**（先关旧的、再启动新的），期间该集群的接口短暂返回「集群正在重载，请稍后重试」。新配置下启动失败时**自动回滚到原配置**，提示「新配置下实例启动失败，已回滚到原配置：…」。如果该集群有**正在执行的变更**，会拒绝：「该集群有正在执行的变更，重载连接信息会中断它；请等执行结束后再改」。
- **改「环境」或「tiup 集群名」**：该集群必须**没有任何进行中的变更或维护**（待审批 / 排队 / 定时 / 执行中的变更、进行中的主机维护），否则拒绝：「该集群还有 N 项进行中的变更 / 维护，修改 env 或 tiup 集群名前请先处理完」。改环境会**立刻改变谁能看到这个集群、每个人在其中的角色、适用审批策略的哪一列**；改 tiup 集群名后，之后的审计 / 通知用新名字，旧名字下的历史记录在审计「集群」筛选里会变成「旧名字（历史记录 / 已删除）」，需要选它才能查到。
- **「模式」从 live 改成 replay**：所有连接信息和已保存的密码都会被清空（保存后无法恢复）；从 replay 改成 live 需要重新填全连接信息。
- **主集群**：只能改「显示名」和「描述」；环境、模式、tiup 集群名和所有连接信息来自平台启动参数（改它们要改启动参数并重启平台），表单里这些控件是禁用的，页面上写着「主集群的环境与连接配置来自平台启动参数，这里只能修改显示名和描述；其余控件已禁用。主集群不能删除。」
- 「集群 id」创建后永远不能改。

**后果**：审计 `cluster.update`（风险：中，摘要只列改了哪些字段，密码只写「已更换 / 清除」）。运行数据（变更记录、写开关、窗口 / 冻结期、通知渠道等）在重建实例时保留。

### 七、删除（移除纳管）

**前置条件**：settings.edit；该集群**没有**待审批 / 排队 / 定时 / 执行中的变更，也没有进行中的主机维护；它不是主集群（主集群的「删除」按钮置灰，悬停提示「主集群来自平台启动参数，不能删除」）。

1. 点该行红色的「删除」。你会看到抽屉「删除集群：显示名」，顶部红色提示「高危操作：移除集群 xxx 的纳管。」，下面列出后果。
2. 认真读后果：
   - 仅**移除纳管**：**不会停止或删除 TiDB 集群**，集群上的业务不受影响。
   - 平台里该集群的运行数据（变更记录、写开关、窗口 / 冻结期、通知渠道、预测等）所在目录会**改名保留**，不会被删除。
   - 有执行中 / 待审批变更时会被拒绝。
   - 审计日志是全局的，仍保留，仍可按集群筛选（该集群在筛选下拉里会显示成「…（历史记录 / 已删除）」）。
3. 在输入框里**输入集群 id**（例如 `stg`）。只有输入完全一致时，「确认删除」才可点。
4. 点「确认删除」（或在输入框里按回车）。预期结果：抽屉标题变成「已移除纳管：显示名」，绿色提示「集群 …（stg）已移除纳管。TiDB 集群本身没有被停止或删除。」，蓝色提示框里给出**保留的目录**，形如 `<数据目录>/clusters/.removed-stg-20261006T124700Z`（后面是 UTC 时间戳；同一秒内重复删除同 id 会追加 `-2`）。`<数据目录>` 是平台启动参数 `--data-dir` 指定的目录（安装包默认 `/var/lib/tidbops`）。
5. 被拒绝时红字提示「该集群有执行中或待审批的变更，请先处理完再操作：该集群还有 N 项待审批 / 排队 / 执行中的变更或进行中的维护，请先处理完（取消 / 驳回 / 等待结束）再删除」。处理办法：切换到该集群，在「节点管理 → 任务中心」把待审批的变更取消 / 驳回、等执行中的结束，再回来删除。
6. 如果删除的是你**正在使用**的集群，结果里会多一条橙色提示「这是你正在使用的集群：下次切换页面时会刷新并回到默认集群。」和按钮「立即切换到默认集群」。

**后果**：审计 `cluster.remove`（**风险：高**）。保留的目录**不会被自动清理**，确认不再需要后由有中控机权限的人手工删除；平台没有「恢复已移除集群」的功能。之后用**同一个 id** 再次接入，得到的是一个全新的空白运行状态（不会自动用回 `.removed-…` 里的数据）。

### 八、接入之后要做的事（新接入的 live / 生产集群建议逐项过一遍）

1. **切换到新集群**（顶栏下拉，或接入结果里的「切换到该集群」按钮），在「集群总览」看数据是否正常：顶部横幅里写着集群名与采集时间；有「N 项数据缺失」点开看缺什么。
2. **核对环境**：顶栏环境标签与下拉框颜色是不是你预期的。
3. **配置该集群自己的设置**：在 [环境与设置](help:settings) 里为它添加通知渠道、检查变更窗口规则、「集群前有负载均衡」；在 [变更排期](help:schedule) 里加冻结期。这些都是**每个集群各一份**。
4. **（sudo 模式）核对 sudo 策略文件**：见上文 ⚠️，做完后再开写开关。
5. **开写操作开关**（需要变更时）：在该集群下，由两名不同的管理员在「权限与审计 → 写操作开关」先后确认，见 [权限与审计](help:security)。
6. **给需要的人分配该环境的角色**：见 [用户管理](help:users)；没有该环境角色的人看不到这个集群。

### 测试各项含义与失败怎么办

回放集群只有一项；live 集群按顺序做下面 6 项（某个地址 / SQL 信息没填的项显示「警告」而不是失败）。

| 检查项 | 平台做什么 | 通过 | 警告 | 失败（怎么办） |
|---|---|---|---|---|
| 回放数据包（仅 replay） | 读取数据包的 `manifest.json` | 「manifest 可读：集群 … 版本，采集于 …，N 个条目」 | — | 「无法读取 manifest：…」：目录不对或不是数据包，用 `tidbops-fixtures verify` 校验，或重新生成 |
| PD 健康（/pd/api/v1/health） | 访问 PD 的健康接口 | 「N 个 PD 成员健康」 | 没填地址（「未配置地址（启动时会尝试自动探测）」）；「没有返回任何 PD 成员」；「x / y 个 PD 成员不健康」；「HTTP 200，但响应不是预期的健康列表」 | 「HTTP 状态码」或网络错误：核对地址与端口（默认 2379）、平台主机到该端口的网络与防火墙；用官方 [PD Control](https://docs.pingcap.com/zh/tidb/stable/pd-control/) 的 `health` 命令在中控机上对照 |
| TiDB 状态端口（/status） | 访问 TiDB 状态端口 | 「HTTP 200」 | 没填地址 | 核对端口（默认 10080）与网络；该接口见官方 [TiDB 集群监控 API](https://docs.pingcap.com/zh/tidb/stable/tidb-monitoring-api/) |
| Prometheus 查询 | 即时查询 `up` | 「查询 up 成功」 | 没填地址 | 核对地址与端口（默认 9090）；返回非 success 说明那不是 Prometheus 或被代理改写 |
| Alertmanager（/api/v2/status） | 访问 Alertmanager 状态接口 | 「HTTP 200」 | 没填地址 | 核对地址与端口（默认 9093）；没部署 Alertmanager 的集群留空即可（告警相关页面会提示未配置） |
| TiDB SQL（SELECT 1） | 用只读账号连 TiDB 执行 `SELECT 1` | 「SELECT 1 成功」 | 「未配置 mysqlHost / mysqlUser」 | 详情里是 mysql 客户端的报错（口令中的敏感内容会被替换成 `***`）：`Access denied` 是账号 / 口令 / 来源主机不对；`Can't connect` 是地址 / 端口 / 网络；找不到命令是「mysql 可执行文件」路径不对 |
| tiup cluster display 集群名 | 执行 `tiup cluster display <tiup 集群名>` | 「可执行，集群版本 vX.Y.Z」或「可执行」 | — | 由**平台运行账号**直接执行（不经 sudo）：核对「tiup 可执行文件」路径、tiup 集群名是否与 `tiup cluster list` 一致；`tiup cluster list` 只列出当前系统用户部署的集群（官方说明），平台运行账号要能执行 tiup 并看到这个集群 |

所有探测都是固定的只读请求，不跟随重定向，响应体最多读 1 MiB；详情最长 300 字符。

### 错误提示对照

接入 / 编辑 / 删除失败时，红字的格式是「分类：具体原因」（分类对应后端错误码）。具体原因里的字段名用的是接口里的名字，对应关系：`id` = 集群 id，`name` = tiup 集群名，`display` = 显示名，`desc` = 描述，`env` = 环境，`mode` = 模式，`fixtures` = fixtures 目录，`pd` / `tidbStatus` / `prom` / `alert` = 四个地址，`mysqlHost` / `mysqlPort` / `mysqlUser` / `mysqlPassword` = SQL 连接，`mysqlBin` = mysql 可执行文件，`tiup` = tiup 可执行文件，`home` = HOME 目录。

| 红字（开头） | 错误码 | 含义 | 怎么办 |
|---|---|---|---|
| 参数不合法：… | invalid | 某个字段不符合规则，后面是具体原因，如「id 只能由小写字母、数字和连字符组成，以字母开头，长度 2–32」「env 只能是 test / staging / prod」「fixtures 目录不在允许的根目录之下（启动参数 --fixtures-root）」「未配置回放数据包的白名单根目录（启动参数 --fixtures-root，或与 --fixtures 同级的目录），不能添加回放集群」「配置了 mysqlHost 就需要 mysqlUser」「pd 不能在 URL 里携带用户名 / 口令」「mysqlBin 的文件名必须是 mysql / mariadb」 | 按原因改对应字段；地址类错误检查是否带了 `?` `#` 空格或用户名 |
| 集群 id 已存在：id / tiup 集群名与已有集群「xxx」冲突 | exists | 新 id 或 tiup 集群名与某个集群的 id 或 tiup 集群名撞了（含主集群） | 换一个 id / tiup 集群名 |
| 集群数量已达上限：最多接入 20 个集群（含主集群） | limit | 已有 20 个 | 先移除不用的集群 |
| 主集群的连接配置来自平台启动参数：只能修改显示名与描述，且不能删除：… | primary | 对主集群改了环境 / 模式 / 连接信息，或尝试删除主集群 | 只改显示名与描述；其他改启动参数并重启平台 |
| 该集群有执行中或待审批的变更，请先处理完再操作：… | in_use | 删除、改环境 / tiup 集群名、或重载连接信息时，该集群有进行中的变更或维护 | 见「七、删除」第 5 步 |
| 集群实例启动失败（连接信息可能有误，或集群暂时不可达）：… | start | 新实例没能启动，已整体回滚（更新时恢复旧配置）；回放集群最常见原因是 manifest 读不了，其他可能是数据目录权限、执行器配置问题 | 看冒号后的具体原因；live 集群连不上**不会**导致启动失败（接入不校验连通性），请用「测试」排查 |
| 保存失败（注册表写入失败，请检查数据目录的权限与磁盘空间）：… | store | `clusters.json` 写盘失败，内存状态已回滚 | 检查数据目录权限（0700 / 属主为平台运行账号）和磁盘空间 |
| 集群不存在（可能已被删除）：没有这个集群 | not_found | 操作的集群已被别人删除 | 点「刷新」 |
| 无法连接后端 / 请求失败（数字） | — | 浏览器连不上平台或被代理拦截 | 稍后重试，联系部署人员 |

### 热生效与重启后的行为

- **通过本页（接口）做的接入 / 编辑 / 删除立即生效，不需要重启平台**。平台先构造并启动新实例，成功后才写 `clusters.json` 并切换路由；任何一步失败都会回滚，不影响其他集群。
- 配置保存在数据目录的 `clusters.json`（权限 0600，原子写入）。**手工编辑 `clusters.json` 需要重启平台才生效**，不要在平台运行时手工改它（可能被下一次保存覆盖）。文件里无法识别的条目（id 不合法 / 重复）不会被加载，只写在服务日志里，并在下次保存时**原样保留**；整个文件不是合法 JSON 时平台拒绝启动。
- 重启后平台按 `clusters.json` 重新创建每个集群的实例。某个集群启动失败（如 `master.key` 变了导致密码解密失败，或 fixtures 目录不再在允许的根目录下）不会让平台起不来：该集群标成「异常」，写一条审计 `cluster.load`（风险：高，结果：失败，用户：system），在「编辑」里修正后保存即可恢复。
- 运行数据放在 `<数据目录>/clusters/<集群 id>/`（文件名与主集群相同）；**主集群的数据仍放在数据目录根下**，布局不变，旧版本升级后行为不变。**备份数据目录时请包含 `clusters.json`、`clusters/` 与 `master.key`。**
- `--dev-seed` 回放演示：数据目录里还没有 `clusters.json` 时，平台会自动登记两个演示集群（`stg`、`dev`），只登记一次；之后删掉也不会再出现。正式部署绝不会自动登记。

## 执行后果与风险

> ⚠️ 接入 / 编辑 / 移除集群**不会对 TiDB 集群执行任何命令，不会重启任何组件**；它们改变的是平台自己的行为：平台开始（或停止）访问这个集群、哪些用户能看到它、它适用哪个环境的权限与审批。尤其**改环境**会立刻改变所有用户在该集群里的角色。

> ⚠️ 平台从接入那一刻起会用你填的只读账号周期性查询集群（慢查询、statement summary 等），对生产集群有一定只读负载；采集有缓存（快照缓存约 10 秒、数据源缓存约 15 秒，由启动参数决定）。

> ⚠️ sudo 模式下漏配 `perCluster` 会让非主集群的 SET CONFIG / SET GLOBAL / 告警静默打到别的集群，而且界面不会告警，详见上文第四节的警告框。务必在开写开关前核对，并在测试环境验证一次。

> ⚠️ 移除集群是**高风险**操作（审计风险等级「高」）：数据目录改名保留、不能一键恢复。接入、编辑、测试都是「中」。所有操作（含失败 / 被拒绝）都写入审计，摘要里**不含任何口令**。

## 常见问题与注意

- **接入时 live 集群连不上也成功了，怎么确认通不通？** 接入本身不校验连通性。接入后立刻点「测试」，再看「状态」列的「可达 / 不可达」。
- **列表里「不可达」但「测试」全是通过？** 状态来自最近一次采集的缓存，可能是接入前的旧结果，等下一轮采集（或切换到该集群点总览顶部「立即刷新」）后再看。
- **改了地址要不要重启？** 不要，保存即热生效。
- **怎么知道有人动过集群配置？** 到 [权限与审计](help:security) 的「审计日志」，「动作」填 `cluster.add` / `cluster.update` / `cluster.remove` / `cluster.test` 查询，可再用「集群」下拉筛选。
- **没有「集群接入」菜单？** 你没有 settings.edit（主集群环境下），见「第 0 步」。
- **更多现象排查**：见 [常见问题](help:faq) 的「集群相关」。

## 已知限制与易混淆点

核对于代码与演示环境，格式为「界面 / 文档写的是 A，实际是 B」。

| 界面 / 你以为 | 实际是 | 建议 |
|---|---|---|
| 不同集群的变更像是排在同一个队列里 | 「排队中」只在**同一个集群内**串行（同一集群同一时刻只执行一个变更）；**不同集群之间并行执行**，没有跨集群的互斥或限流 | 在两个集群同时做变更时，别指望平台替你排先后；同一个特权端被并发调用时 tiup 的并发由 tiup 和操作系统负责 |
| 变更编号 `CHG-0001` 像是全平台唯一 | 每个集群各自从 `CHG-0001` 起编号，**会重复** | 判断一条变更属于哪个集群，看变更详情里的集群 / 环境，或审计日志里的「集群」列（tiup 集群名），不要只凭编号 |
| 审批策略、用户、角色像是每个集群各一份 | 它们**全平台共用一份**；审批策略按**环境**取列（预发集群用「预发」列），不是按集群 | 想让某个集群更严格，把它的环境设成「生产」 |
| 在 B 集群的页面里改了用户 / 角色 / 集群接入，像是只对 B 生效 | 这些页面是**全局**的，授权按**主集群的环境**判断：管理员要在主集群的环境里有对应能力。若某个管理员只在某个非主集群的环境里有角色，他**管不了用户、角色和集群接入**（切到那个集群后「用户管理」「角色权限」菜单可能仍会显示——菜单按当前集群的环境判断——但打开页面会被拒绝；「集群接入」菜单则不会显示） | 给管理员设在「所有环境」，或至少包含主集群的环境 |
| 通知渠道配一次，所有集群通用 | 通知渠道**每个集群各自配置**，消息里带「环境：…　集群：<tiup 集群名>」 | 每个集群都要添加渠道；收到消息看「集群：」确认是哪一个 |
| 通知里的「查看」链接会打开对应集群 | 非主集群的通知链接形如 `<对外地址>/?cluster=<id>#schedule`。页面登录后会读取 `cluster` 参数：该集群对你可见就切过去，并把参数从地址栏去掉；**不可见（你在它的环境里没有角色）时忽略该参数**，仍用你上次选择的或默认集群 | 点链接后看一眼顶栏集群与环境标签是否是消息里写的那个；不是就说明你看不到它，请联系管理员 |
| 写开关在一个集群开启，所有集群都能写 | 写开关及其两名管理员确认是**每个集群各自**的；唯一全局的是 READONLY 文件（存在则所有集群强制只读） | 每个集群单独开 |
| 只读模式（没带 `--data-dir`）也有「集群接入」 | 只读模式**没有集群注册表**，仍是单集群：只有一个集群、没有登录；本页只显示说明卡片 | 要多集群请用运维模式部署 |
| 切换到回放集群做变更，会作用于那个集群 | **回放集群恒用模拟执行器**：流程、审批、审计都真实走，但命令只是模拟输出，**不会改动任何真实集群**，「成功」不代表真实执行过 | 看「写操作开关」页执行器一行的「模拟：不会对集群做变更」 |
| 在回放模式 / `sim` 执行器的平台里接入 live 集群就能做变更 | 平台进程的执行器是 `sim`（主集群是回放）时，**live 集群不配执行器**（`none`），只读：提交变更会被拒绝「未配置执行器，无法执行变更」 | 要对 live 集群做变更，平台需要用 `--exec direct` 或 `--exec sudo` 启动 |
| live 集群连不上会报错 | 不会报错：接入成功；之后该集群的总览等页面数据为空（节点 0 个、KPI 显示「—」），顶部横幅写「N 项数据缺失」可展开看原因，集群列表里状态为「不可达」 | 用「测试」定位是哪一项连不上 |
| 接入成功就说明配置正确 | 接入**只校验格式**，不校验连通性与账号权限；sudo 策略文件的漏配（`perCluster`）更是平台看不到的 | 接入后做「测试」+ 在测试环境验证一次变更 |
| 集群列表里的警告会自动消失 | 执行器预检警告只在创建实例时产生（接入 / 编辑后重建 / 平台重启），修好策略文件后不会自己消失 | 重启平台，或在「编辑」里改任一连接信息字段后保存（触发重建与重新预检） |
| 页面会显示 `clusters.json` 的加载告警 | 接口会给管理员返回加载告警，但当前页面没有显示它，只在服务日志里有「clusters.json：…」 | 怀疑有条目没加载时看服务日志 |
| 删除集群等于清除它的数据 | 只是移除纳管并把数据目录改名保留为 `.removed-…`；不自动清理 | 确认不需要后手工删除目录 |
| 改了 tiup 集群名，审计里新旧记录连在一起 | 审计的「集群」列记的是当时的 tiup 集群名，筛选只认**当前** id 与名字；旧名字的记录要从「…（历史记录 / 已删除）」选项里查（按代码推断） | 改名前记下旧名字 |
| 每个集群的「部署自检」都是同一份 | 自检按**当前所选集群**执行：数据文件权限只检查该集群的运行数据文件（非主集群只有 `changes.json`、`settings.json`；`users.json`、`audit.log`、`roles.json`、`master.key`、`clusters.json` 只在主集群的自检里出现）；执行器、「至少两名管理员」、版本支持、「生产环境使用真实执行器」都按该集群的环境与执行器计算；审计哈希链和 READONLY 文件是全局的 | 部署后对每个集群都点一遍「重新自检」 |
| 切换集群只换了数据 | 还会换掉你的**环境、角色与能力、写开关状态**（它们都是该集群的值） | 在新集群里先看顶栏标签再操作 |
| 删除 / 编辑后列表立刻一致 | 其他用户的页面最多几秒后才同步（定期刷新）；被删集群上的用户下一个请求会触发「当前集群已不可用」的自动切换 | 通知相关同事 |

## 官方参考

以下链接均已用浏览器打开核实（页面存在且内容与所述一致）。TiDB 文档页面以 stable 为准，**以你集群的版本为准**（平台支持 v7.5 / v8.1 / v8.5），必要时把地址里的 stable 换成对应版本路径。

- [tiup cluster list](https://docs.pingcap.com/zh/tidb/stable/tiup-component-cluster-list/)：查看当前登录用户在该中控机上部署的集群；输出 Name / User / Version / Path / PrivateKey 五列；集群数据默认存放在 `~/.tiup/storage/cluster/clusters/`，同一中控机上不同用户无法查看彼此部署的集群。
- [tiup cluster display](https://docs.pingcap.com/zh/tidb/stable/tiup-component-cluster-display/)：`tiup cluster display <cluster-name>` 的语法；输出含集群名、集群版本、Dashboard 地址和各组件的 ID / Role / Host / Ports / Status。
- [tiup cluster deploy](https://docs.pingcap.com/zh/tidb/stable/tiup-component-cluster-deploy/)：`<cluster-name>` 是新集群的名字，不能和现有集群同名——这就是「tiup 集群名」的来源。
- [tiup cluster 命令总览](https://docs.pingcap.com/zh/tidb/stable/tiup-component-cluster/)：子命令列表与全局选项。
- [通过 TiUP 部署 TiDB 集群的拓扑文件配置](https://docs.pingcap.com/zh/tidb/stable/tiup-cluster-topology-reference/)：`monitoring_servers`（Prometheus）与 `alertmanager_servers` 的配置段，对应接入页里的 Prometheus / Alertmanager 地址。
- [TiDB 软件和硬件环境需求 → 网络要求](https://docs.pingcap.com/zh/tidb/stable/hardware-and-software-requirements/)：Prometheus 9090、Alertmanager 9093、PD 客户端 2379、TiDB 状态端口 10080、TiDB 服务端口 4000 的默认端口。
- [TiDB 集群监控 API](https://docs.pingcap.com/zh/tidb/stable/tidb-monitoring-api/)：TiDB 状态端口（默认 10080）的 `/status`，PD API 地址形如 `http://${host}:${port}/pd/api/v1/${api_name}`（默认 2379）。
- [PD 配置文件描述](https://docs.pingcap.com/zh/tidb/stable/pd-configuration-file/)：`client-urls`（PD 监听的客户端 URL，默认 `http://127.0.0.1:2379`）与 `advertise-client-urls`。
- [PD Control 使用说明](https://docs.pingcap.com/zh/tidb/stable/pd-control/)：`health` 命令显示集群健康信息；`-u` 指定 PD 地址（环境变量 `PD_ADDR`）。
- [TiDB 监控框架概述](https://docs.pingcap.com/zh/tidb/stable/tidb-monitoring-framework/)：Prometheus 存储指标、Grafana 可视化、Alertmanager 负责报警。
- [TiDB 集群报警规则](https://docs.pingcap.com/zh/tidb/stable/alert-rules/)：各组件的告警项与处理方法。
- [CREATE USER](https://docs.pingcap.com/zh/tidb/stable/sql-statement-create-user/)、[GRANT <privileges>](https://docs.pingcap.com/zh/tidb/stable/sql-statement-grant-privileges/)、[权限管理](https://docs.pingcap.com/zh/tidb/stable/privilege-management/)：只读账号的创建与授权；本篇已说明这些页面没有写明几张系统表的访问权限，最小权限以真实联调为准。
- [Prometheus HTTP API](https://prometheus.io/docs/prometheus/latest/querying/api/)：`/api/v1/query` 即时查询接口（平台用它查询 `up`）。
- [Alertmanager Management API](https://prometheus.io/docs/alerting/latest/management_api/)：`/-/healthy`、`/-/ready` 等管理端点；[Alertmanager API v2 规范](https://github.com/prometheus/alertmanager/blob/main/api/v2/openapi.yaml)：定义了 `GET /status`、`/alerts`、`/silences`（平台测试用的 `/api/v2/status` 对应它）。
