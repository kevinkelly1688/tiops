# 角色权限

> 💡 查看平台的 7 个内置角色各自能做什么、每个角色有哪些成员，管理员还可以新建 / 复制 / 修改 / 删除**自定义角色**（角色 = 一组能力，每项能力选「允许 / 需审批 / 范围内」），并用「权限模拟器」核对「某个角色在某环境对某项操作会被怎么判定」。**管理员**（内置 admin，users.manage 能力）可以修改；**审计员 / 审批人**等带 audit.view 能力的账号只读；其他角色看不到本页菜单。**只有运维模式（后端带 `--data-dir`）才有真实的角色库；只读 / 回放模式下本页只显示 7 个内置角色的静态权限矩阵。**

> ⚠️ 本页的「角色」是**本平台自己的权限角色**，与 TiDB 数据库里的 `CREATE ROLE` 角色无关：在这里改角色不会改变任何数据库账号的权限。官方文档对数据库角色的说明见页末「官方参考」。

## 这个页面做什么

- **看**：左栏列出全部角色（内置在前、自定义在后），右侧看选中角色的「功能权限」（20 项能力）、「成员」、「权限模拟器」；「对比矩阵」把所有角色 × 所有能力摆在一张表里。
- **改**（仅管理员）：新建自定义角色（空白或复制现有角色）、改名 / 描述、逐项设置能力的授予方式、删除没有成员的自定义角色。内置角色**永远不可修改或删除**。
- **验**：权限模拟器输入「角色 + 能力 + 环境 + 风险 + 环境条件」，给出「允许 / 需 N 级审批 / 拒绝」及判定过程。
- 谁属于哪个角色（给用户分配角色）在「[用户管理](go:users)」页做，见 [用户管理帮助](help:users)。

### 页面布局

| 区域 | 内容 |

| 右侧标签页 | 「功能权限」「成员 (N)」「权限模拟器」 |

### 谁能看到、谁能操作

| 你的情况 | 看得到本页 | 能做什么 |
|---|---|---|
| 运维模式 + 管理员（users.manage） | 是 | 全部 |
| 运维模式 + 只有 audit.view（审计员、审批人等） | 是 | 只读：能看、能用对比矩阵和权限模拟器；「＋」「复制」「改名 / 描述」「删除」置灰，悬停提示「需要 users.manage 能力（只有 audit.view 时只读）」；自定义角色会多一条「只读：当前账号没有 users.manage 能力，无法修改角色。」 |

## 先搞清几个概念

| 术语 | 一句话解释 |
|---|---|
| 角色 | 一组能力的集合，给用户分配角色就是给他这组能力。内置 7 个：访客 viewer、开发 developer、值班 SRE sre、DBA dba、审批人 approver、管理员 admin、审计员 auditor |
| 自定义角色 | 管理员自己建的角色，有 ID、名称、说明和能力集合，最多 50 个 |
| 能力 | 平台里一类操作的许可，共 20 项，如 `inst.op`（单实例操作）。每项能力有固定的代码（`view.overview` 这样的写法）、中文名、说明和风险点 |
| 授予方式 | 一个角色对某项能力的授予程度：无 / 允许 / 需审批 / 范围内（下一节） |
| 仅内置管理员（locked） | 页面上标「🔒 仅内置管理员角色」的 3 项能力：`settings.edit`、`writeswitch`、`users.manage`，自定义角色不可持有 |
| 成员 | 在**任一环境**持有该角色的用户，含已禁用的用户 |
| 环境 | 每个集群所属的环境（测试 / 预发 / 生产）。用户的角色是按环境分配的，所以**环境就是集群的数据范围**：用户在哪个环境有角色，就能看到并使用那个环境的集群（一个环境可以对应多个集群）；某环境没有任何角色，该环境的集群对他不可见。「角色权限」页本身是全局的（所有集群共用同一套角色定义），详见 [用户管理帮助](help:users) 的「环境对应哪些集群、谁能看到哪个集群」与 [集群接入帮助](help:clusters) |

## 授予方式：允许 / 需审批 / 范围内 / 无

每项能力在每个角色里是下面四种之一。同一个用户有多个角色时，每项能力取**最强**的：允许 > 需审批 > 范围内 > 无。

| 授予方式 | 页面标签 / 矩阵符号 | 含义 |
|---|---|---|
| 允许 | 绿色「允许」/ ✔ | 直接可用 |
| 需审批 | 橙色「需审批」/ 「审」 | 「可以发起，但要按风险 × 环境走审批」。适用于会改动集群或平台的写类能力（`inst.op`、`scale`、`config`、`maint`、`backup`、`release`） |
| 范围内 | 蓝色「范围内」/ 「范」 | 仅限被授权的范围。目前只有 `view.sql` 有：只能看用户「授权库」里列出的库的慢 SQL 与执行计划（授权库在 [用户管理](go:users) 里设置） |
| 无 | 「无」/ 「—」 | 没有这项能力 |

> ⚠️ **「允许」与「需审批」在真实变更里没有区别**：平台判定一个变更要不要审批、要几级，只看**变更本身的风险等级 × 环境**（默认值与硬性下限见 [权限与审计帮助](help:security) 和 [节点管理帮助](help:nodes)），**不看**发起人的授予方式是「允许」还是「需审批」。也就是说，给自定义角色的 `inst.op` 选「允许」，他发起的重启在生产环境照样要走审批。内置角色里 DBA、值班 SRE 的写类能力都标「需审批」，建议自定义角色保持一致。权限模拟器对「允许」会显示「无需审批」，和真实行为不一致，见「已知限制与易混淆点」。

| 审批人 approver | 把关：审批中 / 高风险变更；不能执行变更 | 批准 / 驳回中风险与高风险变更（驳回需有对应审批能力）、看诊断与慢 SQL、导出报告、看审计日志 | 不能发起任何变更；申请人不能批自己的变更，同一人不能对同一变更重复批 |
| 管理员 admin | 平台管理：用户与角色、平台设置；不能直接做集群变更 | 管理用户与角色、修改冻结期 / 窗口规则 / 通知渠道 / 审批策略、开启或关闭写操作开关、看审计、看慢 SQL、跑诊断 | **不能发起集群变更**，也不能审批变更；开启写操作开关、授予管理员、改审批策略都需要**另一名管理员**确认 |
| 审计员 auditor | 审计：只读审计日志并导出 | 查看并校验审计日志、导出审计日志（csv / jsonl）；只读查看用户与角色页 | 看不到慢 SQL、不能跑诊断、不能做任何变更 |

## 20 项能力逐项说明

「风险」列是页面上圆点的颜色（● 红 = 高风险，● 黄 = 中风险，无圆点 = 只读 / 无集群影响）；「自定义角色可选」是选择授予方式时按钮的集合；「实际控制什么」来自后端接口的真实判定。

| 能力（代码） | 含义与风险 | 风险 | 自定义角色可选 | 实际控制什么 |
|---|---|---|---|---|
| 查看总览 / 拓扑（`view.overview`） | 看集群总览、拓扑、健康状态。所有角色的最低要求，缺了它用户登录后什么都看不到 | 无 | 允许（必选，不可去掉） | 平台所有读取类页面与接口（总览、架构、主机、事件时间线、配置当前值等） |
| 查看慢 SQL / 执行计划（`view.sql`） | 慢查询与执行计划**含 SQL 文本，可能含业务数据** | 中 | 无 / 允许 / 范围内 | 没有此能力时，所有读取接口里的慢 SQL 被置空；「范围内」时只保留授权库的慢 SQL |
| 运行诊断 / 巡检（`diag.run`） | 运行只读诊断与巡检，会对集群发起只读查询 | 无 | 无 / 允许 | 运行巡检、查看最近一次巡检结果、运行只读命令（`tiup cluster display / check`、BR 日志备份状态、TiCDC capture）、**创建告警静默**（见「已知限制」） |
| 导出诊断 / 巡检报告（`report.export`） | 导出巡检报告 | 无 | 无 / 允许 | 导出巡检报告（Markdown / HTML），写审计 |
| 单实例操作（`inst.op`） | 重启 / 停止 / 启动实例、驱逐 Leader；也包含「按角色滚动重启」 | 高 | 无 / 允许 / 需审批 | 发起上述变更。不能拆开授予「只能重启、不能停止」 |
| 扩缩容 / 升级（`scale`） | 扩容、缩容、新增主机、集群升级 | 高 | 无 / 允许 / 需审批 | 发起扩容 / 缩容 / 滚动升级；登记、编辑、删除、预检候选主机池 |
| 配置变更（`config`） | 修改集群配置（在线 / 需 reload） | 高 | 无 / 允许 / 需审批 | 发起配置变更 |
| 主机维护（`maint`） | 进入 / 退出 / 延长主机维护 | 高 | 无 / 允许 / 需审批 | 发起主机维护的进入 / 结束 / 延长，勾选维护检查单 |
| 备份恢复操作（`backup`） | 发起备份与恢复 | 高 | 无 / 允许 / 需审批 | 发起 BR 备份 / 恢复 / 日志备份启停 |
| 创建变更排期（`sched.create`） | 创建变更排期（执行时仍要走对应能力的鉴权） | 中 | 无 / 允许 | **目前后端没有任何接口按它放行或拒绝**；是否能「定时执行」只取决于你有没有对应变更的发起能力 |
| 审批中风险变更（`approve.mid`） | 批准 / 驳回中风险变更；申请人不能审批自己的变更 | 中 | 无 / 允许 | 批准、驳回风险等级为「中」的变更 |
| 审批高风险变更（`approve.high`） | 批准 / 驳回高风险变更（多级审批） | 高 | 无 / 允许 | 批准、驳回风险等级为「高」的变更 |
| 平台发布（`release`） | 平台自身的发布流程 | 高 | 无 / 允许 / 需审批 | **目前后端没有任何接口检查它**；平台自身的升级 / 回滚通过服务器命令行完成，见 [安装部署帮助](help:deploy) |
| 修改平台设置（`settings.edit`） | 修改冻结期、变更窗口、通知渠道、审批策略等 | 中 | 🔒 仅内置管理员 | 修改冻结期 / 窗口规则 / 负载均衡开关 / 通知渠道；修改页面水印（见 [水印设置](help:watermark)）；发起与确认「修改审批策略」提案 |
| 开启 / 关闭写操作开关（`writeswitch`） | 环境写操作总开关，开启需两名管理员复核 | 高 | 🔒 仅内置管理员 | 提议 / 确认开启、立即关闭、撤销提议 |
| 用户与角色管理（`users.manage`） | 管理用户、角色与权限 | 高 | 🔒 仅内置管理员 | 本页与「用户管理」页的全部写操作；确认「授予管理员」提案 |
| 查看审计日志（`audit.view`） | 查看并校验审计日志 | 无 | 无 / 允许 | 审计日志查询与哈希链校验；同时让用户能**只读**查看「用户管理」「角色权限」页 |
| 导出审计日志（`audit.export`） | 导出审计日志（含全部操作痕迹） | 中 | 无 / 允许 | 导出审计日志 |
| 中控机命令：执行（`shell.run`） | 在「中控机命令」页以 tidb 身份向中控机执行命令、提交变更申请、取消自己的任务；**等同于中控机上的 tidb（有 sudo 免密）权限，只给确实需要的人** | 高 | 无 / 允许 | 「中控机命令」页的 check / 执行 / 提交申请 / 取消（中控机模式才有该页，见 [中控机命令](help:shell)）；只读命令直接执行，变更命令还要有人批准 |
| 中控机命令：批准变更（`shell.approve`） | 批准他人在「中控机命令」页提交的变更命令；申请人不能批准自己的申请 | 高 | 无 / 允许 | 批准变更申请。**与 `shell.run` 分开授予**：想让「执行的人」和「批准的人」是不同的人，就把它们放进不同的角色 |

> 💡 页面上每项能力的「说明」就是上表「含义与风险」那一列；「需审批」在说明里写作「须按风险×环境走审批」。

## 怎么用（按步骤）

以下针对**运维模式**。所有写操作要求 users.manage（内置管理员），并写审计：`role.create`、`role.update`、`role.delete`（风险「高」，摘要里用「+能力(授予方式)」「−能力」「~能力(旧→新)」列出权限差异）。**角色的修改不走双人复核**，一名管理员即可完成。

### 第 0 步：进入页面

1. 登录后点侧栏「平台配置」→「角色权限」。你会看到左栏「角色」列表和右侧第一个角色的详情，右侧有「功能权限」「成员 (N)」「权限模拟器」三个标签。
2. 如果顶部有橙色提示「角色库加载时有降级处理（已丢弃不安全的内容，不会提权）：…」，说明角色库文件 `roles.json` 在启动时有不合法的内容被丢弃了（例如被手工写入的仅管理员能力）。降级只会**减少**权限；请核对相关角色后保存一次。
3. 页面每隔约 9 秒自动刷新（你在输入、打开抽屉时不刷新）。

### 一、查看一个角色的权限

1. 在左栏点想看的角色。如果当前角色有未保存的修改，会先弹出「放弃未保存的修改？」，点「放弃并切换」才会切换。
2. 「功能权限」标签页：顶部一行「已授予 N / 20 项能力」；下面按「查看与诊断」「运维变更」「排期与审批」「平台管理」「审计」五组列出，每组标题后有「已授予 / 总数」。每项显示中文名、风险圆点、代码和说明；右侧内置角色显示授予方式标签（「允许」「需审批」「范围内」；没有授予的显示「无」；仅管理员能力在没授予时显示「🔒 仅内置管理员角色」）。
3. 内置角色顶部有蓝色提示「内置角色不可修改（只读展示）。需要不同权限时，点右上角「复制」得到一个自定义角色再调整。」

### 二、新建自定义角色

**前置条件**：管理员；自定义角色不足 50 个；想好角色 ID、名称、用途，以及需要哪些能力（可先参考「20 项能力逐项说明」）。

1. 点左栏标题右侧的「＋」。右侧弹出抽屉「新建角色」。
2. 「角色 ID（小写字母开头，a-z 0-9 _ -，2–32 位；创建后不可改）」：填如 `restarter`。输入时下面实时提示，规则不符显示红字「需 2–32 位，小写字母开头，只能含小写字母、数字、_ 和 -」；与内置角色 ID 重名显示「与内置角色 ID 重名」；与已有自定义角色重名显示「该 ID 已存在」。
3. 「名称（1–40 字；不能与内置角色显示名重复）」：填如 `重启员`。名称不区分大小写，不能与任何已有角色的名称重复，也不能与内置角色的 ID 相同（如 `dba`）。
4. 「说明（可选，≤200 字）」：写用途，例如「只能发起单实例操作，经审批后执行」。
5. 「初始权限」二选一：
   - 「空白（只有必选的「查看总览」）」：从头逐项勾；
   - 「复制自：」+ 下拉选一个角色：以该角色的能力为起点；复制内置角色时会自动**去掉**仅管理员能力，并提示「已去掉仅管理员能力：settings.edit、writeswitch、users.manage（自定义角色不可持有）。」
6. 所有红字消失后，「创建角色」才可点。点它。**你会看到**：抽屉关闭，提示「已创建角色「重启员」」，左栏「自定义角色」下多出这一项并被选中，右侧显示它的「功能权限」。空白创建的角色此时「已授予 1 / 20 项能力」（只有查看总览）。

**后果**：角色已存在，**没有成员**，对任何人都没有影响；写审计 `role.create`。**撤销**：删除（见「六」）。

**失败怎么办**：抽屉底部红字会写「后端返回：…」并附一句说明：

| 提示 | 含义与处理 |
|---|---|
| 角色 ID 或名称已被占用（含内置角色的 ID 与显示名） | 换 ID 或名称 |
| 自定义角色数量已达上限（50 个） | 先删除不用的角色 |
| 参数不合法，请按提示修改 | 按后端给出的具体文字改（如名称太长、含控制字符） |
| 角色库保存失败：请检查数据目录的权限与磁盘空间后重试 | 服务器问题，找运维处理数据目录 |

### 三、复制一个角色

1. 选中要复制的角色（内置或自定义均可），点右上角「复制」。抽屉标题「复制角色：xxx」。
2. 页面已填好建议值：ID 为 `原ID-copy`（已存在则 `-copy2` …），名称为「原名称（副本）」，说明沿用原说明。按需修改。
3. 点「复制并创建」。你会看到提示「已创建角色「…」」，新角色被选中。

注意：复制的是**已保存**的权限；如果原角色有未保存的修改，抽屉里会提示「复制的是已保存的权限，不含未保存的修改。」

### 四、改名 / 改描述

仅自定义角色。ID 不能改。

1. 选中自定义角色，点「改名 / 描述」。抽屉显示只读的「角色 ID」，可改「名称」「说明」。
2. 点「保存」。没有任何修改时提示「没有修改」；成功提示「已保存名称 / 说明」。
3. 名称改动会立即体现在「用户管理」等页面里该角色的标签上。成员的权限不变，不吊销会话。审计 `role.update`，摘要「名称「旧」→「新」」或「说明已修改」。

### 五、编辑功能权限

**前置条件**：管理员；选中的是自定义角色（内置角色只读）。

1. 选中自定义角色，停在「功能权限」标签页。每项能力右边是一排分段按钮，按钮集合取决于这项能力允许的授予方式（见「20 项能力」表的「自定义角色可选」）：例如 `inst.op` 是「无 / 允许 / 需审批」，`view.sql` 是「无 / 允许 / 范围内」，`diag.run` 是「无 / 允许」。当前选中的按钮高亮。
2. 点按钮选择授予方式。点「无」表示去掉这项能力。**改动过的行会被标出**，左栏该角色名后出现 ●，页面底部出现「● 有未保存的修改（N 项）」。
3. 特殊项：
   - 「查看总览 / 拓扑」：只有一个高亮的「允许」，右边写「必选」，不能去掉（缺了它成员登录后什么都看不到）。
   - 带「🔒 仅内置管理员角色」的 3 项（`settings.edit`、`writeswitch`、`users.manage`）：没有按钮，不可授予。原因：这三项分别能改审批策略 / 冻结期、能打开写操作开关、能管理用户与角色，若允许自定义角色持有，就能绕开「两名管理员复核」「授予管理员需确认」的设计。
4. 顶部有三个快捷按钮（只对自定义角色显示）：
   - 「全选允许」：除仅管理员能力外全部设为「允许」（注意：包括 `inst.op`、`scale` 等高风险项，**不是**「需审批」，用完请手工调整）；
   - 「清空」：只保留必选的「查看总览」；
   - 「仅查看」：只保留「查看总览」「运行诊断 / 巡检」「导出诊断 / 巡检报告」（都是只读、无集群影响，不含「查看慢 SQL」）。
5. 想放弃本次改动，点底部「撤销」，回到已保存的状态。
6. 改好后点底部「保存」。**不会直接保存**，而是弹出抽屉「保存角色「重启员」」，让你确认变更差异：
   - 顶部提示：如果该角色有成员，橙色「将立即对 N 名成员生效：张三、李四…」（最多列 12 个名字，多了写「等」）；没有成员则蓝色「该角色目前没有成员，修改只影响以后分配到该角色的用户。」
   - 「＋ 新增 N 项」（绿）列出新授予的能力及方式；「－ 移除 N 项」（红）列出去掉的能力；「~ 变更授予方式 N 项」列出「旧 → 新」。
7. 核对无误点「确认保存」；想继续改点「返回继续编辑」。**你会看到**提示「已保存「重启员」，已对 N 名成员即时生效」。权限变更**对成员即时生效，不要求他们重新登录、也不吊销会话**：服务端每次请求都按最新权限判定，对方页面刷新后按钮与菜单随之变化。
8. 失败时抽屉里出现红色框，写出原因（见下表）；已选的内容仍在，可修改后重试。

| 红色提示（页面说明） | 含义 |
|---|---|
| 该能力仅内置管理员角色可持有，自定义角色不可授予。 | 选了仅管理员能力（正常操作选不到，除非来自旧数据） |
| 防提权：你只能授予自己已拥有、且授予方式不低于所授予方式的能力。 | 操作者没有该能力。管理员不受此限，所以实际上只有未来放宽入口时才会遇到 |
| 角色必须包含 view.overview … | 缺少必选项 |
| 能力 xxx 不支持授予方式 yyy（可选：…） | 选了该能力不允许的授予方式 |
| 角色不存在（可能已被他人删除），请刷新后重试。 | 别人已经删了这个角色 |
| 角色库保存失败：请检查数据目录的权限与磁盘空间后重试。 | 服务器问题 |

**并发提醒**：如果你编辑期间别人也改了这个角色，会出现橙色提示「你编辑期间，该角色已被其他人修改。保存会整体覆盖当前已保存的权限；建议先「撤销」重新载入后再改。」保存永远是**整体替换**能力集合，不是合并。

**后果与撤销**：保存后立即生效、立即落盘；审计 `role.update`，摘要如「修改自定义角色「重启员」：权限 +inst.op(approval)；即时影响 1 名成员」。没有「回滚」按钮，想恢复就再编辑一次改回去。

### 六、删除自定义角色

**前置条件**：管理员；该角色**没有任何成员**（含已禁用的用户，在任一环境持有都算）。内置角色没有「删除」按钮。

1. 选中自定义角色，点右上角红色「删除」。
2. 如果仍有成员：弹出抽屉「无法删除角色」，写「角色「xxx」仍有 N 名成员，不能删除。请先在「用户管理」里把这些用户的角色改掉（含已禁用的用户），再删除角色。」，下面列出成员账号（可点击跳到用户管理），按钮「去用户管理处理 →」。按提示在「[用户管理](go:users)」里给这些用户换角色（或取消该角色），再回来删。
3. 没有成员时：弹出确认框「删除自定义角色」：「确认删除自定义角色 xxx（id，含 N 项能力）？不可恢复。目前没有成员持有它。」点「确认删除」。**你会看到**提示「已删除角色「xxx」」，左栏该项消失。

**后果**：角色永久删除，**不可恢复**（要恢复只能重新建一个同名角色并重新勾权限）；审计 `role.delete`。

### 七、成员标签页

1. 选中任一角色，点「成员 (N)」。顶部说明「持有该角色的用户（任一环境）。在「用户管理 → 编辑」里为用户分配 / 移除角色。」
2. 表格列出账号；每行「在用户管理中定位 →」会跳到「用户管理」并把账号填进搜索框；顶部「在用户管理中查看 →」会跳转并按该角色筛选。
3. 底部「共 N 名成员（含已禁用的用户）。」自定义角色还会提醒「自定义角色仍有成员时不能删除。」没有成员显示「暂无成员」。

成员在这里**只读**，分配 / 移除要到用户管理页。

### 八、对比矩阵

1. 点右上角「对比矩阵」或左栏底部「▦ 查看全部角色权限矩阵」。右侧弹出宽抽屉「全部角色权限矩阵」。
2. 表格列为全部角色（自定义角色表头有「自定义」小字），行为 20 项能力（分组标题行，风险高的有 ● 标记）。格子里：✔ 允许，「审」需审批，「范」范围内，「—」无。图例在表格上方。当前选中的角色那一列高亮；如果它有未保存的草稿，矩阵显示的是草稿。
3. 「刷新」重新读取；「打印 / 导出」调用浏览器的打印（可另存为 PDF），打印时只打印矩阵。

适合：评审权限、给合规留档、对照内置角色设计自定义角色。

### 九、权限模拟器

**它是什么**：在浏览器里按平台的授权规则「演算」一次：给定角色、能力、环境、风险和环境条件，告诉你会被允许、需要几级审批还是被拒绝，以及每一步的判定。**它不会发起任何真实请求、不会创建变更，也不会读取用户或集群的实时状态。**

1. 选中想验证的角色（模拟器默认就用当前选中的角色），点「权限模拟器」标签页。
2. 顶部蓝色提示说明：审批级数取自当前生效的审批策略（默认或自定义）；MFA 提示仍按默认规则演示，实际要求见「权限与审计 → 审批策略」；以及「模拟按已保存的角色权限计算」，或当角色有未保存修改时「当前角色有未保存的修改，模拟按草稿计算」。
3. 左侧「输入」逐项填：

| 字段 | 填什么 |
|---|---|
| 角色 | 下拉选任一角色（含自定义，标「（自定义）」） |
| 能力 / 动作 | 下拉按分组选一项能力；切换能力时「风险等级」会自动改成该能力的默认风险 |
| 环境 | 测试 / 预发 / 生产（模拟用的环境，**与用户实际被分配的环境无关**） |
| 风险等级 | 低 / 中 / 高。变更实际的风险等级由变更种类和参数决定，这里可手工改着试 |
| 环境条件（复选框） | 「测试环境写操作开关」「预发环境写操作开关」「生产环境写操作开关（默认关闭）」「集群版本在支持矩阵内」「申请人已通过 MFA」 |

4. 右侧「判定结果」顶部一个大标签：绿色「允许」、橙色「需 N 级审批」、红色「拒绝」；下面按顺序列出每一步，带 ✔ ⚠ ✖ ℹ：
   - 「角色」：该角色在这项能力上的授予方式（直接允许 / 需审批 / 仅限被授权范围），没有则 ✖ 拒绝；
   - 「环境写开关」（只对写类能力：单实例操作、扩缩容、配置变更、主机维护、备份恢复）：该环境的开关没勾则 ✖ 拒绝；
   - 「版本兼容」：未勾「集群版本在支持矩阵内」则 ✖ 拒绝；
   - 「审批」：授予方式为「需审批」时按「环境 × 风险」给出级数，如「预发环境 · 中风险：需要 1 级审批（申请人不能自批）」；生产「开启 / 关闭写操作开关」固定「需要两名不同的管理员依次确认」；
   - 「MFA」：生产环境 + 高风险时，没勾「申请人已通过 MFA」给 ⚠ 提示；
   - 「排期规则」：写类能力提示还要满足窗口 / 冻结期规则；「范围」：范围内授予的提示；「审计」：无论结果都写审计。
5. 再往下「执行路径与命令」「将写入的审计记录」展示这项能力对应的命令模板与一条**示例**审计记录（时间、用户是占位符），仅供理解。

**读结果的方法**：先看顶部标签，再从上往下找第一个 ✖——它就是被拒绝的原因。

> ⚠️ 模拟器是前端按规格演算的，**不等于真实服务端的行为**：它对「允许」的写类能力显示「无需审批」，而真实变更始终按风险 × 环境走审批；它只模拟**单个角色**，不会合并一个用户的多个角色；也不检查冻结期、窗口、占用冲突等运行时状态。见「已知限制与易混淆点」。

### 十、完整示例：建一个「重启员」角色并验证

**目标**：一个只负责值班重启 / 启动实例的人，经审批才能执行，不能改配置、不能扩缩容、不能看慢 SQL。（注意：`inst.op` 同时包含停止与驱逐 Leader，无法只授予「重启」。）

**前置条件**：你是管理员；有一个要授予的用户，如 `bob`（没有的话先在「用户管理」里新建）。

1. 「角色权限」→ 点「＋」，抽屉「新建角色」：「角色 ID」填 `restarter`，「名称」填 `重启员`，「说明」填 `只能发起单实例操作，经审批后执行`，「初始权限」选「空白（只有必选的「查看总览」）」，点「创建角色」。你会看到「已创建角色「重启员」」，右侧「已授予 1 / 20 项能力」。
2. 在「运维变更」分组找到「单实例操作 inst.op」，点「需审批」。底部出现「● 有未保存的修改（1 项）」。
3. 点「保存」。抽屉里应显示「该角色目前没有成员…」与「＋ 新增 1 项」「单实例操作 · 需审批」。点「确认保存」，提示「已保存「重启员」，已对 0 名成员即时生效」。
4. 切到「权限模拟器」验证：「能力 / 动作」选「单实例操作」，「环境」选「预发」，「风险等级」选「中」。此时「判定结果」是红色「拒绝」，第二步「环境写开关」✖ ——因为模拟器默认没勾「预发环境写操作开关」；勾上它，结果变成橙色「需 1 级审批」，「审批」一行写「预发环境 · 中风险：需要 1 级审批（申请人不能自批）」。把「风险等级」改成「高」，变成「需 2 级审批」。
5. 去「[用户管理](go:users)」，找到 `bob` 点「编辑」。在「角色（环境 → 角色）」的「所有环境（默认）」行，自定义组里勾上「重启员」；如果不想他同时是访客，取消勾选「访客」（重启员已包含必选的查看总览）。点「保存」，提示「已更新 bob 的角色」。bob 的会话在此刻被吊销。
6. 让 bob 重新登录，核对：
   - 「权限与审计」→「我的账号」里「角色」显示「重启员」，「当前环境下拥有的能力（2）」里有 `view.overview` 和 `inst.op`；
   - 「节点管理」→「节点实例」：行内「重启」「停止」「启动」「驱逐 Leader」可点；「缩容」「扩容」「配置变更」等按钮置灰，悬停提示没有对应权限；
   - 看不到「SQL 优化」里的慢 SQL 内容（没有 `view.sql`）；
   - 在写操作开关已开启的环境里点「重启」→「提交变更」，变更进入「待审批」，需要审批人批准（生产中风险 1 级；测试环境中风险免审批，会立即执行，见 [节点管理帮助](help:nodes)）。
7. 想收回权限：在「用户管理」里把 bob 的「重启员」取消勾选并保存（会吊销会话）；想让所有持有者一起失去某项能力：在「角色权限」里改角色并保存（即时生效，不吊销会话）。

## 自定义角色的约束一览

| 约束 | 内容 | 违反时 |
|---|---|---|
| 数量 | 最多 50 个自定义角色 | 「自定义角色数量已达上限（50 个）」，「＋」置灰 |
| 角色 ID | `^[a-z][a-z0-9_-]{1,31}$`：2–32 位，小写字母开头，只含小写字母 / 数字 / `_` / `-`；创建后不可改；不能与内置角色 ID 相同（viewer developer sre dba approver admin auditor）；不能与已有角色重复 | 红字提示 |
| 名称 | 1–40 个字；不含控制字符；不区分大小写，不能与任何已有角色名称重复，不能与内置角色的显示名（访客、开发、值班 SRE、DBA、审批人、管理员、审计员）或 ID 相同 | 红字提示 |
| 说明 | 最多 200 个字，可空 | 红字提示 |
| 必选能力 | 必须含 `view.overview`（允许） | 被拒绝 |
| 仅内置管理员能力 | 不能授予 `settings.edit`、`writeswitch`、`users.manage`，对所有人（含管理员）生效 | 被拒绝（403） |
| 授予方式 | `inst.op` `scale` `config` `maint` `backup` `release`：无 / 允许 / 需审批；`view.sql`：无 / 允许 / 范围内；其余：无 / 允许 | 被拒绝 |
| 防提权 | 操作者只能授予自己已拥有、且授予方式不低于所授方式的能力；内置管理员不受此限。因为角色写接口本身要求 `users.manage`（仅内置管理员持有），目前**实际只有内置管理员能改角色**，这条是将来放宽入口时的保险 | 被拒绝（403） |
| 内置角色 | 永远不可修改、不可删除（只能复制） | 没有按钮；接口返回 403 |
| 删除 | 仍有成员（含已禁用、任一环境）时不能删除 | 「无法删除角色」抽屉，列出成员 |
| 删除后的残留 | 已被删除（或角色库里丢失）的角色，若还挂在某用户身上，该角色按「无权限」处理，用户列表显示「xxx（已删除）」 | — |
| 角色库损坏 | `roles.json` 内容不合法的部分在启动时被丢弃（只会减少权限）并写日志、审计 `role.load` 与页面橙色提示；JSON 本身无法解析则服务拒绝启动 | 见页面提示 |

自定义角色与其他安全机制的关系：写操作开关的双人确认、「授予管理员需另一名管理员确认」、审批策略的硬性下限（生产高风险至少 2 级且需 MFA、生产中风险至少 1 级、预发高风险至少 2 级）、紧急变更规则都**不会被自定义角色绕过**，因为自定义角色拿不到那三项仅管理员能力。自定义角色**可以**拥有 `approve.mid` / `approve.high`，但申请人仍不能自批、同一人不能重复审批、级数不变。

## 执行后果与风险

> ⚠️ 角色修改立即生效，没有预览环境，也没有回滚按钮。

- **对成员即时生效**：保存会直接改变所有成员的能力，不吊销会话、不通知成员。保存前一定读「将立即对 N 名成员生效」那条提示。
- **一人可操作**：改角色不需要另一名管理员确认。如果一名管理员新建一个带 `approve.high` 的角色并分配给同伙，双人复核（只覆盖授予 admin、写开关、审批策略）并不会拦住——请靠审计复核：「权限与审计」→「审计日志」里筛 `role.create` `role.update` `user.roles`。
- **「全选允许」很重**：会把 `inst.op` `scale` `config` `maint` `backup` `release` 都设为「允许」，成员可以发起任何集群变更（仍走审批策略）。
- **高风险能力要最小化**：只授予完成任务必需的能力；`view.sql` 可能暴露业务数据，优先用「范围内」配合授权库。
- **审计**：创建、修改、删除都有记录，摘要里写明差异；`role.load` 记录启动时的降级。

## 常见问题与注意

- **看不到「角色权限」菜单？** 你的角色没有 users.manage 也没有 audit.view；找管理员。
- **所有按钮都灰？** 你只有 audit.view（审计员 / 审批人），只读；或选中的是内置角色。
- **想改内置角色的权限？** 不可以。点「复制」得到自定义角色再改。
- **「保存」是灰的？** 没有未保存的修改；或你没有 users.manage。
- **保存时提示「角色必须包含 view.overview」？** 查看总览是必选项，不能去掉（页面里它的按钮也是锁死的）。
- **我给角色加了能力，成员为什么还是没有按钮？** 成员页面需要刷新才会更新按钮；同时他在**当前环境**下的角色决定能力——如果你给他在当前环境「单独设置」了别的角色，这个角色根本没起作用（见 [用户管理帮助](help:users) 的「角色按环境分配」）。
- **删除角色一直被拒？** 持有者里包含已禁用的用户，或在其他环境行里持有；在「成员」标签页看全部成员，逐个处理。
- **两个角色权限冲突怎么办？** 不会冲突：同一用户的多个角色逐项取最强授予方式，没有「拒绝」类权限，所以不能用「再加一个角色」来收回权限，只能去掉角色或改角色。
- **自定义角色能让某人审批变更吗？** 可以，授予 `approve.mid` / `approve.high` 即可；申请人不能审批自己的变更，同一人不能对同一变更重复审批。
- **模拟器结果和实际不一样？** 先对照「已知限制与易混淆点」；以真实提交变更时提交抽屉里的审批级数为准。
- **改完权限，怎么确认真的生效？** 用该账号登录，在「权限与审计」→「我的账号」看「当前环境下拥有的能力」。

## 已知限制与易混淆点

核对于代码与演示环境，格式为「界面 / 文档写的是 A，实际是 B」。

| 界面 / 你以为 | 实际是 | 建议 |
|---|---|---|
| 「允许」和「需审批」是两种不同的待遇（「需审批」= 要审批，「允许」= 免审批） | 对变更类能力，后端**只看风险 × 环境决定要不要审批、几级**，不看你是「允许」还是「需审批」。选「允许」的自定义角色发起的生产变更照样要走审批 | 变更类能力统一选「需审批」，与内置角色一致 |
| 模拟器选「允许」的写类能力会显示「无需审批」 | 真实变更不是这样（见上一行）。模拟器只在授予方式为「需审批」时才套用审批级数 | 模拟时选「需审批」，或自己对照审批策略表 |
| 自定义角色有 `backup` / `maint` 就能代别人取消、中止、确认变更 | 取消（尚未执行的变更）、中止（执行中的变更）、「确认人工步骤」在后端只认**申请人本人或内置 DBA 角色**。自定义角色即使有 `backup` / `maint` / `inst.op` 也不能操作别人的变更，只能操作自己发起的 | 需要代他人操作时，请让内置 DBA 做 |
| 部署自检里「至少两名管理员」 | 只统计启用中的**内置 admin 角色**用户（自定义角色拿不到 users.manage，所以本来就不会有第二种管理员） | 以此为准保证有两名启用的管理员 |
| 给角色勾「创建变更排期」才能定时执行 | 后端没有接口按 `sched.create` 放行或拒绝；能不能「定时执行」只取决于你有没有该变更的发起能力 | 不要把它当作安全开关 |
| 「平台发布」`release` 控制平台升级 | 后端没有接口检查它；平台升级 / 回滚是服务器命令行的事 | 不要把它当作安全开关 |
| 「运行诊断 / 巡检」说明写「只读」 | 同一能力还允许**创建告警静默**（写操作：需要写操作开关开启、不走审批、写审计 `alert.silence`） | 需要严格只读时，不要给自定义角色 `diag.run`；评估后再授予 |
| 「单实例操作」可以只授予重启 | 它同时包含停止、启动、驱逐 Leader、恢复 Leader 和「按角色滚动重启」，无法拆开 | 靠审批人把关；高风险的「停止」生产默认需 2 级审批 + MFA |
| 防提权校验让非管理员也能管角色 | 角色写接口要求 `users.manage`，它是仅内置管理员能力，所以目前只有内置管理员能改角色；防提权是预留的纵深防御 | 无需操作 |
| 权限模拟器的环境选项等同于用户的环境 | 模拟器的「环境」「写操作开关」「MFA」复选框都是演算输入，与用户实际被分配的环境、真实的写操作开关状态无关；也不会合并一个用户的多个角色 | 想看真实结果，用该账号登录看「我的账号」，或提交一次变更看提交抽屉 |
| 修改角色等同于修改用户，会让对方下线 | 修改**角色本身**的权限不吊销会话，仅即时生效；修改**用户的角色分配**才吊销会话 | 见 [用户管理帮助](help:users) |
| 双人复核保护了所有高风险权限操作 | 只覆盖「授予 admin」「改审批策略」「开启写操作开关」。创建 / 修改自定义角色、把自定义角色分配给用户都是**一名管理员**直接生效 | 靠审计复核，限制管理员数量 |
| 「说明」「名称」改了会影响权限 | 只是显示信息，不影响任何权限；ID 才是用户与角色关联的依据，且不可改 | — |
| 角色权限页像是「当前集群」的角色 | 角色定义是**全局**的，所有集群共用；管理角色（本页的新建 / 修改 / 删除）的授权按**主集群的环境**判断，管理员只在非主集群的环境里有角色时管不了角色。修改自定义角色会对**所有集群**里持有该角色的人立即生效 | 管理员设在「所有环境」；改角色前想想它在哪些环境的集群里被使用 |
| 成员标签页里的「任一环境」像是只算当前集群 | 成员是在**任一环境**持有该角色的用户，与你当前切换到哪个集群无关；删除角色时也按「任一环境」判断 | 删除被拒时在「成员」页看全部成员 |
| 「打印 / 导出」导出文件 | 调用浏览器打印（可存 PDF），不是服务端导出 | 需要留档时另存为 PDF |

以下链接均已打开核实；本篇的「角色」是**平台自己的权限角色**，TiDB 数据库的角色与权限是另一套体系，这些页面仅供区分与了解。页面以 stable 为准，**以你集群的版本为准**，必要时把地址里的 stable 换成对应版本（如 v8.1）。
