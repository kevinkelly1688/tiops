# 常见问题与提示

> 💡 按「现象 → 原因 → 怎么办」整理的排查表，提示文案取自平台实际弹出的错误 / 拒绝信息，可直接用页面上看到的原话搜索本页。适用所有角色；除「只读模式」一节外，下面都是**运维模式**（带登录）下的问题。

> ⚠️ 平台至今只在「回放数据 + 模拟执行器」下测试过，从未对真实集群执行过命令。涉及真实 tiup / pd-ctl / br 命令的失败原因、输出格式，一律以真实集群联调为准；遇到本页没覆盖的执行失败，先看变更详情里的「执行日志」。

## 这个页面做什么

覆盖十一类问题：登录与会话、账号 / 角色 / 权限管理、被拒绝、变更卡住或失败、回滚、通知、数据为空、集群相关、一键部署与中控机命令（多集群的切换、接入、测试、删除）、负载均衡（拓扑图的负载均衡层与手工登记）、只读模式的按钮；之后是「已知限制与易混淆点」，以及「回放 / 模拟执行 / 真实执行」三者的区别。

## 怎么用（按步骤）

1. 在页面上复制错误提示里的关键词（如「写操作开关未开启」）。
2. 在下面对应章节的表格里找到该提示，按「怎么办」处理。
3. 处理不了时，记下变更编号（`CHG-xxxx`）、提示原文和时间，交给有 `audit.view` 的同事（管理员 / 审批人 / 审计员）到 [权限与审计](go:security) 的「审计日志」里按变更号检索。

## 区域与参数说明

### 登录与会话

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 登录页红字「用户名或口令错误」 | 用户名不对、口令不对，或账号已被禁用。平台**故意不区分**这几种情况；登录只认用户名 + 口令，**不需要**动态验证码 | 核对用户名（不区分大小写）、口令（点「👁」显示出来看）；仍不行请管理员在 [用户管理](help:users) 里确认账号是否被禁用。不要连续试，5 次会被锁定 |
| 登录页红字「登录失败次数过多，请在 HH:MM:SS 后重试」 | 同一用户名**或**同一来源 IP 在 10 分钟内连续失败 5 次，被锁定 10 分钟（失败计数在内存里，平台重启会清零）；锁定期间用户名和口令输对也会被拒 | 见下文「账号被锁定 / 解锁后仍登录不了」 |
| 多人同时被锁定，且都没输错过 | 锁定按来源 IP 计数：经反向代理访问时，平台看到的来源 IP 是代理的地址，任何一个人连续输错 5 次，会让经同一代理登录的所有人一起被锁。这是按代码推断的现象，以真实部署为准 | 等待 10 分钟（管理员的「解锁」解不了 IP 维度）；部署时让代理只对内网开放并限制暴力尝试，或联系平台维护者确认真实 IP 的处理方式 |
| 登录页顶部提示「登录已过期或已在别处退出，请重新登录」（偶尔操作后的提示里会出现「未登录或会话已过期」，是同一件事） | 你已登录的会话失效了：空闲超过 30 分钟或总时长超过 8 小时；管理员对你的账号做了禁用 / 改角色 / 重置口令 / 删除；你在另一个标签页点了「退出」；或平台被重启（会话只在内存里） | 重新登录即可；若刚被管理员改过角色，登录后权限以新角色为准；刚登录又立刻被踢，联系管理员确认账号状态。注意：管理员**修改自定义角色的权限**不会让你掉线 |
| 登录页红字「无法连接后端：…」或「登录失败（502）」之类 | 浏览器连不上平台，或反向代理 / 网关返回了非平台的错误页 | 稍后重试，联系部署人员检查平台进程与反向代理 |
| 点「登 录」没反应，红字「请输入用户名」「请输入口令」 | 浏览器本地校验：对应输入框为空（这类提示不算登录失败） | 补全后重试 |
| 忘记口令，想自助找回 | 平台没有邮件 / 短信自助找回，也没有 LDAP / SSO 登录 | 见下文「忘记口令」 |
| 提交高风险变更提示「动态验证码错误或已被使用」 | 同一 30 秒时间窗内的动态码只能用一次；你刚用这个码提交过高风险变更或在「我的账号」确认过绑定，再用同一个码会被判重放。连续输错 5 次，二次确认会被锁定 10 分钟 | 等认证器刷新出下一个码再填；手机时间要准确 |
| 「高风险变更需要申请人二次验证（MFA）」 | 当前环境 × 风险的审批策略要求申请人 MFA（默认只有生产 · 高风险），但没有填动态码 | 在提交抽屉的「申请人动态验证码（MFA）」里填 6 位码 |
| 「高风险变更需要申请人二次验证（MFA）。你尚未绑定 MFA，请先在「权限与审计」里绑定动态验证码。」 | 你的账号还没绑定 TOTP | 到 [权限与审计](go:security) →「我的账号」→「开始绑定」，用认证器 App 添加密钥后确认 |
| 在「我的账号」改口令提示「当前口令不正确」 | 只有「当前口令」框里填的确实不是你现在的口令才会出现（是否绑定 MFA 不影响；旧版本里已绑定 MFA 的账号会一直误报，现已不会） | 核对当前口令（点「👁」显示出来看）；确实忘了就请管理员在「用户管理」里「重置口令」 |
| 提示「口令至少 10 位」「口令需至少包含大写字母、小写字母、数字、符号中的 3 类」「口令不得包含用户名」 | 不满足口令策略 | 换更长 / 更复杂的口令 |
| 管理员重置了 TOTP，之后提交生产高风险变更提示要先绑定 MFA | 重置只清除绑定，不会吊销会话；登录本来就不需要动态码，影响的只是提交高风险变更：绑定之前会被拒绝 | 到「权限与审计 → 我的账号」重新绑定 |
| 「我的账号」里绑定 MFA，提示「动态验证码错误或已被使用」，连续错误后提示「登录失败次数过多，请在 HH:MM:SS 之后重试」 | 认证器里的码不对（手机时间不准、添加了错误的密钥、选错了账户）或该 30 秒窗口的码已被用过；连续输错 5 次，该账号的 MFA 确认被锁定 10 分钟（这条提示末尾是「之后重试」，登录页的是「后重试」，是同类锁定） | 校准手机时间（设为自动同步）；确认认证器里添加的是页面上显示的 Base32 密钥、类型为基于时间；等下一个码再填；被锁定时让管理员在 [用户管理](help:users) 对你「解锁」，或等 10 分钟 |
| 管理员想给自己「重置口令」「禁用」「删除」，按钮是灰色的 | 这三项对**自己的账号**置灰（避免把自己锁在外面），悬停提示「不能对自己的账号执行该操作…」；「编辑」里自己的角色也不能改，只能改资料 | 自己的口令到「权限与审计 → 我的账号」改；要改自己的角色 / 禁用自己，让另一名管理员操作 |

### 账号、角色与权限管理（用户管理 / 角色权限）

下面每一条都按「现象 → 原因 → 怎么办」写，需要动手的写成编号步骤。涉及的页面：[用户管理](go:users)、[角色权限](go:roles)、[权限与审计](go:security)；账号与角色的概念见 [快速入门](help:quickstart) 的「内置的 7 个角色能做什么」「自定义角色」。

#### 看不到侧栏的「平台配置」（用户管理 / 角色权限）

**现象**：侧栏没有「平台配置」分组；或者直接打开用户管理 / 角色权限页，只看到「当前账号没有查看用户与权限的能力（需要 users.manage 或 audit.view）」。

**原因**：这个分组只对拥有 `users.manage`（用户与角色管理）或 `audit.view`（查看审计日志）的账号显示。默认只有「管理员」「审批人」「审计员」有；「访客」「开发」「值班 SRE」「DBA」没有。另外，平台处于只读 / 回放模式（没有登录）时也不显示。

**怎么办**

1. 确认顶栏右侧有「显示名 · 角色名」和「退出」（说明你在运维模式并已登录）。没有的话，见 [快速入门](help:quickstart) 的「怎么判断当前模式」。
2. 打开「权限与审计 → 我的账号」，看「角色」一行，以及「当前环境下拥有的能力」里有没有 `users.manage` 或 `audit.view`。
3. 没有：请管理员给你加角色。只想**查看**用户与角色，给含 `audit.view` 的角色即可（内置「审计员」，或见下文「想给某人只读审计 + 查看用户」）；要**管理**用户，需要「管理员」角色（授予管理员需另一名管理员确认，见 [权限与审计](help:security)）。
4. 管理员刚给你加了角色但菜单没出现：刷新浏览器页面。角色是按环境授予的，请管理员确认角色加在「所有环境」或**主集群所属的环境**上：用户管理 / 角色权限页本身是全局的，真正的授权按**主集群的环境**判断；而菜单是否显示按你**当前所选集群**的环境判断，所以管理员只在非主集群的环境里有角色时，可能出现「切到那个集群后菜单出现，打开页面却被拒绝（没有权限）」，见 [集群接入帮助](help:clusters) 的「已知限制与易混淆点」。

> 💡 看到菜单不等于能修改：只有 `users.manage` 才能创建、编辑、禁用、解锁、删除；只有 `audit.view` 的账号进入页面后会看到「只读」提示，所有写按钮置灰。

#### 保存角色后，对方的权限没变化

**现象**：管理员在 [角色权限](go:roles) 里改了某个自定义角色，保存成功，但持有该角色的人说看不到新能力（或没失去旧能力）。

**原因**：修改本身是**即时生效**的（成员的下一次请求就按新权限判定，不用重新登录）。没变化通常是下面几种情况之一。

**怎么办（按顺序排查）**

1. 确认保存真的成功：保存后应提示「已保存「角色名」，已对 N 名成员即时生效」；若提示「没有变化」，说明你的改动和原来一样。也可以到「权限与审计 → 审计日志」，「动作」填 `role.update` 查询，看摘要里的「权限 +… −…」与「即时影响 N 名成员」。
2. 确认改的是对的角色：角色权限页左侧「内置角色」是只读的（保存会被拒绝「内置角色不可修改」）；要改请先「复制」成自定义角色，再把用户改挂到新角色上。
3. 确认对方在**当前环境**真的拥有这个角色：打开 [用户管理](go:users)，看该用户「角色（环境 → 角色）」一列。角色是按环境分配的，生效的只有「所有环境」和**当前所选集群所属环境**的角色（顶栏环境标签就是当前集群的环境；切换到另一个环境的集群，生效的角色会跟着换）；如果该用户在本环境被「单独设置」了别的角色，「所有环境」里的角色在这里不起作用。
4. 对方是否还有**其他角色**：多个角色的能力取并集、每项取最强授予方式。你从角色 A 去掉了某项能力，但他的角色 B 仍有，那他还是有。要收回，需要从他所有的角色里都去掉。
5. 能力的授予方式是不是你想要的：「需审批」只代表可以发起、仍要按风险 × 环境走审批；「范围内」（`view.sql`）只对用户被授权的库生效，要在 [用户管理](go:users) 里给用户填「授权库」。
6. 能力有了，操作却仍被拒：还要过写操作开关、READONLY 文件、版本支持、窗口规则等总闸，见下文「被拒绝」。
7. 对方页面没刷新：对方的页面每隔几秒自动同步权限，但在打开着抽屉或正在输入时不会重绘。请对方关闭抽屉后切换一下页面，或刷新浏览器。

#### 账号被锁定 / 解锁后仍登录不了（IP 限制）

**现象**：用户连续输错口令后被锁定；管理员在 [用户管理](go:users) 点了「解锁」，提示已解锁，用户再登录仍提示「登录失败次数过多，请在 HH:MM:SS 后重试」。

**原因**：登录失败同时按「用户名」和「来源 IP」两个维度计数，任一维度 10 分钟内累计 5 次就锁 10 分钟。管理员的「解锁」**只清除用户名维度**（以及该账号动态码二次确认的失败计数），**不清 IP 维度**。多人经同一个反向代理或办公室出口访问时，同一个 IP 上累计的失败很容易满 5 次。

**怎么办**

1. 让用户看提示里的 HH:MM:SS（服务器本地时间），那是该锁定的最晚结束时间；最长 10 分钟。
2. 在那之前**不要再试**（锁定期间输对也会被拒，也不会因此延长）。到点后再登录。
3. 管理员核对：在 [用户管理](go:users) 里该用户的「状态」若已不是「已锁定」，说明用户名维度已解除，剩下的就是 IP 维度。「解锁」按钮对未被锁定的用户是灰色的，悬停提示「该用户当前未被锁定」。
4. 到「权限与审计 → 审计日志」，「动作」填 `auth.login`、「结果」选「拒绝」，用「关键字」搜该 IP，看是谁在反复失败，必要时提醒对方。
5. 万不得已需要立刻放行：在中控机上重启平台服务会清零所有失败计数，但会让所有人重新登录，也会中断页面上的操作，非必要不要这样做。

**后果**：解锁会写审计 `user.unlock`（摘要写明是「解除登录锁定」还是「清除登录失败计数（当时未被锁定）」）；不吊销用户已有的会话。

#### 忘记口令（含管理员自己）

**现象**：登录不了，也想不起口令。

**原因**：本平台只有本地账号，**没有邮件 / 短信自助找回**，也没有 LDAP / SSO 登录。

**怎么办**

1. 普通账号：联系管理员，在 [用户管理](go:users) 对你那一行点「重置口令」，设置一个满足口令策略的临时口令。预期结果：提示「口令已重置，其会话已吊销」。你用临时口令登录后，立刻到「权限与审计 → 我的账号」改成自己的口令。
2. 管理员忘了口令，但还有另一名管理员：请对方做第 1 步（管理员不能给自己重置）。
3. 平台上**只有一名管理员**（或所有管理员都忘了）：需要有中控机命令行权限的人，在**服务停止时**重设。按平台安装脚本的默认值（运行账号 `tidbops`、数据目录 `/var/lib/tidbops`、服务名 `tidbops`；你们的部署不同请替换）：
   - 停止服务：`sudo systemctl stop tidbops`
   - 重设口令（`admin` 换成用户名，`<新口令>` 满足口令策略，示例 `Ab3!example-Pass`，请勿照抄）：

```
sudo -u tidbops env TIDBOPS_USER_PASSWORD='<新口令>' /opt/tidbops/bin/tidbops-server user passwd --data-dir /var/lib/tidbops --name admin
```

4. 看到输出「完成」后，启动服务：`sudo systemctl start tidbops`，用新口令登录。口令不符合策略时命令会输出「失败: …」并说明原因，改正后重试。

**后果**：命令行重设**不写审计日志、不吊销会话**，且运行中的服务不会重新读取用户库，所以必须在服务停止时做（或做完重启）。登录不需要动态码；账号如果还绑定着 MFA，手机丢了会影响提交生产高风险变更，这时把 `passwd` 换成 `totp-reset`（不需要口令环境变量）：`sudo -u tidbops /opt/tidbops/bin/tidbops-server user totp-reset --data-dir /var/lib/tidbops --name admin`。完整说明见 [权限与审计](help:security) 的「命令行：忘记管理员口令或丢失 MFA」。

#### 想给某人「只读审计 + 查看用户」，但不能导出审计、不能改任何东西

**现象 / 需求**：合规或安全同事需要看审计日志、核对用户与角色分配，但不应有任何修改权限。

**原因**：内置角色里，「审计员」能看审计日志，**还能导出**（`audit.export`）；「审批人」虽然也有 `audit.view`，但同时能审批变更。所有含 `audit.view` 的账号都可以只读查看用户清单与角色，写操作仍需要 `users.manage`。

**怎么办**

- 办法 A（允许导出审计）：在 [用户管理](go:users) 里给该用户「编辑」，在角色里勾选内置「审计员」，点「保存」。
- 办法 B（不允许导出）：新建一个只含「查看审计日志」的自定义角色。**前置条件**：你是管理员（有 `users.manage`）。

1. 侧栏「平台配置 → 角色权限」，点左侧「角色」标题右边的「＋」。预期结果：右侧滑出抽屉「新建角色」。
2. 「角色 ID」填 `audit-ro`（小写字母开头，只含小写字母、数字、`_`、`-`，2 到 32 位，创建后不可改），「名称」填「只读审计」，「说明」选填；「初始权限」选「空白（只有必选的「查看总览」）」，点「创建角色」。预期结果：提示「已创建角色「只读审计」」，右侧自动选中它并停在「功能权限」标签。
3. 在「审计」分组里找到「查看审计日志」（`audit.view`），点分段按钮「允许」；「导出审计日志」保持「无」。
4. 点底部「保存」，在抽屉「保存角色「只读审计」」里看差异（新增「查看审计日志 · 允许」），点「确认保存」。预期结果：提示「已保存「只读审计」，已对 0 名成员即时生效」。

5. 侧栏「平台配置 → 用户管理」，找到该用户，点「编辑」。在「角色（环境 → 角色）」的「所有环境（默认）」一行，勾选「自定义」一栏里的「只读审计」，点「保存」。预期结果：提示「已更新 xxx 的角色」。注意：改用户的角色会**吊销该用户的全部会话**，对方要重新登录。
6. 请对方重新登录并核对：侧栏出现「平台配置」分组（用户管理、角色权限），进入后页面提示「只读：当前账号没有 users.manage 能力…」，所有写按钮置灰；「权限与审计」多出「审计日志」标签，且没有「导出 CSV」「导出 JSONL」按钮。

**后果**：该账号能看到所有用户的资料（含邮箱、手机、最近登录）和全部审计记录（含所有人的操作与来源 IP），请按公司规定授权。

#### 自定义角色的人，为什么取消 / 中止不了别人的变更

**现象**：某用户持有的自定义角色里有 `backup`、`maint`、`inst.op` 等能力，能提交变更，但点别人变更上的「取消变更」「中止」或「我已完成，继续」时被拒绝，提示「只有申请人或 DBA 可以取消」「只有申请人或 DBA 可以中止」「只有申请人或 DBA 可以确认人工步骤」。

**原因**：这三个动作不看能力，只认**变更的申请人本人**或**内置的「DBA」角色**。自定义角色即使能力和 DBA 一样，也不能代别人取消 / 中止 / 确认人工步骤（已知限制）。「填写事后复盘」更是只有申请人能做。

**怎么办**

1. 让该变更的申请人本人去「节点管理 → 任务中心」取消 / 中止 / 确认。
2. 需要这个人长期能代操作：请管理员在 [用户管理](go:users) 里给他**额外加上内置「DBA」角色**。DBA 还同时拥有扩缩容、配置变更、主机维护、备份恢复的发起能力，请按最小权限原则评估后再加。
3. 只是想让他审批：审批看的是 `approve.mid` / `approve.high` 能力，自定义角色有这两项就能审批（申请人不能审自己的变更）。

#### 删除角色被拒绝：仍有成员

**现象**：在 [角色权限](go:roles) 点「删除」，弹出「无法删除角色」，列出仍持有该角色的用户；或提示「仍有 N 个用户持有该角色（a、b），请先移除」。

**原因**：只要还有用户（**含已禁用的用户**，任一环境）持有该角色，就不能删除，避免成员突然失去权限。

**怎么办**

1. 在抽屉里点「去用户管理处理 →」，或在 [用户管理](go:users) 的角色下拉里选这个角色筛选出成员。
2. 对每个成员（别漏了已禁用的）点「编辑」，把这个角色从各环境里取消勾选，换成别的角色，点「保存」。
3. 回到 [角色权限](go:roles)，再点「删除」→「确认删除」。**删除不可恢复**；该角色在审计里留 `role.delete`。

#### 用户的角色显示「xxx（已删除）」，或顶栏角色名变成了角色 ID

**现象**：[用户管理](go:users) 里某人的角色标签是橙色的「xxx（已删除）」；或者顶栏「显示名 · 角色名」里显示的是英文 ID。

**原因**：该用户持有的自定义角色在角色库里已经不存在了（通常是 `roles.json` 被手工改过 / 丢失，或启动时因内容不合法被丢弃，审计里会有 `role.load` 记录）。已不存在的角色按「**无权限**」处理。

**怎么办**

1. 到「权限与审计 → 审计日志」查 `role.load`、`role.delete`，弄清角色是怎么没的。
2. 在 [角色权限](go:roles) 里新建一个**角色 ID 相同**的自定义角色并设置好权限；用户持有的是角色 ID，所以新建后会自动恢复（按代码推断，以真实环境为准）。
3. 或者在 [用户管理](go:users) 里把该用户的角色换成现有的角色。

### 被拒绝（权限 / 开关 / 窗口 / 冻结期 / 审批级别 / 频率限制 / 跨站）

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 「没有权限：inst.op」（冒号后是能力键，如 `scale` `config` `maint` `backup` `settings.edit` `users.manage` `audit.view`） | 你的角色在当前环境下没有该能力。拒绝本身也会写一条审计 `authz.deny` | 对照 [快速入门](help:quickstart) 的角色矩阵，或到「权限与审计 → 我的账号」看自己拥有哪些能力；需要权限请管理员调整角色。注意：管理员 / 审批人 / 审计员没有变更执行类能力 |
| 「没有权限：users.manage 或 audit.view」 | 读取用户清单 / 角色列表需要这两个能力之一（审计员现在可以只读查看）；你两个都没有 | 见上文「看不到侧栏的「平台配置」」 |
| 按钮是灰的，悬停提示「权限不足」，点击后按钮旁出现红字「权限不足」 | 运维模式下没有对应能力的按钮会置灰（但仍可点击，只是给出提示，不会提交任何请求） | 同上；或换有权限的账号；缺哪项能力见本页「权限矩阵」，按角色权限由管理员授予 |
| 「写操作开关未开启：由两名管理员确认后才能对该环境执行变更」 | 写操作开关默认关闭，提交变更 / 告警静默 / 开始执行都会被拦 | 由两名不同的管理员先后在 [权限与审计](go:security) →「写操作开关」里「提议开启」→「确认开启」 |
| 「平台处于强制只读（存在 /etc/tidb-ops/READONLY）」 | 中控机上存在 READONLY 熔断文件，与写开关无关 | 由有中控机权限的人确认可以恢复后删除该文件；是否该删请先问是谁、为什么放置的 |
| 「未配置执行器，无法执行变更」或「未配置执行器（启动参数 --exec）」 | 平台以 `--data-dir` 直连真实集群启动但没有指定 `--exec`，执行器为 `none` | 联系部署人员加上 `--exec sudo`（推荐）或 `direct`；演示环境用回放模式（默认 `sim`） |
| 「集群版本 … 不在平台支持范围内（v7.5. v8.1. v8.5.），写操作已降级为只读」 | 集群版本不在 v7.5 / v8.1 / v8.5 系列 | 升级到受支持版本，或接受只读 |
| 「计划时间落在变更冻结期「…」内；确需执行请走紧急变更」 | 计划执行时间（立即执行则为当前时间）与某个冻结期重叠 | 改到冻结期之后；确实要做就勾选「紧急变更」（预发 / 生产至少 2 级审批，事后必须复盘） |
| 「窗口规则拦截：落在禁止变更窗口「…」…」 | 命中了「禁止」模式的变更窗口规则 | 在提交抽屉点「推荐时间」选一个合规时段；或勾选「紧急变更」（留痕并要求事后复盘）。窗口规则在 [环境与设置](go:settings) 里查看 |
| 抽屉里出现「落在不建议变更的窗口…」「按计划时间…」黄色提示 | 命中「不建议」窗口（备份窗口、业务高峰等），只是警告 | 可以继续提交，但建议改到推荐窗口 |
| 「与已排期的变更 CHG-xxxx 在时间与资源上冲突」 | 同一实例 / 主机、时间区间重叠的已排期变更已存在 | 换一个时间，或先处理那条变更 |
| 「计划执行时间已过」 | 选的定时时间早于当前时间 1 分钟以上 | 重新选时间；注意页面选择的是浏览器本地时间 |
| 「前置检查未通过：…」，提交按钮显示「存在阻断项」 | 规划器发现阻断项（✖），如实例已被别的变更占用、剩余副本不足、磁盘水位超 80%、主机正在维护等 | 逐条看抽屉里红色检查项，先解决；这类检查服务端会再算一遍，前端无法绕过 |
| 「没有拓扑数据，无法规划变更：…」 | 当前没采到拓扑（采集失败 / 数据源不可用） | 先看页面顶部「N 项数据缺失」的原因，恢复数据采集后再试 |
| 「CSRF 校验失败」 | 令牌与会话不匹配：常见于在另一个标签页重新登录 / 退出、或换了账号后继续用旧页面 | 刷新页面（必要时重新登录）；此类拒绝会写审计 `security.csrf` |
| 「拒绝跨站请求」 | 请求头 `Origin` 的主机与访问的主机（`Host`）不一致，常见于反向代理改写了 `Host` | 让代理原样透传 `Host` 头（如 nginx 的 `proxy_set_header Host $host;`），并走 HTTPS 时设置 `X-Forwarded-Proto`；此类拒绝写审计 `security.origin` |
| 「请求过于频繁」 | 每个用户的写类请求限速每分钟 60 次（被拒绝的也计数） | 等一分钟；不要写脚本高频调用 |
| 「只读服务：仅支持 GET / HEAD」（HTTP 405） | 平台以只读模式启动（没带 `--data-dir`），不接受任何写请求 | 只读模式本就不能提交变更；需要变更请使用运维模式部署 |
| 「请求体不是合法的 JSON：…」 | 直接调接口时请求格式不对 | 页面操作不会出现；脚本调用请检查 JSON |

### 审批相关

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 「批准」按钮置灰，悬停提示「申请人不能审批自己的变更」 | 职责分离：申请人不能批自己的变更 | 请另一名有审批能力的人批准 |
| 「你已审批过该变更」或「同一人不能重复审批同一变更」 | 多级审批必须是不同的人 | 请下一位审批人批准 |
| 「你没有审批该风险等级变更的权限」或「无权审批该风险等级的变更（用户 …，环境 …，风险 …）」 | 审批需要 `approve.mid`（中风险）/ `approve.high`（高风险）能力；内置角色里只有「审批人」有，含这两项的自定义角色也可以 | 请管理员给你授予审批人角色（或含这两项能力的自定义角色），或找审批人 |
| 「申请人不能驳回自己的变更，请使用取消」 | 驳回是审批人的动作 | 申请人用「取消变更」 |
| 「驳回必须填写原因」 | 驳回时原因必填 | 填写后再点驳回 |
| 「审批已过期」；变更状态变成「已过期」，原因「审批超时未完成，已作废」 | 审批有效期 24 小时（定时变更不早于计划时间），超时作废 | 重新提交；可在 [权限与审计](go:security) 请管理员评估是否调整审批策略以减少级数（受硬性下限约束） |
| 「变更当前状态为 pending / approved / running … ，不能审批」 | 变更已不在「待审批」（可能刚被别人批完、驳回或取消） | 刷新页面看最新状态；提示里的状态是英文原词 |
| 变更一直「待审批」 | 还没凑够级数（看「审批 x/y」）；或没有合适的审批人；或要等的审批人不是你 | 提醒审批人（可开通知渠道推送「有变更等待审批」）；侧栏「变更排期」角标显示待审批数 |

### 变更卡住 / 失败

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 状态「排队中」迟迟不执行 | 同一集群内串行：该集群同一时刻只执行一个变更，前面还有变更在执行（别的集群的变更不会堵住它，也不受它影响） | 在「节点管理 → 任务中心」看谁在执行；等待，或让前一个变更完成 / 中止 |
| 平台重启过，状态「排队中」的变更再也不动 | 引擎重启时只处理了「执行中」（标记失败），不会重新拉起已批准、排队中的变更。按代码推断，需要人工处理；以真实环境为准 | 由申请人或 DBA「取消变更」后重新提交 |
| 状态「已排期」，到点没开始 | 还没到点（时间按服务器本地时区；页面显示服务器时间）；或前面有变更占着执行器 | 核对「变更排期」页顶部的服务器时间；调度每 2 秒检查一次，到点后进入排队 |
| 变更刚批准 / 到点就变成「失败」，原因「执行前检查未通过：…」 | 开始执行前会再次检查总闸，此时写开关被关、READONLY 文件出现、版本不受支持或没有执行器 | 先解除对应总闸，再重新提交（失败是终态，不能重试） |
| 「执行中」卡在 ⏸「待人工确认」 | 某步骤需要人在外部完成（如把 TiDB 从负载均衡摘除 / 加入负载均衡；缩容 / 维护 TiDB 时有没有摘除步骤取决于「环境与设置」里的复选框或登记，见下文「负载均衡」） | 申请人或 DBA 做完后点「我已完成，继续」（平台不会替你操作，也不检查你是否做了）；其他人看到的是「等待申请人 / DBA 确认」；超过 12 小时变失败「等待人工确认超时（12 小时）」 |
| 点「我已完成，继续」提示「只有申请人或 DBA 可以确认人工步骤」 | 只有申请人或 DBA 能确认 | 换申请人 / DBA 操作 |
| 提示「已确认，请稍候」 | 重复点击，上一次确认还没被引擎消费 | 稍等几秒 |
| 失败原因形如「等待实例 Up：等待超时（…）」 | 命令已执行，但等待实例上线 / Leader 迁出 / Store 变 Tombstone 等条件超时（实例 Up 默认等 10–15 分钟，缩容 Region 迁出最长等 48 小时） | 到 [节点管理](go:nodes) 和 [热点与调度](go:hotspot) 看实例与 Store 的真实状态，再决定下一步；缩容过程中不要重复提交 |
| 失败原因形如「<步骤名>：退出码 N」或某条 tiup / pd-ctl 的报错 | 执行器运行的命令返回非 0 | 展开变更详情看「执行日志」里的命令输出；这些命令输出格式以真实集群联调为准 |
| 执行日志里有「[自动修复] 组件 ctl:v… 的可执行文件缺失，正在重新安装」 | 中控机上 tiup 的 ctl / br / cdc 组件目录在、可执行文件不在（安装被中断、被清理、离线镜像不完整），原命令因此没能启动。平台已自动 `tiup uninstall` + `tiup install` 该版本并重试一次 | 看后面一行：「已重新安装，重试原命令」说明已恢复；「重新安装失败」多半是离线环境镜像里没有该组件，请在中控机上用 tidb 用户手动 `tiup install ctl:<版本>`（离线环境先把 toolkit / 组件包导入镜像）。同一组件 10 分钟内只自动修复一次 |
| 失败原因里有「令牌已过期」「令牌与命令不匹配」「缺少审批令牌」 | 执行器的审批令牌校验失败（令牌有效期 15 分钟，绑定命令与变更号） | 重新提交；反复出现请联系平台维护者检查 Web 进程与 exec 入口使用的是否是同一把密钥 |
| 失败原因里有「命令 … 不在白名单内」「集群 … 未接入」「节点 … 不在集群拓扑内」 | 执行器的二次校验拒绝了命令 | 通常是拓扑已变化或策略文件没包含该集群；刷新后重新规划，或联系维护者 |
| 失败原因「平台在执行过程中重启，变更被中断：请核对集群状态后重新规划」或「平台停止，执行被中断…」 | 执行过程中平台进程被重启 / 停止 | 先到集群核对状态（可能残留驱逐 Leader 调度、实例停在一半），再重新规划，不要直接重提 |
| 失败原因「备份存储路径不在允许的前缀内（…）」 | 备份路径不在执行器策略的 `backupRoots` 白名单前缀里 | 改用白名单内的路径，或请维护者调整策略 |
| 「…已被变更 CHG-xxxx（…）占用，请等待其完成或取消」 | 同一实例已有未结束的变更 | 等它结束或取消它 |
| 「…所在主机 … 正在维护（M0001），请在维护流程中操作」 | 主机在维护中，其上实例不能单独操作 | 到「节点管理 → 主机维护」走维护流程 |
| 「…正处于「offline」状态，请等待当前变更完成」 | 实例状态为 joining / offline（刚扩容或正在缩容下线） | 等状态稳定 |
| 「剩余 TiKV 仅 N 个，小于 max-replicas=3…」「迁入数据后剩余 TiKV 磁盘约 X%，超过 80% 水位…」「缩容后 PD 仅剩 N 个…」 | 缩容规划的安全检查 | 先扩容或换更小的缩容范围；一次只下线一个 TiKV |
| 配置变更提示「…是高危参数：修改会触发全量副本变更…」且无法提交 | 高危参数（目前是 `replication.max-replicas`）既标为高风险，又带阻断检查，当前实现下**无法通过平台提交**（疑似与提示语不一致，见联调清单） | 由 DBA 在维护窗口手工评估并在中控机上处理，并留痕 |
| 配置变更提示「未能读取 tiup 的 meta.yaml，无法安全地生成持久化配置…」 | 真实模式下平台读不到 `~/.tiup/storage/cluster/clusters/<集群>/meta.yaml` | 确认平台运行用户可读该文件；回放 / 模拟模式不会遇到 |
| 变更成功了，但想撤销 | 平台没有「撤销已成功变更」的按钮 | 提交一个反向变更（见下一节） |

### 回滚怎么做

平台**没有「回滚」按钮**，也不能「重试」失败的变更（失败 / 中止 / 驳回 / 取消 / 过期都是终态）。引擎只在**失败或被中止**时，按计划里预置的恢复命令「尽力恢复」，单条恢复命令失败会被忽略并写日志。

| 变更类型 | 失败 / 中止时自动做的恢复 | 之后你要做的 |
|---|---|---|
| 重启 / 停止 / 驱逐 TiKV | 移除该 Store 的 evict-leader 调度，让 Leader 回迁 | 在 [节点管理](go:nodes) 确认实例 Up、无遗留驱逐调度；必要时提交「恢复 Leader 调度」「启动实例」 |
| 重启 / 停止 TiDB、PD 等其他组件 | 无 | 提交「启动实例」恢复 |
| 扩容 | 仅当 TiKV 自定义了 store limit：恢复到默认 15。扩出去的节点**不会**被自动撤销 | 想撤销扩容，提交对应的「缩容」 |
| 缩容 | 移除 evict-leader 调度。一旦执行到 `tiup scale-in`（不可中止步骤）就无法回头 | 平台白名单里没有「取消下线」命令，需 DBA 在中控机手工处理 |
| 配置变更 | 把 tiup 保存的拓扑还原为变更前的版本（`edit-config`）。**不会再做滚动 reload**，也**不会还原** SET CONFIG / SET GLOBAL / pd-ctl 的在线修改 | 再提交一次配置变更改回原值；还原后各实例的实际取值以真实联调为准 |
| 进入主机维护 | 还原 PD 的 max-store-down-time、移除 evict-leader 调度，维护记录标记为已取消 | 到「节点管理 → 主机维护」核对 |
| 结束维护 | 无自动恢复，失败后维护记录回到「维护中」 | 处理问题后重试「结束维护」；确需快速恢复可选「紧急恢复」（跳过检查单） |
| 滚动重启 / 滚动升级 / 备份 / 日志备份 / 恢复 | 无 | 人工处理；升级前务必先完成全量备份 |

> ⚠️ 「尽力恢复」不保证集群回到变更前状态，且不会通知你结果以外的细节：失败的变更请先在 [节点管理](go:nodes)、[热点与调度](go:hotspot) 核对实例、Store 与调度器状态，再决定下一步。**中止**只对计划标记为可中止的变更有效：单实例停止 / 重启、缩容、进入主机维护；越过「不可中止」步骤后提示「已越过不可逆步骤，不能中止；请等待完成或按失败处理」。

取消 / 中止相关提示：

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 「只有申请人或 DBA 可以取消」「…可以中止」「…可以确认人工步骤」 | 取消 / 中止 / 确认人工步骤只允许申请人本人或**内置**「DBA」角色；持有同等能力的自定义角色也不行 | 换申请人 / DBA 操作；长期代操作的做法见上文「自定义角色的人，为什么取消 / 中止不了别人的变更」 |
| 「变更当前状态为 running，不能取消（执行中的请使用中止）」 | 取消只用于未开始的变更 | 改用「中止」 |
| 「该变更不支持中止」 | 该类计划（扩容、配置变更、滚动重启、升级、备份、恢复等）不可中止 | 只能等它结束 |
| 「变更当前状态为 …，只有执行中的变更可以中止」 | 变更不在执行中 | 刷新看状态 |
| 紧急变更结束后卡着「待复盘」标签 | 紧急变更必须由**申请人**填写事后复盘 | 申请人在变更卡片点「填写复盘」；提示「只有申请人可以填写复盘」说明你不是申请人 |

### 通知没收到

通知在 [环境与设置](go:settings) 的「通知渠道」里配置（需要 `settings.edit`），支持企业微信 / 钉钉 / 飞书 / Lark / Slack / 其他（通用 JSON Webhook）六种渠道。

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 看不到「通知渠道」卡片，只有橙色提示「需要管理员权限」 | 查看和管理渠道都需要 `settings.edit` | 请管理员配置 |
| 保存渠道时提示「Webhook 地址必须是 https」「主机 … 不在允许列表」「官方域名的 Webhook 不能指定非 443 端口」「Webhook 地址格式不正确」等 | 只允许 https；默认只放行官方域名（`qyapi.weixin.qq.com`、`oapi.dingtalk.com`、`open.feishu.cn`、`open.larksuite.com`、`hooks.slack.com`）；「其他」类型没有官方域名，主机必须由管理员加入允许列表；解析到内网 / 回环地址的目标会被拒绝（管理员追加的允许主机除外） | 使用官方机器人地址；私有网关与「其他」渠道的接收端由部署人员用 `--notify-allow-hosts` 追加允许主机（追加的主机可以是内网地址） |
| 「发送测试」失败 | 中控机到 Webhook 域名 443 不通、地址或密钥不对、机器人开了「自定义关键词」而消息里没有该词、钉钉加签时间偏差过大（超过 1 小时会被拒） | 看测试结果里的错误原文与「最近投递记录」；这些外部平台的具体要求以真实联调为准 |
| 测试成功，但业务事件收不到 | ① 渠道已停用；② 渠道「订阅事件」没勾选该事件（不勾 = 订阅全部）；③ 事件本身不会发：免审批的变更不发「待审批」，「取消」变更不发通知，步骤进度、命令不发，告警 / 诊断**恢复**不发 | 检查渠道状态与订阅；在「最近投递记录」里看有没有对应条目 |
| 严重告警 / 严重诊断没推送 | 监视器每 60 秒轮询一次，只推**新出现**的 critical 告警与 bad / critical 诊断（诊断里「文件系统只读」「inode ≥ 90%」「容量 7 天内到 80%」这类严重项也在其内；处于「观察中」的项按提示级别，不推送）；启动后第一轮只记录基线不发；同一告警 30 分钟内、其他事件 10 分钟内相同的只发一次；一轮最多逐条发 8 条，其余合并成一条汇总 | 等下一轮；已存在的告警不会重复推送 |
| 投递记录里出现 `rate-limited` | 每个渠道每分钟最多 20 条，超出的丢弃 | 精简订阅事件，或拆成多个渠道 |
| 投递记录里出现 `queue-full` / `shutdown` / `channel-deleted` | 发送队列满（默认 256）/ 平台停止时尚未送出 / 渠道已被删除 | 排查是否消息过多；`shutdown` 的需自行补发 |
| 提示「渠道文件读取或解密失败，当前为只读」 | `notify.json` 无法读取或主密钥 `master.key` 不匹配 | 检查后端日志与主密钥；平台为避免覆盖原文件，此时禁止增删改渠道 |
| 消息里没有「查看」链接 | 未配置 `--public-url` | 联系部署人员配置对外访问地址 |
| 失败重试 | 失败会自动重试 3 次（间隔约 1 / 3 / 9 秒），最终失败记在投递记录里 | 不用手工重发，修好渠道后等下一个事件 |

### 数据为空

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 页面顶部显示「N 项数据缺失 ▸」 | 某些数据源没采到：如「告警不可用（未配置 Alertmanager 或无法访问）」「慢查询: …」「热点数据: …」「未配置只读 SQL 连接（--mysql-host / --mysql-user）」「缺少 Prometheus 节点指标…CPU / 内存将显示为 0」「tiup 拓扑不可用，已退化为从 PD / cluster_info 推导」 | 点开看具体项；缺什么补什么（启动参数或对应组件）；平台对取不到的数据显示「—」或「未采集」，**不会猜测** |
| 慢 SQL 列表为空，但别人能看到 | 你的角色看不到 SQL：访客 / 审计员完全看不到；「开发」只能看到管理员授权给你的库 | 请管理员在「用户管理」里给你授权库，或换有 `view.sql` 的角色 |
| 数据一直不变 | 回放模式用的是一份固定的样例数据包，不会更新；页面顶部会写「回放数据」和采集时间 | 想看实时数据，需要连真实集群的部署（只读直连或运维模式） |
| 数据太旧 | 页面每 30 秒自动刷新，快照最多缓存约 10 秒，数据源响应另有缓存 | 点页面顶部「立即刷新」；强制刷新最短间隔 2 秒 |
| 「变更排期」日历是空的 | 日历只显示选了「定时执行」的变更；没有定时变更时看不到任何块 | 到「节点管理 → 任务中心」看全部变更；或在提交抽屉里选定时 |
| 「事件时间线」「环境与设置」里没有内容 | 刚启动、还没有事件；或你没有对应权限 | 先做一次巡检 / 变更；设置类页面需要 `settings.edit` 才能改，登录即可看 |
| 巡检里很多项「未采集」 | 对应数据没取到；勾选「同时检查主机（tiup cluster check）」才有主机项 | 先解决数据缺失，再重新巡检；主机检查较慢，需要几分钟 |
| 排障向导没有「实时数据建议」 | 向导只对少数能被快照回答的问题给建议，其余仍由人选择 | 按页面问题自行判断；建议仅供参考 |

### 集群相关（多集群：切换、接入、测试、删除）

运维模式下平台可以纳管多个集群，概念与完整操作见 [集群接入帮助](help:clusters)。下面按「现象 → 原因 → 怎么办」写，需要动手的写成编号步骤。

#### 集群能看数据，但变更 / 扩缩容 / 重启被拒绝，提示「手工接入的远程集群：平台只读」

**现象**：节点管理、日常运维里提交变更、预览或执行时，闸门写着「该集群是手工接入的远程集群：平台只读，不能执行变更」；「写开关」页也一直显示只读，即使两名管理员已经开启。

**原因**：这个集群是用「＋ 手工接入远程集群（只读）」添加的，平台只拿到它的网络地址，**碰不到它的 tiup / SSH**，所以**不配执行器**，恒为只读（集群接入列表里标「远程接入 · 只读」）。只有在 tiup 中控机上「从本机 tiup 导入」的集群（标「本机 tiup · 可运维」）才能执行变更。

**怎么办**（需要管理员；平台必须是用 `install.sh --local-tiup` 装在这个集群的中控机上）

1. 「平台配置 → 集群接入」，删除这个手工添加的集群（只是移除纳管，不会动 TiDB 集群，数据目录改名保留）。
2. 点「从本机 tiup 导入」，勾选同名集群，选环境后导入。同名的手工集群没删之前，列表里会显示「同名手工集群」，不能导入。
3. 切换到该集群，由两名管理员开启写开关。平台没有装在这个集群的中控机上时没有这条路，只能在中控机上手工执行。

#### 在顶栏集群下拉里看不到某个集群

**现象**：同事能切到集群 `stg`，你的下拉里没有它。

**原因**：你只能看到「在该集群的环境里至少有『查看总览』能力」的集群。你在这个集群的**环境**里没有角色（环境上没有单独设置、「所有环境」也没设；或该环境被「单独设置」成什么角色都不选），这个集群对你就是不可见的——与「集群不存在」表现一致，平台不会提示你它存在。

**怎么办**

1. 先确认这个集群是什么环境：请管理员在「平台配置 → 集群接入」里看它的「环境」列（测试 / 预发 / 生产）。
2. 打开「权限与审计 → 我的账号」，看「当前集群」「当前环境」和角色。再切到你能看到的某个集群，对照它与目标集群的环境是否不同。
3. 把情况告诉管理员：在 [用户管理](go:users) 里编辑你的账号，给你在**目标集群的环境**上授予角色（例如目标是预发集群，就在「预发」行勾选角色，或在「所有环境」行勾选）。说明见 [用户管理帮助](help:users) 的「环境对应哪些集群、谁能看到哪个集群」。
4. 管理员改完后，你的下一次请求就按新角色判定（改用户的角色会让你被要求重新登录）；重新登录后，刷新页面查看下拉。

#### 集群下拉是灰色的，点不开

**现象**：下拉框灰色，悬停提示「当前账号只能看到这一个集群」。

**原因**：你当前能看到的集群只有一个（平台只纳管了一个集群，或你在其他集群的环境里没有角色）。多于一个时下拉才可用。

**怎么办**：属于正常现象时无需处理；想看别的集群，按上一条请管理员给你对应环境的角色。只读 / 回放模式（没有登录）下下拉里本来就只有当前这一个集群，也不能切换。

#### 切换集群后数据没变 / 仍然是旧集群

**现象**：选了另一个集群，页面看起来还是原来的数据，或刷新后又回到了原来的集群。

**原因与怎么办（按顺序排查）**

1. 看下拉框和浏览器标签页标题：切换会**整页刷新**，标题会变成「页面名 · 新集群显示名 · …」。没有刷新说明切换被取消了——如果当时开着抽屉，浏览器会先弹出确认框「当前有打开的抽屉或未保存的内容，切换到集群「X」会刷新页面并丢弃它们。确定切换吗？」，点了「取消」就留在原集群。重新选一次，点「确定」。
2. 你的选择记在**本浏览器的 localStorage**（键 `opCluster`）里。换了浏览器、用隐私窗口、清理过站点数据、或浏览器禁用了本地存储，都会回到默认集群（主集群；对你不可见时是你可见的第一个集群）。这种情况下每次打开都要重新选。
3. 同一个浏览器开了多个标签页：每个标签页用的是各自页面里的集群，**刷新后都会变成最后一次选择的那个**。保留一个标签页，其余关掉。
4. 两个集群看起来数据一样：看总览顶部横幅里的「集群 xxx」和采集时间，以及「集群信息」里的版本、节点数；回放集群读的是固定样例数据，不同集群的样例数据可能很相似。不确定时请管理员在「集群接入」页对照两个集群的 tiup 集群名。
5. 页面卡在旧数据：按 Ctrl + F5 强制刷新（静态脚本有 `no-cache`，一般不需要）。

#### 提示「当前集群已不可用，已切换到默认集群」（或接口提示「集群不存在或无权访问」）

**现象**：页面自己刷新了一下，底部弹出提示「当前集群已不可用，已切换到默认集群」，你回到了默认集群；或操作时提示「集群不存在或无权访问」。

**原因**：你正在使用的集群出了下面三种情况之一，下一次请求得到「集群不存在或无权访问」（HTTP 404）：
- 管理员把这个集群**删除**了（移除纳管）；
- 管理员改了你的角色，你在该集群的环境里**没有角色**了；
- 管理员把该集群的**环境**改成了你没有角色的环境。

页面检测到后会清掉保存的选择并刷新，回到默认集群。**连续自动刷新最多 3 次**，防止异常时无限刷新。

**怎么办**

1. 先看下拉：你能看到的集群里还有没有刚才那个。没有就是被删除或你没有权限了。
2. 向管理员确认：是不是有人删了这个集群、改了它的环境、或改了你的角色（管理员可在「权限与审计 → 审计日志」按「集群」或动作 `cluster.remove` / `cluster.update` / `user.roles` 查）。
3. 需要继续用它：请管理员恢复权限（给你该环境的角色）；被删除的集群需要重新接入（平台没有「恢复」按钮，旧数据目录改名保留在数据目录的 `clusters/.removed-…` 下，见 [集群接入帮助](help:clusters)）。
4. 如果反复出现提示、页面不再自动恢复：清除本站点的浏览器存储（至少 localStorage 的 `opCluster`）后刷新，再从下拉里选一个能用的集群。

#### 接入集群失败

**现象**：在「集群接入」里点「接入集群」或「保存」，抽屉里出现红字。红字格式是「分类：具体原因」，按分类对照：

| 红字开头 | 原因 | 怎么办 |
|---|---|---|
| 参数不合法：… | 某个字段不符合规则（`invalid`）。常见：「id 只能由小写字母、数字和连字符组成，以字母开头，长度 2–32」；「fixtures 目录不在允许的根目录之下（启动参数 --fixtures-root）」；「未配置回放数据包的白名单根目录（启动参数 --fixtures-root，或与 --fixtures 同级的目录），不能添加回放集群」；「fixtures 目录不存在或无法访问」；「配置了 mysqlHost 就需要 mysqlUser」；地址类的「…只允许 http / https 地址」「…不能带查询串或片段」「…不能包含空白、反斜杠或控制字符」；路径类的「mysqlBin 的文件名必须是 mysql / mariadb」「tiup 必须是绝对路径」 | 按冒号后的原因改对应字段（字段名与界面的对应关系见 [集群接入帮助](help:clusters) 的「错误提示对照」）；回放集群的数据包必须放在允许的根目录下，请联系部署人员确认 `--fixtures-root` |
| 集群 id 已存在：id / tiup 集群名与已有集群「xxx」冲突 | `exists`：你填的 id 或 tiup 集群名，与某个已有集群（含主集群）的 id 或 tiup 集群名撞了 | 换一个 id 或 tiup 集群名；在列表里看已有集群的 id（第二行灰字）。注意 id 不能等于另一个集群的 tiup 集群名 |
| 集群数量已达上限：最多接入 20 个集群（含主集群） | `limit`：已达 20 个 | 先移除不用的集群（见下文「删除集群被拒绝」） |
| 集群实例启动失败（连接信息可能有误，或集群暂时不可达）：… | `start`：新实例没能启动，平台已整体回滚，其他集群不受影响（更新时恢复旧配置）。常见：回放集群的数据包 manifest 读取失败；数据目录无法创建 | 看冒号后的具体原因处理；注意 live 集群**连不上不会**导致它启动失败（接入不校验连通性），那种情况请用「测试」排查 |
| 保存失败（注册表写入失败，请检查数据目录的权限与磁盘空间）：… | `store`：`clusters.json` 写盘失败，已回滚 | 请部署人员检查数据目录权限（属主应是平台运行账号）与磁盘空间 |
| 主集群的连接配置来自平台启动参数：只能修改显示名与描述，且不能删除：… | `primary`：对主集群改了环境 / 模式 / 地址等，或尝试删除主集群 | 只改显示名与描述；其余改启动参数并重启平台 |
| 集群不存在（可能已被删除）：没有这个集群 | `not_found`：编辑 / 测试 / 删除时集群已被别人删掉 | 点「刷新」看最新列表 |

#### 「测试」里某一项是失败或警告

**现象**：「集群接入」→ 点该行「测试」，抽屉里某项显示红色「失败」或橙色「警告」。

**原因与怎么办**：测试是只读的，用的是**已保存**的配置，从平台所在主机发起。

1. 先改配置再测试：改了地址或密码后要先点「保存」，再点「重新测试」。
2. 看「检查项」「详情」，对照 [集群接入帮助](help:clusters) 的「测试各项含义与失败怎么办」：PD / TiDB 状态端口 / Prometheus / Alertmanager 失败多是地址、端口或网络问题（在平台所在主机上用 `curl` 访问同一地址验证）；「TiDB SQL（SELECT 1）」失败看 mysql 报错（`Access denied` = 账号、口令或来源主机不对）；「tiup cluster display …」失败看 tiup 路径和 tiup 集群名。
3. 「警告」（如「未配置地址」）表示这项没配置，不是故障；不需要这个数据源时可以忽略，需要时到「编辑」里补上。
4. 全部通过后仍显示「不可达」：状态来自最近一次采集的缓存，等下一轮采集后再看。

#### 删除集群被拒绝（提示「该集群有执行中或待审批的变更…」）

**现象**：点「确认删除」后红字「该集群有执行中或待审批的变更，请先处理完再操作：该集群还有 N 项待审批 / 排队 / 执行中的变更或进行中的维护，请先处理完（取消 / 驳回 / 等待结束）再删除」。

**原因**（错误码 `in_use`）：该集群还有进行中的工作：待审批、排队中、已排期、执行中的变更，或进行中的主机维护（排空 / 维护中 / 恢复中）。直接删除会丢掉它们，所以平台拒绝。

**怎么办**

1. 在顶栏切换到**要删除的那个集群**。
2. 打开「节点管理 → 任务中心」，找出状态为「待审批」「排队中」「已排期」「执行中」的变更：待审批 / 排队 / 已排期的由申请人或 DBA 点「取消」，待审批的也可以由审批人「驳回」；执行中的等它结束，或对可中止的点「中止」（见 [节点管理帮助](help:nodes)）。
3. 在「节点管理 → 主机维护」里把进行中的维护结束（或按流程「紧急恢复」）。
4. 都处理完后，回到「平台配置 → 集群接入」重新删除。删除只是移除纳管，不会停止或删除 TiDB 集群。

#### 两个集群里出现了相同的变更编号（CHG-0001）

**现象**：在 A 集群和 B 集群都看到 `CHG-0001`，担心是重复提交或数据错乱。

**原因**：这是正常的：变更编号**按集群各自编号**，每个集群都从 `CHG-0001` 开始，会重复。它们是两条互不相干的变更。

**怎么办**：区分是哪个集群的变更时，不要只看编号：看变更详情里的集群 / 环境；在 [权限与审计](go:security) 的「审计日志」里用「集群」下拉筛选，或看「集群」列（tiup 集群名）；通知消息里看「集群：…」。向同事报告变更时请同时说「集群 + 编号」。

#### 在非主集群改配置（或做告警静默），结果却打到了主集群 / 另一个集群

**现象**：在 `stg` 集群提交的配置变更（SET CONFIG / SET GLOBAL）或告警静默，生效在了主集群 / 另一个集群上；或者「集群接入」列表里该集群有橙色警告「执行器预检未通过…」。

**原因**：`sudo` 执行器模式下，所有集群共用**一份**特权端策略文件（`--exec-policy`，默认 `/etc/tidb-ops/exec.json`）。其中顶层的 `mysqlHost` / `mysqlPort` / `alertURL` 是全局值，**没有 `perCluster` 项的集群一律沿用它们**。漏配时，非主集群的 SET CONFIG / SET GLOBAL 与告警静默会打到全局值所属的集群。平台读不到这份文件，**发现不了漏配，也不会有警告**。

**怎么办**（需要有中控机权限的人做）

1. **先停手**：对受影响的集群，请管理员关掉写操作开关（「权限与审计 → 写操作开关」→「立即关闭（熔断）」，一名管理员即可），防止继续误操作。
2. 核对已发生的影响：在 [权限与审计](go:security) 的审计日志里按「集群」筛选，看这期间的 `change.command`（命令内容）与 `alert.silence` 记录；到被误打的集群上用 `SHOW CONFIG WHERE name = '<配置名>'`（[SHOW CONFIG](https://docs.pingcap.com/zh/tidb/stable/sql-statement-show-config/)）核对配置值是否被改，在 Alertmanager 页面核对是否多了静默，并按需手工恢复。`<配置名>` 是你提交变更时改的那个配置项，例如 `raftstore.store-pool-size`。
3. 在中控机上编辑策略文件：把每个集群的 tiup 集群名加进 `clusters` 列表，在 `perCluster` 里为**每个集群（含主集群）**写 `mysqlHost`、`mysqlPort`、`alertURL`，并清空顶层的 `mysqlHost` / `alertURL`。完整示例见 [集群接入帮助](help:clusters) 第四节的警告框。
4. 修好后，先在**测试环境**的集群上做一次 SET GLOBAL 与告警静默，确认落到了正确的集群，再重新开启生产集群的写开关。
5. 如果「集群接入」里该集群有橙色「执行器预检未通过」警告：说明特权端策略文件没有允许该集群名，按警告里的提示把它加入 `clusters`；警告不会自动消失，修好后重启平台，或在「编辑」里改任一连接信息字段并保存（会重建实例并重新预检）。

#### 在回放集群里做变更，为什么没有真实效果

**现象**：切到某个集群提交变更，审批、执行都「成功」了，但真实集群没有任何变化。

**原因**：这个集群是**回放（replay）集群**：它读的是一份样例数据包，**恒用模拟执行器**，流程、审批、审计都真实走，但命令只是模拟输出，不会作用于任何真实集群。顶栏下拉里看不出模式，要看「权限与审计 → 写操作开关」页执行器一行的「模拟：不会对集群做变更」，或「集群接入」列表的「模式」列（「replay 回放」）。

**怎么办**：要对真实集群做变更，使用 live（实时）集群，并确认平台的执行器是 `direct` 或 `sudo`（不是 `sim`）。**注意**：如果整个平台进程的执行器是 `sim`（回放演示环境），即使你在里面接入了 live 集群，该集群也是只读的，提交变更会提示「未配置执行器，无法执行变更」——要真实变更，平台需用 `--exec direct` 或 `--exec sudo` 启动。

#### 集群状态「不可达」，或总览是空的

**现象**：「集群接入」列表里某个 live 集群的状态是「不可达」；切到它后总览没有实例、KPI 是「—」，顶部横幅写「N 项数据缺失」。

**原因**：平台连不上这个集群的组件。**接入时不校验连通性**，所以地址写错也能保存成功；连不上时页面**不报错**，而是数据为空（取不到的数据平台不猜测）。

**怎么办**：管理员在「集群接入」页点该集群的「测试」，按失败项排查（见上一条「测试里某一项是失败」）；改完保存后再「重新测试」，数据会在下一轮采集后出现。

#### 通知里的「查看」链接打开了错误的集群

**现象**：收到非主集群的通知，点「查看」打开平台，看到的不是这个集群的数据。

**原因**：非主集群的通知链接带有 `?cluster=<集群 id>`。登录后页面会读取它：如果这个集群对你可见，就切换到它并把参数从地址栏去掉；**如果你在这个集群的环境里没有角色（看不到它），参数会被忽略**，页面用你上次选择的或默认的集群。

**怎么办**：

1. 打开链接后看顶栏集群下拉和环境标签，确认是不是消息里「集群：…」对应的集群（消息里写的是 tiup 集群名，在 [集群接入](go:clusters) 的编辑抽屉里能对应到显示名；没有管理权限时请问管理员）。
2. 是别的集群、且下拉里根本没有目标集群：说明你的账号在它的环境里没有角色，请管理员在 [用户管理](go:users) 里为你补上该环境的角色。
3. 目标集群在下拉里：手工切换过去即可。

### 负载均衡（拓扑图的负载均衡层 / 手工登记）

背景：「集群架构」图的「负载均衡层」= 自动发现的 TiProxy（来自 `tiup cluster display`）+ 在 [环境与设置](go:settings)「负载均衡」卡片手工登记的 HAProxy / LVS / Nginx / 云 SLB / F5 等，**每个集群各自一份**。tiup 之外部署的负载均衡平台发现不了。完整说明见 [集群架构帮助](help:arch) 与 [环境与设置帮助](help:settings)。

#### 图上没有负载均衡框

**现象**：「集群架构」图里，「应用 / MySQL 客户端 / BI 工具」下面直接就是 TiDB 层，图下方有一条蓝色提示「未发现负载均衡：若集群前有 HAProxy / LVS / 云 SLB 等，请到「环境与设置 → 负载均衡」登记。」（只读 / 回放模式下的提示是「未发现 TiProxy。…」）。

**原因**：该集群没有自动发现的 TiProxy，也没有任何人登记过负载均衡。图上没框**不代表**集群前面真的没有负载均衡。（静态原型里则始终有一个写着「（示意）」的演示框，不代表真实。）

**怎么办**

1. 先确认集群前面到底有没有：看应用连接串的地址是 VIP / 域名，还是直接指向某台 TiDB 的 4000 端口；或问网络 / 应用同事。
2. 确认顶栏集群下拉选对了集群（登记按集群各存一份，A 集群的登记在 B 集群看不到）。
3. 确实有负载均衡：请管理员按 [环境与设置帮助](help:settings) 的「登记一条负载均衡」登记；你没有 settings.edit 见下面「非管理员想加登记」。
4. 提示是「平台设置里已勾选「集群前有负载均衡」，但还没有登记具体设备，图中无法画出…」：说明只勾了复选框，没登记具体设备，登记后才会出现。
5. 提示是「负载均衡信息读取失败：…」：读取接口出错，原因写在提示里（如没有权限需要「查看总览」能力、后端版本较旧、无法连接后端）；图的其余部分不受影响，修复后刷新页面。

#### 我有 HAProxy / LVS / 云 SLB，但图上没有

**原因**：这些负载均衡不在 `tiup cluster display` 里，平台无法自动发现；必须手工登记。登记之前图上不会有，缩容 / 维护 TiDB 也不会有「从负载均衡摘除」的人工确认步骤。

**怎么办**：请管理员登记（逐步操作见 [环境与设置帮助](help:settings)「登记一条负载均衡」：类型选 HAProxy / LVS 等，入口地址填客户端连接的 VIP / 域名 : 端口，后端按 IP 填，或点「从拓扑填入当前全部 TiDB」）。登记后进入「集群架构」，你会看到负载均衡层多了一个方框，副标题「手工登记 · 后端 N」。

#### 我部署了 TiProxy，图上没有 TiProxy

**可能原因**与处理：

1. **TiProxy 不是 tiup 部署的**（自己装的）：平台发现不了，按上一条手工登记，类型选「TiProxy（自部署）」。
2. **是 tiup 部署的，但没显示**：平台只认 `tiup cluster display` 里角色为 `tiproxy` 的行；官方文档没有给出这一行的输出样例，平台是按拓扑模板推断的，**以真实集群为准**。到中控机执行 `tiup cluster display <集群名>`（`<集群名>` 是顶栏当前集群对应的 tiup 集群名，见「集群架构」卡片标题「集群拓扑 · …」）看有没有 TiProxy 行、角色列叫什么；叫法不同的话请联系平台维护者。tiup 不可用、拓扑退化为从 PD 推导时也没有 TiProxy。
3. 不要为 tiup 部署的 TiProxy 再登记一条：平台不去重，图上会出现两次。

#### 图上显示「后端与拓扑不一致」

**现象**：某个手工登记的方框变黄，副标题「手工登记 · ⚠ 后端与拓扑不一致」；设置页「负载均衡」卡片有黄色提示。

**原因**：该登记的「后端 TiDB 列表」与拓扑里的 TiDB `IP:SQL 端口` 对不上：「拓扑里有但未登记的 TiDB」（常见于新扩容的 TiDB 没补进登记）；或「登记了但拓扑里没有的后端」（常见于 TiDB 已下线、写错端口、写成域名）。

**怎么办**

1. 点那个方框，在右侧抽屉里看哪些后端带 ⚠、哪些 TiDB 被列在「拓扑里有但未登记的 TiDB」。
2. 对照 HAProxy / LVS / 云 SLB 的**实际**后端，判断是登记过期，还是负载均衡本身漏配。
3. 登记过期：管理员到 [环境与设置](go:settings)「负载均衡」卡片，点该行「编辑」，改「后端 TiDB 列表」，点「保存」。负载均衡漏配：自己在负载均衡上补，平台不会替你改。
4. **域名陷阱**：后端登记成 `tidb-1.example.com:4000`，而拓扑里是 `10.0.1.11:4000`，这一台会同时出现在两边——平台不解析域名，请按 IP 登记。
5. 这个负载均衡只服务一部分 TiDB、你不想要警示：把该登记的「后端 TiDB 列表」留空（留空 = 不做一致性检查）。
6. 后面接的是 TiProxy 而不是直接接 TiDB：同样留空后端列表，否则会一直显示不一致。
7. 改完仍显示不一致：对照的是缓存的拓扑快照，点页面顶部横幅「立即刷新」，或稍等下一次快照。

#### 登记保存失败

在「登记负载均衡 / 编辑负载均衡」抽屉底部会有红色提示，抽屉不关，输入还在。按提示对照：

#### 缩容 TiDB 时多了一个「需人工确认」的摘除步骤

**原因**：平台认为集群前有负载均衡——「环境与设置」里勾选了「集群前有负载均衡」，或登记了至少一条负载均衡。这是预期行为：下线 TiDB 前要先让负载均衡停止给它派连接。

**怎么办**：这是个 ⏸ 步骤，平台不会替你操作。照 [节点管理帮助](help:nodes)「从负载均衡摘除 / 加回 TiDB 的人工确认步骤」做：到说明里点名的负载均衡上把该 TiDB 摘掉，等连接排空，再点「我已完成，继续」。点了之后平台立即执行下线，**不会检查你是否真的摘了**。12 小时没人确认变更失败。若你其实没有负载均衡：到「环境与设置」取消勾选并删除登记，**重新提交**变更（已提交的不变）。反过来，缩容 TiDB 时**没有**这个步骤、但你确有负载均衡：说明没勾选也没登记（自动发现的 TiProxy 不算），先登记或勾选再提交。

#### TiProxy 在实例列表里找不到

**原因**：自动发现的 TiProxy 单独存放，**不在**「节点管理」的实例列表、[集群总览](go:overview) 的实例健康矩阵和实例计数里；平台也不支持对 TiProxy 做扩缩容、重启等操作。

**怎么办**：看 TiProxy，去「集群架构」图的负载均衡层（点小条看详情），或「环境与设置」的「自动发现的 TiProxy」表。需要运维 TiProxy 本身，请在中控机上按官方文档用 tiup 操作（[TiProxy 简介](https://docs.pingcap.com/zh/tidb/stable/tiproxy-overview/)）。

#### 非管理员想加登记

**现象**：「环境与设置」里「＋ 登记负载均衡」「编辑」「删除」是灰的，悬停提示「需要「修改平台设置」（settings.edit）能力」，卡片里还有黄色提示「你没有「修改平台设置」（settings.edit）权限，负载均衡登记为只读…」。

**原因**：登记、编辑、删除要 settings.edit，这项能力只授予内置「管理员」角色，自定义角色也不能被授予（所以无法通过「角色权限」给你开）。你能做的是**查看**：所有登录用户都能看卡片、图与详情。

**怎么办**：把下面信息发给管理员，请他登记：负载均衡类型、名称、客户端连接的入口地址（VIP / 域名 : 端口）、它后面每台 TiDB 的 `IP:4000`（可选）、备注。**不要**把口令或带凭据的连接串发出去。管理员登记不需要打开写操作开关，也不走审批，登记后你刷新「集群架构」即可看到。

## 执行后果与风险

> ⚠️ 本页列出的「怎么办」多数是**恢复总闸或重新提交**。重新提交 = 再次对集群执行一遍计划，请先确认上一次失败留下的状态（evict-leader 调度、Offline 的 Store、停掉的实例）已核对清楚，避免叠加操作。

> ⚠️ 想解除 READONLY 熔断、关闭 / 开启写开关前，请先确认当时为什么触发；这些是线上的紧急止血手段，不要为了让提交通过而随手关闭。

> ⚠️ 「取消」「驳回」不可恢复；「中止」会触发尽力恢复命令，但不保证完全还原。

## 常见问题与注意

### 回放 / 模拟执行 / 真实执行 的区别

这三个概念经常被混淆：**回放**说的是「数据从哪来」，**模拟执行 / 真实执行**说的是「命令怎么跑」，二者独立。

| 对比项 | 回放（replay） | 模拟执行（sim 执行器） | 真实执行（direct / sudo 执行器） |
|---|---|---|---|
| 解决什么 | 数据来源：用一份样例数据包（fixtures）驱动所有页面，不连接任何集群 | 命令执行：校验命令后不启动任何进程，按命令类型生成逼真输出 | 命令执行：真实调用 tiup / pd-ctl / mysql / br |
| 启动参数 | `--fixtures <目录>` | `--exec sim`（回放模式下启用运维模式时默认） | `--exec direct` 或 `--exec sudo`（推荐 sudo） |
| 对集群有影响吗 | 没有，不连集群 | 没有 | **有，真实变更** |
| 数据会变吗 | 固定不变，页面显示采集时间 | 执行「成功」后集群数据不会真的变化，页面里的拓扑 / 指标不会跟着变 | 随集群真实变化 |
| 变更流程（审批、定时、审计、窗口、冻结期、串行） | 不涉及（无写操作） | **完全一样地走**，可以完整演练 | 完全一样 |
| 时间 | 无 | 等待类步骤被压缩到约 2%，每条命令约 1.5 秒（`--sim-delay`），几分钟的变更几秒就「完成」 | 按真实耗时，如缩容可等到 48 小时 |
| 怎么识别 | 页面横幅「回放数据」 | 「写操作开关」页执行器一行带「模拟：不会对集群做变更」；部署自检「特权分离」提示「模拟执行器」 | 执行器显示 `sudo` / `direct` |
| 适用场景 | 演示、培训、开发 | 演练流程、验证权限与审批配置 | 生产与联调 |
| 真实性 | 样例数据 | 命令输出是平台生成的，**不能代表真实 tiup 行为** | 以真实集群联调为准（至今未做过） |

> ⚠️ 看到「变更成功」不等于集群真的变了：先看执行器是不是 `sim`。生产环境用模拟执行器会被部署自检标红（「生产环境使用真实执行器」）。

还有三种容易搞混的组合：

| 组合 | 启动方式 | 说明 |
|---|---|---|
| 只读回放 | `--fixtures`，无 `--data-dir` | 无登录，仅查看，页面里的写操作是前端原型模拟 |
| 只读直连 | 无 `--fixtures`、无 `--data-dir` | 无登录，仅查看真实数据，不做任何写入 |
| 运维演示 | `--fixtures` + `--data-dir`（+ `--dev-seed` 创建演示账号） | 登录、审批、审计全真实，执行器默认 `sim`；演示账号口令统一为 `Tidbops-Demo-1`，仅限演示 |

### 其他提示

- 页面升级后样式 / 脚本不对：静态页面带 `Cache-Control: no-cache`，浏览器会向服务端校验；仍不对时强制刷新（Ctrl + F5）。
- 审批 / 提案 / 写开关等「双人」操作，两个人需要用**不同的账号**，且都是管理员（或对应能力）；同一个人换浏览器也不行。
- 提交生产高风险变更和绑定 MFA 用的动态验证码依赖手机时间，时间偏差大会一直失败（登录不受影响）；服务器时间同样重要（审计时间、窗口规则、冻结期都按服务器本地时区）。
- 想知道某个动作有没有被记录：到 [权限与审计](go:security) →「审计日志」，按变更号或用户检索；被拒绝的请求也会留痕。

## 已知限制与易混淆点

集中列出「界面写的是 A、实际是 B」的地方，遇到时不必怀疑自己操作错了。

| 界面写的是 | 实际是 | 怎么办 |
|---|---|---|
| 登录页「忘记口令？」展开说明里管理员用命令行重设口令 | 命令行直接改用户库，运行中的服务不会重新读取，必须在服务停止时执行（或执行后重启）；命令行不写审计、不吊销会话 | 见上文「忘记口令（含管理员自己）」 |
| 登录页「演示环境」说统一口令见下方，但选 `admin` 时口令框是空的 | 系统建演示账号时 `admin` 口令与其他账号相同，但页面对 `admin` 不自动填，因为它可能被改过 | 向演示环境搭建者确认 |
| 用户管理里的「解锁」按钮 | 只清除「用户名」维度的失败计数，IP 维度不清，同一 IP 连续失败 5 次仍被限制最多 10 分钟 | 见「账号被锁定 / 解锁后仍登录不了」 |
| 锁定提示有两种写法：「请在 HH:MM:SS 后重试」（登录页）和「请在 HH:MM:SS 之后重试」（绑定 MFA 时） | 都是同一类锁定，只是措辞不同；绑定 MFA 的锁定只针对「动态码确认」，登录锁定针对用户名 / IP | 按提示里的时间等待，或让管理员「解锁」 |
| 「用户名或口令错误」 | 用户名不存在、口令错或账号被禁用三种情况都显示这一句，与 MFA 无关（登录不看动态验证码） | 先核对用户名与口令，再查账号状态 |
| 用户管理页对读取被拒时写着「审计员账号拿不到列表」 | 这是旧文案：现在后端允许有 `audit.view` 的账号只读获取用户与角色列表；只有两个能力都没有才会被拒（提示「没有权限：users.manage 或 audit.view」） | 以实际结果为准 |
| 取消 / 中止 / 确认人工步骤写作「申请人或 DBA」 | 认的是申请人本人或**内置** DBA 角色，不看能力，自定义角色不行 | 见「自定义角色的人，为什么取消 / 中止不了别人的变更」 |
| 部署自检「至少两名管理员」 | 只统计内置「管理员」角色；自定义角色的成员不计入 | 保证有两个内置管理员账号 |
| 用户表单里「部门」输入框 | 输入框允许 60 个字，后端只接受 40 个，超过会提示「部门不能超过 40 个字」 | 控制在 40 字内 |
| 审计日志里 `user.roles` 的摘要「角色改为 map[*:[viewer]]」 | 这是平台原样记录的格式：`*` 表示所有环境，方括号里是角色 ID | 对照 [角色权限](go:roles) 的角色 ID 阅读 |
| 审计日志「角色」列 | 显示角色 ID（`dba`、自定义角色的 ID），不是中文名 | 同上 |
| 修改自定义角色的权限 | 不会让成员掉线（即时生效）；而改用户的角色、禁用、重置口令、删除才会吊销该用户的会话 | 不必让成员重新登录 |
| 顶栏集群下拉只是个选择框 | 运维模式下选择会整页刷新，并把你的环境、角色、能力、写开关状态和全部数据换成新集群的；看不到的集群与不存在的集群表现一致（404） | 见上文「集群相关」与 [集群接入帮助](help:clusters) |
| 变更编号 `CHG-0001` 全平台唯一；「排队中」是全平台串行 | 变更编号各集群各自编号、会重复；串行只在同一集群内，不同集群的变更并行执行 | 区分集群看变更详情或审计日志的「集群」列 |
| 在回放集群 / `sim` 执行器的平台里接入的 live 集群能做变更 | 平台执行器是 `sim` 时，live 集群不配执行器（只读），提交变更提示「未配置执行器，无法执行变更」；回放集群恒用模拟执行器 | 要真实变更需 `--exec direct` / `sudo` 启动，并接入 live 集群 |
| 多个集群共用 sudo 策略文件时，非主集群的 SET CONFIG / 告警静默会自动用自己的地址 | 只有在策略文件 `perCluster` 里为该集群配置了 `mysqlHost` / `mysqlPort` / `alertURL` 才会；漏配的集群沿用全局值，可能打到主集群，且平台无法发现 | 按「集群相关」里的步骤配置并在测试环境验证 |
| 「集群架构」图上的「负载均衡 · TiProxy / HAProxy / LVS（示意）」 | 只有静态原型才是固定演示框；有后端时负载均衡层是真实数据（自动发现的 TiProxy + 手工登记），没有可画的内容就不画 | 见上文「负载均衡」小节；HAProxy / LVS / 云 SLB 必须手工登记才会显示 |
| 通知里非主集群的「查看」链接会打开那个集群 | 链接带 `?cluster=<id>`；页面登录后读取它，但只有该集群对你可见时才切换，否则静默忽略（不提示） | 点开后看顶栏集群与环境标签；不是目标集群就联系管理员补权限 |
