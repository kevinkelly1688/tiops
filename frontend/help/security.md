# 权限与审计

> 💡 配置审批策略、处理双人复核提案、控制写操作开关、查询并校验审计日志、做部署自检、管理自己的账号（改口令 / 绑定 MFA）的页面。**运维模式**下登录即可打开，各标签页按你的权限显示；**只读 / 回放模式**（无 `--data-dir`、无登录）下这个页面只是静态规格演示，所有数据都是模拟的，没有任何真实的用户、审计或开关。用户的创建与维护在 [用户管理](help:users)，角色与权限矩阵在 [角色权限](help:roles)，两者都在侧栏的「平台配置」分组里。

> ⚠️ 本页功能至今只在回放数据 + 模拟执行器下测试过，未在真实集群上联调。涉及真实文件权限、反向代理、sudo 入口等部署细节的行为，以真实环境联调为准。

## 这个页面做什么

运维模式下页面顶部有 7 个标签页（从左到右；页面默认打开「审批策略」，不是最左边的「待确认提案」）：

| 标签页 | 内容 | 谁能看到 | 是否真实数据 |
|---|---|---|---|
| 待确认提案 | 「授予管理员」「修改审批策略」两类双人复核提案 | 登录即可：拥有「用户与角色管理」或「修改平台设置」能力的账号（默认只有管理员）看全部，其他人只看自己发起的 | 运维模式真实 |
| 审批策略 | 风险 × 环境 → 审批级数与是否要求申请人 MFA | 登录即可查看；`settings.edit` 才能修改 | 运维模式真实 |
| 审计日志 | 真实审计记录、哈希链校验、导出 | `audit.view`（默认：审批人 / 管理员 / 审计员）；没有该能力时标签页不出现 | 运维模式真实 |
| 命令白名单 | 执行器白名单的示意与校验器 | 登录即可 | 静态示意，**真实白名单在执行器里，种类更多，以执行器为准** |
| 写操作开关 | **当前所选集群**的写开关状态、双人确认、熔断（每个集群各自一个） | 登录即可查看；`writeswitch` 才能操作 | 运维模式真实 |
| 部署自检 | 平台自身的部署安全基线检查（按当前所选集群，范围见下文「部署自检」） | 登录即可 | 运维模式真实 |
| 我的账号 | 自己的角色与能力、改口令、绑定 MFA | 登录即可 | 运维模式真实 |

> 💡 **多集群**：平台可以同时纳管多个集群（见 [集群接入帮助](help:clusters)）。本页里**全局**的内容（所有集群共用）：审批策略、待确认提案（授予管理员、修改审批策略）、审计日志、我的账号、会话；**按集群**的内容（跟着顶栏当前集群走）：写操作开关（含两名管理员确认）和部署自检。操作前先看顶栏集群下拉。

> 💡 以前放在本页的「用户管理」「权限矩阵」「权限模拟器」三个标签页已经迁走：前者到了 [用户管理](go:users)（帮助见 [用户管理](help:users)），后两者到了 [角色权限](go:roles)（帮助见 [角色权限](help:roles)）。侧栏「平台配置」分组只对拥有 `users.manage` 或 `audit.view` 的账号显示。只读 / 回放模式下本页仍显示旧版的静态标签页（含权限矩阵与权限模拟器），那只是规格演示。

### 本平台账号与 TiDB 自身的权限是两套东西

本页以及 [用户管理](help:users)、[角色权限](help:roles) 管的是**登录本平台的账号**（用户名、口令、角色、MFA），数据保存在平台数据目录的 `users.json` / `roles.json` 里。它们**不是** TiDB 数据库里的 SQL 用户与角色：

| 对比项 | 本平台账号 / 角色 | TiDB 的用户与角色（SQL 层 RBAC） |
|---|---|---|
| 管什么 | 谁能在平台上看数据、提交 / 审批变更、改设置、查审计 | 谁能用 SQL 连接数据库、访问哪些库表（`GRANT` / `REVOKE` / `CREATE ROLE`） |
| 在哪里管 | 平台「用户管理」「角色权限」 | 用 MySQL 客户端连 TiDB 执行 SQL |
| 互相影响吗 | 创建平台账号**不会**在 TiDB 里创建用户；给「开发」角色配置的「授权库」也**不会**给 TiDB 授权，只决定该账号能在平台里看到哪些库的慢 SQL | 平台读取集群数据时用的是启动参数配置的只读 SQL 账号（`--mysql-user`），与登录平台的人无关 |

TiDB 自身的权限体系请看官方文档（以你集群的版本为准）：[基于角色的访问控制](https://docs.pingcap.com/zh/tidb/stable/role-based-access-control)、[权限管理](https://docs.pingcap.com/zh/tidb/stable/privilege-management)。

## 怎么用（按步骤）

### 一、新环境的第一次初始化

**前置条件**：平台以运维模式部署完成（带 `--data-dir`），你能登录中控机，也能打开平台地址。下面的命令按平台安装脚本的默认值书写：运行账号 `tidbops`、程序 `/opt/tidbops/bin/tidbops-server`、数据目录 `/var/lib/tidbops`、systemd 服务名 `tidbops`；你们的部署不同时，请替换成实际值（数据目录就是平台启动参数 `--data-dir` 的值）。

1. 取初始口令：首次启动时服务日志会打印一行「首次启动：已创建管理员 admin，初始口令 …（只显示这一次…）」。按安装脚本部署时可在中控机执行 `journalctl -u tidbops` 查看。你会看到一串随机口令。**这是唯一一次显示**，错过了只能用下面「二、命令行」里的办法重设。
2. 打开平台地址，用 `admin` 和该口令登录（登录页的逐步说明见 [快速入门](help:quickstart) 的「怎么登录」）。预期结果：登录页消失，顶栏出现环境标签、「只读」标签、「平台管理员 · 管理员」和「退出」。
3. 进入本页「我的账号」标签页，在「修改口令」里填「当前口令」「新口令」「确认新口令」，点「修改口令」。预期结果：屏幕底部短暂提示「口令已修改」，三个输入框被清空。
4. 仍在「我的账号」，在「多因素认证（TOTP）」卡片点「开始绑定」，按下文「绑定 MFA 的步骤」完成。预期结果：卡片变成绿色提示「已绑定动态验证码…」。登录本身只需要用户名 + 口令；此后提交生产高风险变更（默认策略）时才要输入动态验证码。
5. 创建第二名管理员。写操作开关默认关闭，开启需要**两名不同的管理员**；而「授予管理员角色」本身也需要另一名管理员确认，所以此时只有一名管理员的平台无法在页面上创建第二名管理员，必须在中控机上用命令行创建：

```
sudo -u tidbops env TIDBOPS_USER_PASSWORD='<满足口令策略的初始口令>' /opt/tidbops/bin/tidbops-server user add --data-dir /var/lib/tidbops --name admin2 --display "管理员2" --role admin --env '*'
```

   占位符说明：`<满足口令策略的初始口令>` 由你自己定，至少 10 位、至少含大写 / 小写 / 数字 / 符号中的 3 类、不得包含用户名，例如 `Ab3!example-Pass`（仅示例，请勿照抄）；`--name` 是新管理员的登录名（2 到 64 位，小写字母、数字及 `.` `_` `@` `-`）；`--env '*'` 表示该角色适用于所有环境。预期结果：命令输出「完成」。
6. 让命令行创建的账号对运行中的服务生效。运行中的服务把用户库读进内存，不会重新读取文件，之后每次保存还会按内存状态覆盖文件，所以**命令行的改动要重启服务后才对运行中的实例生效**（按代码推断，具体行为以真实环境联调为准）。最稳妥的做法是在服务停止时执行第 5 步：`sudo systemctl stop tidbops`，执行命令，再 `sudo systemctl start tidbops`。重启会让所有人重新登录。
7. 用 `admin2` 登录，同样改口令并绑定 MFA。然后回到「管理员」账号，打开 [用户管理](go:users) 检查两名管理员都显示「正常」。
8. 其余账号（DBA、SRE、审批人、审计员等）由管理员在 [用户管理](go:users) 里创建，创建步骤见 [用户管理](help:users)。
9. 打开本页「部署自检」，逐项处理红色 / 黄色项（见下文「部署自检」）。
10. 由两名管理员按「写操作开关」一节开启写开关。**开启后，有权限的账号提交并经审批的变更才会真实作用于集群**（执行器为 `direct` / `sudo` 时）。

> ⚠️ 命令行 `tidbops-server user …` 直接读写 `users.json`，**不会写审计日志、也不会吊销任何会话**。请在服务停止时执行，或执行后重启服务并回到 [用户管理](go:users) 核对。

### 二、命令行：忘记管理员口令或丢失 MFA

只有拿到中控机命令行权限的人才能做。平台登录页点「忘记口令？」展开的说明与这里一致，**但登录页没有提到需要重启服务**，请按下面做。

**前置条件**：你能在中控机上以平台运行账号（安装脚本默认 `tidbops`）执行命令；知道平台的数据目录；新口令满足口令策略。

1. 如果还有另一名管理员能登录，优先让他在 [用户管理](go:users) 里对你「重置口令」（或「重置 TOTP」），不需要碰命令行。注意：「重置口令」「禁用」「删除」对**自己的账号**是置灰的，所以管理员不能给自己重置口令；你自己的口令请在「我的账号」里改。
2. 否则，停止平台服务：`sudo systemctl stop tidbops`。预期结果：平台地址打不开。
3. 重设口令（把 `admin` 换成要重设的用户名）：

```
sudo -u tidbops env TIDBOPS_USER_PASSWORD='<新口令>' /opt/tidbops/bin/tidbops-server user passwd --data-dir /var/lib/tidbops --name admin
```

   `<新口令>` 同样要满足口令策略，示例 `Ab3!example-Pass`（请勿照抄）。口令通过环境变量传入，不会出现在命令行参数里，但**会留在 shell 历史里**；介意的话先执行 `read -rs TIDBOPS_USER_PASSWORD; export TIDBOPS_USER_PASSWORD` 交互输入，再执行不带 `env …` 前缀的命令，最后 `unset TIDBOPS_USER_PASSWORD`。预期结果：输出「完成」；口令不符合策略时输出「失败: 口令至少 10 位」之类的原因。
4. 如果还丢了 MFA，把子命令换成 `totp-reset` 清除绑定（不需要口令环境变量）：

```
sudo -u tidbops /opt/tidbops/bin/tidbops-server user totp-reset --data-dir /var/lib/tidbops --name admin
```

5. 启动服务：`sudo systemctl start tidbops`，用新口令登录。预期结果：登录成功；若该账号之前绑定过 MFA 且你重置了它，登录不受影响（登录本来就只认用户名 + 口令），但在重新绑定之前无法提交生产高风险变更，请登录后到「我的账号」重新绑定。

**后果**：命令行重设口令不写审计、不吊销会话；账号若被锁定（连续输错口令），锁定计数在重启服务后清零。

### 三、日常操作

1. 新增账号、调整角色、重置口令 / MFA、解锁：到 [用户管理](go:users)。
2. 新增或修改自定义角色：到 [角色权限](go:roles)。
3. 给人加管理员角色：在 [用户管理](go:users) 里提交后，由另一名管理员到本页「待确认提案」确认（见下文「处理一条提案」）。
4. 临时关闭写操作：「写操作开关 → 立即关闭（熔断）」，一名管理员即可。
5. 事后追查：「审计日志」按用户 / 动作 / 结果 / 时间过滤，必要时点「校验哈希链」。

## 区域与参数说明

### 待确认提案（双人复核）

**两类操作必须由两名不同的管理员先后确认**：

| 提案种类 | 触发方式 | 确认后的后果 |
|---|---|---|
| 授予管理员（`grant-admin`） | 在 [用户管理](go:users) 创建带管理员角色的用户，或给已有用户新增管理员角色（任一环境） | 该用户立即获得完整角色集合，**其现有会话被吊销，需重新登录** |
| 修改审批策略（`approval-policy`） | 「审批策略」标签页提交修改 / 恢复默认 | 新策略立即生效，影响此后提交的所有变更的审批级数与 MFA 要求 |

规则：

- 发起人**不能确认自己的提案**（提示「需要另一名管理员确认：发起人不能确认自己的提案」）。
- 提案有效期 **1 小时**（页面写作「60 分钟内未确认自动作废」），超时自动作废（状态「已过期」）；同一对象（同一用户 / 审批策略）的新提案会取代旧的（旧的状态变「已撤回」，备注「被 xxx 发起的新提案取代」）。
- 提案内容里**不含口令**。授予管理员的提案记录了发起时用户的角色；若确认时该用户的角色已被改动，提案会被标记为已拒绝并提示「请基于最新角色重新发起」，用户已被删除同理。
- 确认审批策略提案时会**再次校验硬性下限**。
- 有提案等你确认时，侧栏「权限与审计」出现数字角标，页面顶部出现黄色横幅（「有 N 条提案等待你确认」，点「去处理」）。
- 历史区显示最近 20 条已处理提案（状态：已生效 / 已拒绝 / 已撤回 / 已过期）。

#### 处理一条提案（以「授予管理员」为例）

**前置条件**：你是另一名管理员（不是发起人），拥有对应能力（授予管理员需 `users.manage`，修改审批策略需 `settings.edit`）。

1. 用你自己的账号登录。你会看到侧栏「权限与审计」旁的数字角标，打开本页后顶部有黄色横幅「有 N 条提案等待你确认」。
2. 点横幅上的「去处理」，或点标签页「待确认提案」。你会看到提案卡片：种类标签、摘要（例如「授予用户 alice 管理员角色（环境：*）」）、发起人、发起时间、剩余有效时间；「授予管理员」卡片还有「环境 / 当前角色 / 确认后的角色」对比表，新增管理员的行高亮并标「新增管理员」。
3. 逐项核对：是不是你预期的用户、环境？有没有对应的工单？不确定就先别点，联系发起人。
4. 同意：点「确认并生效」，在弹窗里再核对一遍，点「确认并生效」。预期结果：提示「提案 PRP-0001 已确认并生效」，卡片消失，历史区出现一行状态「已生效」。
5. 不同意：点「拒绝」，在右侧抽屉里填「拒绝原因」（选填，最多 200 字，会显示在历史里），点「确认拒绝」。提案作废，发起人可重新发起。
6. 如果你是发起人想收回：点「撤回」，在弹窗里点「确认撤回」。

| 按钮 | 谁能点 | 点击后发生什么 | 可撤销吗 | 审计怎么记 |
|---|---|---|---|---|
| 确认并生效 | 另一名管理员（授予管理员需 `users.manage`，审批策略需 `settings.edit`） | 弹窗核对内容后，提案立即应用；应用失败（如用户角色已变化）则提案作废并说明原因 | 已生效的不可撤销，只能再发起新提案反向修改 | `proposal.confirm`（成功 / 失败）；授予管理员另有一条 `user.roles`（摘要含发起人） |
| 撤回 | 发起人（本人的提案） | 弹窗确认后提案作废，不生效 | 不可恢复，需要时重新发起 | `proposal.cancel`（摘要「发起人撤回」） |
| 拒绝 | 另一名管理员 | 弹出抽屉，可填原因（选填），确认后提案作废 | 发起人可重新发起 | `proposal.reject` |
| （自动）过期 | 系统 | 超过 1 小时无人确认，状态变「已过期」 | — | `proposal.expire`（用户=system） |

提案记录保存在数据目录的 `proposals.json`（最多保留约 200 条，待确认的不会被清理）。

> ⚠️ 「开启写操作开关」的双人确认**不走**提案框架，在「写操作开关」标签页单独处理（见下），并且**每个集群各自一份**；而本节的「授予管理员」「修改审批策略」提案是**全局**的，不属于某个集群，在任何集群下看到的待确认提案都是同一批。

### 审批策略

表格是「风险 × 环境」3×3 格，每格两个设置：

| 字段 / 选项 | 含义 | 可选值 / 默认 | 影响 |
|---|---|---|---|
| 审批级数 | 该风险 × 环境的变更需要几个**不同的人**依次批准 | 0–3；默认：低风险全 0；中风险 测试 0 / 预发 1 / 生产 1；高风险 测试 1 / 预发 2 / 生产 2 | 0 = 免审批（仍留痕）；级数越高，变更越慢 |
| 申请人 MFA | 提交该格的变更时，申请人是否必须输入自己的动态验证码 | 勾选 / 不勾选；默认只有「生产 · 高风险」勾选 | 勾选后，没绑定 MFA 的人提交会被拒绝并提示先绑定 |
| 紧急变更（固定行） | 冻结期 / 禁止窗口内强行执行 | 不可配置：预发 / 生产至少 2 级；测试无紧急通道，按常规 | 紧急变更提交后要求事后复盘 |

**硬性下限**（写死在代码里，不能通过配置放宽，提交时与确认时都会再校验）：

| 硬性下限 | 违反时的提示 |
|---|---|
| 生产环境的高风险变更：至少 2 级审批，且必须要求申请人 MFA | 「生产环境的高风险变更至少需要 2 级审批（硬性下限）」「…必须要求申请人 MFA（硬性下限）」 |
| 生产环境的中风险变更：至少 1 级审批 | 「生产环境的中风险变更至少需要 1 级审批（硬性下限）」 |
| 预发环境的高风险变更：至少 2 级审批 | 「预发环境的高风险变更至少需要 2 级审批（硬性下限）」 |

低风险在任何环境都允许 0 级。编辑时违反下限的格子会标红并写出原因；是否通过以后端校验为准。

> 💡 审批策略是**全平台一份**，不是每个集群一份：一个变更按**它所在集群的环境**取对应的列（例如预发集群用「预发」那一列，生产集群用「生产」那一列）。想让某个集群更严格，就把它的环境设成「生产」。修改策略的提案对所有集群生效。授权按主集群的环境判断（需要在主集群的环境里有 `settings.edit`）。

#### 修改审批策略

**前置条件**：你有 `settings.edit`（管理员）；有另一名管理员可以确认；你清楚改动的影响（见下方后果）。

1. 打开「审批策略」标签页，点「修改」。预期结果：每个格子出现级数下拉框和「申请人 MFA」勾选框，下方提示「编辑中…提交后不会立即生效，而是成为提案」。
2. 调整需要的格子。违反硬性下限的格子会变红并显示原因；底部状态行显示「有 N 个格子违反硬性下限…」或「满足硬性下限，可以提交」。
3. 点「提交修改提案」。预期结果：提示「已提交，需要另一名管理员确认」，页面跳到「待确认提案」，顶部提示「审批策略修改已提交为提案 PRP-xxxx…」。若与当前生效策略完全相同，会提示「与当前生效的审批策略相同，无需修改」。
4. 通知另一名管理员按「处理一条提案」确认。确认后新策略立即生效。

**后果**：下调审批级数会让此后的变更更少人把关（硬性下限之外都允许）；生效后立即作用于所有**新提交**的变更，已提交的变更沿用创建时确定的级数。

按钮：

| 按钮 | 谁能点 | 点击后发生什么 | 可撤销吗 | 审计怎么记 |
|---|---|---|---|---|
| 刷新 | 登录即可 | 重新读取生效策略与待确认提案 | — | 不记 |
| 修改 | `settings.edit`（管理员） | 进入编辑模式：每格出现级数下拉与「申请人 MFA」勾选 | 点「取消」放弃 | 不记 |
| 提交修改提案 | `settings.edit` | 校验通过后**不会立即生效**，生成一条「修改审批策略」提案（HTTP 202），等另一名管理员确认 | 发起人可撤回提案 | `proposal.create`；校验不通过记 `policy.propose`（拒绝） |
| 恢复默认 | `settings.edit`（当前已是默认时置灰） | 弹窗确认后以「默认策略」同样生成提案，需另一名管理员确认 | 同上 | 同上 |

注意：

- 同一时间只保留一条待确认的策略提案：再发起新的会把旧的标记为「已撤回（被新提案取代）」。
- 编辑期间如果生效策略被别人改了，页面会提示「生效中的审批策略在你编辑期间已变化」，建议取消后重新编辑，否则提案会整体覆盖当前策略。
- 若启动时带了 `--no-mfa`（仅测试 / POC），页面会提示「申请人 MFA」暂不生效。
- 落盘的策略如果启动时校验不通过，平台会退回默认策略并写一条审计 `policy.load`（系统，失败）。

### 写操作开关

页面展示**当前所选集群**的写开关状态，卡片标题写着「写操作开关　集群 显示名 · test 环境」（环境是该集群的环境）。**写开关是每个集群各自一个**：在生产集群开启，不影响预发集群；新接入的集群默认关闭；两名管理员的确认也是针对某一个集群的。只有 READONLY 熔断文件是全局的（存在即所有集群强制只读）。**操作前先在顶栏切换到目标集群，并核对卡片标题里的集群名与环境。**

| 行 | 含义 |
|---|---|
| 开关 | 已开启 / 已关闭（默认关闭） |
| 当前不能写的原因 | 如「写操作开关未开启…」「平台处于强制只读（存在 …）」「未配置执行器，无法执行变更」「集群版本 … 不在平台支持范围内」；为空表示可以提交变更 |
| READONLY 熔断 | 中控机上的 `/etc/tidb-ops/READONLY`（可由 `--readonly-file` 改）存在时显示「文件存在：强制只读」，与开关无关 |
| 待确认提议 | 谁在何时提议开启，超过 1 小时显示「已超时（1 小时）」 |
| 执行器 | `sim` / `direct` / `sudo` / `none`；`sim` 带「模拟：不会对集群做变更」 |

#### 开启写操作开关（两名管理员）

**前置条件**：两名**不同的**管理员账号（都拥有 `writeswitch`）；已在「部署自检」处理完红色项；你们确认当前执行器是你们想要的（`sim` 不会真的改集群，`direct` / `sudo` 会）；**两人都切换到了同一个目标集群**（顶栏下拉；提议与确认必须针对同一个集群，在 A 集群提议、在 B 集群确认是不会生效的）。

1. 管理员 A 在顶栏选好目标集群，打开「写操作开关」标签页，核对标题里的集群与环境，点「提议开启写操作」。预期结果：提示「已提议开启，等待另一名管理员确认」；「待确认提议」一行出现「A 于 … 提议开启」，页面提示「你已提议开启，需要另一名管理员登录后确认」。此时写操作**仍未开启**。
2. 管理员 B 在 1 小时内登录，**切换到同一个集群**，打开同一标签页，点「确认开启写操作」。预期结果：提示「写操作已开启」，右上角状态由「只读」变为「写操作已开启」（若还有别的总闸未满足，仍显示「只读」，悬停可见原因）。

按钮（按开关状态显示不同按钮；没有 `writeswitch` 能力的账号全部置灰，只能看）：

| 按钮 | 何时出现 | 点击后发生什么 | 可撤销吗 | 审计怎么记 |
|---|---|---|---|---|
| 提议开启写操作 | 开关关闭且没有待确认提议 | 登记一条「开启」提议（发起人=你，1 小时有效），**此时写操作仍未开启** | 点「撤销提议」 | `writeswitch.propose`（风险=高） |
| 确认开启写操作 | 有别人发起的、未超时的提议 | **另一名**管理员点击后，写操作立即开启 | 可随时「立即关闭」 | `writeswitch.on`（摘要「两名管理员确认，开启写操作」） |
| 重新提议开启 | 提议已超时 | 用你的名义重新发起提议 | 同上 | `writeswitch.propose`（摘要「上一个提议已超时，重新提议」） |
| 撤销提议 | 有待确认提议（任一管理员都可点，包括发起人） | 清除提议 | — | `writeswitch.cancel` |
| 立即关闭（熔断） | 开关已开启 | 确认后**一名管理员即可**立即关闭，并清除未决提议 | 需再次两名管理员确认才能重新开启 | `writeswitch.off`（风险=高） |

> ⚠️ 关闭开关后，**该集群**的所有变更提交与告警静默都会被拒绝（其他集群不受影响），直到再次由两名管理员确认开启；**已在执行中的变更不会被中断**（开关只在提交时和变更开始执行前检查）。需要立刻停手请用「变更取消 / 中止」或在中控机上 `touch` READONLY 文件阻止新变更。

> ⚠️ 开启开关等于允许有权限的账号对真实集群执行变更（执行器为 `direct` / `sudo` 时）。确认前请看「部署自检」与执行器一行。

### 审计日志

**前置条件**：你的角色有 `audit.view`（默认：审批人 / 管理员 / 审计员，或包含该能力的自定义角色）。没有该能力时本标签页不出现。

#### 怎么查一条记录

1. 打开「审计日志」标签页。你会看到最近 200 条记录，按时间倒序（页面标题旁写「本次查询 N 条」）。
2. 在过滤条件里填写需要的条件（见下表），点「查询」或在文本框里按回车。例如查某次变更：「关键字」填 `CHG-0001`。
3. 预期结果：表格只显示符合条件的记录；没有结果时显示「没有符合条件的记录」。

过滤条件：

| 字段 / 选项 | 含义 | 可选值 / 默认 | 影响 |
|---|---|---|---|
| 用户 | 操作人 | 精确匹配（区分大小写，登录名为小写） | 为空不限 |
| 动作 | 动作名，如 `change.created` | 精确匹配；输入框带当前结果里出现过的动作提示 | 为空不限 |
| 结果 | 允许 / 拒绝 / 成功 / 失败 | 全部 | 见「结果取值」 |
| 集群 | 按记录所属的集群过滤（审计日志是全平台一条链，记录里带着是哪个集群） | 下拉选项：「全部集群」（默认）、你可见的每个集群（显示名）、以及审计里出现过但已不在列表里的集群，标成「xxx（历史记录 / 已删除）」。只有平台纳管了集群时才出现这个下拉 | 选某个集群后只返回它的记录（按集群 id 或 tiup 集群名匹配）。全平台级的动作（登录、用户 / 角色管理、双人复核提案）记在**主集群**名下（环境也是主集群的环境），所以选主集群时会包含它们，选其他集群只看到发生在该集群里的动作（变更、写开关、设置、通知渠道、对该集群的接入 / 测试 / 编辑 / 移除等）；少数更早的记录集群列为空，只在选「全部集群」时出现 |
| 时间范围 | 最近 1 小时 / 24 小时 / 7 天 / 30 天 | 全部 | 按记录时间过滤 |
| 关键字 | 在所有文本字段（用户、角色、IP、环境、集群、动作、目标、风险、摘要、结果、关联号）里子串匹配，不区分大小写 | 空 | 用于搜变更号、IP、实例名等 |
| 条数 | 最多返回的条数 | 100 / 200 / 500 / 1000，默认 200 | 返回的是**最近**的 N 条，按时间倒序 |

表格列：

| 列 | 含义 |
|---|---|
| # | 序号（全局递增、连续；不连续说明有记录缺失） |
| 时间 | 记录时间（浏览器本地时区；库里存 UTC） |
| 用户 | 操作人；平台自身的动作是 `system`；登录失败记录的是**输入的用户名**（统一转小写） |
| 角色 | 该用户在当前环境下的角色 **id**（如 `dba`，自定义角色显示其 id 而不是中文名；多个以逗号分隔）；`system` 或登录失败为空 |
| 环境 | 该记录所属集群的环境：`test` / `staging` / `prod` |
| 集群 | 该记录所属集群的 **tiup 集群名**（不是平台 id；例如平台 id 是 `stg`、tiup 集群名是 `stg-tidb-01` 时，这里显示 `stg-tidb-01`），鼠标悬停显示集群显示名；没有集群归属的记录显示「—」。**不同集群的变更编号会重复，要区分是哪个集群的变更就看这一列** |
| 动作 | 动作名，见下表 |
| 目标 | 动作作用的对象：用户名、角色 id、变更号、实例、提案号等 |
| 风险 | 低 / 中 / 高，部分记录为空 |
| 摘要 | 一句话说明。长度上限 4096 字节；疑似口令 / 令牌（`password=`、`token=`、`Bearer …`、URL 里的口令等）会被替换成 `***` |
| 结果 | 允许 / 拒绝 / 成功 / 失败；失败行会高亮 |
| 哈希 | 该记录的 SHA-256 哈希，只显示前 10 位，鼠标悬停看完整值 |

导出文件还包含 `ip`（来源 IP，页面表格里**没有**这一列，但可以用「关键字」搜到）、`ref`（关联变更号）、`prev`（前一条哈希）几列，并带 `env` 与 `cluster`（tiup 集群名，与页面表格里的「环境」「集群」两列一致），时间为 UTC。

**谁能看到哪些记录**：只返回你在该记录的环境下拥有 `audit.view` 的记录（没有环境归属的记录按主集群的环境算）。例如你只在「测试」环境有审计权限，就只能看到测试环境集群的记录，看不到生产集群的。「用户 / 动作」等其他筛选与它叠加。

结果取值：

| 结果 | 含义 |
|---|---|
| 允许 | 预留取值，当前版本的平台没有任何动作写入「允许」，筛选它不会有结果 |
| 拒绝 | 被权限、写开关、CSRF、Origin、校验等规则拒绝，**拒绝也会留痕**；登录失败也记为「拒绝」 |
| 成功 | 动作已执行成功 |
| 失败 | 动作执行了但失败（如变更失败、通知渠道测试失败、审计链校验失败） |

常见动作：

| 动作 | 含义 |
|---|---|
| `auth.login` / `auth.logout` | 登录（成功 / 拒绝=失败，含因锁定被拒的尝试，摘要「登录失败」）/ 退出 |
| `auth.password` / `auth.totp` | 自己改口令 / 自己绑定 TOTP |
| `watermark.update` | 修改页面水印设置（见 [水印设置](help:watermark)；风险 mid，摘要写变更了哪些字段；不走审批） |

| `shell.run` `shell.request` `shell.approve` `shell.cancel` `shell.settings` | 「中控机命令」（中控机模式）：执行（只读为低风险，变更为高；摘要含执行路径「平台进程内 / 临时单元」、目录与逐条命令；被护栏拒绝也记一条，含原因）/ 提交变更申请 / 批准 / 取消 / 改策略设置；命令里的 `--password=`、`-pxxx` 已打码；执行不需要 root 密码（经 sudoers 放行的 `shell-exec` 入口以 tidb 身份执行） |

| `user.profile` | 改用户资料（显示名 / 部门 / 邮箱 / 手机 / 备注）；摘要只写改了哪几项，**不写内容** |
| `user.unlock` | 管理员解锁账号；摘要区分「解除登录锁定（原锁定至 …）」和「清除登录失败计数（当时未被锁定）」 |
| `role.create` `role.update` `role.delete` | 自定义角色的新建 / 修改 / 删除；摘要含权限差异（`+能力键(授予方式)` 新增、`−能力键` 移除、`~能力键(旧→新)` 变更）和「即时影响 N 名成员」；规则拒绝（如授予仅管理员能力、删除有成员的角色）记「拒绝」 |

| `authz.deny` / `security.csrf` / `security.origin` | 缺少能力 / CSRF 不匹配 / 跨站请求，被拒绝 |
| `platform.start` | 平台启动（含版本、执行器、写开关状态） |

> 💡 页面说明里的「读写请求」并不意味着所有读请求都被审计：普通的页面数据读取（总览、拓扑、慢 SQL、用户与角色列表等）**不写审计**，被审计的读类动作只有巡检、只读命令、导出报告、导出审计日志等。查询审计日志本身也不写审计。

按钮：

| 按钮 | 谁能点 | 点击后发生什么 | 可撤销吗 | 审计怎么记 |
|---|---|---|---|---|
| 查询 | `audit.view` | 按条件读取日志，只读 | — | 不记 |
| 校验哈希链 | `audit.view` | 后端从头重算整条链并给出结果横幅 | — | 通过时不记；**失败时记** `audit.verify`（失败，风险=高） |

#### 哈希链校验的含义

- 每条记录的哈希 = SHA-256（前一条的哈希 + 换行 + 本条规范化后的各字段）。第一条的「前一条」为空。因此任何一条记录被改、删、插入，其后的链都对不上。
- 校验成功：「哈希链完整：共 N 条记录全部校验通过」。
- 校验失败：「哈希链断裂：第 N 条被篡改或缺失」，并附原因：

| 原因 | 说明 |
|---|---|
| 记录无法解析 | 该行不是合法 JSON |
| 序号不连续，记录缺失或被替换 | 出现了跳号：有记录被删除或被替换 |
| 与前一条记录的哈希不衔接 | 该记录的「前一条哈希」对不上，中间有记录被删除、插入或重排 |
| 内容与哈希不一致 | 该记录的内容被修改过 |
| 尾部记录缺失 | 校验到的条数少于平台内存里记录的最大序号：尾部记录被删 |

> ⚠️ 校验失败意味着审计文件（数据目录下的 `audit.log`）**很可能被人为改动过**，或磁盘 / 手工编辑导致损坏。此时不要继续依赖该日志做追责：保留现场（不要手工修复），立即通知安全负责人，核对备份与文件权限（应为 0600、仅平台账号可写）；部署自检里的「审计哈希链」也会标红。

> ⚠️ 已知边界（来自实现注释）：攻击者如果重算其后全部记录的哈希，离线无法发现；平台运行期间删除尾部记录可发现，**重启之后删除尾部记录则发现不了**；同一文件只支持单个进程写入；平台**目前没有接入向外部（syslog / 外部日志系统）实时转发的出口**，也没有按天数自动归档 / 清理的功能（原型页面上写的「保留 180 天、转发 syslog」尚未实现）。建议用文件系统权限与定期备份补强。

> ⚠️ 启动时如果发现审计文件**尾部记录**哈希不一致，平台会拒绝启动；如果末尾只是崩溃留下的半行，则会自动补全或截掉该半行后继续。

静态示意：列出执行器放行的命令模板（共 9 条）、永远禁止的命令，以及一个「命令校验器」，输入一条命令看是否放行。校验器只模拟判断，**不会执行任何东西**；真实白名单在执行器里，种类更多，以执行器为准。

### 部署自检

**前置条件**：登录即可。每次打开标签页都会重新检查，**不是**定时任务；点「重新自检」可手动再查一次。

**检查范围（多集群）**：自检按**当前所选集群**执行，对每个集群分别点一遍。具体来说：
- 跟着集群走的项：执行器（特权分离、生产环境使用真实执行器）、「至少两名管理员」（统计的是**该集群的环境**下启用的内置管理员）、「集群版本在支持矩阵内」、该集群自己的运行数据文件权限（非主集群只有 `changes.json`、`settings.json`）；
- 全局的项：审计哈希链、READONLY 熔断文件、会话策略、MFA 设置；`users.json`、`audit.log`、`roles.json`、`master.key`、`clusters.json` 的权限只在**主集群**的自检里出现。

1. 打开「部署自检」标签页。预期结果：先显示「正在自检…」，随后出现一条汇总提示（红色「N 项未通过」/ 橙色「关键项通过，另有 N 项警告」/ 绿色「全部通过」）和检查项表格。
2. 逐行看「结果」列（通过 / 警告 / 失败），失败行高亮；「详情」列写明原因。
3. 按下表处理后点「重新自检」，确认变绿。

检查项：

| 检查项 | 通过条件 | 不通过时 |
|---|---|---|
| 不以 root 运行 | 平台进程不是 root | 失败：被攻破即获得整机权限 |
| 数据文件权限 `<文件名>` | 数据目录里存在的 `users.json` `audit.log` `changes.json` `settings.json` `roles.json` `master.key` `clusters.json` 各一行，权限为 0600（非主集群看到的是它自己运行数据目录里的文件，见上文「检查范围」） | 失败，显示实际权限（文件不存在则没有这一行） |
| 审计哈希链 | 链完整 | 失败，显示断裂位置 |
| 特权分离（Web 进程 + sudo 受限 exec 入口） | 执行器为 `sudo` | `direct` / `sim` / 未配置均为警告 |
| 至少两名管理员（写开关双人复核） | 本环境下启用的**内置「管理员」角色**用户 ≥ 2 | 失败：无法完成写开关双人确认（自定义角色的成员不计入） |
| 高风险申请人 MFA | 未带 `--no-mfa` | 警告 |
| READONLY 熔断文件 | 文件不存在 | 警告：平台强制只读 |
| 会话策略 | （信息项）显示空闲 / 绝对超时与 Cookie、CSRF、Origin 防护 | — |
| 集群版本在支持矩阵内 | v7.5 / v8.1 / v8.5 系列 | 警告：写操作降级为只读 |
| 生产环境使用真实执行器 | 仅环境为生产时出现：执行器不是 `sim` | 失败 |

Windows 上「不以 root 运行」与「数据文件权限」合并成一条警告「运行账号与文件权限」（不检查 POSIX 权限与 root）。页面提示「请先修复再开启写操作」只是建议：**自检结果目前不会自动阻止写开关的开启**（原型里「关键项失败即强制只读」的描述尚未实现）。

### 我的账号

打开「我的账号」标签页：

| 区块 | 说明 |
|---|---|
| 我的账号 | 用户名、显示名、「当前集群」（显示名与 id）、当前环境（`test` / `staging` / `prod`，是**当前所选集群**的环境）、角色（中文名标签）、MFA 状态，以及你在当前集群的环境下拥有的全部能力键（悬停可见授权方式，括号里是能力个数）。切换集群后，环境、角色与能力都会变成新集群的 |
| 修改口令 | 填「当前口令」「新口令」「确认新口令」；新口令需满足口令策略。成功后记 `auth.password`（不含口令）。**不会吊销你的其他会话** |
| 多因素认证（TOTP） | 见下 |

> 💡 「我的账号」里的角色与能力是你**此刻**的实际权限。管理员修改你的角色或自定义角色的权限后，页面会在几秒内自动同步（页面空闲、没有打开抽屉、没有在输入时才会重绘）；想立刻看到最新结果，切换一下标签页或刷新浏览器。

#### 修改自己的口令

**前置条件**：你知道当前口令；新口令满足口令策略（至少 10 位、至少 3 类字符、不含用户名、最长 128 位）。是否绑定 MFA 不影响改口令。

1. 「我的账号」→「修改口令」，依次填「当前口令」「新口令」「确认新口令」。
2. 点「修改口令」。预期结果：提示「口令已修改」，三个输入框清空。
3. 出错提示：「请填写当前口令和新口令」「两次输入的新口令不一致」「新口令至少 10 位」；服务端返回的「当前口令不正确」或口令策略原因（如「口令不得包含用户名」）。

**后果**：新口令立即生效；你已登录的其他浏览器会话**不会被吊销**。

#### 绑定 MFA 的步骤

TOTP（基于时间的一次性口令）是认证器 App 每 30 秒生成一次的 6 位数字，规范见 [RFC 6238](https://www.rfc-editor.org/rfc/rfc6238)。

**前置条件**：手机上装有认证器 App（如 Google Authenticator 或同类 App）；手机时间准确（偏差大会一直失败）；你的账号当前**未绑定** MFA。

1. 「我的账号」→「多因素认证（TOTP）」→ 点「开始绑定」。预期结果：出现「密钥（Base32，手动输入到认证器）」（带「复制」按钮）、「otpauth URI」和「输入认证器当前显示的 6 位码以确认」输入框，**没有二维码**。
2. 在认证器 App 里手动添加账户：选「输入设置密钥」之类的入口，账户名随意（建议写 `TiDB-Ops` 与你的用户名），密钥粘贴上一步的 Base32 密钥，类型选基于时间（TOTP），算法 SHA-1、6 位、30 秒（认证器默认值通常就是这样）。
3. 输入认证器当前显示的 6 位数字，点「确认绑定」。预期结果：提示「MFA 已绑定」，卡片变成绿色提示「已绑定动态验证码…」，「我的账号」里 MFA 显示「已绑定」。
4. 不想继续时点「放弃」，回到绑定前的状态（服务端未确认的密钥会在下一次「开始绑定」时被覆盖）。

出错提示：「请输入 6 位数字验证码」（不是 6 位数字）；「动态验证码错误或已被使用」（码不对，或这个 30 秒窗口的码已被用过）；连续输错 5 次，该账号的 MFA 确认被锁定 10 分钟，提示「登录失败次数过多，请在 HH:MM:SS 之后重试」（管理员可在 [用户管理](go:users) 对该账号「解锁」）。

**后果**：登录仍只需用户名 + 口令，**不需要**动态验证码；此后提交生产高风险变更（默认策略，审批策略可配）时要填。已绑定的账号想换设备，需要管理员在 [用户管理](go:users) 里「重置 TOTP」后重新绑定。

> 💡 密钥只在绑定那一步显示。TOTP 密钥在数据目录里用 `master.key` 加密保存，**务必备份 `master.key`**：丢失后用户库里的 TOTP 密钥无法解密，平台会拒绝启动。

### 会话管理

本页没有「在线会话列表」或「强制下线」按钮，会话按下面的规则产生与结束：

| 事件 | 会话怎么变 |
|---|---|
| 登录 | 新建会话，Cookie 有效期 = 绝对超时 |
| 空闲 30 分钟 / 满 8 小时 | 过期；页面开着时的自动刷新会不断续期「空闲」，8 小时绝对上限不会续。过期后任何操作都会回到登录页，并提示「登录已过期或已在别处退出，请重新登录」 |
| 点「退出」 | 立即销毁（需通过 CSRF 校验） |
| 管理员改用户的角色 / 禁用 / 重置口令 / 删除用户 / 授予管理员提案生效 | **吊销该用户的全部会话** |
| 管理员修改**自定义角色的权限** | **不吊销**会话；成员的下一次请求就按新权限判定 |
| 用户自己改口令 / 管理员重置 TOTP / 管理员解锁 | **不会**吊销会话 |
| 平台重启 | 会话只保存在内存里，**所有人需要重新登录** |

## 执行后果与风险

> ⚠️ **授予管理员**：管理员能创建 / 删除用户、改角色、改审批策略、开关写操作，是权限最高的角色（但不能直接执行集群变更或审批变更）。务必核对提案里的用户与环境后再确认。

> ⚠️ **修改审批策略**：下调审批级数会让此后的变更更少人把关（硬性下限之外都允许）；提案生效后立即作用于所有新提交的变更，已提交的变更沿用创建时确定的级数。

> ⚠️ **开启写操作开关**：之后有权限的账号提交并经审批的变更会真实作用于集群；平台**没有**在页面上提供对已完成变更的「一键回滚」。

> ⚠️ **禁用 / 删除 / 重置口令 / 改角色**（在 [用户管理](go:users) 里做）：会立即吊销该用户全部会话，正在填写中的操作会丢失；不会中断该用户已经提交并在执行中的变更。

| 提案提示「提案已过期，请重新发起」 | 超过 1 小时，重新发起 |
| 创建带管理员角色的用户后，该用户没有管理员权限 | 正常：授予管理员需另一名管理员在「待确认提案」里确认 |
| 提示「不能删除、禁用或降级最后一个管理员」 | 先创建 / 提升另一名管理员（需双人复核）再操作 |
| 写开关已开，顶栏仍显示「只读」，悬停有原因 | 还有其他总闸未满足：READONLY 文件、未配置执行器、集群版本不受支持；见「写操作开关」页的「当前不能写的原因」 |

更多「现象 → 原因 → 怎么办」见 [常见问题](help:faq)。
