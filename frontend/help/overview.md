# 集群总览

> 💡 值班第一屏：一眼看清集群「有没有出事、哪里在变化、容量还能撑多久」。所有角色都能打开（权限项 `view.overview`）；本页本身只读，不会改动集群。只读 / 回放模式无需登录；运维模式需先登录，并额外多出「事件时间线」和告警行上的「静默」按钮（静默是运维模式下本页唯一的写动作，见「执行后果与风险」）。平台至今没有对真实集群运行过，本页「真实数据」的口径来自代码与回放样例，联调后请以 Grafana 为准。

## 这个页面做什么

- 用 4 张 KPI 卡片展示 QPS、P99 延迟、连接数、存储使用（含容量预测）。
- 画出最近 60 分钟的 QPS 与 P99 趋势、数据库时间（DB Time）按 SQL 类型的构成。
- 用「实例健康矩阵」列出 TiDB / TiKV / PD 每个实例的状态、CPU、内存、磁盘。
- 列出活跃告警和「优先处理建议」（来自 [智能诊断](go:diag) 的严重项）。
- 提供入口：「一键诊断」「执行巡检」「查看架构图 →」「深入诊断 →」。
- **显示的是「当前集群」**：运维模式下平台可以纳管多个集群，本页的所有数据（KPI、趋势、健康矩阵、告警、事件时间线、集群信息）都是顶栏集群下拉里选中的那个集群的；浏览器标签页标题（如「集群总览 · 开发集群」）和数据来源横幅里的「集群 xxx」都会告诉你当前是哪一个。切换方法见 [集群接入帮助](help:clusters)；只读 / 回放模式只有一个集群，下拉里只有它自己。

## 先看懂几个词

| 术语 | 一句话解释 | 官方文档 |
|---|---|---|
| TiDB / PD / TiKV / TiFlash | TiDB 是无状态的 SQL 层；PD 负责元信息、时间戳（TSO）与调度；TiKV 是行存的分布式存储；TiFlash 是列存的分析副本 | [TiDB 整体架构](https://docs.pingcap.com/zh/tidb/stable/tidb-architecture) |
| Region / Leader | 数据按 Key 范围切成 Region（默认约 256 MiB），每个 Region 有多个副本组成一个 Raft 组，其中 Leader 处理读写 | [TiDB 数据库的存储](https://docs.pingcap.com/zh/tidb/stable/tidb-storage) |
| Store | PD 对一个 TiKV（或 TiFlash）存储节点的称呼，容量与 Region 数以 Store 为单位统计 | 同上 |
| DB Time（数据库时间） | TiDB 处理 SQL 累计花费的时间，用来判断时间花在哪类 SQL、哪个阶段 | [性能分析和优化方法](https://docs.pingcap.com/zh/tidb/stable/performance-tuning-methods) |
| QPS / P99 | 每秒查询数；99% 的查询比这个耗时短（即长尾延迟） | [Performance Overview 面板](https://docs.pingcap.com/zh/tidb/stable/grafana-performance-overview-dashboard) |
| 告警 / Alertmanager | Prometheus 规则触发告警，由 Alertmanager 负责发送与管理（含静默） | [监控框架](https://docs.pingcap.com/zh/tidb/stable/tidb-monitoring-framework) |
| 静默 | 在 Alertmanager 里给某条告警设一段「不通知」的时间，不修复问题 | 同上 |

## 怎么用（按步骤）

### 日常查看：从上到下读一遍总览

1. 在左侧栏「概览」分组点「集群总览」。你会看到：顶栏右侧有数据来源角标，导航栏下方可能有一条横幅，页面上方是 4 张 KPI 卡片。
2. **确认数据来源**。看顶栏右侧角标和导航栏下方的横幅，对照「如何分辨数据来源」。
  - 角标「产品演示」：全部是演示数字，到此为止，不要据此做任何判断。
  - 「回放数据」：样例包里的数据，不是实时的。
  - 「真实数据 · 只读」：继续下一步。
3. **看横幅有没有「N 项数据缺失 ▸」**。有的话点它，横幅下方展开一行行黄色文字，列出哪类数据没采到及原因（例如 Prometheus 端点未配置）。缺失的那一块页面上显示「—」「未采集」或 0，**不要把它当成正常**。
4. **看 4 张 KPI 卡片**（QPS / P99 延迟 / 连接数 / 存储使用）。每张卡片大字是当前值，小字是变化。对照下面的「阈值速查」判断颜色。你会看到：QPS 或 P99 的小字变红表示明显上升；存储卡小字里有「预计 N 天后达 80%」。
5. **看趋势图**（「QPS 与延迟」）。找尖刺和台阶：台阶式上升是业务量变化；P99 尖刺而 QPS 平稳是个别慢 SQL 或节点抖动；两条线同时断崖多半是采集断了，先确认 Prometheus。
6. **看「数据库时间分解」**。你会看到一条彩色堆叠条，占比最大的 SQL 类型就是优先关注对象。要看按处理阶段、执行阶段的拆分，点卡片右上角「深入诊断 →」。某类占比突然变大，去 [SQL 优化](go:sql) 查这一类的慢 SQL。
7. **看「实例健康矩阵」**。有红点 / 黄点或进度条变色的实例需要关注。点那一行，页面跳到 [集群架构](go:arch) 并选中该实例（步骤见该页）。
8. **看右栏「活跃告警」和「优先处理建议」**。点「查看根因与处置 →」，页面跳到 [智能诊断](go:diag)；到那里还要点「开始诊断」才会展开对应项（见智能诊断页）。
9. 需要深挖：「一键诊断」去智能诊断，「执行巡检」去 [日常运维](go:ops)。两个按钮都只是跳转，不会执行任何诊断或巡检（见「已知限制与易混淆点」）。

### 静默一条告警（仅运维模式）

前置条件：已登录运维模式；你的角色有 `diag.run`；「写操作开关」已开启（顶栏显示「写操作已开启」）；告警行上能看到「静默」按钮。

1. 在右栏「活跃告警」里找到那条告警，点它右侧的「静默」。你会看到右侧抽屉「静默告警」，上面列出告警名、实例、描述。
2. 在「静默时长（分钟，1–1440）」里填分钟数，默认 60。
3. 在「备注」里写原因，最多 200 字，例如「磁盘扩容中，已知问题」。备注会连同你的用户名一起写入 Alertmanager。
4. 点「确认静默」。你会看到抽屉关闭，底部弹出「已静默 告警名 N 分钟」，「事件时间线」随之刷新。
5. 与预期不符：
  - 抽屉里出现红字「时长需在 1–1440 分钟之间」：改正时长后重试。
  - 红字含「静默失败：…」或提示写操作被拒：多半是「写操作开关」关闭、执行器为 `none`，或 Alertmanager 不可达。找 admin 处理，或见 [常见问题与提示](help:faq)。
  - 不想静默了：点「取消」或按 Esc 关闭抽屉，不会产生任何改动。

静默的后果见「执行后果与风险」。

### 使用示例：交接班晨检（读数 5 分钟）

场景：已连接回放或真实数据，打开本页（以下数字是回放样例）。

1. 横幅显示「真实数据（只读）· 集群 prod-tidb-01 · 采集于 09:02:11」，没有黄色「N 项数据缺失」，说明数据完整。
2. QPS `10,530`，副标题「▲ 6.2% 较窗口起点」为灰色，属正常波动；P99 `38 ms`，副标题「▲ 12ms 较 1 小时前」为红色（上升超过 5 ms 即标红），记下来，到趋势图看是否持续爬升。
3. 存储卡 `8.4 TiB / 15 TiB`，副标题「56% · TiKV Store 合计 · 预计 41 天后达 80%（按最近 7 天线性回归）」。41 天远大于常规扩容周期（采购与扩容通常需要提前量，这是经验，平台不判定），本班无需处理；若写「已超过 80% 水位」或「不到 1」天，立即转 [节点管理](go:nodes) 评估扩容。
4. 健康矩阵里 tikv-4 磁盘条红色（86%）。点该行跳到 [集群架构](go:arch)，右侧详情「关联诊断」里点「磁盘使用率超过 80% 水位」那一项，到 [智能诊断](go:diag) 读证据与处置建议。
5. 活跃告警里的 2 条严重告警与诊断结论一致（tikv-4 磁盘、tikv-2 Raftstore CPU），记录后交给对应负责人。

## 区域与参数说明

### 如何分辨数据来源

| 来源 | 怎么识别 | 特点 |
|---|---|---|
| 静态原型（模拟） | 顶栏角标「产品演示」；没有导航栏下方的横幅；QPS 图标题括号里写「模拟」；KPI 固定为 10,530 / 38 ms / 731 / 8.4 TiB | 打开 index.html 且没有后端时的演示数据，数字全是假的，扩缩容、排期等也都是前端模拟 |
| 回放（replay） | 横幅「⏪ 回放数据」，角标「回放数据」，图标题「回放数据」 | 后端读取样例数据包，不连接任何集群。数据是样例导出那一刻的；横幅里的「采集于」是服务端生成快照的时间，不代表数据本身的时间 |
| 真实只读采集（live） | 横幅「🟢 真实数据（只读）」，角标「真实数据 · 只读」，图标题「真实数据」 | 后端只读采集 Prometheus、PD、TiDB 状态接口、tiup display、information_schema 等。目前尚未对真实集群验证 |

后两种在横幅里还有说明「扩缩容 / 配置变更 / 主机维护等写操作仍是原型模拟，不会作用于集群」：只读模式下成立；运维模式下这句不适用，写操作真实走变更引擎（用模拟执行器时除外），见 [快速入门](help:quickstart)、[日常运维](go:ops)、[节点管理](go:nodes)。

### 页面顶部的提示与刷新

| 元素 | 含义 | 影响 |
|---|---|---|
| 数据来源横幅 | 显示模式、集群名（当前集群的）、快照采集时间 | 仅提示 |
| 顶栏集群下拉 | 运维模式下选择要看的集群（选项形如「预发集群（预发）」，生产集群旁有红色「生产环境」标签）；选另一个会整页刷新，本页数据整体换成新集群的 | 只能看到一个集群时是灰色的；逐步操作见 [集群接入帮助](help:clusters) |
| 某集群连不上时 | 该集群的总览不会报错，而是数据为空（实例 0 个、KPI 显示「—」），横幅写「N 项数据缺失」，点开看缺哪些数据源；管理员可在「集群接入」页对它做「测试」 | 见 [常见问题](help:faq) 的「集群相关」 |
| 「N 项数据缺失 ▸」 | 点开列出本次快照里采集失败的数据源及原因；黄色表示有缺失 | 缺失的那块显示「—」「未采集」或 0，不要当成正常 |
| 「立即刷新」 | 跳过快照缓存重新生成一次快照，成功后弹出「已刷新」 | 服务端至少间隔 2 秒才会真正重采；**不会绕过数据源响应缓存**（`--cache-ttl`，默认 15 秒），所以刚发生的变化可能还要等十几秒 |
| 自动刷新 | 页面每 30 秒取一次快照并重绘（右侧抽屉打开或正在输入 / 选择下拉框时不重绘） | 服务端快照缓存 10 秒 + 数据源缓存 15 秒，画面最多可能落后约 40 秒；每次重绘页面会回到顶部 |
| 🛠 维护提示条 | 有主机处于「正在排空 / 维护中 / 正在恢复」时出现：主机 IP、维护类型、计划分钟数 | 仅提示；「查看维护流程 →」跳到 [节点管理](go:nodes) 的主机维护页 |
| 📅 排期提示条 | 3 天内最近一个变更排期及待审批数量 | 仅提示；「查看排期 →」跳到 [变更排期](go:schedule) |

### KPI 卡片

只读采集模式下的口径。取点：Prometheus 区间查询，窗口最近 1 小时、步长 60 秒；「当前值」取最后 3 个点的平均，「窗口起点」取最前 3 个点的平均。

| 卡片 | 取值（PromQL / 来源） | 副标题 | 颜色 | 看数要点 |
|---|---|---|---|---|
| QPS | `sum(rate(tidb_server_query_total[1m]))`；为 0 或没取到显示「—」 | 「▲ / ▼ x% 较窗口起点」，即 (当前 − 起点) / 起点 | 上升超过 10% 变红，否则灰；**下降再多也不变红** | QPS 骤降到接近 0 比上升更危险：先确认应用与 TiDB 连通 |
| P99 延迟 | `histogram_quantile(0.99, ...tidb_server_handle_query_duration_seconds_bucket...)`，换算为毫秒 | 「▲ / ▼ x ms 较 1 小时前」，即当前与起点的差值 | 上升超过 5 ms 变红，否则灰 | 绝对值要结合业务 SLA，平台没有设阈值。P99 升而 QPS 没涨，多半是慢 SQL / 热点 / 磁盘，转 [智能诊断](go:diag) |
| 连接数 | `sum(tidb_server_connections)` | 「Region N · Store 上线数/总数 Up」 | 灰 | Region 数来自 PD 统计；Store 数含 TiFlash，「Up」指 PD 里状态为 Up。上线数小于总数说明有 Store 离线或下线中 |
| 存储使用 | 全部 TiKV Store 的（容量 − 可用）合计 / 容量合计（取自 PD，不含 TiFlash），以 TiB 显示 | 「N% · TiKV Store 合计」，其后异步追加容量预测 | 灰；预测「数据不足」或「已超过 80% 水位」时副标题变红 | 这是磁盘整体占用（含 TiKV 之外占用同一块盘的文件），与容量预测使用的「数据文件大小」口径不同，两者数字可能对不上 |

### 阈值速查：正常 / 关注 / 异常与下一步

下表全部是平台在代码里写死的阈值，不是 TiDB 官方阈值；官方没有对应「标准值」的地方不另编数字。

| 看什么 | 平台阈值 | 看到后下一步 |
|---|---|---|
| QPS 副标题 | 较窗口起点上升 >10% 变红 | 看趋势图是台阶还是尖刺；到 [SQL 优化](go:sql) 看哪类 SQL 增长 |
| QPS 骤降 / 为「—」 | 无颜色提示 | 先点横幅「N 项数据缺失」确认是不是没采到；再看活跃告警与健康矩阵里 TiDB 是否「已停止」 |
| P99 副标题 | 较 1 小时前上升 >5 ms 变红 | 转 [智能诊断](go:diag) 看 DB Time 分解与慢 SQL |
| Store 上线数 / 总数 | 上线数 < 总数即异常 | 到 [集群架构](go:arch) 找「已停止 / 下线中」的 TiKV / TiFlash，再看诊断项「状态异常」 |
| 实例状态「告警」（黄） | 磁盘 ≥85%，或 CPU ≥85%，或内存 ≥80%，任一触发 | 点该行到 [集群架构](go:arch) 看实例备注里写的触发原因 |
| 进度条变色 | CPU / 内存：≥70% 黄、≥85% 红；磁盘：≥75% 黄、≥85% 红 | 同上；磁盘红色先按 [智能诊断](go:diag) 的磁盘项处理 |
| 容量预测 | 见下文「容量预测」 | N 很小或已超水位，转 [节点管理](go:nodes) 评估扩容 |
| 活跃告警 | 严重 / 警告 / 提示按 Alertmanager 的 `severity` 标签 | 有严重告警，先看「优先处理建议」是否已有对应诊断项 |

注意：进度条颜色与实例状态是两套阈值。例如内存 82% 的实例，进度条是黄色（≥70% 黄、≥85% 红），但实例状态已经是「告警」（内存 ≥80%），这不是显示错误。

### QPS 与延迟趋势图

| 项 | 含义 | 说明 |
|---|---|---|
| 标题括号 | 「模拟 / 回放数据 / 真实数据」 | 与「如何分辨数据来源」一致 |
| 窗口与取点 | 最近 60 分钟，每 60 秒一个点 | 后端固定 1 小时窗口；横轴标签固定写「-60m … 现在」 |
| 纵轴 | 从 0 起，最大值为数据最大值的 1.1 倍，5 条网格线 | 数值 ≥1 万显示为「x.x 万」 |
| 左图 QPS / 右图 P99(ms) | 真实 / 回放只画 P99 一条线；静态原型还会画 P95 | 没取到趋势时整块显示「未取得 Prometheus 趋势数据」；只缺 P99 时右图是空白坐标 |

### 数据库时间分解（按 SQL 类型）

DB Time 是 TiDB 处理 SQL 累计花费的时间（官方定义见 [性能分析和优化方法](https://docs.pingcap.com/zh/tidb/stable/performance-tuning-methods)）。本卡片只画「按 SQL 类型」一个维度；按处理阶段、执行阶段的细分在 [智能诊断](go:diag) 页。

| 项 | 含义 | 口径 |
|---|---|---|
| 色块 | 各 SQL 类型（select / insert / update / commit 等，名称取自指标的 `sql_type` 标签）占比，合计恒为 100% | `sum(rate(tidb_server_handle_query_duration_seconds_sum{sql_type!="internal"}[1m])) by (sql_type)` 在窗口内的平均，取前 6 名，其余合并为「其他」；不含内部 SQL |
| 色块里的文字 | 占比 ≥7% 才在色块内写出名称，其余只在图例里列出 | 鼠标悬停可见名称和占比 |
| 「未采集（需要 Prometheus 的 DB Time 指标）」 | 没取到该指标 | 此时不会出现在「数据缺失」横幅里，需自行确认 Prometheus 配置 |

这是相对占比，不是绝对耗时：它回答「时间花在哪类 SQL 上」，不回答「总共花了多少」。

### 实例健康矩阵

### 容量预测（存储卡副标题）

后端取最近 7 天、每小时一个点的 TiKV 已用字节（`sum(tikv_store_size_bytes{type="used"})`）与容量，做最小二乘线性回归，得出每天增长量，再算「已用」增长到「容量的 80%」还要几天。结果在服务端和浏览器各缓存 5 分钟。80% 这条线与 PD 的 `low-space-ratio`（默认 0.8，节点空间占用超过它后 PD 会尽量避免往该节点迁移数据，见 [PD 配置文件](https://docs.pingcap.com/zh/tidb/stable/pd-configuration-file)）一致；官方告警规则里也有 `TiKV_space_used_more_than_80%`（见 [报警规则](https://docs.pingcap.com/zh/tidb/stable/alert-rules)）。

| 显示文字 | 含义 | 下一步 |
|---|---|---|
| 预计 N 天后达 80%（按最近 7 天线性回归） | 正常预测；不足 1 天写「不到 1」 | N 很小就要立即排扩容；鼠标悬停副标题可看依据（样本数、窗口、每天增长 GiB） |
| 数据不足 24 小时，暂无法预测 | 小时点少于 24 个，或时间跨度不足 23 小时；**也会在没采到容量指标时显示**（悬停可见「未采集到容量指标」） | 刚部署 / Prometheus 保留期过短时属正常；红色只是提醒，不代表容量有问题 |
| 近 7 天存储基本不增长，无达到 80% 的预测 | 回归斜率 ≤0 且当前未超水位 | 数据稳定或在下降，无需处理 |
| 已超过 80% 水位 | 已用已超过容量的 80% | 立即安排扩容，见 [节点管理](go:nodes) 与官方 [扩缩容文档](https://docs.pingcap.com/zh/tidb/stable/scale-tidb-using-tiup) |
| （没有追加文字） | 预测接口请求失败，页面静默忽略 | 刷新页面或检查后端日志；运维模式下需有登录会话 |

注意：预测是线性外推，遇到批量导入、归档清理等非线性变化会失真，只作参考。数据不足时即使已超 80% 也显示「数据不足…」。

## 执行后果与风险

> ⚠️ 本页绝大部分是只读：采集动作是对 Prometheus、PD、TiDB 的读请求（SQL 仅 SELECT，经 mysql 客户端），服务端有缓存与 2 秒最短刷新间隔，多人打开页面不会放大压力。

> ⚠️ **告警「静默」会写入 Alertmanager（仅运维模式）**：创建一条临时静默规则，到期自动失效，时长 1–1440 分钟，可填备注。属低风险写操作，**不走审批**，但需要 `diag.run` 权限、受「写操作开关」约束，并写入审计日志。静默期间同名同实例告警不再通知，可能延误对真实故障的发现；静默不会修复任何问题，也无法在平台内撤销（需在 Alertmanager 里删除静默）。回放模式下由模拟执行器代为「执行」，不会改动任何系统。该写路径没有在真实集群上验证过。

> ⚠️ 「一键诊断」「执行巡检」「深入诊断 →」「查看架构图 →」都只是跳转，不会对集群执行诊断命令或变更。

## 已知限制与易混淆点

| 界面写的 | 实际是 | 怎么办 |
|---|---|---|
| 静态原型 QPS 小字「较昨日同期」 | 真实 / 回放模式是「较窗口起点」（1 小时前），不是昨日同期 | 对比昨日请用 Grafana |
| 「立即刷新」 | 只跳过快照缓存，数据源响应缓存仍有 15 秒（默认）；两次刷新至少间隔 2 秒 | 变更后等十几秒再刷新 |
| 「一键诊断」 | 只跳转，不运行诊断 | 到诊断页再点「开始诊断」 |
| 「执行巡检」 | 只跳转到「日常运维」，落点不一定是巡检标签 | 再点「巡检」标签 |
| 导航栏红色数字 | 只在首次加载时算一次，不随 30 秒自动刷新更新；口径是严重 + 警告，不含提示，与「活跃告警」数字不同 | 以页面内的「活跃告警」为准；刷新浏览器可重算 |
| 健康矩阵的 CPU / 内存 | 是所在主机的使用率，不是进程占用 | 同机多实例读数相同 |
| 健康矩阵的磁盘 0% | TiDB / PD 没采集，不代表很空 | 不要据此判断它们的磁盘健康 |
| 存储卡大字与容量预测 | 大字用 PD 的（容量 − 可用），预测用 TiKV 的数据文件大小，口径不同 | 数字对不上属正常 |
| 只读模式的维护 / 排期提示条 | 前端演示数据 | 以运维模式或 [变更排期](go:schedule) 为准 |
| 事件时间线副标题「告警 · 变更 · 维护 · 诊断」 | 按代码，诊断项目前不会进入时间线，实际只有告警、变更、维护（疑似问题，未在真实环境验证） | 诊断结果看 [智能诊断](go:diag) |
| 已静默的告警 | 平台读 Alertmanager 告警列表时没有过滤静默状态，静默后可能仍显示（疑似问题，未在真实 Alertmanager 验证） | 以 Alertmanager 页面为准 |
| 每 30 秒自动刷新 | 按代码，每次自动重绘后页面回到顶部（抽屉打开或正在输入时不重绘）；页面上没有暂停自动刷新的开关（以真实浏览器表现为准） | 读到一半被拉回顶部属正常，请先记下关键数字再往下看 |

## 常见问题与排查

- **KPI 显示「—」**：对应指标没取到或为 0。先点横幅「N 项数据缺失」看原因；常见是没配置 Prometheus（`端点 "prom" 未配置`）。
- **CPU / 内存全是 0%**：没有部署 node_exporter 或 Prometheus 里没有主机指标；横幅会提示「缺少 Prometheus 节点指标」。
- **数字与 Grafana 对不上**：这里取最近 3 点平均、1 分钟 rate，且有最多约 40 秒缓存延迟；联调清单约定允许 ±5%。
- **回放数据看起来是「最新」的**：回放读的是样例包，「采集于」只是生成快照的时刻。
- **运维模式下某些内容为空**：没有对应权限时区块为空而不是报错（例如没有 `view.sql` 时 [SQL 优化](go:sql) 列表为空）。
