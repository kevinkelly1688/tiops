# 节点管理

> 💡 一个页面管理集群的全部实例与主机：单实例重启 / 停止 / 启动 / 驱逐 Leader、扩容、缩容、主机维护、配置变更，以及候选主机池与预检。所有登录用户都能查看；发起写操作需要对应能力（实例操作：sre / dba；扩缩容、配置变更、主机维护：dba），审批由 approver 角色完成。**只读 / 回放模式下所有写操作只是前端模拟，不会作用于集群；运维模式下才会走服务端「规划 → 审批 → 执行 → 审计」。平台至今没有在真实集群上跑过，下文所有命令的真实表现都以真实集群联调为准。**

## 这个页面做什么

页面顶部有 6 个标签页，另有每个实例的「详情 / 配置」抽屉：

| 标签页 | 用途 | 是否改动集群 |
|---|---|---|
| 节点实例 | 实例列表（状态 / 资源 / 负载），单实例重启、停止、启动、驱逐 / 恢复 Leader，入口跳转到缩容、详情 | 写操作 |
| 主机池 | 集群内主机规格与状态；候选主机池（尚未加入集群的机器）的登记、编辑、预检；进入主机维护 | 候选池登记与预检不改动集群；进入维护是写操作 |
| 扩容 / 新增节点 | 4 步向导：选角色、选主机并预检、配参数、预览提交 | 写操作 |
| 缩容 / 下线 | 3 步向导：选节点、影响评估、确认提交 | 写操作 |
| 主机维护 | 排空 → 停机 → 维护窗口倒计时 → 恢复验证的完整流程 | 写操作 |
| 任务中心 | 运维模式下：所有变更的审批、进度、步骤、日志；只读 / 回放模式下：前端模拟任务 | 审批 / 中止 / 取消 |
| 详情 / 配置抽屉 | 子页「概览」「配置变更」「变更历史」「操作」；配置变更覆盖 TiDB / TiKV / PD / TiFlash / TiCDC 参数 | 配置变更是写操作 |

本页**没有**滚动升级、按角色滚动重启、备份与恢复：它们在 [日常运维](go:ops) 页（同一套变更引擎、同一套审批与窗口规则，见 [日常运维帮助](help:ops)）。

### 本页用到的术语

| 术语 | 一句话解释 | 官方文档 |
|---|---|---|
| 实例 / 主机 | 实例 = 集群里的一个进程，如 `tikv-2`；主机 = 运行实例的机器（IP），一台主机可以跑多个实例 | [tiup 拓扑文件说明](https://docs.pingcap.com/zh/tidb/stable/tiup-cluster-topology-reference) |
| Region / Leader | Region 是 TiKV 里数据切分的基本单位，每个 Region 有多个副本，其中一个是 Leader，负责读写 | [TiDB 数据库的调度](https://docs.pingcap.com/zh/tidb/stable/tidb-scheduling) |
| Store | PD 对一个 TiKV 实例的称呼。下线过程是 Up → Offline → Tombstone；失联过久（超过 max-store-down-time）会变 Down | [TiDB 数据库的调度](https://docs.pingcap.com/zh/tidb/stable/tidb-scheduling) |
| evict-leader-scheduler | PD 的调度器，把某个 Store 上所有 Region 的 Leader 调度出去；重启 / 停止 TiKV 前先加上，之后移除 | [PD Control](https://docs.pingcap.com/zh/tidb/stable/pd-control) |
| store limit | PD 对每个 Store 每分钟添加 / 删除副本数量的上限，决定 Region 迁移快慢 | [PD Control](https://docs.pingcap.com/zh/tidb/stable/pd-control) |
| tiup / 中控机 | tiup 是 TiDB 的集群管理工具；中控机是运行平台与 tiup 的那台机器，所有命令都从它发出 | [tiup cluster 命令总览](https://docs.pingcap.com/zh/tidb/stable/tiup-component-cluster) |
| 拓扑 | tiup 保存在中控机上的集群定义（实例、端口、配置），`edit-config` 修改的就是它 | [tiup cluster edit-config](https://docs.pingcap.com/zh/tidb/stable/tiup-component-cluster-edit-config) |
| reload | 把拓扑里的配置发布到各主机并按顺序滚动重启实例 | [tiup cluster reload](https://docs.pingcap.com/zh/tidb/stable/tiup-component-cluster-reload) |
| SET CONFIG | 一条 SQL，在线修改 TiKV / PD 的配置，不重启 | [在线修改集群配置](https://docs.pingcap.com/zh/tidb/stable/dynamic-config) |
| 变更（CHG-xxxx） | 平台里一次写操作的完整记录，编号形如 `CHG-0007`，贯穿审批、执行、审计 | 平台概念 |
| 写操作开关 | **每个集群各自一个**的总闸，关闭时只能看不能改；开启需两名管理员确认 | 平台概念 |
| 当前集群 | 顶栏集群下拉里选中的集群。本页的实例、主机池、变更与任务中心都只属于它；提交抽屉顶部的「集群 X」标签就是变更将提交到的集群 | 平台概念 |
| 窗口 / 冻结期 | 窗口规则标注「不建议 / 禁止 / 推荐」的时间段；冻结期是更强的绝对禁止 | 平台概念 |
| 审批级数 / MFA | 需要几个不同的 approver 各批一次；MFA = 申请人提交时要输入的 6 位动态验证码 | 平台概念 |

占位符约定（下文代码块里的尖括号内容都要换成你自己的值）：

| 占位符 | 从哪里取值 | 示例 |
|---|---|---|
| `<集群名>` | 页面顶部状态条「集群 …」后面的名字（**当前所选集群**的 tiup 集群名）；或在中控机执行 `tiup cluster list` 看 Name 列。平台纳管多个集群时，切换集群后这里的值也跟着变 | `prod-tidb` |
| `<版本>` | 实例「详情 / 配置」抽屉顶部显示的版本；或 `tiup cluster display <集群名>` 输出开头的 Cluster version | `v8.5.2` |
| `<PD 地址>` | `tiup cluster display <集群名>` 里任一状态为 Up 的 PD 的 ID 列（host:2379） | `10.0.1.21:2379` |
| `<storeId>` | TiKV 实例「详情 / 配置」→「概览」里的「Store ID」 | `5` |
| `<host:port>` | 「节点实例」页该实例的「地址」列 | `10.0.2.12:20160` |
| `CHG-xxxx` | 提交成功后任务中心里显示的变更编号 | `CHG-0007` |

## 怎么用（按步骤）

### 第 0 步：先确认你在哪种模式

| 你看到的 | 模式 | 写操作是真的吗 |
|---|---|---|
| 顶部条写「回放数据」 | 回放模式（后端以 `--fixtures` 启动，不连任何集群） | 否：前端模拟，状态存在浏览器内存里，刷新即丢失 |
| 顶部条写「真实数据（只读）」，没有登录框 | 只读模式（后端未设置 `--data-dir`） | 否：同上，页面顶部明确写着「扩缩容 / 配置变更 / 主机维护等写操作仍是原型模拟，不会作用于集群」 |
| 登录框 + 右上角出现「环境（生产 / 预发 / 测试）· 写操作已开启或只读 · 用户名 · 角色」 | 运维模式（后端设置了 `--data-dir`） | 取决于执行器：sim = 校验、审批、令牌全部照常，但命令只是模拟输出，集群不变；direct / sudo = 真实执行 tiup / pd-ctl / SQL |

只读 / 回放模式下，各按钮的行为：

- 单实例操作：弹出抽屉展示「将执行的命令 / 前置检查 / 执行步骤」，按钮是「提交并执行（模拟）」；高风险操作要先在抽屉里输入「确认」。
- 扩容 / 缩容 / 主机维护：向导的最后一步按钮带「（模拟执行）」，另有「预约到低峰窗口…」（前端预约，不是服务端定时）。
- 主机池：「集群内主机」可看；「候选主机池」在真实数据只读模式下只显示一条提示「需要运维模式」；纯静态原型里则是模拟的主机池（预检、「自动修复」都是假的）。
- 配置变更：「当前」值在有真实数据时取自集群，但提交只是前端模拟。

> ⚠️ 只读 / 回放模式里点「提交并执行（模拟）」不会改动集群，但会在页面里改动内存中的节点状态（例如把某个实例显示为已停止），刷新页面后恢复。不要把模拟任务的「成功」当成集群已变更。

> ⚠️ **多集群：动手前先看顶栏。** 运维模式下平台可以纳管多个集群（见 [集群接入帮助](help:clusters)），本页的节点、主机池、变更、任务中心都是**当前所选集群**的（顶栏集群下拉；生产集群的下拉旁还有红色「生产环境」标签）。变更提交抽屉顶部有一个**「集群 X」标签**，写着这个变更将提交到哪个集群——**提交前先核对它**；切换集群前，先把手上的抽屉关掉（切换会整页刷新并丢弃未保存的内容）。不同集群的变更编号 `CHG-0001` 各自编号、会重复；不同集群的变更互不排队、可同时执行。

以下所有「公共流程」「操作步骤」「完整示例」都针对**运维模式**。

### 公共流程 A：提交一个变更（申请人）

所有写操作（重启、扩容、缩容、改配置、进入 / 结束维护……）最后都走同一个提交抽屉。

**前置条件**

- 已登录，右上角能看到环境标签（生产 / 预发 / 测试，是**当前集群**的环境）、「写操作已开启」和你的角色。显示「只读」时无法提交，悬停可看原因（见「写操作总闸」）。顶栏集群下拉选的就是你要操作的集群。
- 你的角色有该类变更的发起能力（见「谁能发起、谁来审批」）。
- 目标实例 / 主机没有被未结束的变更占用，所在主机不在维护中。

**步骤**

1. 在对应标签页选好对象与参数，点最后的提交类按钮（实例行的「重启」「停止」等；向导里的「提交扩容申请…」「提交缩容申请…」；维护表单的「评估并提交维护申请…」；配置预览里的「提交变更申请…」）。按钮灰色说明你没有该能力，悬停提示「当前账号没有「…」权限（需 DBA 角色）」。
2. 右侧弹出抽屉，先显示「正在由服务端规划并检查…」。规划只读：不落库、不执行任何命令，通常几秒完成。你会看到抽屉标题变成该变更的标题（如「重启 tikv-2」）。如果抽屉里只有一条红色错误（如「集群拓扑中没有实例 …」「计划时长不能超过 24 小时」），说明参数本身不合法，点「关闭」回去改。
3. 按下一节的判读表读完抽屉的每个区块。
4. 如果前置检查里有 ✖：按钮变成灰色的「存在阻断项」，而且「变更说明」「执行时间」等输入框都不会出现。点「取消」关闭抽屉，先处理阻断项再重新发起；⚠ 警告不阻止提交，但要读懂再继续。
5. 在「变更说明 / 工单号」写工单号和原因（平台不强制必填，但审批人与审计都靠它判断）。
6. 在「执行时间」选「审批通过后立即执行」或「定时执行…」。选后者会出现日期时间框，下面还有一排「推荐时间」按钮（形如「10-08 22:30 · 评分 70」），点一个会自动切成定时执行并回填时间，窗口检查随之刷新。时间敏感的变更一律选定时执行（原因见「变更窗口、冻结期与推荐时间」）。
7. 只有确实要在冻结期 / 禁止窗口内执行时才勾「紧急变更（可进入冻结期，审批更严，事后必须复盘）」。如果出现「申请人动态验证码（MFA）」输入框，填入你验证器里当前的 6 位码；没绑定会提示先到「权限与审计」→「我的账号」绑定。
8. 点「提交变更」。你会看到：抽屉关闭，弹出提示（「变更 CHG-xxxx 已提交，等待审批」「已排期」或「已开始执行」），页面自动跳到「任务中心」并展开这条变更（「延长维护窗口」例外，留在「主机维护」页）。
9. 提交失败时，错误会以红字显示在按钮上方，常见的有：「计划时间落在变更冻结期「…」内；确需执行请走紧急变更」「窗口规则拦截：…」「与已排期的变更 CHG-xxxx 在时间与资源上冲突」「计划执行时间已过」。按提示改时间或参数后再点「提交变更」。

**提交之后**：变更已创建并占用目标实例，但**在审批通过之前不会执行任何命令**（免审批的低风险变更除外，它们立即开始）。待审批时可以由申请人或 dba「取消」；关闭抽屉但没点「提交变更」则什么都没有发生。

#### 提交抽屉里每个区块怎么判读

| 区块 | 你会看到 | 怎么判读 / 怎么办 |
|---|---|---|
| 顶部一行 | 风险标签（低 / 中 / 高风险）、**「集群 X」**（悬停「本变更将提交到此集群」）、「prod 环境需 N 级审批」、「预计 N 分钟」、右侧「操作说明与后果 ↗」 | 「集群 X」确认这是你要动的集群，不对就关闭抽屉、切换集群再来；N = 0 表示免审批；预计分钟只是计划预估，不是实际耗时（缩容 TiKV 实际可能是数小时）；「操作说明与后果 ↗」在新标签页打开本帮助，不会丢失当前表单 |
| 黄色「当前不能提交：…」 | 写操作总闸没放行的原因 | 提交按钮是灰的。按原因找管理员处理，见「写操作总闸」 |
| 前置检查（服务端） | 每行以 ✔ / ⚠ / ✖ / ℹ 开头 | ✔ 满足；ℹ 提示信息；⚠ 有风险但允许，读完再决定；✖ 阻断，必须先解决（常见：「xxx 已被变更 CHG-xxxx 占用」「所在主机正在维护」「该组件只有这一个健康实例」） |
| 窗口检查 | 小字写明依据（「按当前时间（审批通过后立即执行）」或「按计划时间 …」）；每行 ✔ / ⚠ / ✖ | ⚠「落在不建议变更的窗口…」建议改期；✔「落在推荐窗口…」最好；✖「落在禁止变更窗口…」时按钮变成「窗口规则禁止」，改时间或勾「紧急变更」（降为 ⚠）。没有命中规则时显示「未命中任何窗口规则」 |
| 将执行的命令 | 按顺序列出命令 | 核对对象是否就是你要动的实例。这里是简化写法：pd-ctl 命令显示为 `pd-ctl …`，实际执行为 `tiup ctl:<版本> pd -u http://<PD 地址> …`；tiup 命令实际会追加 `-y` 跳过交互确认。以 `# 人工操作：` 开头的行不是命令，是需要人手做的事 |
| 执行步骤 | 编号列表，可带标签 | 「需人工确认」= 执行到这一步会停下等你；「不可中止」= 从这一步开始不能再中止。没有这两个标签的步骤可以随时中止 |
| 变更说明 / 工单号、执行时间、紧急变更、MFA | 输入项 | 见上面步骤 5–7 |

### 公共流程 B：审批一个变更（审批人）

**前置条件**：你是 approver；你不是该变更的申请人；你没批过它；你具备该风险等级的审批能力（中风险 approve.mid，高风险 approve.high）。申请人自己不能批。审批有效期 24 小时，过期自动变「已过期」。

1. 登录后进入「节点管理」→「任务中心」。标签上会显示「· N 待审批」，侧栏「变更排期」旁的角标也是待审批数量。
2. 页面顶部「⚠ 待你审批（N）」区域列出你能批的变更，每行有编号、标题、风险、「紧急」标签、申请人、创建时间、申请说明、「已批 x/y」。如果该变更没出现在这里，说明你不满足上面任一条件（请找符合条件的同事审批）。
3. 点「查看详情」（或点卡片标题展开），逐项核对：目标实例是不是对的；申请说明 / 工单是否匹配；前置检查里的 ⚠ 能否接受；「执行命令」是否只动了目标实例；步骤里有没有你不认识的操作；定时时间是否避开业务高峰。
4. 同意：点「批准」，右侧会打开确认面板，列出变更标题、风险、申请人、类型、环境 / 集群、目标实例和申请说明，核对后（可选填「审批意见」）再点「**确认批准**」才会提交。批准一旦提交立即生效，**也没有「撤销批准」**。你会看到提示「已批准 CHG-xxxx」，卡片上「审批 x/y」加一。需要多级时由不同的 approver 依次批准；达到级数后状态变为「排队中」（立即执行）或「已排期」（定时执行）。
5. 不同意：点「驳回」，在抽屉「驳回变更 · CHG-xxxx」里填「驳回原因（必填）」，点「确认驳回」。状态变「已驳回」，占用的实例立即释放，申请人要重新提交。

### 公共流程 C：跟踪进度、点人工确认、中止与取消

1. 进入「节点管理」→「任务中心」，用筛选「全部 / 待审批 / 排队 · 执行中 / 已结束」找到该变更，点标题展开。页面每 2–8 秒自动刷新。
2. 看卡片：进度条（已完成步骤 / 总步骤，包含等待步骤）；步骤图标 ✔ 完成、◔ 执行中、○ 等待、⏸ 人工确认、✖ 失败、↷ 跳过；步骤右侧的耗时与说明（如「状态 Offline，剩余 Region 128」）；底部「执行日志」（只显示最近约 20 行）。
3. 遇到 ⏸ 步骤：展开后步骤下方有黄框写着要你手工做什么（如把某个 TiDB 从负载均衡摘除；负载均衡类步骤的做法见「从负载均衡摘除 / 加回 TiDB 的人工确认步骤」）。按指引在负载均衡上做完，再点「我已完成，继续」（只有申请人或 dba 能点，其他人只看到「等待申请人 / DBA 确认」）。你会看到提示「已确认，继续执行」，步骤继续。12 小时没人确认，该步骤失败。
4. 想让变更不要执行：还没开始（待审批 / 排队中 / 已排期）点「取消」，抽屉里「取消原因（可选）」→「确认取消」；正在执行点「中止」，抽屉「中止执行 · CHG-xxxx」→「确认中止」，提示「已发出中止指令」。「中止」只对计划标记为可中止的变更有效，越过「不可中止」步骤后会提示「已越过不可逆步骤，不能中止」。
5. 终态为「成功 / 失败 / 已中止」。失败时红字「失败原因」和日志会说明卡在哪一步；平台不会自动重试，核对集群状态、处理好后重新提交一个新变更。紧急变更到终态后，申请人还要点「填写复盘」补写（「复盘内容（必填）」→「提交复盘」）。

## 通用机制（运维模式）

### 谁能发起、谁来审批

| 动作 | 需要的能力 | 哪些角色有 | 说明 |
|---|---|---|---|
| 单实例重启 / 停止 / 启动 / 驱逐 / 恢复 Leader | inst.op | sre、dba（「审」：可发起，按风险与环境走审批） | 也包括「日常运维」页的按角色滚动重启 |
| 扩容、缩容、主机池的增删改与预检 | scale | dba | 候选主机池的登记 / 预检本身不走审批，也不要求写操作总闸，但要有 scale 能力 |
| 配置变更 | config | dba | |
| 主机维护（进入 / 结束 / 延长 / 勾检查单） | maint | dba | |
| 批准 / 驳回 | approve.mid（中风险）/ approve.high（高风险） | approver | 申请人不能审批自己的变更；同一个人不能对同一变更重复审批；低风险没有审批 |
| 取消、中止、确认人工步骤 | 申请人本人，或任何 dba | | 取消 = 尚未开始执行的变更；中止 = 正在执行的变更 |
| 填写紧急变更复盘 | 只有申请人 | | |
| 查看实例 / 主机 / 主机池 / 变更列表 | 登录即可 | 所有角色 | 预览与推荐时间接口同样要求具备该变更类型的发起能力，否则 403 |

viewer、developer、auditor、admin 角色**不能**发起上述变更（admin 管理用户、平台设置与写操作开关，见 [权限与审计](help:security)）。一个用户在某环境下可以同时拥有多个角色，取其中最强的授权。

### 风险等级与审批级数

| 操作 | 风险等级 |
|---|---|
| 启动实例、恢复 Leader、延长维护窗口 | 低 |
| 重启实例、驱逐 Leader、扩容、配置变更、结束维护 | 中 |
| 停止实例、缩容、进入维护 | 高 |
| 配置变更里含「高危参数」 | 高（但目前会被阻断，见「已知限制与易混淆点」） |

默认审批策略（管理员可经「双人复核」修改，但有硬性下限）：

| 风险 | 测试 test | 预发 staging | 生产 prod |
|---|---|---|---|
| 低 | 免审批 | 免审批 | 免审批 |
| 中 | 免审批 | 1 级 | 1 级 |
| 高 | 1 级 | 2 级 | 2 级 + 申请人必须 MFA |

硬性下限（不可调低）：生产的高风险至少 2 级且必须 MFA；生产的中风险至少 1 级；预发的高风险至少 2 级。「级」只表示需要几个不同的 approver 各批一次，不区分第几级由谁批。免审批的变更会留痕（审计里有记录），提交后立即开始执行。

> ⚠️ 免审批不等于没有风险：测试环境的「重启」「扩容」「配置变更」提交后立刻执行，没有任何人确认。

### 紧急变更

提交抽屉里的「紧急变更」复选框。含义：

- 允许落在**冻结期**内（非紧急变更在冻结期内会被服务端拒绝创建）；
- 落在「禁止」类窗口时，检查项从 ✖ 阻断降级为 ⚠ 警告，允许提交；
- 预发 / 生产环境审批级数**至少 2 级**（即使风险是低或中）；测试环境没有紧急通道，按常规处理；
- 变更打上红色「紧急」标签，终态后若申请人没有填写，显示「待复盘」；复盘是事后提示，平台不会因为没写复盘而阻止后续操作。

> 💡 注意区分：主机维护的「紧急恢复」是维护流程里「跳过检查单与预检、直接启动实例」的一种结束方式，它不是「紧急变更」，不会提高或降低审批级数。

### 写操作总闸

提交与执行都要经过总闸，任何一项不满足都会拒绝（抽屉顶部显示原因，执行时则变更直接失败并写明「执行前检查未通过」）：

1. 服务器上不存在强制只读文件（默认 `/etc/tidb-ops/READONLY`；存在即平台强制只读，用于紧急熔断）；
2. **当前集群**的「写操作开关」已开启（每个集群各自一个）：在 [权限与审计](go:security) 的「写操作开关」页，开启需要**两名不同的管理员**先后确认（一人提议、另一人确认，提议 1 小时内有效）；关闭只需一名管理员，立即生效；
3. 已配置执行器（启动参数 `--exec`）；
4. 集群版本在支持矩阵内（v7.5.x / v8.1.x / v8.5.x），不在范围内时写操作降级为只读。

右上角状态条「写操作已开启 / 只读」悬停可看原因。

### 变更窗口、冻结期与推荐时间

提交抽屉里的「窗口检查」把「计划执行时间起，持续预计时长」与窗口规则做相交判断（规则按**服务器本地时区**解释；页面选择的时间按浏览器本地时区显示，两者时区不同时要自己换算）：

| 规则模式 | 命中后的行为 |
|---|---|
| 禁止（block） | ✖ 阻断，提交按钮变成「窗口规则禁止」；勾选「紧急变更」后降为 ⚠ 警告，可以提交 |
| 不建议（avoid） | ⚠ 警告，建议改期；不阻止提交 |
| 推荐（prefer） | ✔ 提示：整个变更落在推荐窗口内，或部分落在推荐窗口内 |

规则只作用于风险等级 / 变更种类匹配的变更（空 = 全部）。**默认规则**（管理员可在 [环境与设置](go:settings) 自定义，见 [环境与设置帮助](help:settings)；默认没有任何「禁止」规则）：

| 名称 | 时间 | 模式 | 适用风险 |
|---|---|---|---|
| 备份窗口 | 每天 01:30–04:00 | 不建议 | 中、高 |
| 业务高峰（上午） | 周一至周五 09:00–12:00 | 不建议 | 中、高 |
| 业务高峰（下午） | 周一至周五 14:00–18:00 | 不建议 | 中、高 |
| 夜间低峰 | 每天 22:00–06:00（跨午夜，按起点所在日算星期） | 推荐 | 全部 |

**冻结期**是比窗口规则更强的绝对阻断，在 [变更排期](go:schedule) 页设置（需要 settings.edit 权限）：落入冻结期的非紧急变更，创建时直接报错「计划时间落在变更冻结期「…」内；确需执行请走紧急变更」。

**推荐时间**：抽屉里「执行时间」下方的一排按钮，格式「月-日 时:分 · 评分 N」，悬停显示理由与预计结束时间。算法：在未来 7 天内每 30 分钟取一个起点（不早于当前时间 +10 分钟）；排除落在冻结期、命中「禁止」规则、与已排期 / 执行中的变更在同一资源上时间重叠的起点；命中推荐窗口加分、命中「不建议」窗口扣分、越晚越低分；同一天相隔不足 2 小时的只留分高的；最多 5 个。

> ⚠️ 窗口与冻结期**只在创建变更时检查一次**。需要审批的「立即执行」变更，实际开始时间是审批通过的那一刻，如果审批拖到了不建议甚至禁止的时段，平台不会再次拦截。对时间敏感的变更请使用「定时执行」。

> ⚠️ 窗口检查使用的是计划预估时长（单实例重启 / 停止约 5 分钟，扩容 10 + 5×主机数分钟，缩容 TiKV 约 40 分钟起，配置变更 5 分钟或 reload 时 3×实例数分钟，进入维护 = 计划分钟数 + 10 分钟，结束维护 15 分钟）。缩容 TiKV 的 Region 迁出实际可能持续数小时，窗口检查和排期冲突检查都不会覆盖这段时间。

### 定时执行

选「定时执行…」并指定时间：

- 时间不能早于当前时间 1 分钟之前；
- 创建时检查冻结期、窗口规则、以及「与已排期 / 执行中变更在同一实例或主机、同一时间窗口内冲突」（冲突直接拒绝：「与已排期的变更 CHG-xxxx 在时间与资源上冲突」）；
- 审批有效期 24 小时；若计划时间晚于创建后 24 小时，有效期延长到计划时间。审批没在有效期内完成 → 变更自动变为「已过期」；
- 审批全部通过后，如果计划时间在未来 → 「已排期」，到点（调度每 2 秒检查）自动转为执行；如果审批通过时计划时间已过 → 直接执行；
- 「已排期」的变更可以被申请人 / DBA 取消；占用的实例在取消前一直被占用。

### 执行引擎的规则

- **同一集群内串行**：同一个集群里同一时刻只执行一个变更（跨所有类型、所有实例）。其他已批准的变更显示「排队中」，等前一个结束。**不同集群之间互不串行、可以同时执行**。TiKV 缩容的等待步骤最长 48 小时、备份最长 12 小时，期间所有变更都排队，请安排好顺序。
- **资源占用**：待审批 / 排队中 / 已排期 / 执行中的变更占用它涉及的实例；其他变更对同一实例的规划会得到阻断「xxx 已被变更 CHG-xxxx 占用」，实例行的按钮会被禁用并显示「变更 CHG-xxxx（状态）」可点击跳转。取消待审批变更可以立即释放。
- **主机在维护中**：该主机上所有实例的重启 / 停止 / 驱逐 / 配置变更 / 缩容都被阻断（启动例外：服务端允许，「启动」按钮也可点；1.6.4 前该按钮会置灰，与服务端不一致）；扩容也不能选正在维护的主机。
- **每条命令**：白名单内的固定模板，不经过 shell，参数逐项校验，配置值先归一化；每条写命令携带 15 分钟有效、绑定命令内容的审批令牌；执行日志里以 `$ 命令` 记录；命令输出实时进入日志，输出里出现的运维账号密码会被替换为 `***`。
- **超时（命令级）**：重启 / 停止 / 启动 10 分钟；扩缩容 1 小时；prune 5 分钟；edit-config 2 分钟；reload 30 分钟；pd-ctl 命令 30 秒；SQL（SET CONFIG / SET GLOBAL）10 秒；`tiup cluster check` 120 秒；升级 3 小时；备份 / 恢复 12 小时。超时即视为该步骤失败。
- **等待步骤**：执行完命令后再轮询一个条件直到满足或超时，超时即失败。条件有：Leader 数归零（读 PD store 的 `leader_count`）、Store 状态到达 Tombstone、实例在 `tiup cluster display` 里变为 Up、无 down-peer 与 pending-peer。
- **人工确认步骤**：典型是「从负载均衡摘除 / 加回 TiDB」，操作见「公共流程 C」；这类步骤什么时候出现、点「我已完成，继续」到底意味着什么，见「区域与参数说明」里的「从负载均衡摘除 / 加回 TiDB 的人工确认步骤」。
- **平台重启**：执行中的变更会被标记为失败（原因「平台在执行过程中重启，变更被中断：请核对集群状态后重新规划」）；正在「排空」的主机维护记录被标记为「已取消」。重启后必须用 `tiup cluster display` 与 pd-ctl 核对残留的驱逐调度、被临时调大的 `max-store-down-time` 等中间状态。

### 中止、取消、回滚的含义

- **取消**：只用于尚未开始执行的变更（待审批 / 排队中 / 已排期）；执行中的变更用「中止」。
- **中止**：只对计划标记为「可中止」的变更有效：单实例重启、停止、缩容、进入维护。中止会取消正在运行的命令（终止 tiup 子进程），然后尽力执行回滚命令。
- **回滚**不是「撤销整个变更」：它是计划里预先登记的一小组恢复命令，在失败或中止时按**倒序**逐条尽力执行（单条失败只记警告，整体最多 10 分钟），然后变更进入「失败」或「已中止」。各操作的回滚内容见各操作的步骤表；没有回滚命令的操作（如扩容）失败后需要人工处理。
- 平台不会自动重试，也没有「撤销已成功的变更」按钮：要改回去就提交一个反向变更。

### 变更状态

| 状态 | 含义 |
|---|---|
| 待审批 | 已创建，等待所需级数的审批；占用目标实例；超过有效期自动变「已过期」 |
| 排队中 | 审批完成（或免审批），等待执行；有变更正在执行时在此排队 |
| 已排期 | 审批完成，等待计划时间 |
| 执行中 | 正在逐步骤执行 |
| 成功 / 失败 / 已中止 | 终态 |
| 已驳回 / 已取消 / 已过期 | 未执行就结束；释放占用 |

变更的创建、审批、命令、终态都会写入审计日志，并可按设置推送到通知渠道（见 [环境与设置帮助](help:settings)）。侧栏「节点管理」旁的角标显示运行中 / 排队中变更数。

### 命令类别说明

步骤表的「命令类别」列写的是执行器白名单里的命令种类与它的风险分类（读 / 写·低 / 写·中 / 写·高）。这个分类是执行器内部的命令风险，**不等同**于变更的风险等级。

| 类别 | 实际命令 |
|---|---|
| 读 | `tiup cluster display`、`tiup cluster check`、pd-ctl 的 `store` / `member` / `scheduler show` / `region check`、`tiup cdc cli capture list`、`tiup br log status` |
| 写·低 | `tiup cluster start -N` |
| 写·中 | `tiup cluster restart`、`scale-out`、`prune`、`edit-config`、`reload`；pd-ctl 的 `config set`、`scheduler add / remove evict-leader-scheduler`、`store limit all`、`member leader transfer`；SQL `SET CONFIG` / `SET GLOBAL`；BR 全量备份、日志备份启停 |
| 写·高 | `tiup cluster stop`、`scale-in`、`upgrade`；BR 全量恢复 |

pd-ctl 都是 `tiup ctl:<版本> pd -u http://<PD 地址>` 的形式，版本与 PD 地址只来自拓扑，不来自请求。SQL 通过 `mysql` 客户端用「运维账号」执行（该账号只应有 SET GLOBAL / SET CONFIG 权限，密码走环境变量，不进命令行与日志）。

> ⚠️ **多集群 + sudo 执行器**：SET CONFIG / SET GLOBAL 连接的 TiDB 地址取自执行器策略文件（`/etc/tidb-ops/exec.json`）。多个集群共用这一份文件时，必须在其 `perCluster` 里为**每个集群**配置各自的 `mysqlHost` / `mysqlPort` / `alertURL`，否则在非主集群提交的配置变更可能被打到主集群（平台发现不了漏配）。配置方法与示例见 [集群接入帮助](help:clusters) 第四节的警告框。

### 节点详情抽屉

点实例行的「详情 / 配置」打开，顶部显示实例状态、地址、可用区与版本，有 4 个子页：

- **概览**：实例信息（地址、状态地址、拓扑标签 zone / rack / host、部署 / 数据 / 日志目录、TiKV 的 Store ID）、资源使用、关联的诊断发现；底部有「配置变更 →」「查看所在主机 →」。真实数据模式下进程 PID、已运行时长显示「—（未采集）」，日志目录若是按 tiup 默认约定推断的会标「（推断）」。
- **配置变更**：见「配置变更」一节。
- **变更历史**：列出服务端里该实例（或同角色「应用到全部实例」）的配置变更，含时间、申请人、状态、风险、每项的「原值 → 新值」，点变更编号跳到任务中心。运维模式下**没有**「回滚到旧值」按钮——要改回去就再提交一次把值改回去的变更。
- **操作**：与行内按钮相同的实例操作，加「缩容 / 下线」，以及常用命令（`tiup cluster display <集群名> -N <host:port>`、`tiup cluster exec … tail` 查看日志）。

### 配置变更

适用：在线调整 TiKV / PD / TiDB / TiFlash / TiCDC 的参数。能发起：dba（config 能力）。风险：中（配置变更含「高危参数」时为高，但会被阻断）。

#### 操作：修改一个或多个配置项

**前置条件**：运维模式、写操作开关已开启；你是 dba；目标实例所在主机不在维护中，实例不是「扩容中 / 下线中」，没有变更占用；你清楚要改哪一项、为什么改。「需 reload」类项会滚动重启实例，务必选在低峰。

1. 在「节点实例」找到目标实例，点「详情 / 配置」，在抽屉的子页里点「配置变更」。你会看到先出现「正在读取集群里的配置当前值」的占位骨架，几秒后每个配置项显示「默认 X · 当前 Y」。读取失败时顶部黄框写「读取配置当前值失败：…」，可点「重新读取」；读不到的项显示「—（未采集）」，仍可修改，但提交时「原值」会留空。
2. 找到要改的配置项。每行有：名称、配置键、标签（「在线生效」或「需 reload」；「集群级」或「实例级」；「配置漂移」）、输入框（布尔与枚举是下拉）、说明。「在线生效」= 不重启；「需 reload」= 提交后会滚动重启所选范围内的每个实例。
3. 在输入框改成新值。填错时行下面立即出现红色 ✖（必须改）或黄色 ⚠（风险提示）；规则见下表。改回原值则该项不计入变更。
4. 如果行上有红色「配置漂移」，说明同角色各实例取值不一致（`16GiB` 与 `16GB` 视为一致）。点旁边的「对齐 →」会把输入框填成多数派取值；是否对齐由你决定。
5. 如果改了实例级项，底部会出现「应用范围」单选：「仅 <实例>」或「全部 N 个 <角色>」。默认「仅 <实例>」，改一个实例会让各实例取值不一致（出现「配置漂移」）；集群级项（TiDB 系统变量、PD 集群级参数）不受影响，始终是集群范围。
6. 点底部「预览变更（N）」（N 是改动项数；想全部放弃点「重置」）。你会看到「变更预览」：变更表（配置项、原值 → 新值、生效方式、校验结果）、「风险与影响」、「将执行的命令」。任何一行 ✖，或「风险与影响」里有 ✖，下方只显示「存在错误 / 阻断项，请返回修改」，点「← 返回修改」。
7. 读「风险与影响」：✔「全部为在线生效项，无需重启实例」表示不重启；⚠「需滚动 reload N 个 TiKV，逐个重启（TiKV 先驱逐 Leader），每个约 2–3 分钟」表示会重启，确认时段与影响。
8. 勾选「我已确认影响」（含重启时文字为「我已确认影响（含滚动重启）」），点「提交变更申请…」。进入「公共流程 A」的提交抽屉：服务端会重新规划，以服务端的检查、命令、步骤为准（前端预览与服务端不一致时听服务端的）。
9. 审批与执行见「公共流程 B / C」。完成后：重新打开该实例的「配置变更」，「当前」应显示新值（平台没有在变更后自动回读校验，请以这次重新读取为准）；「变更历史」里能看到这条变更。

**执行后果与撤销**

- 在线生效项：不重启，改动立即生效；同时写入 tiup 拓扑，避免之后 reload / 升级时被旧配置覆盖。
- 「需 reload」项：写入拓扑后滚动重启（TiKV 每个先驱逐 Leader，约 2–3 分钟 / 个，全部 TiKV 需数十分钟），期间有短暂抖动。这一步不可中止。
- 没有一键回滚。想改回去：再提交一次把值改回原值的变更。
- 失败时的自动回滚只把**拓扑**恢复成变更前的版本，**不会**撤销已经通过 `SET CONFIG` / `SET GLOBAL` / pd-ctl 在线生效的值，也不会重新 reload。例如写入拓扑那一步失败：运行中的 TiKV 已是新值，拓扑却是旧值，下次 reload 会被改回旧值，需要人工决定以哪个为准。
- 去哪看进度：「任务中心」。失败怎么办：见「公共流程 C」第 5 步；先用下面「验证」里的命令核对实际值。

**验证**：用 `SHOW CONFIG WHERE type = 'tikv' AND name = 'raftstore.store-pool-size';`（把 type、name 换成你改的项）查看各实例当前值（[SHOW CONFIG](https://docs.pingcap.com/zh/tidb/stable/sql-statement-show-config)），或查询 `INFORMATION_SCHEMA.CLUSTER_CONFIG`（列 TYPE / INSTANCE / KEY / VALUE，见 [CLUSTER_CONFIG](https://docs.pingcap.com/zh/tidb/stable/information-schema-cluster-config)）；拓扑里的值可在中控机的 `~/.tiup/storage/cluster/clusters/<集群名>/meta.yaml` 里搜索配置键。

客户端校验（填错立即在行下面显示 ✖ 或 ⚠；✖ 会阻止提交）：

| 类型 | 规则 |
|---|---|
| 整数 | 必须是整数，且在该项的取值范围内 |
| 容量 | 形如 `16GB`、`512MB`（单位 KB / MB / GB / TB，大小写不限） |
| 时长 | 形如 `30m`、`2h`、`90s` |
| 布尔 | ON 或 OFF |
| 枚举 | 只能是列出的取值 |
| 特例 | `replication.max-replicas` 大于 TiKV 数 → ✖；为偶数 → ⚠；与当前值不同 → ⚠ 会触发全量补副本；`raftstore.store-pool-size` > 5 → ⚠；`schedule.max-store-down-time` < 10 分钟 → ⚠ 过短、> 180 分钟 → ⚠ 过长；`schedule.region-schedule-limit` > 4096 → ⚠；`tidb_distsql_scan_concurrency` > 64 → ⚠；日志级别 debug → ⚠ |

服务端再做一遍规划与校验（以服务端为准）：配置项必须在白名单目录内；值经「归一化」（容量统一为大写单位如 `12GB`；时长统一为最简整单位如 `90m`；布尔为 ON / OFF；整数不能带符号与小数点），只允许字母、数字、`.`、`_`、`-`，其余一律拒绝；变更涉及的实例若处于「扩容中 / 下线中」或所在主机维护中会被阻断。前后端有细微差异：前端的时长不接受 `1h30m` 这样的组合，服务端接受；前端接受 `500ms`，服务端拒绝；前端要求 Block Cache ≥ 1GB，服务端没有这一下限。拿不准时按「纯整数 + 单一单位」（如 `90m`、`12GB`）填写。

提交后服务端按配置项类型决定执行什么：

| 配置项类型 | 执行 | 是否写入 tiup 拓扑 | 是否重启 |
|---|---|---|---|
| TiDB 系统变量（`tidb_*`） | `SET GLOBAL <变量> = <值>`（容量换算成字节），集群范围 | 否 | 否 |
| PD 集群级参数（`schedule.*`、`replication.*`） | `pd-ctl config set <短键> <值>`（如 `max-store-down-time`） | 否 | 否 |
| 其他「在线」项（TiKV 的在线项） | 仅此实例：`SET CONFIG "<host:状态端口>" 配置键 = 值`；全部实例：`SET CONFIG tikv 配置键 = 值` | 是（`edit-config`） | 否 |
| 「需 reload」项 | 无在线下发 | 是 | 是：`tiup cluster reload` 滚动重启（仅此实例用 `-N`，全部实例用 `-R <角色>`） |

> ⚠️ 全部实例范围写入的是拓扑里 `server_configs.<角色>`；如果某个实例在拓扑里有自己单独的覆盖值，按 tiup 的规则实例自己的值优先，改动对它不生效（以真实集群联调为准）。「配置漂移」提示正是为了发现这种情况。官方也说明：TiKV 在线改动会写入该实例的配置文件，但仍需同步修改 tiup 拓扑，否则之后的升级或 reload 会覆盖在线修改（[在线修改集群配置](https://docs.pingcap.com/zh/tidb/stable/dynamic-config)）。

配置项目录（可变更的全部项；该目录同时是服务端白名单，目录之外的任何配置项都无法通过平台修改）。「默认」是平台内置的展示值，**不一定等于你集群版本的实际默认值**，以每行的「当前」为准（见「已知限制与易混淆点」）。各参数含义见官方 [TiKV 配置文件](https://docs.pingcap.com/zh/tidb/stable/tikv-configuration-file)、[PD 配置文件](https://docs.pingcap.com/zh/tidb/stable/pd-configuration-file)、[TiDB 配置文件](https://docs.pingcap.com/zh/tidb/stable/tidb-configuration-file)、[TiDB 系统变量](https://docs.pingcap.com/zh/tidb/stable/system-variables)。

### 单实例操作

适用于「节点实例」行内按钮与抽屉「操作」页。能发起：sre、dba（inst.op，审批按风险与环境）。表单本身没有字段，提交抽屉里只有通用的「变更说明 / 执行时间 / 紧急变更」。

各操作的前置检查（服务端；✖ 阻断，⚠ 警告）：

| 操作 | 阻断（✖） | 警告 / 提示 |
|---|---|---|
| 重启 | 该组件只有这一个健康实例；实例处于扩容中 / 下线中；所在主机维护中 | TiKV：其余健康 TiKV 少于 2 个 ⚠；TiKV 重启前先驱逐 Leader，抖动通常为秒级 ✔；PD Leader 重启会触发重新选举 ⚠；TiDB 约 N 个连接会断开，建议先从负载均衡摘除 ⚠ |
| 停止 | 该组件只有这一个健康实例；TiKV：停止后其余健康 TiKV 少于 max-replicas（默认 3）；PD：停止后失去多数派；同上的状态 / 维护阻断 | TiKV：PD 会在 max-store-down-time（默认 30 分钟）后判定该 Store Down 并开始补副本，计划内停机请在此之前启动 ⚠；TiDB 约 N 个连接立即中断 ⚠ |
| 启动 | 实例处于扩容中 / 下线中 | ✔ 会自动重新加入集群；TiKV 逐步恢复 Leader / Region 均衡 |
| 驱逐 Leader | 非 TiKV 不支持；缺少 Store ID | ✔ 通过 TransferLeader 迁移，不涉及数据拷贝；⚠ N 个 Leader 将迁到其余 TiKV，读写压力随之转移 |
| 恢复 Leader | 非 TiKV 不支持 | ✔ PD 会逐步把 Leader 均衡回该 Store |

> ⚠️ 服务端要求「停止 / 维护一个 TiKV 之后，仍有至少 max-replicas 个健康 TiKV」，所以 3 个 TiKV、3 副本的集群无法用平台停止或维护其中任何一个（至少需要 4 个 TiKV）。这比「保持 Raft 多数派」更严格；回放模式的前端模拟用的是较宽松的判定。

官方对这些命令的说明：`tiup cluster restart` 重启期间服务会有一段时间不可用（[restart](https://docs.pingcap.com/zh/tidb/stable/tiup-component-cluster-restart)）；`tiup cluster stop` 停掉核心服务后集群无法提供服务（[stop](https://docs.pingcap.com/zh/tidb/stable/tiup-component-cluster-stop)）；[start](https://docs.pingcap.com/zh/tidb/stable/tiup-component-cluster-start)。平台对 TiKV 额外先驱逐 Leader 以降低抖动；对 TiDB / PD / TiFlash / TiCDC 不做额外处理。

#### 操作：重启一个实例

**前置条件**：sre / dba；写操作开关已开启；实例状态为「运行中」或「告警」，没有「变更 CHG-…」「主机维护中」标签；同组件还有其他健康实例；重启 TiDB 前已把它从负载均衡摘除（平台不会替你摘）；选在低峰。

1. 进入「节点管理」→「节点实例」，用角色筛选或搜索框找到实例，点该行「重启」。按钮灰色就悬停看原因。你会看到右侧抽屉「正在由服务端规划并检查…」，随后标题变为「重启 <实例名>」，显示「中风险」。
2. 读前置检查（见「公共流程 A」判读表）。TiKV 应有 ✔「重启前先驱逐 Leader…」和 ✔「其余 N 个 TiKV 健康…」；出现 ⚠「其他健康 TiKV 少于 2 个」先停手评估；出现 ✖ 就关闭抽屉先处理。
3. 在「将执行的命令」确认只有这个实例（TiKV 为驱逐 Leader、重启、移除驱逐调度三条），在「窗口检查」确认不在业务高峰。
4. 填「变更说明 / 工单号」、选执行时间，点「提交变更」。你会看到提示并跳到任务中心。预发 / 生产需 1 级审批，测试环境免审批立即执行。
5. 审批通过后执行（公共流程 B / C）：TiKV 依次「驱逐 Leader」（日志 `leader_count=…` 降到 0）→「重启实例」（日志先是 tiup 输出，再反复「等待实例 Up：状态 …」直到 Up）→「移除驱逐调度，Leader 回迁」。其他角色只有「重启实例」一步。
6. 完成后卡片显示「成功」，实例行回到「运行中」。验证见示例 1。

**执行后果**：TiKV 先迁 Leader，业务抖动通常秒级；PD Leader 重启触发选举，TSO 秒级不可用；TiDB 重启立即断开其全部连接。重启本身没有「撤销」；执行中可以「中止」，但中止会终止 tiup 进程，实例可能停在已停止或半重启状态，回滚只移除驱逐调度，所以**中止或失败后必须自己核对实例状态**（`tiup cluster display <集群名>`），必要时用「启动」把它拉起。

#### 操作：停止一个实例

**前置条件**：同「重启」，另外：确认停止后集群仍满足上表的 ✖ 条件；TiKV 要在 max-store-down-time（默认 30 分钟）内重新启动，否则 PD 开始补副本；高风险，生产需 2 级审批 + 申请人 MFA。

1. 在「节点实例」点该行「停止」。抽屉标题「停止 <实例名>」，显示「高风险」，「prod 环境需 2 级审批」。
2. 读前置检查：TiKV 必有 ⚠「PD 在 max-store-down-time（30 分钟）后会把该 Store 判为 Down…」；✖「停止后健康 TiKV 少于 N 个」表示不满足 max-replicas，不能停。
3. 填说明与执行时间，生产环境填「申请人动态验证码（MFA）」，点「提交变更」。
4. 审批通过后执行：TiKV 先「驱逐 Leader」再「停止实例」；其他角色只有「停止实例」。**「停止实例」之后驱逐调度会保留**，直到你「启动」该实例（启动时会自动移除遗留的驱逐调度）。
5. 完成后实例行显示「已停止」，行内按钮变成「启动」。

**后果与撤销**：用「启动」恢复；停止期间该实例上的服务不可用。中止 / 失败后的核对要求同「重启」。

#### 操作：启动一个已停止的实例

**前置条件**：实例状态「已停止」；低风险，所有环境免审批，提交后立即执行。

1. 在「节点实例」点已停止实例行的「启动」。抽屉标题「启动 <实例名>」，显示「低风险」。
2. 读检查：应只有 ✔「启动后会自动重新加入集群…」。点「提交变更」。
3. 执行：`tiup cluster start <集群名> -N <host:port>` → 等待实例 Up（最长 10 分钟）；TiKV 额外尝试移除遗留的驱逐调度（失败忽略）。
4. 完成后实例行变「运行中」，TiKV 的 Leader 数在几分钟内逐步回升。启动没有回滚。

#### 操作：驱逐 / 恢复一个 TiKV 的 Leader

**用途**：只想把某个 TiKV 上的 Leader 临时迁走（例如排查、人工维护前），而不重启它。驱逐是中风险，恢复是低风险（免审批）。

1. 在「节点实例」找到 TiKV 实例行（状态未停止），点「驱逐 Leader」。抽屉标题「驱逐 <实例名> 的 Leader」，检查里有 ⚠「N 个 Leader 将迁到其余 TiKV，其读写压力随之转移，请确认剩余节点余量」。
2. 提交并（审批后）执行：`pd-ctl scheduler add evict-leader-scheduler <storeId>`，等 `leader_count` 归零（最长 10 分钟）。完成后用 `tiup ctl:<版本> pd -u http://<PD 地址> scheduler show` 确认列表里有 `evict-leader-scheduler`（运维模式下实例行**不会**出现「Leader 已驱逐」标签，平台不读取驱逐状态）。
3. 用完要恢复：点该行「恢复 Leader」→ 抽屉「恢复 <实例名> 的 Leader 调度」→「提交变更」。执行 `pd-ctl scheduler remove evict-leader-scheduler-<storeId>`，PD 逐步把 Leader 均衡回来。

**后果**：驱逐期间其余 TiKV 承担更多读写；**忘记恢复**会让该 Store 长期没有 Leader。失败时回滚 = 移除驱逐调度。

各操作的步骤明细（服务端）：

**重启 TiKV**（中风险，预计 5 分钟，可中止）

| 步骤 | 做什么 | 命令类别 | 失败时怎么办 | 能否回滚 |
|---|---|---|---|---|
| 驱逐 Leader | 给该 Store 加驱逐调度，等待 `leader_count` 归零（最长 10 分钟，5 秒轮询） | 写·中 `pd-ctl scheduler add evict-leader-scheduler <storeId>` | 变更失败；自动执行回滚 | 是：移除该驱逐调度 |
| 重启实例 | `tiup cluster restart <集群名> -N <host:port> -y`，再等待实例在 display 里 Up（最长 10 分钟） | 写·中 | 变更失败；回滚只移除驱逐调度，**不会**帮你启动实例，需人工核对 | 部分 |
| 移除驱逐调度，Leader 回迁 | `pd-ctl scheduler remove evict-leader-scheduler-<storeId>` | 写·中 | 忽略失败（日志里记 ⚠，变更仍算成功）；若残留调度需手工移除 | — |

重启 PD / TiDB / TiFlash / TiCDC：只有「重启实例」一步（命令同上，等待 Up），没有驱逐 Leader，也没有回滚。TiDB 重启会断开该节点的连接，**不会**自动摘除负载均衡。

**停止 TiKV**（高风险，预计 5 分钟，可中止）：「驱逐 Leader」（同上，可回滚）→「停止实例」`tiup cluster stop <集群名> -N <host:port> -y`（写·高，失败则变更失败并回滚驱逐调度）。其他角色只有「停止实例」一步。

**启动**（低风险，免审批）：`tiup cluster start <集群名> -N <host:port>`（不带 `-y`），等待 Up（最长 10 分钟）；TiKV 额外尝试移除遗留驱逐调度。无回滚。

**驱逐 Leader**（中风险）：`pd-ctl scheduler add evict-leader-scheduler <storeId>`，等待 Leader 迁出（最长 10 分钟）；失败回滚 = 移除该调度。**恢复 Leader**（低风险）：`pd-ctl scheduler remove evict-leader-scheduler-<storeId>`，无等待、无回滚。

#### 候选主机池（仅运维模式）

候选主机 = 已准备好但**尚未加入集群**的机器。登记在平台的主机池文件里（主集群是 `<data-dir>/hostpool.json`，其他集群是 `<data-dir>/clusters/<集群 id>/hostpool.json`；`<data-dir>` 是平台启动参数 `--data-dir` 指定的数据目录，`<集群 id>` 见 [集群接入帮助](help:clusters)；**每个集群各自一份主机池**，在 A 集群登记的候选主机在 B 集群看不到；每个集群最多 500 台），为扩容向导提供候选，并保存最近一次预检结果。读取列表登录即可；新增 / 编辑 / 删除 / 预检需要 scale 能力（dba）；这些操作**不走审批、也不受写操作总闸限制**，但预检需要已配置执行器。

##### 操作：新增（或编辑）一台候选主机

**前置条件**：你是 dba；知道它的 IPv4、计划放哪个可用区；机器已装好操作系统，并能被中控机 SSH 免密登录（预检与扩容时 tiup 要连它；平台命令不带 `--user` 参数，SSH 用户以你的 tiup 部署为准）。

表单字段：

| 字段 | 含义 | 可选值 / 默认 | 校验与填错后果 |
|---|---|---|---|
| 主机 IP（IPv4） | 候选主机地址 | 规范写法的 IPv4，如 `10.0.2.20`（编辑时不可改） | 前端提示「IP 格式不正确」；服务端拒绝前导零、IPv6、0.0.0.0 / 回环 / 组播 / 广播；已在集群拓扑里 →「已在集群拓扑里，不能加入候选主机池」；已在池里 →「已在候选主机池里」 |
| 可用区 (zone) | 写入新 TiKV 的 zone 标签 | 下拉为拓扑里已有的 zone，可选「其他（手填）…」；新增时默认第一个已有 zone | 字母、数字、`_` `.` `-`，不超过 32 字符；可留空，但**扩容 TiKV 时必须有 zone**，否则规划报错「TiKV 扩容需要指定主机的可用区」 |
| 机架 (rack) | 写入 rack 标签 | 可空 | 同上；留空时扩容 YAML 里用 `r00` |
| 备注 | 备注 | 可空 | 不超过 200 字符，不能含换行等控制字符 |

1. 进入「节点管理」→「主机池」，在「候选主机池」卡片点右上角「＋ 新增候选主机」（扩容向导第 2 步里也有同名按钮）。你会看到抽屉「新增候选主机」。
2. 按上表填「主机 IP（IPv4）」「可用区 (zone)」「机架 (rack)」「备注」。可用区下拉里选已有的 zone，或选「其他（手填）…」后在下面输入。
3. 点「添加到候选主机池」（编辑时是「保存」）。你会看到抽屉关闭、提示「<IP> 已加入候选主机池」（或「<IP> 已保存」），列表出现该行，「最近预检」为「未预检」。表单下方红字报错时按提示改；报「冲突」类错误后页面会自动刷新列表。
4. 要改 zone / rack / 备注：点该行「编辑」，抽屉「编辑候选主机 <IP>」，改完点「保存」。IP 不能改，要换 IP 就删除后重新添加。

**后果**：只是在平台里登记，不会对该主机做任何操作。

##### 操作：对候选主机做预检

**前置条件**：dba；执行器已配置（否则报「服务端未配置执行器」）；已知这台主机计划承担的角色。预检**只读**：由中控机运行 `tiup cluster check <集群名> <只含这台主机的最小拓扑文件> --cluster`，不修改主机、不安装任何东西。

1. 在「候选主机池」该行点「预检」（已预检过的是「重新预检」）。你会看到抽屉「预检 <IP>」。
2. 在「目标角色」下拉选这台主机将承担的角色（TiKV / TiDB / PD / TiFlash / TiCDC）。不同角色检查的端口与目录不同，选错会让端口 / 目录类检查项不适用；默认取上次预检的角色，否则按备注猜（备注含 TiFlash / TiDB 则猜对应角色，否则 TiKV），不要想当然，必须确认。
3. 点「开始预检」。抽屉关闭，该行「最近预检」列显示「正在预检（约 1–2 分钟）…」和角色。页面最长等待 3 分钟（执行器单次 120 秒超时）。
4. 完成后页面出现提示框：「<IP> 预检完成（TiKV）：x 项失败 / y 项警告 / z 项通过。点「查看检查项」查看详情与修复命令」，该行显示「预检通过」或「通过（N 项警告）」或「N 项失败」及时间。
5. 点「查看检查项」。抽屉「预检结果 · <IP>」按「失败（N）」「警告（N）」分组展示，「通过（N）」默认折叠。每项显示检查名、说明，以及（有的话）修复命令和「复制修复命令」。
6. 对失败 / 警告项，点「复制修复命令」（或「复制全部修复命令」），**在目标主机上以 root 执行**，然后回到该行点「重新预检」。直到没有 ✖ 失败项。
7. 预检失败（而不是检查项失败）时：提示框写「<IP> 预检失败（命令没有跑起来）：…」「（服务端未配置执行器）」。tiup 没能启动 / 没有该主机的检查行时报「预检执行失败 / 预检没有返回该主机的检查结果」；tiup 跑了但失败（如 SSH 连不上、输出里没有检查表），会被记为一项失败的「tiup cluster check（预检执行）」并带最后几行输出——先排查 SSH 免密、`tiup` 版本，再重试。

结果含义：

| tiup 结果 | 平台显示 | 含义 |
|---|---|---|
| Pass | ✔ 通过 | 该项满足要求 |
| Warn | ⚠ 警告 | 不推荐但不致命，不阻止扩容 |
| Fail | ✖ 失败 | 不满足要求，扩容大概率失败或埋下隐患 |

同一检查项在该主机上有多行时取最严重的结果。检查项包括：操作系统版本、CPU 核数、内存容量、Swap、透明大页（THP）、时间同步（chrony / ntp）、时区、SELinux、文件句柄 / 栈 ulimit、数据盘 nodelalloc / noatime、内核参数（sysctl）、网络、必需命令、系统服务（irqbalance 等）、CPU 调频、epoll 独占唤醒、磁盘 IO 性能（fio）、目录权限、服务端口未占用（逐项含义见官方 [tiup cluster check](https://docs.pingcap.com/zh/tidb/stable/tiup-component-cluster-check) 与 [部署前环境检查](https://docs.pingcap.com/zh/tidb/stable/check-before-deployment)）。

对失败 / 警告项，平台会按检查项给出**修复建议命令**（仅 THP、Swap、SELinux、ulimit、sysctl、时间同步、数据盘挂载选项、CPU 调频、系统服务有；其余显示「没有给出修复命令，需手动处理」）。**平台不会自动修复主机**。（纯静态原型里的「自动修复」按钮是模拟的。）

预检结果在**运维模式**下的实际作用：

- 失败项不会硬性阻止扩容向导，只在向导里给出 ⚠ 警示（「最近一次预检有 N 项失败」）；
- 服务端扩容规划只参考**最近 5 分钟内**的预检：最近一次预检未通过会给出 ⚠「主机 x 最近一次预检未通过」；超过 5 分钟的预检结果规划**不再参考**（也不再警告）；
- 预检时选的角色与扩容角色不同会提示「端口 / 目录检查项可能不适用」；
- 真正执行扩容时，变更的第一步还会用最终的 scale-out 拓扑再跑一次 `tiup cluster check`。

> ⚠️ 超过 5 分钟的预检失败记录不会再触发任何警告。**在扩容向导里请对准备使用的主机在提交前重新预检**，不要依赖早先的结果。

##### 操作：把候选主机移出候选池 / 清理记录

1. 在「候选主机池」该行点「删除」，抽屉「移出候选主机池 <IP>」会显示该主机的可用区 / 机架 / 备注 / 最近预检。点「确认移出」。你会看到提示「<IP> 已移出候选主机池」。
2. 后果：只是把它从清单里移除（含预检记录），不会对该主机做任何事；可重新添加。
3. 如果某台候选主机后来被加进了集群，它不再出现在候选池里，页面提示「<IP> 已在集群拓扑里，不再作为候选主机显示」，点「清理这些记录」即可（提示「已清理已加入集群的主机池记录」）。

### 扩容 / 新增节点

能发起：dba（scale）。风险：中（预发、生产需 1 级审批；测试免审批）。预计耗时 10 + 5×主机数 分钟（窗口检查用，不含 Region 均衡时间）。官方扩容流程见 [使用 TiUP 扩容缩容 TiDB 集群](https://docs.pingcap.com/zh/tidb/stable/scale-tidb-using-tiup) 与 [tiup cluster scale-out](https://docs.pingcap.com/zh/tidb/stable/tiup-component-cluster-scale-out)（扩容拓扑文件只含新增部分）。

#### 操作：扩容一个角色（新增 TiKV / TiDB / PD / TiFlash / TiCDC 实例）

**前置条件**：运维模式、写操作开关已开启；你是 dba；新机器已在「候选主机池」登记（含 zone，扩容 TiKV 必须有）并在**提交前 5 分钟内**通过预检；没有变更占用、不在维护中；扩容 TiKV / TiFlash 会引起数据搬迁，选在低峰；扩容 TiDB 要知道你的负载均衡是 HAProxy 还是 TiProxy（第 3 步「负载均衡」下拉，只影响人工确认步骤里的提示文字，见下表）。

第 3 步字段：

| 字段 | 含义 | 默认 | 校验与影响 |
|---|---|---|---|
| 服务端口 | 实例服务端口 | TiDB 4000、TiKV 20160、PD 2379、TiFlash 3930、TiCDC 8300 | 前端不校验；服务端：端口与该主机上任何已有实例冲突 → ✖ 阻断「host:port 已被某实例使用」；填成非数字会被当作 0 → 取默认端口 |
| 部署目录 / 数据目录 | `/tidb-deploy/<角色>-<端口>` 与 `/tidb-data/<角色>-<端口>`（TiDB 无数据目录） | 只读显示 | 不可改 |
| 部署用户 / 版本 | 与集群一致 | 只读显示 | — |
| block-cache 容量 (GB)（仅 TiKV） | 写入新 TiKV 的 `storage.block-cache.capacity` | 目标主机内存的 45%；主机内存没采集到时为 0（= 不写入，用 TiKV 默认值） | 与其他服务混部请调低，过大会 OOM；负数 → ✖ 阻断 |
| 迁移速度 (个/分钟)（仅 TiKV） | PD store limit | 15 | 取值 1–200，否则 ✖「store limit 取值范围 1–200」；等于 15 或 0 时不执行调速步骤；> 30 时前端提示可能影响线上延迟 |
| 负载均衡（仅 TiDB） | 手工加入负载均衡的提示文案 | 下拉：HAProxy（默认）/ TiProxy | **只影响**「把新 TiDB 加入负载均衡」这一步里的提示文字（写「HAProxy」还是「TiProxy」）。它**不会**写入集群拓扑，**不会**写入「环境与设置」的负载均衡登记，也不会让平台去改任何负载均衡；界面没有「无负载均衡」选项，TiDB 扩容总会有这一步人工确认，也与有没有登记无关 |

1. 进入「节点管理」→「扩容 / 新增节点」，顶部步骤条显示「选择角色 → 选择主机并预检 → 配置参数 → 预览与执行」。第 1 步页面可能先给出建议（如「tikv-3 磁盘 85% 超过 80% 水位 → 建议扩容 TiKV」），点建议链接或下面 5 张角色卡片之一（每张写明「何时扩容 / 影响 / 注意」），直接进入第 2 步。
2. 第 2 步「选择目标主机」：列表是候选池里**不在集群拓扑内**的主机，每行显示 IP、zone / rack、规格（候选主机通常没有采集数据，显示「—」）、预检状态与时间 / 角色、备注。勾选主机：PD 一次只能选 1 台（再选会替换），其他角色可多选。主机还没预检或已过期：点该行「预检」（会按你在第 1 步选的角色直接预检，不再弹选择框）；还没有候选主机：点「＋ 新增候选主机」，或「管理主机池 →」。
3. 读选择后的提示：TiKV / TiDB 会显示各可用区数量（当前 → 选中后）；TiKV 各 AZ 数量不均衡时 ⚠「各可用区的 TiKV 数量将不均衡…」，建议每个 AZ 同步增加；已选主机有警示时出现黄框（「尚未预检」「最近一次预检有 N 项失败」「预检结果已超过 5 分钟」「预检是按 … 角色做的，与本次扩容角色 … 不同」），可以继续，但**建议先处理并重新预检**。「下一步 →」只在有主机正在预检时灰色；没勾主机也不能继续。点「下一步 →」。
4. 第 3 步「配置参数」：按上面「第 3 步字段」表核对 / 填写（部署目录、数据目录、部署用户 / 版本只读）。右侧「拓扑标签」表展示将写入的 zone / rack / host（host = IP 把 `.` 换成 `-`）。标签缺失会让 PD 无法按故障域打散副本。点「下一步 →」。
5. 第 4 步「预览与执行」：左边「scale-out.yml」是将生成的扩容拓扑文件（形如下面的 TiKV 示例），下面「执行命令」；右边「影响评估」（前端按快照估算：每个新 Store 预计承载的 Region、预计迁移耗时、各节点平均 QPS / CPU 变化）与警告。核对 IP、端口、zone、rack 无误。
6. 勾选「我已确认变更窗口、回滚方案与影响范围」，点「提交扩容申请…」。进入「公共流程 A」：在抽屉里确认前置检查（PD 扩容后成员数为偶数 → ⚠ 容错不提升，建议保持奇数；TiKV 有 ℹ「Region 将由 PD 逐步均衡到新 Store…」；任何 ✖ 先处理）、窗口、命令、步骤（「tiup scale-out」带「不可中止」，TiDB 扩容带「需人工确认」），提交。
7. 审批通过后看「任务中心」（公共流程 C）。TiDB 扩容到「把新 TiDB 加入负载均衡」⏸ 步骤时，按指引把新实例加入 HAProxy / TiProxy 后端并 reload，确认有流量后点「我已完成，继续」。
   - 你会看到：黄框文字形如「把 10.0.1.14:4000 加入 HAProxy 后端并 reload，确认后继续」（`10.0.1.14:4000` 是新实例的地址，HAProxy / TiProxy 取决于你在第 3 步选的）。平台**不会**替你加，也不会检查你加没加，你点「我已完成，继续」它就当做完了。
   - 用 HAProxy / LVS 等：在该负载均衡上把新实例加入后端（具体方法按你们团队对它的运维规范），再确认新实例已有连接。官方 HAProxy 示例里后端是 `server tidb-1 10.9.18.229:4000 check inter 2000 rise 2 fall 3` 这样的一行（[HAProxy 在 TiDB 中的最佳实践](https://docs.pingcap.com/zh/best-practices/haproxy-best-practices/)）。
   - 用 TiProxy：官方说明 TiProxy 能自动发现 TiDB server 列表，扩容 / 缩容 TiDB 时无需人工更新列表（[TiProxy 简介](https://docs.pingcap.com/zh/tidb/stable/tiproxy-overview/)），所以通常不需要手工「加入」；你只需确认新实例已被 TiProxy 发现并开始有连接（以真实集群联调为准），再点继续。界面文案写的是「加入 TiProxy 后端并 reload」，是通用提示。
   - 做完后若你在 [环境与设置](go:settings) 登记过这套负载均衡并填了后端列表，请回去「编辑」补上新 TiDB 的 `IP:4000`，否则 [集群架构](go:arch) 图上会显示「后端与拓扑不一致」。
8. 验证：变更「成功」后，「节点实例」页出现新实例且「运行中」；在中控机 `tiup cluster display <集群名>` 看新实例 Status 为 Up。**TiKV 注意**：「成功」只代表新实例启动了，Region 均衡还在后台进行（见下方警告），用 TiDB 执行 `SELECT STORE_ID, ADDRESS, STORE_STATE_NAME, LEADER_COUNT, REGION_COUNT FROM INFORMATION_SCHEMA.TIKV_STORE_STATUS`（[TIKV_STORE_STATUS](https://docs.pingcap.com/zh/tidb/stable/information-schema-tikv-store-status)）观察新 Store 的 REGION_COUNT 逐步上升，直到各 Store 趋于均衡。

生成的 TiKV 拓扑形如：

```
tikv_servers:
  - host: 10.0.2.20
    port: 20160
    status_port: 20180
    deploy_dir: /tidb-deploy/tikv-20160
    data_dir: /tidb-data/tikv-20160
    config:
      server.labels: { zone: "az1", rack: "r15", host: "10-0-2-20" }
      storage.block-cache.capacity: "20GB"
```

**执行步骤（服务端）**

| 步骤 | 做什么 | 命令类别 | 失败时怎么办 | 能否回滚 |
|---|---|---|---|---|
| 预检目标主机 | `tiup cluster check <集群名> scale-out.yml --cluster` | 读 | 真实执行器：失败即变更失败（仅模拟执行器忽略失败） | 无需 |
| 调整 Region 迁移速度（仅 TiKV 且速度不等于 15） | `pd-ctl store limit all <速度>`（对**所有** Store 生效） | 写·中 | 变更失败 | 失败时尝试恢复为 15 |
| tiup scale-out | 分发组件并启动新实例：`tiup cluster scale-out <集群名> scale-out.yml -y`（超时 1 小时） | 写·中，**不可中止** | 变更失败，没有回滚；可能留下半成品实例，需人工用缩容清理 | 否 |
| 等待 host:port 就绪（每台一步） | 轮询 `tiup cluster display` 直到该实例 Up（最长 15 分钟，10 秒轮询） | 读（探测） | 超时即失败 | — |
| 恢复默认迁移速度（仅 TiKV 且速度不等于 15） | `pd-ctl store limit all 15` | 写·中 | 忽略失败 | — |
| 把新 TiDB 加入负载均衡（仅 TiDB） | **人工确认**：把新实例加入 HAProxy / TiProxy 后端并 reload，完成后点「我已完成，继续」 | 无命令 | 12 小时无人确认则失败 | — |
| 查看集群状态 | `tiup cluster display <集群名>` | 读 | — | — |

> ⚠️ 扩容 TiKV 成功只代表新实例已启动并在 display 里 Up。**不会等待 Region 均衡完成**：PD 之后在后台继续把副本迁到新 Store，耗时取决于数据量与调度速度（数百 GB 到数 TB 可能是数小时），期间磁盘 / 网络 I/O 上升，可能带来读写延迟抖动。「迁移速度」只在 scale-out 命令前后临时生效，平台随后就会把速度恢复成 15（写死为 15，不是调速之前的原值）。

> ⚠️ 业务影响：扩容 TiDB / TiCDC / PD 不涉及数据搬迁，在线完成；TiDB 新节点要手工加入负载均衡才会有流量。TiFlash 新节点会以 Learner 拉取副本数据，网络与磁盘压力较大。数据不会丢失，但扩容**不能**缓解单 Region 写热点。`scale-out` 一旦开始就不能中止、也没有自动回滚，失败后用「缩容」清理半成品实例。

### 缩容 / 下线

能发起：dba（scale）。风险：**高**（测试 1 级、预发 2 级、生产 2 级 + 申请人 MFA）。预计耗时 30 分钟 + TiKV 已用容量折算（每 200GB +1 分钟）+ 10 分钟（**实际 Region 迁出可能久得多**）。官方说明见 [tiup cluster scale-in](https://docs.pingcap.com/zh/tidb/stable/tiup-component-cluster-scale-in)：TiKV / TiFlash 下线是异步的，命令发出后立即返回，要等节点状态变为 Tombstone 后再执行 `tiup cluster prune` 清理（[prune](https://docs.pingcap.com/zh/tidb/stable/tiup-component-cluster-prune)）；Store 的 Offline → Tombstone 过程见 [TiDB 数据库的调度](https://docs.pingcap.com/zh/tidb/stable/tidb-scheduling)（剩余满足副本要求的 Store 不足时，Store 会一直停在 Offline）。

#### 操作：下线一个或多个实例

**前置条件**：运维模式、写操作开关已开启；dba；若集群前有负载均衡，已在 [环境与设置](go:settings) 勾选「集群前有负载均衡」或登记了该负载均衡（二者任一，缩容 / 维护 TiDB 时才会出现「需人工确认」摘除步骤；都没有则 TiDB **直接被下线**，连接直接断；自动发现的 TiProxy 不算，见「从负载均衡摘除 / 加回 TiDB 的人工确认步骤」）；目标实例没有变更占用、不是「扩容中 / 下线中」、所在主机不在维护中；缩容 TiKV 时剩余节点磁盘充足且接下来十几个小时没有其他变更排队；强烈建议 TiKV **逐个**下线。

1. 进入「缩容 / 下线」第 1 步「选择要下线的节点」：用角色筛选，勾选要下线的实例（处于「扩容中 / 下线中」或有任务占用的实例不可选，复选框灰色）。也可以在「节点实例」行内点「缩容」，直接跳到第 2 步且已预选该实例。点「下一步 →」。
2. 第 2 步「影响评估」：左边「前置检查」列表，右边「剩余节点影响预测」（假设各节点容量相同、数据均匀迁移）。有任何 ✖ 时页面显示「存在阻断项，无法继续」，「下一步 →」灰色：按提示调整所选节点，或先扩容 / 修复。评估规则见下表。核对 ✔ 剩余 TiKV 仍满足副本数、磁盘迁入后 < 70%、ℹ 需迁移 Region 数与估算耗时。点「下一步 →」。
3. 第 3 步「确认并执行」：左边「将执行的命令」（前端示意，实际以提交抽屉里服务端规划为准），右边「最终确认」显示下线节点与预计影响。在「此操作不可直接撤销，请输入「确认缩容」」输入框里输入 `确认缩容`，红色「提交缩容申请…」才可点。
4. 点「提交缩容申请…」，进入「公共流程 A」：生产高风险要「申请人动态验证码（MFA）」；窗口检查用「推荐时间」避开业务高峰；注意「预计」只有约 40 分钟起，**实际会久得多**，建议选一个后面 10 小时以上没有其他安排的低峰时段；抽屉的执行步骤里「tiup scale-in」带「不可中止」。
5. 需要 2 级审批（预发 / 生产）：两名**不同**的 approver 依次批准，你不能批自己的（公共流程 B）。
6. 执行中看「任务中心」（公共流程 C）：先「驱逐 Leader · <实例>」→「tiup scale-in：Store 进入 Offline」（从这一步起不可中止）→「等待 Region 迁出 · <实例>」每 30 秒更新日志「状态 Offline，剩余 Region N」（可能数小时）→「清理 Tombstone 残留（tiup cluster prune）」→「查看集群状态」。
7. 变更「成功」后验证（示例 3）。需要复用这台主机的话，到「主机池」手工登记为候选主机并重新预检；平台不会自动把它放回候选池，主机上的目录是否清理以 tiup 行为为准。

评估规则（前端与服务端基本一致；提交时服务端会再检查一遍）：

| 角色 | ✖ 阻断 | ⚠ 警告 / ℹ 提示 |
|---|---|---|
| TiKV | 剩余 TiKV 少于 max-replicas（默认 3）；下线让带 zone 标签的可用区数从 ≥ max-replicas 降到 < max-replicas（没有 zone 标签的 TiKV 不参与；集群本来就不足的只给 ⚠）；迁入数据后剩余 TiKV 磁盘 ≥ 80%；缺少 Store ID | 一次下线多个 TiKV ⚠；迁入后磁盘 70%–80% ⚠ 余量偏小；需迁移的 Region 数与估算耗时（前端：按 store limit 15 个/分钟/目标 Store 估算）ℹ；写热点节点下线后热点会转移 ℹ |
| PD | 缩容后少于 3 个 | 缩容后为偶数 ⚠；Leader 在下线范围内 ⚠（先 transfer leader，TSO 秒级抖动） |
| TiDB | 这是最后一个 TiDB | 缩容后只剩 1 个 → ⚠ 单点；约 N 个连接在摘除后断开并重连 ℹ |
| TiFlash | 最后一个 TiFlash | 剩余不足 2 个 ⚠（表的 TiFlash 副本数为 2 时，需先 `ALTER TABLE … SET TIFLASH REPLICA 1`，**平台不替你执行这条 SQL**，见 [构建 TiFlash 副本](https://docs.pingcap.com/zh/tidb/stable/create-tiflash-replicas)） |
| TiCDC | 最后一个 TiCDC | changefeed 迁移到剩余 capture，同步延迟短暂上升 ℹ |

此外执行器还有一道硬护栏：缩容后剩余 TiKV 少于 3 个（可由执行器策略 `minTiKV` 调整）、或 PD / TiDB 被全部清空，命令会被直接拒绝。

**执行步骤（服务端）**：多种角色同时下线时按 TiDB → TiCDC → TiFlash → TiKV → PD 的顺序逐个角色处理。

| 步骤 | 做什么 | 命令类别 | 失败时怎么办 | 能否回滚 |
|---|---|---|---|---|
| 从负载均衡摘除并等待连接排空（仅 TiDB，且平台认为集群前有负载均衡：「环境与设置」里勾选了「集群前有负载均衡」或登记了负载均衡） | **人工确认**，说明文字点名入口，见下一节 | 无命令 | 12 小时无人确认则失败 | — |
| 下线 TiDB / TiFlash / TiCDC | `tiup cluster scale-in <集群名> -N <host:port>,… -y`（超时 1 小时） | 写·高，**不可中止** | 变更失败，无回滚，需核对拓扑 | 否 |
| 迁移 PD Leader（仅 Leader 在下线范围内） | `pd-ctl member leader transfer <剩余 PD 成员名>`（成员名形如 `pd-<IP>-2379`） | 写·中 | 变更失败 | 否 |
| 下线 PD | `tiup cluster scale-in …`（同上） | 写·高，不可中止 | 同上 | 否 |
| 驱逐 Leader · tikv-n（每个 TiKV 一步） | `pd-ctl scheduler add evict-leader-scheduler <storeId>`，等待 Leader 归零（最长 15 分钟） | 写·中 | 变更失败；自动回滚 | 是：移除驱逐调度 |
| tiup scale-in：Store 进入 Offline | `tiup cluster scale-in <集群名> -N <所有待下线 TiKV> -y` | 写·高，**不可中止** | 变更失败；自动回滚只移除驱逐调度，Store 可能已是 Offline，需人工处理 | 否（过了这一步不能中止） |
| 等待 Region 迁出 · tikv-n（每个 TiKV 一步） | 每 30 秒读一次 PD 该 Store 状态，等它变成 Tombstone（Store 不存在也算完成），最长 **48 小时**；日志里显示「状态 Offline，剩余 Region N」 | 读（探测） | 超时即失败 | — |
| 清理 Tombstone 残留 | `tiup cluster prune <集群名> -y` | 写·中 | 变更失败 | 否 |
| 查看集群状态 | `tiup cluster display <集群名>` | 读 | — | — |

> ⚠️ 缩容 TiKV 是**异步长耗时**操作：Store 先变 Offline，PD 把它上面的所有 Region 副本搬到其他 Store，搬完才变 Tombstone。耗时取决于该节点数据量与调度速度，数百 GB 通常以小时计，几 TB 可能超过 10 小时，且受 PD 调度限速与业务压力影响。期间集群磁盘 / 网络 I/O 上升；剩余节点磁盘持续增长。这个等待步骤占用全局执行引擎，期间**所有其他变更排队**。

> ⚠️ 一旦执行了 `tiup scale-in`（日志里有该步骤），变更**不能再中止**，也没有「撤销缩容」按钮。如果在 Offline 阶段需要止损，要人工用 pd-ctl 的 `store cancel-delete <storeId>` 把 Store 从 Offline 恢复为 Up（官方 [PD Control](https://docs.pingcap.com/zh/tidb/stable/pd-control) 说明该命令撤销已用 `store delete` 下线并处于 Offline 的 Store；平台的 scale-in 是否与它等价，以真实集群联调为准）。48 小时仍未 Tombstone 时变更会标记失败，但 Store 仍可能在迁移中，需要人工跟进。

### 从负载均衡摘除 / 加回 TiDB 的人工确认步骤

TiDB 是无状态的 SQL 层，业务连接经负载均衡（HAProxy / LVS / 云 SLB 等）分发到各个 TiDB。下线或停止一个 TiDB 之前，应先让负载均衡**不再给它派新连接**并等已有连接排空；否则这台 TiDB 上的连接会被直接切断（缩容抽屉里的 ℹ「约 N 个连接会在摘除后断开并重连，请先从负载均衡摘除并等待排空」说的就是这件事，它对每次 TiDB 缩容都会显示）。平台**不连接**你的负载均衡，所以把这一步做成「需人工确认」：由你自己在负载均衡上操作，再回来点确认。

**什么时候出现**

| 变更 | 步骤名 | 出现条件 |
|---|---|---|
| 缩容（下线）TiDB | 「从负载均衡摘除并等待连接排空」，之后才是「下线 TiDB」 | 平台认为「集群前有负载均衡」，且本次下线包含 TiDB |
| 进入主机维护 | 「从负载均衡摘除并排空连接」，之后才是迁移 PD Leader、停止实例等 | 同上，且该主机上有 TiDB |
| 结束主机维护 | 「重新加入负载均衡并恢复流量」，在实例启动、就绪之后 | 同上，且该主机上有 TiDB；**按结束维护那一刻**的设置判断（进入与结束是两个独立的变更，各自生成步骤） |

「平台认为集群前有负载均衡」= 「环境与设置」里**勾选了**「集群前有负载均衡」，**或已手工登记**至少一条负载均衡（环境与设置帮助里叫「有效值」，依据显示在「负载均衡」卡片顶部，见 [环境与设置帮助](help:settings) 的「与原有复选框的关系」）。两个都没有时，这个步骤**不出现**，TiDB 会被直接下线 / 停止。

不出现这个步骤的情况，容易误解，请特别注意：

- **自动发现的 TiProxy 不算**：[集群架构](go:arch) 图上有 TiProxy，也不会触发这个步骤。官方说明 TiProxy 在 TiDB 缩容、滚动升级、滚动重启时能把连接迁移到其他 TiDB，但需要事先配好 TiDB 的 `graceful-wait-before-shutdown`（[TiProxy 简介](https://docs.pingcap.com/zh/tidb/stable/tiproxy-overview/)）；平台没在真实集群验证过这个过程，所以不替你判断。只有 TiProxy 又想保留人工确认，请勾选「集群前有负载均衡」。
- **单实例的重启 / 停止 TiDB 永远没有这个步骤**（「节点实例」里的操作），请自己先摘；**滚动重启、滚动升级**也不使用这个设置。
- 只在**生成变更计划时**判断一次；你提交之后再勾选 / 登记，已提交的变更不会多出这个步骤。

**步骤说明文字（黄框）怎么写、怎么点名入口**

| 情况 | 缩容 / 进入维护的摘除步骤 | 结束维护的加回步骤 |
|---|---|---|
| 已手工登记（无论复选框是否勾选） | 先从负载均衡 <名称>（<类型>，<入口地址>） 摘除 <host:端口>，并等待连接排空，确认后继续 | 把 <host:端口> 加回负载均衡 <名称>（<类型>，<入口地址>） 的后端并确认流量恢复 |
| 没有登记，只勾选了复选框 | 把 <host:端口> 从负载均衡后端摘除，并等待连接排空，确认后继续 | 把 <host:端口> 加回负载均衡后端并确认流量恢复 |

- 占位符：`<名称>`、`<类型>`、`<入口地址>` 来自「环境与设置 → 负载均衡」里你登记的记录（例如 `生产 HAProxy 主（HAProxy，10.0.0.5:3306）`）；`<host:端口>` 是被摘除 / 加回的 TiDB（例如 `10.0.1.13:4000`），一次下线多台时用「、」连起来。
- 登记了**多条**时，文字里会把**全部**登记的入口都列出来（用「、」连接），**不区分**这台 TiDB 实际在哪个负载均衡后面——请你按实际情况，只在它所属的那几个负载均衡上操作。
- 想让文字点名具体入口，就去登记（见 [环境与设置帮助](help:settings) 的「登记一条负载均衡」）；不登记、只勾选复选框也能工作，只是文字更笼统。

**怎么做这一步（逐步）**

**前置条件**：能点确认的只有变更的申请人或内置 DBA 角色；该步骤等 12 小时无人确认就会失败，所以要在你能值守的时间段执行。

1. 变更执行到该步骤时，任务中心里它显示 ⏸「待人工确认」，展开能看到上面的黄框说明；有登记时，说明里点名了入口。
2. 到**被点名的**负载均衡（HAProxy / LVS / 云 SLB 等）上，把说明里的 TiDB（`<host:端口>`）摘除：让它不再接收新连接。具体做法按你们团队对该负载均衡的运维规范（例如改配置并 reload，或用它的管理接口把该后端设为停用），平台不规定，也不会替你做。
3. 等该 TiDB 上已有连接排空：在 [集群架构](go:arch) 点该 TiDB，看详情里的「连接数」下降到接近 0（该数据取自 Prometheus，有延迟，以你负载均衡自己的监控为准）。排空太慢又不能等的话，要接受剩余连接被切断。
4. 确认无误后，回到任务中心点该步骤的「我已完成，继续」。
   - 你会看到：提示「已确认，继续执行」，步骤变 ✔，变更继续执行下一步（缩容里是「下线 TiDB」）。
5. 「加回」步骤同理：实例已启动并恢复后，在负载均衡上把它加回后端，确认有流量，再点「我已完成，继续」。

> ⚠️ **点「我已完成，继续」只意味着「你声明已经做完了」**：平台**不会**替你摘除 / 加回，**也不会检查**你是否真的做了、负载均衡里该后端是否已摘掉。点了之后它立刻执行下一步（比如 `tiup cluster scale-in` 或停止实例，且是不可中止、不可撤销的步骤）。没摘就点，这台 TiDB 上的连接会被切断，业务会报错或重连。确认前也想一想：被点名的入口之外，是否还有别的负载均衡或应用直连这台 TiDB（平台只知道你登记过的）。

登记不影响这一步以外的任何事，也不会因为你点了确认而自动更新：缩容 TiDB 成功后，如果登记里填了后端，请回 [环境与设置](go:settings) 把已下线的 TiDB 从登记里「编辑」掉，否则 [集群架构](go:arch) 图会提示「后端与拓扑不一致」。

### 主机维护

适用场景：对整台主机做内核 / OS 升级、换盘、硬件检修、网络变更、重启，期间该主机上所有实例临时下线，结束后恢复。能发起：dba（maint）。**一台主机同一时刻只能有一个进行中的维护；同时只允许一台带 TiKV 的主机处于维护中**（否则部分 Region 会同时失去 2 个副本）。

PD 补副本阈值：TiKV 失联超过 PD 的 `max-store-down-time`（默认 30 分钟，实际读取集群当前值）后，PD 会判定该 Store Down 并开始为它上面的 Region 补副本——那是一次大规模数据搬迁，维护结束后还要再均衡（[TiDB 数据库的调度](https://docs.pingcap.com/zh/tidb/stable/tidb-scheduling)）。「PD 补副本阈值策略」就是为此设计的：

| 策略 | 行为 |
|---|---|
| 自动 | 主机有 TiKV 且计划分钟数 > 阈值 − 5 → 用「延长」，否则「标准」 |
| 标准 | 阈值保持不变。计划分钟数 > 阈值 − 5 时服务端直接 ✖ 阻断，要求改选「延长」 |
| 延长 | 进入维护时临时把阈值调为 `max(计划分钟 + 30, 原阈值)` 分钟，结束维护时恢复为原值 |

#### 操作：进入维护

**前置条件**：dba（maint）；写操作开关已开启；该主机没有进行中的维护，没有变更占用其实例；若主机带 TiKV，没有别的带 TiKV 的主机在维护；高风险（生产需 2 级审批 + MFA），要提前约好审批人；若集群前有负载均衡，已在 [环境与设置](go:settings) 勾选「集群前有负载均衡」或登记了该负载均衡（主机上有 TiDB 时才会有摘除 / 加回步骤）；准备好维护后要做的事（检查单）。

表单字段：

| 字段 | 含义 | 可选值 / 默认 | 校验与填错后果 |
|---|---|---|---|
| 维护主机 | 单选；每台显示 az / rack、实例标签 | 已在维护中的主机置灰；有未结束变更的显示「有变更 CHG-xxxx」 | 主机上没有实例 → 规划报错 |
| 维护类型 | 点选：内核 / OS 升级、磁盘更换 / 扩容、硬件检修（内存 / 电源 / 网卡）、网络变更、仅重启主机（取自服务端） | 默认时长：25 / 90 / 120 / 30 / 10 分钟；切换类型会重置时长 | 类型决定后面的检查单内容 |
| 预计停机时长（分钟） | 计划维护窗口 | 默认随类型；服务端上限 24 小时（1440 分钟） | 必须 > 0；填 0 或非数字则提交按钮灰；超过 24 小时被拒；`<= 0` 在服务端会取类型默认值 |
| 数据盘上的数据是否保留？（仅「磁盘更换 / 扩容」） | 保留（扩容 / 重新挂载）/ 不保留 | 默认保留 | 选「不保留」→ ✖ 阻断「已不是停机 → 恢复，请改走缩容下线 + 扩容新增替换节点」 |
| PD 补副本阈值策略（仅主机上有 TiKV） | 下拉：自动 / 标准 / 延长 | 自动 | 见上表 |
| 维护原因 | 文本 | 必填 | 为空按钮灰 |
| 变更工单号（可选） | 工单编号 | 如 `CHG-12345`；默认空 | 会被拼在原因前面 `[CHG-12345] 原因`；不会单独出现在维护卡片的「工单」位置 |

1. 进入「节点管理」→「主机池」，在「集群内主机」找到目标主机，点「进入维护」；或直接进入「主机维护」标签。你会看到「新建主机维护计划」表单（若已有进行中的维护，上方还有「进行中的维护」卡片）。
2. 按上表填写：点选「维护主机」（左侧）和「维护类型」，填「预计停机时长（分钟）」「维护原因」，按需选「PD 补副本阈值策略」与「变更工单号（可选）」。
3. 点「评估并提交维护申请…」（没有 maint 能力时置灰；还缺主机 / 时长 / 原因时旁边提示「请选择主机并填写预计时长与原因」）。进入「公共流程 A」：读服务端评估（见下表），尤其是 ✖ 与 ⚠，窗口检查，以及步骤里的「需人工确认」（TiDB 摘除）和「不可中止」（停止实例）。
4. 提交并审批通过后，在「主机维护」卡片看进度：状态「进入维护中」，显示当前步骤与进度条，期间可点「中止并恢复」（需变更仍可中止）。TiDB 摘除是 ⏸ 人工步骤，按公共流程 C 处理。
5. 成功后卡片变「维护中」，开始倒计时；你就可以在主机上做实际维护了。

服务端评估：

| 项 | ✖ 阻断 | ⚠ 警告 / ℹ 提示 |
|---|---|---|
| 主机冲突 | 同主机已有进行中维护；两台带 TiKV 的主机同时维护 | 另一台主机也在维护 ⚠（请确认不影响多数派与容量） |
| 实例状态 | 实例处于扩容中 / 下线中 | — |
| TiDB | 唯一健康的 TiDB | 约 N 个连接排空并重连 ℹ |
| PD | 停掉后健康 PD 少于 2 个（失去多数派） | PD Leader 先 transfer ⚠ |
| TiKV | 停掉后健康 TiKV 少于 max-replicas；缺 Store ID | 将驱逐 N 个 Leader，约 N 个 Region 在维护期只有 max-replicas − 1 个副本 ℹ；其他 TiKV 磁盘 ≥ 80% ⚠ |
| TiFlash / TiCDC | — | 唯一的 TiFlash / TiCDC：列存 / MPP 回退或失败、changefeed 中断 ⚠ |
| 阈值 | 标准策略且时长超阈值 −5 | 延长策略将临时调大阈值 ⚠ |
| 时间 | — | 当前接近每日 02:00 的备份窗口（本地时间 01:00–03:59）⚠ |

**进入维护**的步骤（maint.enter，**高风险**，可中止；预计 计划分钟 + 10 分钟）

| 步骤 | 做什么 | 命令类别 | 失败时怎么办 | 能否回滚 |
|---|---|---|---|---|
| 临时调大 max-store-down-time（仅「延长」策略） | `pd-ctl config set max-store-down-time <限值>m` | 写·中 | 变更失败 | 是：恢复为原阈值 |
| 从负载均衡摘除并排空连接（仅主机上有 TiDB，且平台认为集群前有负载均衡：勾选了「集群前有负载均衡」或有登记） | **人工确认**，说明文字点名入口 | 无 | 12 小时超时失败 | — |
| 迁移 PD Leader（仅 PD Leader 在该主机，需有其他健康 PD） | `pd-ctl member leader transfer <其他 PD>` | 写·中 | 变更失败 | 否 |
| 确认 changefeed 已迁移（仅有 TiCDC） | `tiup cdc cli capture list`（只读） | 读 | 忽略失败 | — |
| 驱逐 Leader · tikv-n（每个 TiKV 一步） | `pd-ctl scheduler add evict-leader-scheduler <storeId>`，等 Leader 归零（最长 15 分钟） | 写·中 | 变更失败 | 是：移除驱逐调度 |
| 停止实例（按 TiDB → TiCDC → TiFlash → TiKV → PD 顺序） | `tiup cluster stop <集群名> -N <该主机全部实例> -y` | 写·高，**不可中止** | 变更失败，维护记录标「已取消」，回滚（移除驱逐 / 恢复阈值）后实例可能已部分停止，需人工核对并启动 | 部分 |

表中 `<限值>` = max(计划分钟 + 30, 原阈值)；`<其他 PD>` 是剩余健康 PD 的成员名（形如 `pd-<IP>-2379`，可在 `pd-ctl member` 的输出里看到）。

#### 操作：维护中的卡片、检查单与延长窗口

「维护中」卡片内容：「已维护」分钟数、「计划窗口」（计划 + 已延长）、进度条（超过窗口或阈值变红）、「距 PD 补副本阈值还剩 N 分钟」（有 TiKV 时；剩余 ≤ 5 分钟出现黄色警示，超过阈值变红色「已超过 PD 阈值 …：PD 已判定 TiKV Store Down 并开始补副本」，这个判断来自平台按已维护时间推算，不是读取 PD 实际状态）、「维护检查单」、「主机实例」各实例状态。有未结束的「结束 / 延长」变更时按钮置灰，卡片提示该变更编号。

检查单（勾完才允许普通结束）：

| 类型 | 检查项 |
|---|---|
| 内核 / OS 升级 | 升级内核 / 系统包并重启主机；确认 THP、Swap、sysctl 等参数未被还原；确认时间同步（chrony / ntp）正常 |
| 磁盘更换 / 扩容 | 更换或扩容磁盘并重新挂载（nodelalloc,noatime）；确认数据目录权限、空间与文件系统；抽样校验数据目录文件完整 |
| 硬件检修 | 完成硬件检修并上电；确认 BIOS 电源策略为高性能；确认网卡速率与双工模式 |
| 网络变更 | 完成网络变更；验证到 PD / TiKV / TiDB 各节点互通；确认跨机房时延在阈值内（< 5ms） |
| 仅重启主机 | 重启主机；确认系统服务与 tiup 目录挂载正常 |

1. 在主机上完成实际维护，每做完一项就在卡片的「维护检查单」里勾选（勾选会写回服务端，需要 maint 能力；失败会提示「保存检查单失败」）。
2. 随时留意「距 PD 补副本阈值还剩 N 分钟」。窗口只剩几分钟时，点「延长 15 分钟」/「延长 30 分钟」/「延长 60 分钟」。延长是低风险、免审批，抽屉标题「延长维护窗口 +N 分钟（<IP>）」，点「提交变更」后几乎立即完成，仍停留在「主机维护」页。若新窗口超过当前阈值，会同步执行 `pd-ctl config set max-store-down-time <新窗口+15>m` 并把策略改为「延长」。
3. 若已经触发补副本，延长无法撤销已发生的补副本，只是延后恢复时间。

#### 操作：结束维护（恢复）

**前置条件**：检查单全部勾选（否则 ✖「检查单还有 N 项未勾选（紧急恢复可跳过）」）；主机已可用；中风险，预发 / 生产需 1 级审批——**结束维护也要审批**，要提前与审批人约好，窗口剩几分钟时先用「延长」保住 PD 阈值。

1. 在「维护中」卡片点「结束维护（恢复）」。抽屉标题「结束维护 <IP>」，显示「中风险」。
2. 读检查：⚠ 若已超过 PD 阈值会提示「PD 已为该 Store 补副本，恢复后会有额外 Region 均衡」；✖ 检查单未勾完。点「提交变更」。
3. 审批通过后执行（卡片状态「恢复中」，显示进度）：见下表。TiDB 恢复到 ⏸「重新加入负载均衡并恢复流量」时，按指引加回并确认流量，点「我已完成，继续」。
4. 完成后卡片消失，出现在「历史维护」表里（「计划 / 实际（分钟）」，触发过补副本的有「触发过补副本」标记）。
5. 失败时：维护记录回到「维护中」，实例可能已部分启动；先看失败原因与日志、`tiup cluster display <集群名>`，处理好后再点「结束维护（恢复）」重试。

**结束维护**的步骤（maint.exit，**中风险**，不可中止；预计 15 分钟）

| 步骤 | 做什么 | 命令类别 | 失败时怎么办 | 能否回滚 |
|---|---|---|---|---|
| 主机预检（紧急恢复跳过） | `tiup cluster check <集群名> --cluster`（重启后参数是否还原） | 读 | 忽略失败 | — |
| 按依赖顺序启动实例 | `tiup cluster start <集群名> -N …`（顺序 PD → TiKV → TiFlash → TiCDC → TiDB） | 写·低 | 变更失败；维护记录回到「维护中」，实例可能已部分启动，处理后重试 | 无 |
| 等待每个实例就绪 | 轮询 display 到 Up，最长 15 分钟 | 读 | 超时失败 | — |
| 移除 Leader 驱逐调度 · tikv-n | `pd-ctl scheduler remove evict-leader-scheduler-<storeId>` | 写·中 | 忽略失败 | — |
| 恢复 max-store-down-time（仅「延长」策略） | `pd-ctl config set max-store-down-time <原值>m` | 写·中 | 变更失败 | 否 |
| 重新加入负载均衡并恢复流量（主机上有 TiDB，且平台认为集群前有负载均衡：勾选了「集群前有负载均衡」或有登记） | **人工确认**，说明文字点名入口 | 无 | 12 小时超时失败 | — |
| 验证：无 down-peer（仅主机上有 TiKV / TiFlash 时） | 读 `region check down-peer`（经 `tiup ctl:<版本> pd`，需要中控机装有 ctl 组件），并等待 PD 报告无 down-peer / pending-peer（最长 20 分钟） | 读 | 命令失败或超时即变更失败；维护记录回到「维护中」 | — |

#### 操作：紧急恢复与中止进入维护

- **紧急恢复**：维护中卡片的红色「紧急恢复」。抽屉标题「紧急恢复 <IP>」，跳过检查单与第一步预检，直接启动实例，并给出 ⚠「请在恢复后补做主机预检」。仍是中风险、仍要审批。恢复后必须在「主机池」里对该主机补做预检（只对候选主机池有预检入口；已在集群里的主机请在中控机用 `tiup cluster check <集群名> --cluster`，见官方 [tiup cluster check](https://docs.pingcap.com/zh/tidb/stable/tiup-component-cluster-check)）。
- **中止进入维护**：「进入维护中」阶段卡片上的「中止并恢复」，抽屉「确认中止」。越过「停止实例」步骤后不能中止。中止后回滚移除驱逐调度 / 恢复阈值，维护记录标「已取消」，但实例可能已部分停止，需核对并「启动」。

> ⚠️ 进入维护是高风险（生产 2 级 + MFA），结束维护也要审批（中风险：预发 / 生产 1 级）。「disk」类型选「不保留数据」被阻断，该走缩容 + 扩容。

## 执行后果与风险

各操作的影响速查：

| 操作 | 对集群 / 业务的影响 | 能否撤销 | 去哪看进度 | 失败后要做什么 |
|---|---|---|---|---|
| 重启 / 停止实例 | TiKV 先迁 Leader（秒级抖动）；PD Leader 重启触发选举，TSO 秒级不可用；TiDB 立即断开其连接；停止 TiKV 超过 max-store-down-time 会触发补副本 | 重启无需撤销；停止用「启动」恢复；可「中止」但会杀 tiup 进程 | 任务中心 | `tiup cluster display` 核对实例状态，残留驱逐调度手工移除，必要时「启动」 |
| 启动 / 驱逐 / 恢复 Leader | 低风险；驱逐期间其余 TiKV 压力上升 | 驱逐用「恢复 Leader」撤销 | 任务中心 | 核对驱逐调度是否残留（`scheduler show`） |
| 扩容 | 新实例上线；TiKV / TiFlash 触发后台数据搬迁，I/O 上升；新 TiDB 需手工加入负载均衡才有流量 | `scale-out` 不可中止、无回滚；要撤销只能「缩容」 | 任务中心；Region 均衡看 `TIKV_STORE_STATUS` | 半成品实例用缩容清理；重新预检后再试 |
| 缩容 | TiKV 下线是数小时的异步迁移，I/O 升高、全局变更排队；剩余节点磁盘持续增长 | `scale-in` 之后不可中止；Offline 阶段只能人工 `store cancel-delete` | 任务中心（等待 Region 迁出步骤） | 核对 PD 里该 Store 状态与剩余 Region，再决定等待还是恢复 |
| 配置变更 | 在线项无重启；reload 项滚动重启（TiKV 约 2–3 分钟 / 个）；debug 日志明显拖慢性能 | 无一键回滚，需提交改回去的变更；失败回滚只恢复拓扑 | 任务中心；实际值用 `SHOW CONFIG` 核对 | 核对在线值与拓扑是否一致 |
| 主机维护 | 停掉该主机全部实例；约 N 个 Region 在维护期少一个副本（可读写，容错下降）；超 PD 阈值开始补副本 | 进入维护可在停止前中止；之后用「结束维护」恢复 | 「主机维护」卡片与任务中心 | 看失败原因，`tiup cluster display` 核对，处理后重试；窗口将尽先「延长」 |

> ⚠️ **模拟执行器（sim）**：在回放模式或 `--exec sim` 下，命令只是按模板生成输出，集群拓扑和状态不会变化，步骤等待条件也由模拟探测器快速满足。变更记录和审批流程是真的，集群动作是假的；看到「成功」不代表任何事发生过。

> ⚠️ **未经真实集群验证**：以下点在执行器的说明里明确标注「需要在真实 tiup 上实测」，首次使用请在测试环境演练：`tiup cluster edit-config --topology-file … -y` 的版本支持（官方 [edit-config](https://docs.pingcap.com/zh/tidb/stable/tiup-component-cluster-edit-config) 页面只描述了交互式编辑，没有列出这个选项）；`pd-ctl` 各子命令写法；`SET CONFIG` / `SET GLOBAL` 的值字面量；`tiup cluster check <集群名> <文件> --cluster`；TiFlash 状态端口；`tiup cluster scale-in` 对 TiKV 的实际等待 / 清理行为。

## 完整操作示例

以下三个示例假设：运维模式；环境为生产（prod）；执行器为 direct 或 sudo；写操作开关已开启；默认审批策略；账号：小李（dba）、小王与小张（approver）。命令里的 `<集群名>`、`<版本>`、`<PD 地址>`、`<storeId>` 见上文「占位符约定」。

### 示例 1：重启一个 TiKV 节点（tikv-2，Leader 先迁走再重启）

**目标**：重启 `tikv-2`（地址 `10.0.2.12:20160`，Store ID 假设为 `5`），业务只有秒级抖动。预计风险：中；生产需 1 级审批。

1. **【申请人 小李】** 打开平台地址，在登录页填「用户名」「口令」，点「登 录」。你会看到右上角出现 `生产`、`写操作已开启`、「小李 · dba」。如果是「只读」，悬停看原因（见「写操作总闸」），先找管理员处理，不要继续。
2. 先在中控机做一次事前确认（只读）：`tiup cluster display <集群名>`，确认 tikv-2 与其余 TiKV 的 Status 都是 Up（输出列与状态含义见官方 [tiup cluster display](https://docs.pingcap.com/zh/tidb/stable/tiup-component-cluster-display)：Up 正常、Down / Unreachable 未启动或网络问题、Pending Offline 正在下线）。有 TiKV 不是 Up 时不要重启另一个。
3. 左侧点「节点管理」，默认就是「节点实例」标签。点角色筛选 `TiKV`，找到 tikv-2：状态标签应是「运行中」，没有「变更 CHG-…」「主机维护中」标签。
4. 点 tikv-2 行的「重启」。你会看到抽屉先显示「正在由服务端规划并检查…」，随后标题变成「重启 tikv-2」，顶部显示「中风险」「prod 环境需 1 级审批」「预计 5 分钟」。
5. 读「前置检查（服务端）」：应有 ✔「重启前先驱逐 Leader，业务抖动通常为秒级」和 ✔「其余 N 个 TiKV 健康，Raft 多数派不受影响」。判读：只有 ✔ / ℹ → 继续；出现 ⚠「其他健康 TiKV 少于 2 个，重启期间多数派风险升高」→ 停手，先恢复别的 TiKV；出现 ✖（常见：「tikv-2 所在主机 … 正在维护」「已被变更 CHG-xxxx 占用」）→ 按钮会变成「存在阻断项」且没有输入框，点「取消」关闭，先处理阻断项。
6. 读「窗口检查」：如果出现 ⚠「落在不建议变更的窗口「业务高峰（上午）」（周一至周五 09:00–12:00）：计划 10-08 10:00 起约 5 分钟，建议改到其他时段」，在「执行时间」下方的推荐时间里点评分最高的按钮（如「10-08 22:30 · 评分 70」）。你会看到「执行时间」自动变成「定时执行…」，窗口检查随之刷新成 ✔「落在推荐窗口「夜间低峰」（每天 22:00–06:00）」。
7. 读「将执行的命令」，确认是这三条（pd-ctl 在这里是简化显示；`10.0.2.12:20160` 与 Store ID 要和 tikv-2 一致）：`pd-ctl scheduler add evict-leader-scheduler 5`、`tiup cluster restart <集群名> -N 10.0.2.12:20160`、`pd-ctl scheduler remove evict-leader-scheduler-5`。读「执行步骤」：「驱逐 Leader」「重启实例」「移除驱逐调度，Leader 回迁」三步，**没有**「需人工确认」「不可中止」标签，说明任何时候都可以中止。
8. 在「变更说明 / 工单号」填 `OPS-1234 tikv-2 例行重启`；不勾「紧急变更」；中风险没有 MFA 输入框。点「提交变更」。你会看到提示「变更 CHG-0007 已提交，等待审批」，页面跳到「任务中心」并展开 CHG-0007：状态「待审批」「审批 0/1」。不符预期时看按钮上方红字（如「窗口规则拦截」「与已排期的变更…冲突」）。
9. **【审批人 小王】** 登录，进入「节点管理」→「任务中心」。顶部「⚠ 待你审批（1）」里有 CHG-0007；点「查看详情」，核对：目标实例是 tikv-2，申请说明有工单号，命令只有上面三条，定时时间在夜间低峰。点「批准」，在确认面板里再核对一遍，点「确认批准」。你会看到「已批准 CHG-0007」，状态变成「已排期」（定时）或「排队中」（立即执行）。不同意就点「驳回」填原因。
10. **【申请人 小李 观察执行】** 到点后，在任务中心（CHG-0007）会看到状态变「执行中」，步骤依次：「驱逐 Leader」（日志里 `等待 Leader 迁出：leader_count=…` 逐渐降到 0）→「重启实例」（先是 tiup 输出，再反复 `等待实例 Up：状态 …` 直到 Up）→「移除驱逐调度，Leader 回迁」。若前面有别的变更在执行，会先显示「排队中」，这是正常的（同一集群内串行）。
11. 完成后卡片「成功」。展开确认最后一步没有 ⚠「忽略失败」。如果有，说明驱逐调度可能没移除干净，见第 12 步「命令三」。
12. **验证**：
   - 平台：「节点实例」页 tikv-2 为「运行中」，几分钟内「Leader」数逐步回升。
   - 命令一：在中控机 `tiup cluster display <集群名>`，tikv-2 Status 为 Up（[display](https://docs.pingcap.com/zh/tidb/stable/tiup-component-cluster-display)）。
   - 命令二：在 TiDB 上执行 `SELECT STORE_ID, ADDRESS, STORE_STATE_NAME, LEADER_COUNT, UPTIME FROM INFORMATION_SCHEMA.TIKV_STORE_STATUS`，该 Store 为 Up，UPTIME 很短（刚重启过），LEADER_COUNT 在上升（字段见 [TIKV_STORE_STATUS](https://docs.pingcap.com/zh/tidb/stable/information-schema-tikv-store-status)）。
   - 命令三：`tiup ctl:<版本> pd -u http://<PD 地址> scheduler show`，列表里不应再有 `evict-leader-scheduler`（`scheduler show` 显示所有已创建的调度器，见 [PD Control](https://docs.pingcap.com/zh/tidb/stable/pd-control)）。残留的话执行 `scheduler remove evict-leader-scheduler-5` 手工移除，否则 tikv-2 上的 Leader 回不来。
13. **失败时**：看卡片红色「失败原因」和日志。回滚只会移除驱逐调度，**不会**帮你启动实例；用 `tiup cluster display <集群名>` 核对 tikv-2；若是 Down，在「节点实例」点「启动」（低风险、免审批）；确认集群正常后再重新提交。执行中途想停可点「中止」，同样要核对 tikv-2 状态。

> 💡 要「滚动重启整个 TiKV 角色」请用 [日常运维](go:ops) 页的「滚动重启」（`tiup cluster restart -R tikv`，同一套审批）。

### 示例 2：在线调整一个 TiKV 参数（raftstore.store-pool-size 由 2 调到 3）

**目标**：把 tikv-2 的 Raftstore 线程数从 2 调到 3，不重启。预计风险：中；生产需 1 级审批。

1. **【申请人 小李】** 登录并确认右上角 `生产`、`写操作已开启`、「小李 · dba」（同示例 1 第 1 步）。
2. 进入「节点管理」→「节点实例」，点 tikv-2 行的「详情 / 配置」，在抽屉里点「配置变更」。你会看到「正在读取集群里的配置当前值」，几秒后「Raftstore 线程数」行显示「默认 2 · 当前 2」，带「在线生效」「实例级」标签。若行上还有红色「配置漂移」，说明各 TiKV 取值不一致，先决定要不要点「对齐 →」。读不到时显示「—（未采集）」，先点「重新读取」。
3. 把输入框改成 `3`。你会看到行下无 ✖ / ⚠（超过 5 才警告），底部「预览变更（1）」可点，「应用范围」出现。
4. 选「应用范围」：「仅 tikv-2」或「全部 N 个 TiKV」。线程数通常希望所有 TiKV 一致，选后者；若只想先在单节点试验，选前者，之后各节点会出现「配置漂移」，属预期。
5. 点「预览变更（1）」。你会看到变更表：`2 → 3`、「在线生效」、「✔ 通过」；「风险与影响」：✔「全部为在线生效项，无需重启实例」；「将执行的命令」：`SET CONFIG "10.0.2.12:20180" raftstore.store-pool-size = 3;` 与一段 `tiup cluster edit-config <集群名>` 的拓扑片段（全部实例时 SET CONFIG 的目标写 `tikv`；`10.0.2.12:20180` 是 tikv-2 的状态端口）。这里是前端预览，**以随后服务端抽屉为准**。
6. 勾「我已确认影响」，点「提交变更申请…」。在提交抽屉里确认：中风险、「prod 环境需 1 级审批」；前置检查 ✔「全部为在线生效项，无需重启实例」「变更前的拓扑已随计划保存，失败时可恢复」；执行步骤「在线下发配置（1 项）→ 写入 tiup 拓扑 → 查看集群状态」，**没有 reload，没有重启**。命令里值带引号的写法是展示，实际整数不加引号。「变更说明 / 工单号」填 `OPS-1235 TiKV raftstore 线程 2→3`，选执行时间，点「提交变更」。你会看到提示「变更 CHG-0008 已提交，等待审批」，页面跳到任务中心。若出现 ✖（例如「所在主机正在维护」「已被变更占用」）就先处理。
7. **【审批人 小王】** 同示例 1 第 9 步：核对目标实例、配置键、新值与「不重启」，点「批准」，在确认面板里点「确认批准」。
8. **【申请人 小李 观察执行】** 执行：`SET CONFIG` 通过 mysql 运维账号执行（10 秒超时），`edit-config` 写入拓扑（2 分钟超时），`display` 收尾。卡片「成功」。
9. **验证**：
   - 平台：重新打开该实例「配置变更」，「当前」应显示 3（平台没有自动回读，以这次读取为准）；「变更历史」里有 CHG-0008。
   - 命令一：在 TiDB 上执行 `SHOW CONFIG WHERE type = 'tikv' AND name = 'raftstore.store-pool-size'`，应看到 tikv-2（或全部 TiKV）为 3（[SHOW CONFIG](https://docs.pingcap.com/zh/tidb/stable/sql-statement-show-config)）。
   - 命令二：在中控机 `grep -n "store-pool-size" ~/.tiup/storage/cluster/clusters/<集群名>/meta.yaml`，拓扑里也应是 3，避免之后 reload / 升级被旧值覆盖（[在线修改集群配置](https://docs.pingcap.com/zh/tidb/stable/dynamic-config) 对此有同样提醒）。
10. **失败时**：失败发生在「写入 tiup 拓扑」时，回滚会把拓扑恢复为变更前的版本，但**已经通过 SET CONFIG 在线生效的值不会被还原**——运行中的 TiKV 仍是 3，而拓扑是 2，下次 reload 会被改回，需要人工决定以哪个为准（上面的命令一、二可以看出两边各是什么）。
11. 想改回 2：再提交一次把值改回 2 的变更即可（运维模式没有一键回滚）。

> 💡 如果改的是「需 reload」的项（如 `server.grpc-concurrency`），步骤会变成「写入 tiup 拓扑 → 滚动 reload（逐个重启）→ 逐实例等待就绪」，预览里会出现 ⚠「需滚动 reload N 个 TiKV」，每个节点约 2–3 分钟，总时间随节点数增长，且 reload 步骤不可中止。官方说明 reload 会先把 PD / TiKV 的 Leader 迁走再重启（[tiup cluster reload](https://docs.pingcap.com/zh/tidb/stable/tiup-component-cluster-reload)）。

### 示例 3：缩容一个 TiKV 节点（tikv-6，所在主机 10.0.2.16）

**目标**：下线 tikv-6（`10.0.2.16:20160`，Store ID 假设为 `9`）。高风险：生产需 2 级审批 + 申请人 MFA。

**前提检查（缺一不可）**：现有 TiKV 数量 − 1 ≥ max-replicas（默认 3，且执行器硬下限 3）；每个 AZ 仍保留至少 1 个 TiKV；剩余节点迁入数据后磁盘 < 80%（最好 < 70%）；没有其他变更占用 tikv-6，所在主机不在维护中；接下来 10 小时以上没有别的变更要执行；你绑定了 MFA（「权限与审计」→「我的账号」）；已约好两名不同的 approver。

1. **【申请人 小李】** 登录（同示例 1 第 1 步）。先在中控机看现状：`tiup cluster display <集群名>` 确认 tikv-6 是 Up；`tiup ctl:<版本> pd -u http://<PD 地址> store`，记下各 Store 的 `region_count`、容量使用，确认剩余节点装得下（Store 状态含义见 [TiDB 数据库的调度](https://docs.pingcap.com/zh/tidb/stable/tidb-scheduling)）。
2. 「节点管理」→「节点实例」，找到 tikv-6，点「缩容」，直接进入「缩容 / 下线」第 2 步（已预选 tikv-6）。
3. 读「前置检查」：应有 ✔「剩余 N 个 TiKV，仍满足 3 副本（max-replicas=3）」；✔ 或 ⚠ 磁盘评估（✔ < 70%；⚠ 70%–80% 余量偏小，建议先扩容；✖ ≥ 80% 必须先扩容）；ℹ「需迁移约 X 个 Region（≈ Y TiB）；按默认 store limit 15/分钟、N 个目标 Store 估算，约 Z 小时」。右侧「剩余节点影响预测」看各剩余 TiKV 磁盘缩容前 → 缩容后。有 ✖ 时页面写「存在阻断项，无法继续」，「下一步 →」灰色，先解决（例如先扩容）。
4. 点「下一步 →」，在第 3 步确认「将执行的命令」，在「此操作不可直接撤销，请输入「确认缩容」」输入框输入 `确认缩容`，点「提交缩容申请…」。
5. 提交抽屉：「高风险」「prod 环境需 2 级审批」；前置检查是服务端重新评估的结果；因为生产高风险要求 MFA，会出现「申请人动态验证码（MFA）」，填验证器里的 6 位码（没绑定会提示先到「权限与审计」绑定）。「窗口检查」选「推荐时间」避开业务高峰。「执行步骤」里「tiup scale-in：Store 进入 Offline」带「不可中止」标签。预计时间只有约 40 分钟，**实际迁移会久得多**，选一个后面 10 小时以上空闲的夜间时段。填工单号，点「提交变更」，提示「变更 CHG-0009 已提交，等待审批」。
6. **【审批人 小王、小张】** 两人各自登录，在「任务中心」→「待你审批」里依次「批准」（公共流程 B）。你不能批自己的，也不能同一人批两次；两人都批完状态变为「已排期」或「排队中」，卡片「审批 2/2」。
7. **【申请人 小李 观察执行】** 开始执行后在任务中心看：先「驱逐 Leader · tikv-6」，等待 Leader 归零；然后 `tiup cluster scale-in <集群名> -N 10.0.2.16:20160 -y`，从这一步起「不可中止」；接着「等待 Region 迁出 · tikv-6」每 30 秒更新一次日志「状态 Offline，剩余 Region N」。这一步可能持续数小时，期间其他变更都会排队；可以在 [集群总览](go:overview) 的「QPS 与延迟」和 [热点与调度](go:hotspot) 页观察业务延迟。想知道进度也可以在中控机跑 `tiup cluster display <集群名>`，下线中的 tikv-6 会显示 Pending Offline（官方 display 说明：Pending Offline = 数据迁移进行中）。
8. Store 变为 Tombstone（或 PD 里已查不到）后，平台执行 `tiup cluster prune <集群名> -y` 并 `tiup cluster display <集群名>`，变更变为「成功」。
9. **验证**：
   - 平台：「节点实例」页不再有 tikv-6。
   - 命令一：`tiup cluster display <集群名>` 里已没有 tikv-6（官方 [prune](https://docs.pingcap.com/zh/tidb/stable/tiup-component-cluster-prune) 清理 Tombstone 实例并更新拓扑）。
   - 命令二：在 TiDB 上执行 `SELECT STORE_ID, ADDRESS, STORE_STATE_NAME, LEADER_COUNT, REGION_COUNT FROM INFORMATION_SCHEMA.TIKV_STORE_STATUS`，剩余 Store 都是 Up，LEADER_COUNT / REGION_COUNT 相对均衡；tikv-6 的 Store 若还列出，状态应是 Tombstone、REGION_COUNT 为 0，这是正常的（Tombstone 记录较新版本 PD 约一个月后自动清理，也可用 `store remove-tombstone` 手工清除，见 [PD Control](https://docs.pingcap.com/zh/tidb/stable/pd-control)）。
   - 命令三：`tiup ctl:<版本> pd -u http://<PD 地址> region check miss-peer`，返回的 Region 数应为 0（`region check` 的类别见 PD Control）。
   - 需要复用 10.0.2.16：到「主机池」登记为候选主机并重新预检。
10. **出问题时**：
   - 驱逐阶段失败 → 自动移除驱逐调度，集群回到原状，可重新提交；
   - 已 scale-in 后失败或超时 → 不能撤销，需人工查看 PD 中该 Store 的状态与剩余 Region（`store <storeId>`），再决定继续等待，还是用 `store cancel-delete 9` 把 Store 从 Offline 恢复为 Up；
   - 中途想停：scale-in 之前可点「中止」；之后不能。

## 已知限制与易混淆点

下面每一条都是「界面写的是 A，实际是 B」，已对照当前代码核实。

| 界面写的是 A | 实际是 B | 你该怎么做 |
|---|---|---|
| 变更提交抽屉、任务中心像是平台里唯一的一份 | 平台可纳管多个集群，本页的实例、主机池、变更、任务中心都是**顶栏当前集群**的；变更编号 `CHG-0001` 各集群各自编号，会重复；不同集群的变更互不排队 | 提交前核对抽屉顶部的「集群 X」标签；区分集群看审计日志的「集群」列 |
| 回放集群（顶栏里 replay 模式的集群）上也能提交变更 | 回放集群恒用**模拟执行器**，流程完整但**不会作用于任何真实集群**，「成功」不代表真实执行过 | 看「权限与审计 → 写操作开关」页执行器一行的「模拟：不会对集群做变更」 |
| 配置变更目录里有 `replication.max-replicas`，并预留了「高危变更，输入「确认」」流程 | 该项被标为高危后，客户端与服务端都会给出 ✖「高危参数」阻断，确认框根本不会出现，**任何修改都无法提交** | 不要在平台里改副本数。确需修改时在中控机用 pd-ctl 手工 `config set max-replicas`，并走你们自己的变更流程；评估容量后选低峰（参数说明见 [PD 配置文件](https://docs.pingcap.com/zh/tidb/stable/pd-configuration-file)） |
| 配置预览写「变更前将备份当前配置，可随时回滚」；服务端抽屉写「失败时可恢复」 | 只有**变更失败 / 被中止**时才自动把**拓扑**恢复成旧版本；不会撤销已在线生效的值，也不会重新 reload；事后没有「回滚」按钮 | 想改回去就再提交一个把值改回原值的变更；失败后用 `SHOW CONFIG` 与 `meta.yaml` 对比在线值和拓扑值 |
| 扩容向导里的「迁移速度（个/分钟）」像是整个均衡期间的限速 | 只在 `scale-out` 前后临时设置，随后恢复成写死的 15（不是调速前的原值）；设置对**所有** Store 生效；平台不等待 Region 均衡完成 | 变更「成功」后用 `TIKV_STORE_STATUS` 观察 Region 均衡；需要长期调速请手工用 pd-ctl `store limit`，均衡完成后改回你集群原来的值 |
| 窗口检查与冻结期看起来会一直保护变更 | 只在**创建变更时**检查一次，审批拖延后不会再拦；预计时长远小于缩容 TiKV 的实际迁移时长 | 对时间敏感的变更选「定时执行」；缩容 TiKV 自己预留十几个小时，别指望窗口检查覆盖 |
| 缩容提交抽屉顶部「预计 N 分钟」（TiKV 约 40 分钟起） | TiKV 缩容实际常是数小时到十几个小时（等待步骤最长 48 小时）；同一集群内串行，期间该集群的所有变更排队；`scale-in` 之后不可中止、没有「撤销缩容」按钮 | 缩容 TiKV 前清空后续排期；逐个下线；Offline 阶段需要止损只能人工 `store cancel-delete`（以真实集群联调为准） |
| 前置检查写「失去多数派」 | 服务端实际判据是**剩余健康 TiKV 少于 max-replicas**（默认 3）就阻断：3 个 TiKV、3 副本时，无法用平台停止、维护、缩容其中任何一个；执行器还有 `minTiKV=3` 的硬护栏 | 想做这类操作先扩容到至少 4 个 TiKV；不要把 max-replicas 改小来绕过（该项本来也改不了） |
| 提交抽屉顶部「prod 环境需 N 级审批」 | 勾选「紧急变更」后这个数字不刷新，仍按非紧急计算；实际预发 / 生产紧急变更至少 2 级 | 以任务中心该变更的「审批 x/y」为准，提前通知足够的审批人 |
| 按钮灰色提示「当前账号没有「…」权限（需 DBA 角色）」 | 实例操作（重启 / 停止 / 启动 / 驱逐 / 恢复 Leader）sre 也有；扩缩容、配置变更、主机维护才是 dba | 看「谁能发起、谁来审批」表判断该找谁 |
| 配置项旁的「默认 X」 | 是平台内置的展示值，不一定是你集群版本的实际默认。已核对的差异：`storage.block-cache.capacity` 官方默认是系统内存的 45%（raft-kv 引擎），界面写 16GB；`readpool.unified.max-thread-count` 官方默认 MAX(4, CPU 配额×0.8)，界面写 16；`server.grpc-concurrency` 官方 v8.5.4 起默认为 grpc-raft-conn-num×3+2，之前为 5 | 以每行的「当前」值为准，不要因为「默认」不同就认为被改过；默认值查官方 [TiKV 配置文件](https://docs.pingcap.com/zh/tidb/stable/tikv-configuration-file) |
| 扩容 TiDB 的「负载均衡」下拉只有 HAProxy / TiProxy | 没有「无」选项，扩容 TiDB 总会有一步「把新 TiDB 加入负载均衡」人工确认；下拉只改这一步提示文字里写的是 HAProxy 还是 TiProxy，**不写入拓扑，也不写入「环境与设置」的登记** | 你没有负载均衡时，核对新 TiDB 能连上后直接点「我已完成，继续」；12 小时内必须点，否则失败 |
| 扩容 TiDB 选「TiProxy」后，步骤写「加入 TiProxy 后端并 reload」 | 是通用提示文字；官方说明 TiProxy 会自动发现 TiDB server 列表，通常无需手工加入 | 确认新 TiDB 已被 TiProxy 发现并有连接后点继续（以真实集群联调为准） |
| 缩容 / 维护 TiDB 的向导里写「先从负载均衡摘除」（缩容抽屉的 ℹ「请先从负载均衡摘除并等待排空」对每次 TiDB 缩容都显示） | 只有「环境与设置」里**勾选了**「集群前有负载均衡」**或登记了**负载均衡，变更里才会有「需人工确认」摘除步骤；两者都没有则直接下线 / 停止，连接直接断。**自动发现的 TiProxy 不算** | 有负载均衡的环境请先在 [环境与设置](go:settings) 勾选该选项或登记负载均衡；单实例重启 / 停止 TiDB 永远没有摘除步骤，请自己先摘 |
| 步骤「从负载均衡摘除…」点名了好几个入口 | 有登记时说明文字列出**全部**登记的入口，不区分这台 TiDB 实际在哪个负载均衡后面 | 只在它实际所属的负载均衡上操作；登记里后端填对，对照「集群架构」详情里的后端列表 |
| 点「我已完成，继续」 | 只是你的声明：平台不会替你摘除 / 加回，也不检查你是否做了，点后立即执行下一步（如不可中止的 `tiup cluster scale-in`） | 先在负载均衡上做完并确认连接排空，再点 |
| 扩容 / 缩容 TiDB 成功后，登记里的后端没跟着变 | 平台不会自动更新「环境与设置」里的登记；「集群架构」图会提示「后端与拓扑不一致」 | 回 [环境与设置](go:settings)「编辑」登记，补上新 TiDB / 删掉已下线的 TiDB |
| 扩容向导里主机带红色「⚠ 预检未通过」、黄色「预检已过期」标签，像是要求通过预检 | 运维模式下只要没有主机正在预检就能继续；未预检、失败、过期、角色不匹配都只是警示；服务端只参考最近 5 分钟内的预检，更早的失败不再警告 | 提交前对准备使用的主机重新预检并处理失败项，不要依赖旧结果 |
| 实例行有「驱逐 Leader」「恢复 Leader」，驱逐后应出现「Leader 已驱逐」标签 | 运维模式下平台不读取 PD 的驱逐调度状态：标签不会出现，「驱逐 Leader」与「恢复 Leader」两个按钮始终同时可点 | 驱逐 / 恢复后用 `scheduler show` 确认调度器是否存在；不要靠实例行判断，重复驱逐前先查 |
| 维护表单的「变更工单号（可选）」 | 会被拼进原因文字 `[CHG-12345] 原因`，维护卡片的「工单」位置永远不显示 | 把工单号同时写在提交抽屉的「变更说明 / 工单号」里 |
| 「已超过 PD 阈值…PD 已判定 Store Down」红色提示 | 是平台按已维护时间推算的，不是读取 PD 的实际状态 | 以 `tiup ctl:<版本> pd -u http://<PD 地址> store` 里该 Store 的 `state_name` 为准 |
| 任务中心「执行日志」像是完整日志 | 只显示每条变更最近约 20 行；完整日志（最多 3000 行）保存在服务端，页面没有入口 | 要看更早的内容请找平台管理员在数据目录的 `changes.json` 里查，或看审计日志 |
| 配置值的前端校验与服务端校验一致 | 前端时长不接受 `1h30m`、接受 `500ms`、要求 Block Cache ≥ 1GB；服务端相反或没有这些限制 | 一律用纯整数 + 单一单位（`90m`、`12GB`） |
| 提交抽屉里的命令是实际命令 | 是简化写法：pd-ctl 命令省略了 `tiup ctl:<版本> pd -u …` 前缀，tiup 命令实际会追加 `-y`；`edit-config` 显示为 `--topology-file <平台生成并 diff 过的拓扑>`（官方 [edit-config](https://docs.pingcap.com/zh/tidb/stable/tiup-component-cluster-edit-config) 页面没有该选项，待真实集群联调） | 审阅命令时看对象与顺序；手工复现时按官方文档写完整命令 |
| TiFlash 日志级别选项 `warning` | 官方 TiFlash 配置页写的是 `warn`；TiCDC 的 `per-table-memory-quota` 在官方 TiCDC Server 配置页面里没有找到 | 这两项是否对你的版本有效以真实集群联调为准，首次使用先在测试环境验证（[TiFlash 配置](https://docs.pingcap.com/zh/tidb/stable/tiflash-configuration)、[TiCDC Server 配置](https://docs.pingcap.com/zh/tidb/stable/ticdc-server-config)） |
| 回放 / 只读模式里的「提交并执行（模拟）」「开始扩容（模拟执行）」 | 只改浏览器内存里的状态，刷新即丢失，集群不变；前端判定（如停止 TiKV 的多数派）比服务端宽松 | 不要把模拟结果当真；真实验证用运维模式 + 测试环境 |

## 常见问题与注意

**提交抽屉说「当前不能提交：写操作开关未开启…」？** 需要两名管理员在「权限与审计」→「写操作开关」先后开启；或者服务器上存在强制只读文件、执行器未配置、集群版本不受支持，见「写操作总闸」。

**提示「xxx 已被变更 CHG-xxxx 占用」？** 该实例有未结束的变更（含待审批）。先到任务中心取消或等待它结束。

**提示「计划时间落在变更冻结期…」「窗口规则拦截：…」？** 改期（用推荐时间），或勾「紧急变更」（审批更严、事后复盘）。

**提示「与已排期的变更 CHG-xxxx 在时间与资源上冲突」？** 同一实例或主机在重叠时间段已有排期，换个时间。

**扩容 TiKV 报「需要指定可用区」？** 候选主机没有 zone，到「主机池」点「编辑」补全后重新预检。

**预检一直失败？** 看「查看检查项」里每项的说明与修复命令；SSH 连不上、tiup 版本不一致也会表现为一项「tiup cluster check（预检执行）」失败。预检最长等待 3 分钟（执行器 120 秒超时），主机慢时可能超时，可重试。

**为什么候选主机看不到规格？** 候选主机还没加入集群，没有 node_exporter 指标，规格显示「—」是正常的。

**缩容 / 进入维护 TiDB 时多了一个「需人工确认」的摘除步骤？** 平台认为集群前有负载均衡（勾选了「集群前有负载均衡」或登记了负载均衡）。这是预期行为，做法见「从负载均衡摘除 / 加回 TiDB 的人工确认步骤」；若你其实没有负载均衡，到 [环境与设置](go:settings) 取消勾选并删除登记后重新提交变更（已提交的变更不会改变）。

**图上有 TiProxy，缩容 TiDB 却没有摘除步骤？** 自动发现的 TiProxy 不触发这个步骤，见上面同一节。

**平台重启后变更变成「失败」？** 执行中途平台被重启，变更会被标记为失败并提示核对集群状态；正在「排空」的维护记录标为「已取消」。请用 `tiup cluster display` 与 pd-ctl 核对残留的驱逐调度、被临时调大的 `max-store-down-time` 等中间状态。

**审批过期了？** 审批有效期 24 小时（或到计划时间），过期后变更为「已过期」，需要重新提交。

**测试环境为什么不用审批？** 默认策略下测试环境的低、中风险免审批，高风险 1 级；这是策略，不是缺陷，可由管理员经双人复核修改。
