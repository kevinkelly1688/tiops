# 帮助文档编写规范（给维护者）

`frontend/help/*.md` 是平台「使用帮助」的唯一来源：

- 页面右上角「? 帮助」和侧栏「使用帮助」由 `js/help.js` 在浏览器里加载并渲染这些文件；
- 发布包会带上 `help/*.md`，服务端白名单放行 `/help/<id>.md`；
- 文件名即主题 id：`quickstart overview arch diag sql hotspot trouble nodes schedule deploy shell ops settings security users roles clusters watermark faq`，
  其中页面 id 与前端 `pages.<id>` 一致，右上角帮助按钮按当前页面 id 打开同名文档。

## 支持的 Markdown 子集（help.js 内置渲染器）

| 写法 | 说明 |
|---|---|
| `#` `##` `###` | 标题；`#` 每篇只有一个；`##` 生成右侧目录 |
| 段落、`-` 无序列表（可缩进两格嵌套一层）、`1.` 有序列表 | |
| `**粗体**`、`` `行内代码` `` | |
| 表格（`\| a \| b \|` + 分隔行） | 参数/选项说明主要用表格 |
| 代码块（三个反引号） | 命令示例，带复制按钮 |
| `> ⚠️ ...` | 红/黄色警示框（执行后果、风险） |
| `> 💡 ...` | 蓝色提示框 |
| `> ...` | 普通引用 |
| `[文字](go:nodes)` | 跳转到平台页面（页面 id） |
| `[文字](help:faq)` | 跳转到另一篇帮助 |
| `[文字](https://...)` | 外链，新窗口打开 |

不支持：图片、HTML、脚注、表格内换行与竖线（竖线用 `/` 代替）。

## 每个页面文档的统一结构

```
# 页面名

> 💡 一句话用途。谁能用（角色）。只读模式与运维模式的差异。

## 这个页面做什么
## 怎么用（按步骤）
## 区域与参数说明        （### 每个区块一节，参数用表格：字段/选项 | 含义 | 可选值 / 默认 | 影响）
## 执行后果与风险         （> ⚠️ 逐项写：会执行什么命令、影响哪些组件/业务、是否重启、能否回滚、需要谁审批）
## 常见问题与注意
## 相关页面
```

写作原则：以代码为准，不编造；区分「回放/只读模式」与「运维模式」；区分「模拟执行器（演示）」与「真实执行」；
没在真实集群验证过的行为要如实标注。

## 质量标准（逐步操作文档）

目标：值班同事照着做，不会因为文档产生疑问或做出意外操作。

1. **每个操作 = 编号步骤**。每一步只做一件事，写明：在哪个页面/标签页、点哪个按钮（按钮文字与界面完全一致，用「」括起）、填哪个字段（字段名与界面一致）、填什么。
2. **每一步写预期结果**：「你会看到……」；与预期不符时写怎么办（或指向 faq）。
3. **操作前写前置条件**（角色/能力、环境、写开关、需要先准备什么），**操作后写后果**（对集群/业务/审计/通知的影响，是否可撤销）。
4. **术语统一**：同一个概念全篇只用一个叫法（变更 / 变更单；写开关 / 写操作开关 以界面为准）。第一次出现的专业词给一句话解释，并给官方文档链接。
5. **占位符必须解释**：文中出现 `<集群名>` 之类，紧跟说明从哪里取值、示例值是什么。
6. **官方文档引用**：凡涉及 TiDB / TiKV / PD / TiFlash / tiup / pd-ctl / BR / Dashboard 自身的概念、命令、参数、系统变量，在「官方参考」小节或行内给出 docs.pingcap.com/zh 的链接。**链接必须已用 WebFetch 打开核实过**（页面存在、内容与所述一致）；平台支持 v7.5 / v8.1 / v8.5，优先用 `/zh/tidb/stable/` 或对应版本路径，并注明「以你集群的版本为准」；不确定的不要写链接，不要编造 URL。
7. **不夸大、不含糊**：没在真实集群验证过的写「以真实集群联调为准」；平台实际行为与界面文案不一致的地方，集中写在页面末尾「已知限制与易混淆点」，说清「界面写的是 A，实际是 B」。
8. **不写内部实现细节**（函数名、文件路径）给普通读者，除非是运维必需（数据目录文件、命令行）。
