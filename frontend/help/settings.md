# 环境与设置

> 💡 查看平台从中控机与集群里自动探测到的环境信息，管理通知渠道（企业微信 / 钉钉 / 飞书 / Lark / Slack / 其他）、变更窗口规则，登记 HAProxy / LVS 等负载均衡（运维模式），查看版本与升级历史。所有登录用户都能打开；**修改需要「修改平台设置」权限（settings.edit，默认只有管理员角色）**。只读模式下页面只展示探测结果，修改不会保存到服务器；运维模式下设置会保存到后端并写入审计。

## 这个页面做什么

页面由几块组成，不同模式下看到的内容不同：

| 区域 | 静态原型（无后端） | 只读 / 回放模式（后端无 `--data-dir`） | 运维模式（需登录） |
|---|---|---|---|
| 环境探测（中控机 / tiup / 集群 / 组件地址） | 模拟值 | 回放或真实探测值 | 同左 |
| 覆盖 / 恢复自动 | 仅当前页面内存，刷新即丢 | 同左，不会保存到服务器 | 保存到后端 `settings.json`，需 settings.edit |
| 版本兼容性 | 按版本在前端演示 | 按探测到的版本显示 | 同左；后端对写操作有真实的版本闸门 |
| 用户自定义设置（登录方式、存储、通知、审计保留期、窗口、写操作开关） | 全部 11 项，仅演示 | 同左，不保存 | 只显示「登录方式、平台元数据存储、审计保留期」3 项；通知、窗口、写操作开关已被真实功能取代并隐藏 |
| 平台设置卡片（负载均衡、写操作开关状态、冻结期数量、覆盖数量） | 无 | 无 | 有 |
| 负载均衡（自动发现的 TiProxy + 手工登记） | 无 | 无 | 有，**当前集群的**（每个集群各一份）；所有登录用户可看，登记 / 编辑 / 删除需要 settings.edit |
| 通知渠道、变更窗口规则 | 无 | 无 | 有，**当前集群的**（每个集群各一份）；通知渠道仅 settings.edit 可见 |
| 关于与升级 | 无 | 无 | 有（全局，平台自身的版本与升级历史，与所选集群无关） |
| 侧栏版本号（标题下与左下角） | 无 | 有（只要后端可达） | 有 |

> 💡 **多集群：本页的内容都是「当前所选集群」的**（顶栏集群下拉，见 [集群接入帮助](help:clusters)）。环境探测的是该集群；「平台设置」卡片、「通知渠道」「变更窗口规则」卡片标题里会写「集群 显示名」；**每个集群各自一份**通知渠道、窗口规则、「集群前有负载均衡」、负载均衡登记、覆盖值，改之前先看顶栏当前集群。唯一全局的是「关于与升级」卡片（平台自己的版本与升级历史）。

先认识几个词：

- **探测 / 覆盖**：平台自动从中控机命令与集群接口取到环境信息叫「探测」；你手工填的值叫「覆盖」。
- **中控机**：装有 tiup、用来管理 TiDB 集群的那台机器，平台与它同机部署（[tiup cluster 文档](https://docs.pingcap.com/zh/tidb/stable/tiup-cluster)）。
- **Webhook**：群机器人提供的一个网址，向它发送一条 HTTP 请求，消息就会出现在群里。**Webhook 地址等同于发消息的密码**，泄露后别人也能往你的群里发消息。
- **加签 / 签名校验**：机器人的一种安全设置，平台发送时用一个密钥对时间戳做签名，机器人只接受签名正确且时间在有效期内的请求。
- **变更窗口规则**：规定哪些时段适合 / 不适合做变更，作用于提交变更时的检查、推荐时间和变更排期的着色。

> ⚠️ 平台从未对真实集群运行过，本页探测值的格式、通知渠道的真实投递、升级流程都以真实环境联调为准；升级流程尚未在真实中控机上演练过。

## 怎么用（按步骤）

### 查看环境探测并核对

1. 在左侧菜单点「环境与设置」，看页面顶部「环境探测」卡片。
   - 你会看到：一行「数据来源」、一个「重新探测」按钮，下面一行「取值优先级：用户自定义 ＞ 自动探测 ＞ 默认值」。
   - 真实数据是否新鲜请看页面最上方的横幅「采集于 hh:mm:ss」，**不要看「上次探测：N 分钟前」**（见已知限制）。
2. 向下逐张表（中控机、tiup、集群、组件地址）核对「当前生效值」和「来源」。
   - 你会看到：来源是绿色「自动探测」说明取到了值；黄色「未探测到」且值为「—」说明该项没取到（不会阻塞其他页面）。
3. 对「未探测到」的项排查：到中控机上手工执行该行「探测命令」列里的命令看是否可用（例如 `tiup --version`），或确认该集群是否真的部署了该组件（如没有 Alertmanager）。
4. 右侧「探测概况」卡片汇总：可自动探测项数、未探测到项数、用户覆盖项数。

### 覆盖或恢复某一项探测值

**前置条件**：具备 settings.edit（没有时「覆盖」「保存」「恢复自动」按钮是灰的，「平台设置」卡片里有黄色提示，找管理员）。**先看后果**：覆盖值目前只是记录和展示，**不会改变平台的采集和写操作闸门**（见下方警告）。

1. 在目标行点「覆盖」。
   - 你会看到：该行「当前生效值」变成输入框，内容被选中。
2. 输入新值（不能为空），点该行的「保存」；不想改点「取消」。
   - 你会看到：提示「已覆盖，来源变为“用户自定义”」，来源标签变蓝；运维模式下紧接着提示「设置已保存到后端」。如果与探测值不同，值下方有黄字「与探测值不一致：…」。
   - 与预期不符：提示「值不能为空；如需回到自动请点“恢复自动”」→ 输入框是空的，填值或点「取消」；提示「保存失败」→ 看提示里的原因，多数是会话过期或权限不足。
3. 要回到自动值：点该行「恢复自动」（仅覆盖过的行有此按钮）。
   - 你会看到：提示「已恢复为自动探测」，来源变回「自动探测」或「未探测到」。

> ⚠️ **覆盖值目前只是记录和页面展示，不会改变平台的行为**：后端不读取覆盖值，数据采集仍用启动参数（`--pd`、`--prom`、`--alert`、`--cluster` 等）和自动探测，写操作的版本闸门用的也是探测到的版本。例如在这里把 Alertmanager 覆盖成某个地址，平台并不会因此开始读取它；要让平台使用，需要用启动参数重启服务。

> ⚠️ 覆盖值保存时会把**整张覆盖表**一次性写回后端，两个管理员同时修改时后保存的会覆盖先保存的。

### 点「重新探测」会发生什么

1. 点顶部「重新探测」。
   - 你会看到：按钮变灰显示「探测中…」，下面滚动出每一项的「$ 命令 → 结果」，结束时提示「探测完成」。
2. 注意：这**只是用当前快照里的值演示一遍**，不会重新连接集群。要真正重新取数，点顶部横幅的「立即刷新」（后端对强制刷新有 2 秒节流），页面会随后重绘并提示「已刷新」。

### 读「版本兼容性」

右侧「版本兼容性」卡片由探测到的 TiDB 版本决定（平台支持 v7.5 / v8.1 / v8.5 三个 LTS 系列，LTS 即长期支持版本，见 [TiDB 版本规则](https://docs.pingcap.com/zh/tidb/stable/versioning)）：

| 你看到 | 含义 | 后端实际行为 |
|---|---|---|
| 绿色「vX.Y.Z 在支持矩阵内」 | 版本属于 v7.5 / v8.1 / v8.5 系列（如 v8.5.2） | 写操作闸门放行（还需写操作开关已开、已配置执行器、没有 READONLY 熔断文件） |
| 黄色「vX.Y.Z 不在已验证的支持矩阵内（版本偏旧 / 版本较新，尚未适配 / 未验证）」 | 如 v6.5.9、v7.1.5、v9.0.0；读取与诊断仍可用并带「未验证」标记，部分指标可能缺失 | 提交变更时被拦下，提示「集群版本 X 不在平台支持范围内（…），写操作已降级为只读」；顶部「写操作已开启 / 只读」标签显示「只读」，鼠标悬停可看原因；巡检报告里「合规」项显示警告 |
| 红色「未获取到 TiDB 版本」 | 版本探测为空 | **后端在版本为空时不会拦截写操作**，且前端覆盖的版本值不会传给后端，见已知限制 |

遇到黄色时的处理：回退到受支持版本，或等平台适配；在本页把「TiDB 版本」覆盖成受支持版本**不能**解除降级。

卡片下方的「演示：模拟探测到的版本」下拉框是原型的演示控件，真实 / 回放模式下请不要使用（见已知限制）。

### 设置「集群前有负载均衡」

**前置条件**：运维模式、settings.edit。**后果**：改变之后生成的变更计划，不影响已有变更；无需重启，写审计（`settings.update`）。

1. 在「平台设置」卡片勾选或取消「集群前有负载均衡」。
   - 你会看到：勾选后提示「已开启：负载均衡摘除为人工步骤」，取消提示「已关闭」。
2. 开启后，在 [节点管理](go:nodes) 对 TiDB 节点做缩容 / 进入维护时，变更计划里会多一个「需人工确认」的步骤，要求你先在负载均衡上摘除该节点再继续。
3. 想让变更步骤里**点名具体是哪台负载均衡**、并让它出现在 [集群架构](go:arch) 图里，除了勾选这个复选框，还可以在下面的「负载均衡」卡片登记（见下一节）。**只要登记了任意一条，即使不勾选这个复选框，缩容 / 维护 TiDB 时也会出现人工摘除步骤**，详见「与原有复选框的关系」。
   - 勾选 / 取消复选框保存成功后，下方「负载均衡」卡片里的「当前平台认为…」那条提示会随之更新（几秒内）；没变的话点卡片右上角的「刷新」。

### 登记一条负载均衡

先说明用途：拓扑图里的「负载均衡层」有两类来源。tiup 部署的 TiProxy 平台能**自动发现**；除此之外的负载均衡——HAProxy、LVS、Nginx、云负载均衡（SLB）、F5，以及 tiup 之外自己部署的 TiProxy——不在 `tiup cluster display` 里，平台**发现不了**，需要管理员在这里**手工登记**一条记录，它们才会出现在图上、并在缩容 / 维护 TiDB 的人工确认步骤里被点名。

> 💡 下文尖括号里的写法是占位符：`<名称>`、`<类型>`、`<入口地址>`、`<id>` 是你登记那条记录时填的值；`<host:端口>` 是被摘除的那台 TiDB 的地址，例如 `10.0.1.13:4000`；`<显示名>` 是顶栏当前集群的名字（例如「预发集群」）。

**前置条件**

- 运维模式（已登录）。静态原型与只读 / 回放模式没有这张卡片。
- 具备 `settings.edit`（「修改平台设置」）。这项能力**只授予内置「管理员」角色**，自定义角色也不能被授予（见 [角色权限帮助](help:roles)）。没有时「＋ 登记负载均衡」「编辑」「删除」置灰，悬停提示「需要「修改平台设置」（settings.edit）能力」，卡片里还有黄色提示「你没有「修改平台设置」（settings.edit）权限，负载均衡登记为只读：登记 / 编辑 / 删除按钮已置灰。」——请找管理员。
- **不需要**打开写操作开关，也**不走审批、不需要双人确认、不受变更窗口与冻结期限制、不产生变更单**：登记是平台自己的一条记录，不是对集群的变更。
- 顶栏集群下拉选对了集群。**每个集群各自一份登记**（卡片标题里写着「集群 <显示名>」），在集群 A 登记的负载均衡在集群 B 里看不到、也不影响 B 的变更计划。
- 手头准备好这些信息：
  1. 负载均衡的类型（HAProxy / LVS / Nginx / SLB / F5 / 自部署 TiProxy / 其他）。
  2. **客户端实际连接的入口地址**：VIP 或域名 + 端口，例如 `10.0.0.5:3306`。取值方法：看应用连接串里的主机与端口；HAProxy 看配置里监听的 `bind` 地址；LVS 可在 director 上执行 `ipvsadm -L -n` 查看虚拟服务地址；云 SLB 在云控制台看监听地址与端口。这里的 `10.0.0.5:3306` 只是示例，以你的环境为准。
  3. （可选）它**实际转发到的每一台 TiDB** 的 `IP:SQL 端口`，通常是 `IP:4000`——注意是 SQL 端口，不是 10080 状态端口。HAProxy 在配置文件的 `server` 行里（官方示例形如 `server tidb-1 10.9.18.229:4000 check inter 2000 rise 2 fall 3`，其中 `10.9.18.229:4000` 就是要填的后端）；其他类型在对应的管理界面或配置里找。

> ⚠️ 名称、入口地址、备注会显示给所有能打开「集群架构」的登录用户（权限项 `view.overview`，几乎所有角色）。**不要在里面写口令、密钥、带凭据的连接串**——地址里含 `@` 的会被拒绝，备注则不做内容检查。

**操作步骤**

1. 在左侧点「环境与设置」，向下滚动到「负载均衡」卡片（在「探测概况」「设计要点」之后、「通知渠道」之前）。
   - 你会看到：标题「负载均衡 集群 <显示名> · 拓扑图的负载均衡层 · 自动发现 + 手工登记」，右上角有「刷新」「＋ 登记负载均衡」两个按钮；下面依次是一条彩色提示、「自动发现的 TiProxy」表、「手工登记」表。
2. 先读现状（读法见下一节「读懂负载均衡卡片」），确认要登记的负载均衡确实还没登记过，也不是已经被「自动发现」的 TiProxy。
3. 点「＋ 登记负载均衡」。
   - 你会看到：右侧抽屉「登记负载均衡」，从上到下是 id、类型、名称、入口地址、后端 TiDB 列表、备注。
4. 按下表逐项填写。每个输入框下面有即时提示：灰字是说明，绿色「✔」表示通过，红色「✖」写明原因。

| 字段 | 含义 / 从哪取 | 规则 | 示例 | 不合规时的提示 |
|---|---|---|---|---|
| id | 平台里给这条登记起的唯一标识；审计日志里的目标就是它。**创建后不能修改** | 2–32 位，小写字母开头，只含小写字母 / 数字 / 连字符；同一集群内不能重复 | `haproxy-prod` | 「✖ 格式不符：小写字母开头，只含小写字母 / 数字 / 连字符，2–32 位」；重复时「✖ 该 id 已存在」 |
| 类型 | 负载均衡的种类，决定图上方框左上角的标签 | 下拉：HAProxy / LVS / Nginx / 云负载均衡(SLB) / F5 / TiProxy（自部署）/ 其他；默认 HAProxy | HAProxy | 「TiProxy（自部署）」只用于 **tiup 之外**自己部署的 TiProxy；tiup 部署的已被自动发现，不要再登记（平台不去重，会在图上出现两次） |
| 名称 | 给人看的名字 | 1–40 个字，不能含换行 | `生产 HAProxy 主` | 「✖ 名称最多 40 个字」；留空保存时「名称需为 1–40 个字」 |
| 入口地址 | 客户端连接的 VIP / 域名 : 端口，即上面第 2 点的取值 | `主机:端口`；主机是 IP 或域名，端口 1–65535；IPv6 写成 `[::1]:3306`；不能带协议、凭据、路径、空白；保存时主机会转成小写 | `10.0.0.5:3306` | 见下面「入口地址 / 后端地址的错误提示」 |
| 后端 TiDB 列表（可选） | 这个负载均衡实际转发到的 TiDB，平台用它与拓扑做一致性对照 | 每行一个 `主机:端口`（TiDB 的 SQL 端口），最多 64 个，重复项保存时自动去重；**留空 = 不做一致性检查**；请按 **IP** 写，不要写域名（原因见「读懂负载均衡卡片」） | `10.0.1.11:4000` 换行 `10.0.1.12:4000` | 逐行校验；有问题显示「✖ 第 N 行「…」：<原因>」，多行有问题时追加「（另有 M 行有问题）」；超过 64 个「✖ 最多 64 个后端」 |
| 备注（可选） | 自由文字，如维护人、机房 | ≤200 个字，不能含控制字符 | `机房 A 的 VIP，由网络组维护` | 「✖ 备注最多 200 个字」 |

   「后端 TiDB 列表」下面有按钮「从拓扑填入当前全部 TiDB」（旁边小字「会覆盖文本框里的内容」）：点它，平台把拓扑里**所有** TiDB 的 `IP:SQL 端口` 填进文本框，并提示「已填入 N 个 TiDB」。适用于所有 TiDB 都在这个负载均衡后面的常见情况；如果这个负载均衡只负责其中一部分，请填入后删掉多余的行。没有实时拓扑数据时按钮置灰（悬停「没有实时拓扑数据」），拓扑里没有 TiDB 时提示「当前拓扑里没有 TiDB 实例」。
   填了后端以后，文本框下面还会给出即时对照：「✔ 与当前拓扑里的 TiDB 完全一致」，或黄字「⚠ 与当前拓扑对比：N 个后端不在拓扑里；拓扑里有 M 个 TiDB 未包含（可保存，保存后会在卡片和图里提示）」——黄字只是提醒，**不阻止保存**。
   如果这个负载均衡后面接的是 TiProxy（例如 HAProxy 在 TiProxy 前面）而不是直接接 TiDB，后端列表填 TiProxy 的地址会被判成「拓扑里没有」，且所有 TiDB 都会被判成「未登记」；这种情况请把「后端 TiDB 列表」**留空**（按平台的比对规则推断，以实际界面为准）。

5. 点抽屉底部的「登记」。
   - 你会看到：抽屉关闭，页面弹出提示「已登记负载均衡 <名称>」，「手工登记」表多出一行，标题处计数「N / 20 条」加一。
   - 与预期不符：抽屉里出现红色提示 → 对照下面「保存失败时的提示」。
6. 回到 [集群架构](go:arch) 核对：图上方「负载均衡层」多了一个方框，标题括号里出现「手工登记 N」。

**入口地址 / 后端地址的错误提示**（输入时就会在输入框下面显示，保存时再检查一遍）

| 你填的 | 提示 | 怎么改 |

| `[::1]3306` | IPv6 格式应为 [::1]:3306 | 方括号后加冒号 |
| `10.0.0:3306`、`300.1.1.1:3306` | 主机部分不是合法的 IP 或主机名 | 纯数字加点但不是合法 IPv4 的写法一律拒绝；改成正确 IP 或域名 |
| `10.0.0.5:0`、`10.0.0.5:70000`、`10.0.0.5:abc` | 端口需为 1–65535 的整数 | 改端口 |

| 提示 | 原因 | 怎么办 |

| 参数不合法：… | 后端的校验没通过（前端已拦截的情况下通常不会出现，除非前端与后端规则有出入或有人直接调接口） | 按「…」里的具体原因修改 |

### 读懂负载均衡卡片

卡片从上到下：

| 区域 | 内容 | 怎么读 |
|---|---|---|
| 权限提示（黄色，仅无权限时） | 「你没有「修改平台设置」（settings.edit）权限，负载均衡登记为只读…」 | 你只能看，不能登记 / 编辑 / 删除 |
| 生效判定（绿色或黄色） | 绿色「✔ 当前平台认为集群前有负载均衡。」或黄色「⚠ 当前平台认为集群前没有负载均衡。」，后面跟「依据：…」和对缩容 / 维护的影响，下面一行小字说明复选框保持不变 | 决定缩容 / 维护 TiDB 时有没有人工摘除步骤；三种「依据」见「与原有复选框的关系」 |
| 一致性提示（黄色，最多 3 条） | 「拓扑里有但未登记的 TiDB（负载均衡 <名称>（<入口>））：…」「登记了但拓扑里没有的后端（负载均衡 …）：…」；超过 3 条时再追加「另有 N 条登记的后端与拓扑不一致，见下表中标有「与拓扑不一致」的行（点「详情」查看差异）。」 | 见下面「一致性提示怎么处理」 |
| 「自动发现的 TiProxy」表 | 标题后小字「来自 tiup cluster display · 只读 · N 个」；列：实例 id / 地址 host:sqlPort / API 端口 / 状态 / 来源（「自动发现」） | 只读，不能编辑、不能删除。没有时一行「未发现 TiProxy（集群里没有 TiProxy 组件，或平台还没有拓扑快照）」 |
| 「手工登记」表 | 标题后小字「N / 20 条」；列：类型 / 名称（下面小字是 id）/ 入口 / 后端数 / 备注 / 更新人 · 时间 / 操作 | 「后端数」显示「N 个」或「未登记」，有差异时加黄色标签「与拓扑不一致」；操作列有「详情」「编辑」「删除」。没有时一行「还没有手工登记。若集群前有 HAProxy / LVS / 云 SLB 等，点右上角「＋ 登记负载均衡」。」 |
| 底部小字 | 「登记是平台元数据，不会改动 HAProxy / LVS 本身，也不要求打开写操作开关、不走审批（会写入审计：lb.add / lb.update / lb.delete）…」 | 即本节说的不影响项 |

右上角的「刷新」：重新读取一遍并提示「已刷新」（失败提示「刷新失败」）。卡片读取失败时显示红色提示：「没有权限读取负载均衡信息（需要「查看总览」能力）」「后端不支持负载均衡接口（版本较旧？）」「无法连接后端」或「读取失败（HTTP 状态码）」。

**一致性提示怎么处理**

| 提示 | 含义 | 处理 |
|---|---|---|
| 「拓扑里有但未登记的 TiDB」（missing） | 拓扑里有这台 TiDB，该登记的后端里没有 | 常见于刚扩容的 TiDB。先到负载均衡上确认它是否已被加入后端：没加，自己在负载均衡上加（平台不会替你加）；加了，就「编辑」登记补上这个后端。这台 TiDB 本来就不在这个负载均衡后面时，要么接受提示，要么把该登记的后端留空 |
| 「登记了但拓扑里没有的后端」（extra） | 登记里有这个地址，拓扑里没有对应的 TiDB | 常见于 TiDB 已缩容下线、地址或端口写错、写成了域名。核对后「编辑」登记删掉或改正；注意端口要写 TiDB 的 SQL 端口 |
| 域名与 IP 的陷阱 | 平台拿登记的后端与拓扑里的 `IP:端口` 做字符串比较（主机名不区分大小写），**不会做 DNS 解析**。后端登记成域名 `tidb-1.example.com:4000` 而拓扑里是 `10.0.1.11:4000` 时，这一台会**同时**出现在上面两种提示里 | 后端一律按 **IP** 登记 |
| 没有提示 | 要么一致，要么没有可对照的数据 | 「手工登记」表里，没登记后端的行不做检查；刚启动、还没有拓扑快照时，详情里会写「尚无拓扑快照，无法对照」，稍后点「刷新」 |

对照的是平台缓存的拓扑快照（页面顶部横幅「采集于 hh:mm:ss」），扩缩容后要等下一次快照才会变化，可点横幅的「立即刷新」。这些提示**只是提醒，不会拦截任何操作**。

### 编辑一条登记

**前置条件**：同「登记一条负载均衡」（运维模式、settings.edit、选对集群）。**后果**：只改平台里的记录，不改你的负载均衡设备；已经生成的变更计划不变，之后新生成的计划按新内容点名。

1. 在「负载均衡」卡片的「手工登记」表里找到那一行，点该行「编辑」。
   - 你会看到：右侧抽屉「编辑负载均衡：<名称>」，字段与登记时相同，但 id 只显示、不能改（旁边写「（不可修改）」）。
2. 修改需要改的字段（规则与提示同「登记一条负载均衡」），按钮是「保存」而不是「登记」。
3. 点「保存」。
   - 你会看到：抽屉关闭，提示「已保存 <名称>」，表里该行的「更新人 / 时间」变成你和当前时间。
   - 提示「找不到该负载均衡登记：<id>（可能已被他人删除）」：见上面「保存失败时的提示」。

> ⚠️ 登记簿没有版本历史，更新是「最后保存的人胜出」：两位管理员同时改同一条，后保存的会覆盖先保存的，只能靠审计日志追溯。改之前先点「刷新」看最新内容。

### 删除一条登记

**前置条件**：同上。**后果**：只删除平台里的记录，**不会改动那台负载均衡设备本身**；删除后不能撤销（没有回收站），要恢复只能重新登记。

1. 在「手工登记」表里点该行红色的「删除」。
   - 你会看到：确认框「删除负载均衡登记」，内容「确认删除负载均衡登记 <名称>（<类型>，入口 <入口地址>）？只删除平台里的登记信息，不会改动该负载均衡设备本身。」
   - 如果这是**最后一条**登记（且「集群前有负载均衡」复选框没勾），还会多一行：「这是最后一条登记：删除后（且未勾选「集群前有负载均衡」），缩容 / 维护 TiDB 时将不再要求人工摘除。」——这意味着之后缩容 TiDB 会**直接下线**而不再让你先摘除，请想清楚再点。
2. 点「确认删除」（不删点「取消」）。
   - 你会看到：提示「已删除 <名称>」，该行消失；图上对应方框消失。如果别人已经删掉了它，提示「该登记已不存在」。

### 与原有复选框的关系

「平台设置」卡片里原有的复选框「集群前有负载均衡」**保持不变**。平台判断「集群前有没有负载均衡」用的是**有效值**：

`有效值 = 复选框已勾选 或 已登记至少一条手工登记`

「负载均衡」卡片的生效判定里写出了依据，共三种：

| 依据 | 界面文字 | 什么情况 | 缩容 / 维护 TiDB 时 |
|---|---|---|---|
| 旧开关（`legacy-flag`） | 「依据：已勾选上方「平台设置」卡片里的复选框「集群前有负载均衡」（旧开关）；同时也登记了 N 条具体设备」或「…；还没有登记具体设备」 | 复选框已勾选（不管有没有登记） | 有人工摘除步骤；有登记时点名登记的入口，没登记时用通用文案 |
| 手工登记（`manual`） | 「依据：已手工登记 N 条负载均衡（未勾选旧开关）。」 | 复选框没勾，但登记了至少一条 | 有人工摘除步骤，并点名所有登记的入口 |
| 都没有（`none`） | 「依据：既没有勾选「集群前有负载均衡」，也没有手工登记任何负载均衡。」 | 两者都没有 | **没有**人工摘除步骤，TiDB 会被直接下线 / 停止；若集群前其实有负载均衡，请登记或勾选 |

**自动发现的 TiProxy 不参与这个判定**：图上有 TiProxy，也不会让缩容 / 维护 TiDB 多出人工摘除步骤。原因与依据：

- 官方说明 TiProxy 能自动发现 TiDB server 列表，并在 TiDB 缩容、滚动升级、滚动重启时把连接迁移到其他 TiDB，从而保持客户端连接不断开（[TiProxy 简介](https://docs.pingcap.com/zh/tidb/stable/tiproxy-overview/)）；但这要求事先配好 TiDB 的 `graceful-wait-before-shutdown`——官方要求它**比应用最长事务的持续时间大 10 秒以上**，否则 TiDB 下线时客户端连接可能中断。官方同时列出限制，例如 TiDB 意外故障（非计划内维护）时无法保持连接。
- 平台**还没有在真实集群里验证**：缩容 / 维护 TiDB 时 TiProxy 发现后端的延迟、连接迁移是否优雅、你的集群有没有配 `graceful-wait-before-shutdown`，都未验证（以真实集群联调为准）。所以平台保守地不替你判断，仍由复选框 / 手工登记决定。
- 怎么选：只有 TiProxy、并且你已按官方文档配好 `graceful-wait-before-shutdown`、确认连接迁移符合预期 → 可以不勾选、不登记，缩容 / 维护 TiDB 时直接下线；想保留一道人工确认 → 勾选「集群前有负载均衡」（会得到通用文案「把 <实例> 从负载均衡后端摘除，并等待连接排空，确认后继续」）。**不要为此再登记一条类型「TiProxy（自部署）」**：它与自动发现的是同一台，平台不去重，图上会出现两次。

### 登记会影响什么、不影响什么

**会影响（对平台自己）**

| 对象 | 影响 |
|---|---|
| 「集群架构」图 | 负载均衡层多一个方框；后端与拓扑对不上时方框变黄并提示 |
| 缩容 TiDB（[节点管理](go:nodes)「缩容 / 下线」） | 变更计划多一步「从负载均衡摘除并等待连接排空」（需人工确认）。文案点名**全部**已登记的入口：「先从负载均衡 <名称>（<类型>，<入口地址>）摘除 <host:端口>，并等待连接排空，确认后继续」，登记了多条时用「、」连起来（不区分这台 TiDB 是不是该登记的后端，登记的入口都会被点名）；没登记（只勾了复选框）时是「把 <host:端口> 从负载均衡后端摘除，并等待连接排空，确认后继续」 |
| 进入 / 结束主机维护（含 TiDB 的主机） | 进入维护多一步「从负载均衡摘除并排空连接」；结束维护多一步「重新加入负载均衡并恢复流量」，文案「把 <host:端口> 加回负载均衡 <名称>（<类型>，<入口地址>） 的后端并确认流量恢复」，没登记时是「把 <host:端口> 加回负载均衡后端并确认流量恢复」 |
| 审计日志 | 每次登记 / 编辑 / 删除都留痕，见下 |

这些人工步骤的操作方法和「点确认意味着什么」见 [节点管理帮助](help:nodes)。

**不会影响**

- **不会改动 HAProxy / LVS / Nginx / SLB / F5 / TiProxy 本身**：平台根本不连接它们（没有它们的地址以外的任何信息，也没有它们的账号）。
- **不会探测它们的健康状态**：图上登记方框没有「运行中 / 已停止」，因为平台不知道。
- **不会自动摘除或加回后端**：真正的摘除 / 加回永远是你自己在负载均衡上做的人工步骤。
- **不影响扩容 TiDB**：扩容 TiDB 本来就总有「把新 TiDB 加入负载均衡」的人工确认步骤，与有没有登记无关，登记也不会被自动更新（新 TiDB 加进负载均衡后，要自己回来「编辑」登记补上后端）。
- **不影响单实例的重启 / 停止 TiDB**（没有摘除步骤，请自己先摘）、滚动重启、滚动升级。
- **不影响 TiDB 集群本身**：不会重启任何组件，不产生变更单，不需要写操作开关。

**审计**：动作 `lb.add`（登记）、`lb.update`（编辑）、`lb.delete`（删除），风险「中」，目标是登记 id；摘要只写变更的**字段名**和入口地址，例如「修改负载均衡登记 生产 HAProxy 主：修改字段 addr,backends，入口 10.0.0.6:3306」，**不写备注原文**。校验失败、id 冲突、超过上限、写盘失败也会记一条，结果为「失败」；越权（非管理员）由通用的 `authz.deny` 记录。到 [权限与审计](go:security) 的「审计日志」里按动作检索。

**多集群**：登记按集群各存一份；切换顶栏集群后看到的是那个集群自己的登记，互不影响。新接入的集群没有任何登记，需要在它自己里面再登记一遍。


「写操作开关」「变更冻结期」在此卡片只显示状态：开启写操作需要**两名不同管理员**先后确认（提议后 1 小时内由另一人确认），关闭只需一名管理员立即生效，到 [权限与审计](go:security) 管理；冻结期到 [变更排期](go:schedule) 管理。

### 修改「用户自定义设置」（运维模式 3 项）

| 设置项 | 默认值 | 说明 |
|---|---|---|
| 登录方式 | 本地账号（可选 LDAP / OIDC 企业 SSO） | **仅记录，不生效**：当前后端只有本地账号 + 口令登录，没有 LDAP / SSO。本地 TOTP 不是登录方式，只用于高风险变更提交时的申请人二次确认 |
| 平台元数据存储 | SQLite（单机）（可选 MySQL / TiDB） | **仅记录，不生效**：当前后端把用户、审计、变更、设置存在数据目录下的 JSON 文件里 |
| 审计保留期（天） | 180 | **仅记录，不生效**：审计日志只追加，当前没有按天清理的机制；输入框不做数字校验 |

修改下拉框后立即保存；文本框修改后点页面空白处（失去焦点）或按回车保存；保存成功提示「设置已保存到后端」。保存值只是一个字符串写进 `settings.json`，改回默认值等于删除该覆盖。静态原型与只读模式里还会看到「通知渠道、备份窗口、业务高峰、推荐低峰、变更冻结期、测试 / 预发 / 生产环境允许写操作」这些项，它们只是原型演示，值既不保存也不生效；运维模式下已被下面的真实功能替代并隐藏。

### 配置通知渠道（完整流程）

通知渠道把「变更待审批、执行失败、新出现严重告警」等事件推送到企业微信 / 钉钉 / 飞书 / Lark / Slack 群，或者推送到你自己的接收端（「其他」：通用 JSON Webhook）。整个流程分四步：先在 IM 平台创建机器人（「其他」则先准备好接收端地址），再在本平台添加渠道，然后发送测试，最后按需调整订阅。

**先确认集群**：通知渠道是**每个集群各自一份**。先在顶栏切换到你要配置的集群，核对卡片标题里的「集群 显示名」；想让多个集群都往同一个群发消息，就在每个集群下各添加一次渠道。消息正文里会带「环境：…　集群：<tiup 集群名>」，收到消息时据此区分是哪个集群。

**前置条件**：运维模式、已登录、具备 settings.edit（没有时卡片只显示「需要管理员权限：查看与管理通知渠道需要「修改平台设置」（settings.edit）」）；**平台所在的中控机能直接访问 IM 官方域名的 443 端口**（平台不读取 `HTTP_PROXY` 等环境代理，也没有代理启动参数）；你在目标群里有添加机器人的权限。

#### 第一步（企业微信）创建机器人并拿到 Webhook

官方文档：[企业微信「消息推送配置说明」](https://developer.work.weixin.qq.com/document/path/91770)（现称「消息推送」，原名「群机器人」）。

1. 在企业微信客户端打开要接收通知的群，在群设置里找到「添加群机器人 / 消息推送」入口新建一个机器人（入口名称随客户端版本而变，以你的客户端为准），填名称。
2. 创建完成后复制 Webhook 地址，形如 `https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=xxxxxxxx`。官方说明创建者可在「创建消息推送页面、创建完成页面、消息推送详情页面」看到该地址。
3. 保密该地址：官方明确要求不要分享到 github、博客等可公开查阅的地方。
4. 安全设置：上述官方页面没有提到加签、关键词或 IP 白名单这类设置；平台里「加签密钥」框因此是灰的，**Webhook 地址本身就是唯一凭据**，务必保密。
5. 频率与长度：官方限制每个机器人每分钟不超过 20 条，markdown 消息不超过 4096 字节（平台按此限速和截断）。

#### 第一步（钉钉）创建机器人并拿到 Webhook

> ⚠️ 钉钉开放平台的文档页面是前端渲染的，本帮助未能自动抓取正文核实，所以不附链接。下面的步骤与限制来自平台代码约定和钉钉自定义机器人的常见说明，请以钉钉开放平台「自定义机器人接入」文档与你客户端的实际界面为准。

1. 在钉钉客户端打开目标群，群设置里进入「机器人」（智能群助手），选择「添加机器人」→「自定义（通过 Webhook 接入）」，填机器人名称。
2. 在「安全设置」里**至少选一种**（常见说明要求至少一种）：
   - 加签：钉钉生成一串以 `SEC` 开头的密钥，复制保存。**推荐**，平台完整支持。
   - 自定义关键词：消息内容里必须含其中一个关键词。若选此项，设为 `TiDB`；但平台消息里含「[TiDB 运维]」的是标题字段，正文不一定含「TiDB」，钉钉是否把标题计入匹配请以第三步的「发送测试」结果为准。
   - IP 地址段：只有来自该 IP 段的请求才被接受，填中控机访问外网的出口 IP（向网络管理员确认，通常是 NAT 后的公网 IP）。
3. 完成后复制 Webhook 地址，形如 `https://oapi.dingtalk.com/robot/send?access_token=xxxxxxxx`。
4. 钉钉自身也有频率限制（常见说明是每个机器人每分钟 20 条，超限会被短暂限流），请不要让平台订阅过多高频事件。

#### 第一步（Lark）创建机器人并拿到 Webhook

官方文档：[Lark「自定义机器人使用指南」](https://open.larksuite.com/document/client-docs/bot-v3/add-custom-bot)。

1. 在 Lark 目标群的群设置里依次进入「群机器人」→「添加机器人」→「自定义机器人」，设置名称与描述，点「添加」。
2. 复制 Webhook 地址，形如 `https://open.larksuite.com/open-apis/bot/v2/hook/xxxxxxxx`，并妥善保管。
3. 按官方文档的三种安全设置选择（可多选）：
   - 签名校验：官方要求请求体带 `timestamp`（秒）与 `sign`，时间戳须在一小时以内。**推荐**，平台完整支持，把页面给出的密钥填进平台的「签名校验密钥」。
   - 自定义关键词（最多 10 个，消息需含其一）：平台 Lark 消息的第一行总是「[TiDB 运维]【级别】标题」，所以关键词可设为 `TiDB 运维`。
   - IP 白名单（支持 `123.12.1.*` 或 `123.1.1.1/24` 这种写法）：填中控机访问外网的出口 IP。
4. 官方限制：单租户单机器人每分钟 100 次、每秒 5 次，请求体不超过 20 KB。
5. 飞书（国内版，域名 `open.feishu.cn`）请选下面的「飞书」类型。以前用 Lark 类型填了 `open.feishu.cn` 地址的渠道仍然可用（兼容旧配置），不需要重建。

#### 第一步（飞书）创建机器人并拿到 Webhook

官方文档：[飞书「自定义机器人使用指南」](https://open.feishu.cn/document/client-docs/bot-v3/add-custom-bot)。飞书（国内版）和 Lark（国际版）的机器人做法一样，只是域名不同；在平台里请选「飞书群机器人」类型。

1. 在飞书目标群里点右上角「更多」→「设置」，在右侧面板进入「群机器人」，点「添加机器人」→「自定义机器人」。
2. 设置头像、名称与描述，点「添加」。
3. 复制 Webhook 地址，形如 `https://open.feishu.cn/open-apis/bot/v2/hook/xxxxxxxx`，点「完成」。官方明确要求妥善保存，不要公布在 Gitlab、博客等可公开查阅的地方，防止被人恶意调用。
4. 按官方文档的三种安全设置选择（可多选，建议至少开一种）：
   - 签名校验：官方算法是 `HmacSHA256(timestamp + "\n" + 密钥)` 再 Base64，时间戳距当前不能超过 1 小时。**推荐**，平台完整支持，把页面给出的密钥填进平台的「签名校验密钥」。
   - 自定义关键词（最多 10 个，消息需含其一，只对文本类字段生效）：平台飞书消息的第一行总是「[TiDB 运维]【级别】标题」，所以关键词可设为 `TiDB 运维`。
   - IP 白名单（最多 10 个，支持单个 IP 或 `123.12.1.*`、`123.1.1.1/24` 这种地址段）：填中控机访问外网的出口 IP。
5. 官方限制：单租户单机器人每分钟 100 次、每秒 5 次，请求体不超过 20 KB；官方建议避开整点和半点发送。
6. 保密 Webhook 地址；怀疑泄露就在飞书里删除机器人重建，再到平台里「编辑」换成新地址。

#### 第一步（Slack）创建机器人并拿到 Webhook

官方文档：[Slack「Sending messages using incoming webhooks」](https://docs.slack.dev/messaging/sending-messages-using-incoming-webhooks/)。Slack 没有「群机器人」这个入口，要先建一个 Slack App，再给它开通 Incoming Webhooks。你需要有在该工作区创建 App 并授权的权限（部分工作区由管理员限制，见下面的 `action_prohibited`）。

1. 打开 [api.slack.com/apps](https://api.slack.com/apps)，点「Create New App」（官方文档里写作 Create an app）：输入应用名称（例如 `TiDB Ops`），选择要发消息的工作区，点「Create」。
2. 进入这个应用的设置页，在左侧找到「Incoming Webhooks」，把「Activate Incoming Webhooks」开关打开。
3. 页面下方点「Add New Webhook to Workspace」，选择要接收通知的频道（每个 Webhook 绑定一个频道），点「Authorize」（允许）。
4. 回到「Incoming Webhooks」页，复制新生成的 Webhook URL，形如 `https://hooks.slack.com/services/T00000000/B00000000/XXXXXXXXXXXXXXXXXXXXXXXX`。
5. 保密这个地址：官方说明它含有密钥，不要公开分享（包括公开的代码仓库），Slack 会主动搜索并撤销泄露的密钥。
6. 在平台里选「Slack」类型，Webhook URL 粘贴上面的地址。**Slack Incoming Webhook 没有签名校验**，平台里的签名密钥框是灰的，Webhook 地址本身就是唯一凭据；想换频道就重新在 Slack 里 Add New Webhook 一次，再到平台里「编辑」换地址。
7. 成功判定：Slack 对成功的请求返回 HTTP 200 和纯文本 `ok`，平台据此判定；失败时响应体是一个错误码，平台会把它带进错误信息，常见的见下面「测试失败排查」。
8. 频率：Slack 官方这篇文档没有给出 Webhook 的频率限制数字；平台仍按每渠道每分钟最多 20 条限速，请不要订阅过多高频事件。
9. 消息格式：平台发 `{"text": …}` 的 mrkdwn 文本，标题加粗、明细用「•」列表，链接显示为「查看详情」。标题或明细里的 `&` `<` `>` 会被转义，`*` `_` `~` 会换成全角字符，所以不会因为变更标题里带了 `<!channel>` 之类的内容而误触发 @ 通知。

#### 第一步（其他）准备通用 Webhook 接收端

「其他」类型用来把通知送到平台没有专门适配的系统（自建网关、告警中转、企业内部 IM 机器人、Teams / Mattermost 的转发服务等）。平台只负责按固定格式 POST JSON，接收端怎么处理由你决定。

1. 准备一个 **https** 接收地址，例如 `https://hooks.example.com/tidbops`，它必须能被中控机访问。
2. **请管理员把这个主机加入允许主机**：「其他」没有官方域名，只有出现在服务启动参数 `--notify-allow-hosts`（逗号分隔，可写 `host` 或 `host:port`）里的主机才允许；改完要重启平台。只有这种额外允许的主机才可以是内网地址，也才可以用非 443 端口。不在列表里保存时会报「「其他」类型的 Webhook 主机 X 不在允许列表：需由管理员在启动参数 --notify-allow-hosts 里加入该主机」。

**请求格式**：接收端会收到 `POST`，`Content-Type: application/json`，请求体形如：

```json
{
  "source": "tidb-ops",
  "version": 1,
  "event": "change.failed",
  "level": "critical",
  "title": "变更执行失败",
  "env": "prod",
  "cluster": "prod-tidb-01",
  "lines": ["变更：重启 tikv-2（CHG-20260101-001）", "风险：中", "申请人：dba"],
  "link": "https://ops.example.com/#schedule",
  "time": "2026-01-02T03:04:05+08:00",
  "text": "[TiDB 运维]【严重】变更执行失败\n环境：prod　集群：prod-tidb-01\n…"
}
```

字段含义：`event` 是事件键（见下文「可订阅的事件」，测试消息是 `test`）；`level` 取 `info` / `success` / `warning` / `critical`；`lines` 是明细行（不含命令、命令输出、凭据与完整 SQL）；`link` 仅在服务配置了 `--public-url` 时才有；`text` 是同一条消息的纯文本渲染，接收端想直接转发到聊天工具时用它最省事；`version` 是载荷版本，目前固定为 1。

**签名（可选）**：在平台里给渠道填了「签名密钥」，每个请求会多两个请求头：

- `X-TiDBOps-Timestamp`：发送时间，Unix 秒。
- `X-TiDBOps-Signature`：`sha256=` 加十六进制字符串，计算方法是 `HMAC-SHA256(key=你填的密钥, msg=时间戳 + "." + 原始请求体)`。

接收端应当：用同样的方法算一遍并做常量时间比较；检查时间戳与当前时间相差不大（例如 5 分钟内），防重放。不填密钥就没有这两个头，此时请用网络层手段（IP 白名单、网关鉴权）保护接收端。

**成功判定**：接收端返回任意 2xx（200 / 202 / 204 都行）就算成功，响应体不解析；3xx 重定向、4xx、5xx 都算失败（重定向不会被跟随，也不重试）。请尽快返回，平台单次请求超时 10 秒。

**限速与重试**：平台对「其他」同样限速（每渠道每分钟 20 条）、去重和失败重试 3 次，规则见下文「消息内容与投递限制」。

#### 第二步 在本平台添加渠道

1. 在「环境与设置」页面向下找到「通知渠道」卡片，点右上角「＋ 添加渠道」。
   - 你会看到：右侧抽屉「添加通知渠道」。如果按钮是灰的并有红色提示「渠道文件读取或解密失败，当前为只读」，见下文「常见问题」。
2. 「渠道类型」从下拉框选：「企业微信群机器人」「钉钉群机器人」「飞书群机器人」「Lark（国际版）自定义机器人」「Slack」「其他（通用 Webhook）」。**创建后不能改类型**，选错只能删除后新建。选了类型后，输入框下面会显示该类型的地址示例；选「其他」时还会提示「主机必须由管理员在启动参数 --notify-allow-hosts 里加入」。
3. 「名称」填一个好认的名字，1–40 个字符、不含换行，例如 `DBA 值班群`。它会显示在列表、投递记录和测试消息里。
4. 「Webhook URL」粘贴第一步复制的**完整地址**（含 `key=` 或 `access_token=`）。
   - 要求：必须是 https；不能含用户名口令或 `#`；长度不超过 1024；官方域名下路径必须符合所选类型的形态；官方域名不能指定 443 以外的端口。
5. 「加签密钥」：钉钉填 `SEC` 开头的密钥（标签「加签密钥（SEC 开头）」）；飞书、Lark 填「签名校验密钥」；「其他」填你和接收端约定的签名密钥（标签「签名密钥（可选，HMAC-SHA256）」，占位提示「可选：填写后每次请求附带 HMAC-SHA256 签名头」）；企业微信和 Slack 该框禁用（企业微信无签名校验，Slack Incoming Webhook 无签名校验）。没有开启加签 / 签名校验就留空（最长 128 字符、不含换行）。
6. 「订阅事件」勾选这个渠道要接收的事件；**一个都不勾 = 订阅全部**，全选等价于订阅全部；「全选 / 清空」是快捷链接。事件说明见下文表格。值班群建议只勾「有变更等待审批」「变更执行失败」「新出现严重告警」。
7. 保持「启用该渠道」勾选，点「保存」。
   - 你会看到：抽屉关闭，提示「渠道已添加」，列表新增一行：类型、名称（配置了密钥会带「已加签」）、Webhook（已脱敏，只显示末 4 位）、订阅事件、状态「启用」。
   - 与预期不符：抽屉里红字提示「请填写渠道名称」「请填写 Webhook URL」或服务端校验原因（见下表「保存失败」）；修正后再点「保存」。

#### 第三步 发送测试并确认

1. 在渠道行点「发送测试」。
   - 你会看到：按钮短暂变成「发送中…」；该行下方出现绿字「✔ 测试消息已发送（时间）」，同时提示「测试消息已发送」；目标群里收到一条标题含「[TiDB 运维]」前缀、内容为「这是一条测试消息，收到说明渠道「名称」配置正确。」的消息。
   - 「已发送」表示机器人接口返回成功（企业微信 / 钉钉要求 errcode 为 0，飞书 / Lark 要求 code 为 0，Slack 要求 HTTP 200 且响应体为 `ok`，「其他」要求任意 2xx），不代表群里每个人都看到了；以群里实际收到为准。
2. 在卡片下方「最近投递记录」确认多了一条事件为「测试消息」、结果「✔ 成功」的记录。
3. 失败时该行下方显示红字「✖ 测试失败：原因」，按下表排查，修正后重新「发送测试」。

测试失败排查（原因文本会已对令牌和密钥打码）：

| 失败提示 | 原因 | 处理 |
|---|---|---|
| 保存时：「Webhook 地址必须是 https」 | 地址以 `http://` 开头 | 改成 https 地址 |
| 保存时：「主机 X 属于企业微信，与所选渠道类型（钉钉）不匹配」之类 | 渠道类型与地址的平台不一致 | 删除后用正确类型新建 |
| 保存时：「主机 X 不在允许列表…」 | 不是官方域名 | 复制官方 Webhook；确需私有网关，由管理员用启动参数 `--notify-allow-hosts` 追加主机并重启平台 |
| 保存时：「企业微信 / 钉钉 / 飞书 / Lark / Slack Webhook 形如 …」 | 地址路径或必需参数不对（Slack 的路径必须是 `/services/T…/B…/…` 四段） | 重新复制完整地址（企业微信 / 钉钉须含 `key=` / `access_token=`） |
| 保存时：「「其他」类型的 Webhook 主机 X 不在允许列表：需由管理员在启动参数 --notify-allow-hosts 里加入该主机」 | 「其他」没有官方域名，主机不在管理员配置的允许主机里 | 让管理员把该主机加入 `--notify-allow-hosts` 并重启平台，再保存 |
| 保存时：「Slack Incoming Webhook 没有签名密钥」 | 给 Slack 渠道填了签名密钥 | 把密钥框留空 |
| 保存时：「渠道类型必须是 wecom、dingtalk、feishu、lark、slack 或 other」 | 通过接口直接提交了不认识的类型（页面下拉不会出现） | 改用上面 6 个类型之一 |
| 保存时：「官方域名的 Webhook 不能指定非 443 端口」「不能包含 # 片段」「不能包含用户名口令」「Webhook 地址过长 / 格式不正确」 | 地址被改动或粘贴不完整 | 重新复制 |
| 保存时：「渠道名称长度须在 1–40 个字符之间」「签名密钥过长」「渠道数量已达上限（20）」 | 字段超限 | 按提示修改 / 删除不用的渠道 |
| 「目标地址属于回环 / 私网 / 链路本地地址，已拒绝（防 SSRF）」 | 域名在中控机上被解析到了内网地址（如内网 DNS 劫持、hosts 配置） | 检查中控机 DNS 与 `/etc/hosts`，使官方域名解析到公网 |
| 超时、连接被拒、`i/o timeout` 之类的网络错误 | 中控机出不去外网、防火墙未放行 443，或必须经代理才能出网（平台不走代理） | 让网络管理员放行中控机到官方域名的 443；必须经代理的环境需另行评估 |
| 「收到重定向响应，已拒绝跟随」 | 出口网关把请求重定向了（常见于认证门户） | 让该域名免认证直连 |
| 「HTTP 4xx / 5xx」或「响应不是合法 JSON」 | 被中间设备拦截，或官方接口异常 | 在中控机用 `curl` 访问同一域名对比；稍后重试 |
| 「errcode=…：…」（企业微信 / 钉钉） | 机器人接口返回了非 0 错误码，冒号后是官方 errmsg | 对照官方文档查该错误码；钉钉常见原因是关键词不匹配、签名错误或 IP 不在白名单，企业微信常见原因是 Webhook 的 key 无效或超频 |
| 「飞书 返回 code=19021」或「Lark 返回 code=19021」 | 签名错误，或时间戳与当前时间相差超过一小时 | 核对密钥；让中控机用 NTP 校时 |
| 「飞书 返回 code=19022」或「Lark 返回 code=19022」 | 请求 IP 不在机器人的 IP 白名单 | 把中控机出口 IP 加入白名单 |
| 「飞书 返回 code=19024」或「Lark 返回 code=19024」 | 消息不含机器人设置的关键词 | 关键词设为 `TiDB 运维`，或改用签名校验 |
| 「飞书 返回 code=11232」或「Lark 返回 code=11232」 | 触发飞书 / Lark 频率限制 | 减少订阅事件或稍后重试 |
| 「Slack 返回 HTTP …：invalid_payload」 | 请求体格式不被 Slack 接受 | 先用 curl 向同一地址 POST `{"text":"hi"}` 对比；排除中间设备改写了请求 |
| 「Slack 返回 HTTP …：no_service」或 `no_active_hooks` | 这个 Incoming Webhook 已被停用或删除（也可能是泄露后被 Slack 撤销） | 在 Slack 里重新「Add New Webhook to Workspace」，在平台「编辑」里换成新地址 |
| 「Slack 返回 HTTP …：channel_not_found」或 `channel_is_archived` | 绑定的频道不存在或已归档 | 重新生成绑定到有效频道的 Webhook |
| 「Slack 返回 HTTP …：action_prohibited」 | 工作区管理员限制了这类消息的发送方式 | 联系 Slack 工作区管理员 |
| 「Slack 返回非预期内容：…」 | HTTP 200 但响应体不是 `ok`，多半是被代理 / 网关拦截返回了别的页面 | 在中控机用 `curl` 访问同一地址对比 |
| 「其他」渠道：「HTTP 4xx」「HTTP 5xx」 | 接收端拒绝或出错（如签名校验不过、鉴权失败） | 看接收端日志；确认签名算法与时间戳校验一致 |
| 「其他」渠道：「收到重定向响应，已拒绝跟随」 | 接收端或网关把请求重定向了（常见于 http→https、登录门户） | 直接填最终的 https 地址 |

> 💡 飞书 / Lark 的 19021 / 19022 / 19024 / 11232 含义来自官方「自定义机器人使用指南」；Slack 的错误码含义来自 Slack 官方「incoming webhooks」文档，没有列出的错误码以官方文档为准；企业微信、钉钉的 errcode 请以各自官方文档为准。「飞书 返回 …」与「Lark 返回 …」只是按渠道类型加的前缀，含义相同。

#### 第四步 日常调整

| 想做什么 | 怎么做 | 后果 |
|---|---|---|
| 改订阅 / 改名 | 渠道行点「编辑」，改完点「保存」，提示「渠道已更新」 | 立即生效；Webhook URL 和密钥留空表示不修改 |
| 换 Webhook 或密钥 | 「编辑」里填新值；要删掉密钥，勾选「清除已设置的密钥」 | 旧值被覆盖，无法找回 |
| 暂停通知 | 取消该行「状态」复选框（提示「渠道已停用」） | 不再收到事件，但仍可「发送测试」；比删除安全 |
| 删除渠道 | 点「删除」，在确认框「删除通知渠道」里点「确认删除」，提示「渠道已删除」 | Webhook 配置无法找回 |

以上所有改动、测试都写审计（`notify.channel.add / update / delete / test`），不需要审批，保存后立即生效，不需要重启平台。

**Webhook URL 的允许范围**：

| 类型 | 官方地址形态 | 额外说明 |
|---|---|---|
| 企业微信 | `https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=…` | 无签名校验 |
| 钉钉 | `https://oapi.dingtalk.com/robot/send?access_token=…` | 若机器人开启了「自定义关键词」，见上文钉钉步骤 |
| 飞书 | `https://open.feishu.cn/open-apis/bot/v2/hook/…` | 签名校验密钥可选 |
| Lark（国际版） | `https://open.larksuite.com/open-apis/bot/v2/hook/…`（为兼容旧配置也接受 `https://open.feishu.cn/open-apis/bot/v2/hook/…`） | 签名校验密钥可选 |
| Slack | `https://hooks.slack.com/services/T…/B…/…` | 无签名校验，不接受密钥 |
| 其他（通用 Webhook） | 没有官方域名：任意 https 地址，但主机必须在 `--notify-allow-hosts` 里 | 签名密钥可选（HMAC-SHA256 请求头）；任意 2xx 视为成功 |

只允许官方域名，且域名必须与所选渠道类型匹配（例如不能给「钉钉」类型填企业微信的地址）。私有化部署的网关主机必须由管理员用服务启动参数 `--notify-allow-hosts`（逗号分隔）追加，并重启服务；追加的主机才可以是内网地址。卡片底部会列出当前允许的主机。

**可订阅的事件**（共 12 个，抽屉里分「变更 / 维护 / 告警与诊断」三组）：

| 事件 | 触发时机 | 级别 |
|---|---|---|
| 有变更等待审批（change.pending） | 创建了需要审批的变更（免审批变更不发） | 警告 |
| 变更审批通过（change.approved） | 审批通过；多级审批时中间级会提示「已通过一级审批，等待下一级」 | 信息 |
| 变更被驳回（change.rejected） | 审批人驳回，带驳回原因 | 警告 |
| 变更开始执行（change.started） | 变更开始执行 | 信息 |
| 变更执行成功（change.succeeded） | 执行成功，带耗时 | 成功 |
| 变更执行失败（change.failed） | 执行失败，带失败步骤与摘要 | 严重 |
| 变更被中止（change.aborted） | 有人中止了执行 | 警告 |
| 变更已过期（change.expired） | 超过有效期仍未批准 / 执行 | 警告 |
| 变更等待人工确认（change.manual） | 执行到需要人工操作的步骤 | 警告 |
| 维护超过 PD 阈值（maint.overdue） | 主机维护时间超过 PD 判定 Store 下线的阈值 | 严重 |
| 新出现严重告警（alert.critical） | 后台每 60 秒取一次快照，对比上一轮，新出现的 critical 告警 | 严重 |
| 新出现严重诊断发现（diag.critical） | 同上，新出现的严重诊断项（只带标题、范围、可能原因，不带证据） | 严重 |

告警 / 诊断监视器的细节：平台启动后第一轮只记录基线、不发消息；告警恢复不通知；采集失败导致的空结果不会被当作「全部恢复」；每轮最多逐条发送 8 条，超出的合并成一条汇总。

没有的功能：当前**没有**「@某人」、「最低严重级别」、自定义消息模板、按集群 / 环境过滤；只能通过「订阅事件」筛选。只有 critical 级告警会触发 alert.critical。

**消息内容与投递限制**：

| 项 | 说明 |
|---|---|
| 内容 | 标题带前缀「[TiDB 运维]」，正文有环境、集群、变更标题与编号、风险、申请人 / 审批人、原因、时间；**不含命令、命令输出、凭据与完整 SQL**，并对形如 password=、token= 的片段做掩码 |
| 格式 | 企业微信、钉钉用 markdown，飞书 / Lark 用纯文本，Slack 用 mrkdwn 文本，「其他」用 JSON（含一份纯文本 `text`）；企业微信内容超过 4096 字节时从尾部按行丢弃明细 |
| 链接 | 仅当服务用 `--public-url` 配置了平台对外地址时才附带跳转链接 |
| 限速 | 每个渠道每分钟最多 20 条，超出的丢弃，投递记录里原因为「超出每分钟限速，已丢弃」 |
| 队列 | 全局队列 256 条，满了丢弃（原因「发送队列已满，已丢弃」） |
| 去重 | 相同「事件 + 去重键」10 分钟内只发一次；alert.critical、diag.critical、maint.overdue 为 30 分钟 |
| 重试 | 失败后按 1 秒、3 秒、9 秒退避，最多重试 3 次（总共最多尝试 4 次）；配置 / 安全类错误（地址校验失败、目标为内网地址、被重定向）不重试 |
| 超时 | 单次请求 10 秒，不跟随重定向，响应最多读 64KB |
| 存储 | 渠道保存在数据目录的 `notify.json`，Webhook 与密钥用 AES-256-GCM 加密，密钥来自数据目录下自动生成的 `master.key` |

「最近投递记录」显示最近 50 条（后端保留 200 条），列：时间、渠道、事件、标题、结果、尝试、错误。重试过程中的中间失败不单独记录，只记最终结果与总尝试次数。随页面刷新自动更新。渠道数量上限 20 个。

### 配置变更窗口规则

窗口规则决定一个变更「什么时候适合 / 不适合做」，作用于：提交变更时的窗口检查、「推荐时间」的打分、[变更排期](go:schedule) 周视图的底色着色。**窗口规则是每个集群各自一份**（卡片标题写着「集群 显示名」）：先在顶栏切到目标集群再改；新接入的集群用默认规则。时间按**服务器本地时区**，窗口检查只在**提交（创建）变更时**按计划时间（立即执行则按当前时间）判断一次，审批拖延导致实际开始时间变化后不会重新判断。

**前置条件**：运维模式；修改需要 settings.edit（没有时规则只读，卡片上有黄色提示）。**后果**：保存后立即生效，不需要审批和重启，写审计（`settings.update`）；新增「禁止」规则会让相应时段的非紧急变更无法提交。

先看当前规则：「变更窗口规则」卡片标题后会写「N 条 · 默认规则」或「已自定义」；表格列：名称、星期、时间、模式、适用风险 / 类型、状态、操作。

**新增一条规则**：

1. 点卡片右上角「＋ 新增规则」。
   - 你会看到：右侧抽屉「新增窗口规则」，表单已预填：开始 `22:00`、结束 `06:00`、模式「不建议」，其余为空，「启用该规则」已勾选。
2. 「名称」填规则名（必填，最长 40 字符），例如 `周五晚高风险禁变`。
3. 「星期」勾选适用的星期；**不勾选 = 每天**。
4. 「开始（HH:MM）」「结束（HH:MM，可小于开始表示跨午夜；24:00 表示当天结束）」填 24 小时制时间，例如 `18:00`、`24:00`。
   - 开始不能写 `24:00`；起止不能相同（全天请写 `00:00`–`24:00`）；跨午夜的规则按「起点所在日」判断星期。
5. 「模式」选一项（含义见下表）。
6. 「适用风险」勾选低风险 / 中风险 / 高风险；**不勾选 = 全部风险**。
7. （可选）展开「限定变更类型」勾选实例操作、扩容、缩容、配置变更、进入维护、结束维护、延长维护、备份、恢复、滚动重启、滚动升级；**默认全部类型**。
8. （可选）「备注」最长 200 字符，会显示在提示里。保持「启用该规则」勾选，点「保存」。
   - 你会看到：抽屉关闭，提示「规则已添加」，列表出现新行；同时「变更排期」周视图对应时段按模式着色。
   - 与预期不符：抽屉里红字提示「请填写规则名称」「开始时间格式应为 HH:MM（00:00–23:59）」「结束时间格式应为 HH:MM（00:00–24:00）」「开始与结束时间不能相同（全天请用 00:00–24:00）」，或「窗口规则不合法：…」；修正后重试。

**其他操作**：列表里每行「编辑」（抽屉「编辑窗口规则」，保存提示「规则已更新」）、「删除」（确认框「删除窗口规则」→「确认删除」，提示「规则已删除」）、「状态」复选框（即时切换并保存，提示「规则已启用 / 已停用」）；卡片右上角「恢复默认」会用默认规则**替换全部**现有规则（确认框「恢复默认窗口规则」→「恢复默认」，提示「已恢复默认规则」，自定义的规则会丢失）。最多 50 条规则。

| 模式 | 提交变更时 | 推荐时间 | 排期周视图 |
|---|---|---|---|
| 禁止 | 命中则**拒绝提交**（提示窗口规则拦截），紧急变更可通过但给出警告并要求事后复盘 | 不会推荐该时段 | 红色斜纹 |
| 不建议 | 给出警告，仍可提交 | 降分 | 橙色 |
| 推荐 | 给出「落在推荐窗口」的通过提示 | 加分 | 绿色 |

默认规则（没有自定义过时使用，也是「恢复默认」的内容）：

| 名称 | 星期 | 时间 | 模式 | 适用风险 |
|---|---|---|---|---|
| 备份窗口 | 每天 | 01:30–04:00 | 不建议 | 中、高 |
| 业务高峰（上午） | 周一至周五 | 09:00–12:00 | 不建议 | 中、高 |
| 业务高峰（下午） | 周一至周五 | 14:00–18:00 | 不建议 | 中、高 |
| 夜间低峰 | 每天 | 22:00–06:00（跨午夜） | 推荐 | 全部 |

> 💡 默认规则里没有「禁止」模式的规则，所以默认情况下窗口规则只会警告，不会拦截；要硬性拦截请自行新增「禁止」规则。变更冻结期是比窗口规则更强的拦截，在「变更排期」页管理。

### 读「关于与升级」卡片

位于页面最下方，只读展示，数据来自平台自身的版本接口（登录即可看）。

1. 先看左上「版本 / 提交 / 构建时间 / Go 版本 / 系统与架构」确认当前运行的平台程序。
2. 看「数据 schema」：写着「X（程序支持 Y）」。X 是数据目录里记录的数据格式版本，Y 是当前程序支持的版本。
   - X 与 Y 一致：正常。
   - 后面带「待迁移」：数据目录比程序旧（没有 `VERSION` 文件的旧数据目录按 schema 0 处理）。新版程序可以迁移旧数据，升级流程里的「数据迁移」一步会处理；一直停在「待迁移」说明迁移没有完成，到「最近升级历史」看有没有失败或回滚的记录。
   - 后面带「数据较新」：数据目录由更新版本的程序创建，当前程序为避免损坏数据会拒绝读取。按程序提示使用对应版本，或用 `admin rollback` / 从备份恢复。
3. 看「已运行」：进程运行时长与启动时间。刚升级完应该只有几分钟；如果远比预期长，可能是升级后没有真正重启，请对照「最近升级历史」确认。
4. 看「当前 release」「已安装版本」：只有平台按发布包布局安装在 `.../releases/<版本>/bin/` 下才显示；否则提示「未按发布包布局安装（开发 / 手工部署）」。「已安装版本」里标「（当前）」的就是正在运行的版本，其余是可回滚的旧版本。
5. 看「最近升级历史」（最近 10 条，来自数据目录 `upgrades.jsonl`）：
   - 列：时间、动作（安装 / 升级 / 回滚 / 数据迁移）、版本（旧 → 新）、结果（✔ 成功 / ↺ 已回滚 / 预演 / ✖ 失败）、回滚、备份、操作人。
   - 失败的行底色标红；鼠标悬停在「结果」上可看错误信息；「备份」列是升级前的数据备份文件路径，回滚或手工恢复时要用。
6. 最下面是页面内置的「升级与回滚操作说明」。

**页面不能直接升级**，升级在中控机上用命令完成（`<版本>`、`<架构>` 取自发布包文件名，例如 `1.4.0`、`amd64`）：

```
sha256sum -c tidbops-<版本>-linux-<架构>.tar.gz.sha256
tar xzf tidbops-<版本>-linux-<架构>.tar.gz
cd tidbops-<版本>-linux-<架构>
./bin/tidbops-server admin upgrade --dry-run
sudo ./upgrade.sh
# 需要手动回滚到上一版本时
sudo /opt/tidbops/current/bin/tidbops-server admin rollback
```

> ⚠️ 升级流程为：校验清单 → 备份数据目录到 `/var/backups/tidbops/` → 安装到 `releases/<新版本>` → 数据迁移 → 切换 current → 重启 → 健康检查，任一步失败会自动回滚。升级期间平台会短暂不可用（页面提示约 10–30 秒），**有执行中的变更时升级会被拒绝**，请先等变更结束或中止。该流程尚未在真实中控机上演练过，上线前请先在测试机完整走一遍预演、升级与回滚。详细步骤见 [安装部署](help:deploy)。

## 区域与参数说明

### 环境探测与取值优先级

页面顶部写明了优先级：**用户自定义 ＞ 自动探测 ＞ 默认值**。

| 来源标签 | 含义 | 何时出现 |
|---|---|---|
| 用户自定义（蓝） | 你点「覆盖」保存的值，优先级最高 | 该项存在覆盖值 |
| 自动探测（绿） | 后端采集到的值 | 没有覆盖值，且探测成功 |
| 未探测到（黄） | 探测失败或没有该数据，当前值显示「—」 | 没有覆盖值，且探测失败 |
| 默认值（灰） | 「用户自定义设置」里的内置默认 | 仅用户自定义设置项，值未改动 |

探测项没有「默认值」：探测不到又没有覆盖时就是「未探测到」，**不会阻塞其他页面**，只是该项显示「—」。

可探测的项（真实 / 回放模式）：

| 分组 | 项目 | 探测方式 | 探测不到时 |
|---|---|---|---|
| 中控机 | 主机 | `hostname -I` 的第一个地址 | 显示「未探测到」 |
| 中控机 | 操作系统 | `/etc/os-release` 的 PRETTY_NAME | 同上 |
| 中控机 | 内核 | `uname -r` | 同上 |
| 中控机 | CPU / 内存 | `nproc` 与 `free -m`，两者都成功才显示，如「8 核 / 32 GiB」 | 同上 |
| 中控机 | 时区 | `timedatectl` 的 Time zone 行 | 同上 |
| 中控机 | SSH 部署用户 | 拓扑里的 Deploy user | 同上 |
| tiup | tiup 版本 | `tiup --version` | 同上 |
| tiup | tiup cluster 组件版本 | `tiup cluster --version` | 同上 |
| 集群 | 中控机管理的集群 | `tiup cluster list` | 同上 |
| 集群 | 接入的集群 | 拓扑里的集群名 | 同上 |
| 集群 | TiDB 版本 | `tiup cluster display` 的 Cluster version（[输出说明](https://docs.pingcap.com/zh/tidb/stable/tiup-component-cluster-display)） | 同上；并影响「版本兼容性」 |

| 组件地址 | PD / Prometheus / Grafana / Alertmanager | `tiup cluster display` 里的各组件（Prometheus、Grafana、Alertmanager 的角色见 [监控框架](https://docs.pingcap.com/zh/tidb/stable/tidb-monitoring-framework)） | 该集群没部署（如没有 Alertmanager）时「未探测到」 |

| 控件 | 含义 | 可选值 / 默认 | 影响 |
|---|---|---|---|
| 覆盖 | 把该行变成输入框 | 值不能为空 | 保存后来源变「用户自定义」 |
| 保存 / 取消 | 确认或放弃输入 | 无 | 运维模式下，保存会立即把全部覆盖值写入后端 |
| 恢复自动 | 删除该项的覆盖值，回到自动探测 | 仅覆盖过的项显示 | 来源变回「自动探测」或「未探测到」 |
| 重新探测 | 在页面上逐条展示每项的探测命令与结果 | 探测中按钮置灰 | 见上文，只是演示 |

### 平台设置卡片（运维模式）

## 执行后果与风险

> ⚠️ 修改本页设置不会对 TiDB 集群执行任何命令，也不会重启 TiDB / TiKV / PD；但会影响平台自身的行为：负载均衡开关与负载均衡登记会改变后续变更计划的步骤，窗口规则会改变后续变更能否提交，通知渠道会向外部群发消息。

> ⚠️ 登记负载均衡只是平台里的一条记录：**不会改动 HAProxy / LVS / TiProxy 等设备**，不探测其健康，不会自动摘除或加回后端，也不要求写操作开关、不走审批。但它会让后续缩容 / 维护 TiDB 的变更计划多出「需人工确认」的摘除步骤；删除**最后一条**登记（且没勾复选框）则会让这个步骤消失，TiDB 将被直接下线 / 停止。

> ⚠️ 修改（覆盖、窗口规则、负载均衡复选框、负载均衡登记的增删改、通知渠道增删改与启停、测试发送）都会写入审计日志（动作如 `settings.update`、`lb.add / update / delete`、`notify.channel.add / update / delete / test`），不需要审批，**保存后立即生效，不需要重启平台**。

> ⚠️ 「发送测试」会真的把消息发到对应的企业微信 / 钉钉 / 飞书 / Lark / Slack 群（或「其他」的接收端），群成员都会看到；测试前确认群的订阅者，并避免对生产值班群频繁测试。

> ⚠️ 删除通知渠道后，Webhook 配置无法找回；停用比删除安全。更换 Webhook 地址或密钥时，旧值会被覆盖。

> ⚠️ 「恢复默认」窗口规则会丢失全部自定义规则；新增「禁止」规则会让相应时段的非紧急变更无法提交，请确认不会影响值班的紧急处置流程。

> ⚠️ `--notify-allow-hosts` 与 `--public-url` 是服务的启动参数，在页面上改不了，需要修改服务启动配置并重启平台；重启期间页面会短暂不可用。

> ⚠️ 备份数据目录时请连同 `master.key` 一起保存；丢失它将无法解密通知渠道，卡片会进入只读。

## 完整使用示例

示例 1：禁止周五晚高风险变更。

1. 在「变更窗口规则」点「＋ 新增规则」。
2. 名称「周五晚高风险禁变」，星期只勾「周五」，开始 `18:00`，结束 `24:00`，模式选「禁止」，适用风险只勾「高风险」，点「保存」。
3. 到「变更排期」周视图，周五 18:00 之后出现红色斜纹。此后提交周五 18:00 之后的高风险变更会被「窗口规则拦截」，紧急变更仍可提交但会警告并要求事后复盘。

示例 2：探测到的版本不在矩阵内。

1. 集群从 v8.5.2 升级到 v9.0.0 后，等到下一次刷新，「版本兼容性」变黄：「不在已验证的支持矩阵内（版本较新，尚未适配）」。
2. 顶部写操作标签变为「只读」，悬停可看原因；此时提交变更会被拦下，读取、诊断、巡检仍可用，数据可能有缺失。
3. 处理办法：回退到受支持版本，或等待平台适配后升级平台本身。在这里把「TiDB 版本」覆盖成 v8.5.2 **不能**解除降级。

通知渠道的完整示例见上文「配置通知渠道」四步。

## 常见问题与注意

- **「重新探测」没反应 / 值没变**：它只是演示，不重新连接集群。请点顶部横幅的「立即刷新」，页面会随后重绘；后端对强制刷新有 2 秒节流，快照另有缓存。
- **组件地址显示的是 10.0.1.21 之类的示例值，却标「自动探测」**：真实模式下如果读取 `tiup cluster display` 失败，PD / Prometheus / Grafana / Alertmanager 这几项后端不会返回，前端会退回显示原型的演示值。看到明显不属于你环境的地址，请当作未探测到处理，并检查 tiup 是否可用。
- **没有 settings.edit**：覆盖、保存、恢复自动、通知渠道、窗口规则的编辑控件会置灰或隐藏，「平台设置」卡片里有黄色提示；找管理员处理。
- **负载均衡卡片里「＋ 登记负载均衡」「编辑」「删除」是灰的**：你没有 settings.edit（只有内置管理员有），找管理员；已有 20 条时「＋ 登记负载均衡」也会置灰。更多负载均衡问题见 [常见问题](help:faq) 的「负载均衡」小节。
- **想改登记的 id**：不能改；删除后用新 id 重新登记（会写两条审计）。
- **想改登记的类型**：可以，「编辑」里改「类型」即可。
- **想改登录有效期**：当前固定为空闲 30 分钟、绝对 8 小时，页面上没有对应设置。
- **渠道保存失败提示「不在允许列表」**：见「配置通知渠道」第三步的排查表，私有网关需用 `--notify-allow-hosts` 追加。
- **通知卡片出现红色提示「渠道文件读取或解密失败，当前为只读」**：数据目录下的 `notify.json` 无法读取，或 `master.key` 丢失 / 与文件不一致；此时不能新增、修改、启停、删除，以避免覆盖原文件。检查后端日志与 `master.key`，从备份恢复。
- **「变更窗口规则」提示「没有窗口规则：任何时间都不做窗口检查」**：规则被删光了，点「恢复默认」或新增规则。

## 已知限制与易混淆点

| 界面写的是 | 实际是 | 建议 |
|---|---|---|
| 「当前生效值」「来源：用户自定义」 | 覆盖值只被记录和展示，后端采集与写操作闸门都不读取它；闸门用的是自动探测到的版本 | 要让平台改用某个地址，改启动参数并重启；不要把覆盖当成「修正」 |
| 「重新探测」按钮、「探测中…」动画与逐条命令输出 | 只是用当前快照里的值演示一遍，不重新连接集群 | 要重新取数点顶部横幅的「立即刷新」 |
| 「上次探测：N 分钟前」 | 页面加载时从固定的「3 分钟前」起算，不是真实探测时间 | 以顶部横幅的「采集于 hh:mm:ss」为准 |
| 「数据来源：replay（fixtures/control-node/ 录制数据）· 生产部署后切换为 live」 | 固定文案，不随实际模式变化 | 以顶部横幅（回放数据 / 真实数据）为准 |
| 「探测命令」列显示 `grep user ~/.tiup/…/meta.yaml` 等命令 | 这列是前端写死的说明文字；例如「SSH 部署用户」后端实际取自 `tiup cluster display` 的 Deploy user；「TiDB 版本」写了可用 `select tidb_version()` 交叉验证，实际没有做 SQL 交叉验证 | 当作大致说明，以后端实际来源为准 |
| 组件地址标「自动探测」却是 10.0.1.21 等示例值 | 后端没返回该项时前端回退到演示值，仍标「自动探测」 | 当作未探测到处理，检查 tiup 是否可用 |
| 「探测概况」里的提示「Alertmanager 未探测到：告警相关页面会提示“未配置”」 | 无论哪一项没探测到，这段提示都固定写 Alertmanager | 看表格里具体是哪一行「未探测到」 |
| 版本卡片红色「未获取到 TiDB 版本，所有功能不可用，请填写版本」 | 后端只在拿到版本且不在矩阵内时降级；版本为空时**不拦截**写操作；前端覆盖的版本值也不会传给后端 | 先查明为什么探测不到版本（`tiup cluster display` 是否可用），不要靠覆盖版本绕过 |
| 前端接受不带 `v` 的版本号（如 8.5.2） | 后端只认以 `v7.5.`、`v8.1.`、`v8.5.` 开头的版本 | 以 `tiup cluster display` 输出的 `vX.Y.Z` 形式为准 |
| 「演示：模拟探测到的版本」下拉框与「版本由 vA 变为 vB：…写操作已自动降级为只读」的黄色提示 | 仅在静态原型里改变探测版本；真实 / 回放模式下选择版本不改变集群版本，只触发一次演示探测并可能弹出与真实版本无关的「版本变化」提示，其中「写操作已自动降级」并未发生 | 真实 / 回放模式下不要使用，提示请忽略 |
| 「设计要点」：集群升级后自动重新探测并对比旧值；多集群时由用户选择接入哪些 | 「集群升级后自动重新探测并对比旧值」没有实现；「多集群」已在运维模式实现：主集群由启动参数 `--cluster` 或自动探测决定，其他集群由管理员在 [集群接入](go:clusters) 页接入，用顶栏下拉切换（页面里这段「设计要点」文字是旧文案） | 升级后点「立即刷新」；接入 / 切换集群见 [集群接入帮助](help:clusters) |
| 本页的覆盖值、通知渠道、窗口规则像是全平台一份 | 都是**当前所选集群**的，每个集群各一份（「关于与升级」除外）；非主集群的连接地址、账号等在「集群接入」页维护，不在这里覆盖，也不来自启动参数 | 改之前先看顶栏当前集群与卡片标题里的「集群 X」 |
| 「登录方式」「平台元数据存储」「审计保留期（天）」 | 只存字符串，不生效：只有本地账号（口令登录），TOTP 仅用于高风险变更二次确认；数据存在数据目录的 JSON 文件里；审计只追加，没有按天清理 | 不要指望改这三项改变行为；审计留存靠备份数据目录 |
| 抽屉里「发送测试」/ 行内「✔ 测试消息已发送」 | 表示机器人接口返回成功，不代表群里的人都看到 | 以目标群实际收到为准 |
| 通知「订阅事件」全选与一个都不选 | 两者等价，都是订阅全部 | 只想收部分事件才勾选 |
| 钉钉关键词提示「关键词设为 TiDB」（卡片说明与上文） | 平台消息里含「[TiDB 运维]」的是标题字段，钉钉是否把标题计入关键词匹配以实测为准 | 优先用加签；用关键词必须先「发送测试」 |
| 「通知渠道」卡片说明里的限速 20 条 | 这是平台对每个渠道的限速；IM 平台自己还有限速（企业微信官方 20 条 / 分钟，飞书 / Lark 100 条 / 分钟且 5 条 / 秒；Slack 官方这篇文档没有给出数字），超出可能被对方拒绝 | 少订阅高频事件 |
| 窗口检查 | 只在提交（创建）变更时判断一次，审批拖延后不重新判断；时间按服务器本地时区 | 排期时按服务器时区理解时间 |
| 卡片说「自动发现的 TiProxy 来自 tiup cluster display」 | 平台按拓扑模板**推断**该命令里 TiProxy 一行的格式（角色 `tiproxy`、端口列 `6000/3080`）；官方文档没有给出这一行的输出样例，**以真实集群为准** | 部署了 TiProxy 却没显示时，在中控机执行 `tiup cluster display <集群名>` 核对（`<集群名>` 见页面「集群」表里的集群名） |
| 「负载均衡」卡片里 TiProxy 的状态「运行中」 | 只是 tiup 报告的实例状态；平台不探测 TiProxy / HAProxy / LVS 的健康，也不检查客户端能否经它连上 TiDB | 业务连通性以应用与负载均衡自己的监控为准 |
| 登记表像是同步了 HAProxy / LVS 的配置 | 登记簿只是人手填的文字，平台不连接这些设备，不读取它们的配置；登记的后端写错、过期，平台只会提示「不一致」 | 负载均衡配置变了就回来「编辑」登记 |
| 登记的类型「TiProxy（自部署）」 | 只用于 tiup 之外自己部署的 TiProxy；与自动发现的 TiProxy 不做去重 / 关联，同一台两处都有会各出现一次 | tiup 部署的 TiProxy 不要再登记 |
| 复选框「集群前有负载均衡」：「保持不变」 | 复选框本身没变，但现在「勾选 **或** 有登记」都会触发人工摘除步骤；取消勾选后，只要还有登记，摘除步骤仍然存在 | 想让摘除步骤消失：取消勾选，**并**删除全部登记 |
| 自动发现的 TiProxy 不触发摘除步骤 | 因为 TiProxy 在本平台缩容 / 维护流程里的行为（后端发现延迟、连接迁移是否优雅、`graceful-wait-before-shutdown` 是否配置）没在真实集群验证过，保守起见不替你判断 | 见「与原有复选框的关系」；需要人工确认就勾选复选框 |
| 一致性提示 | 只比较 TiDB 的 `主机:SQL 端口`；不解析域名，不比较权重 / 健康检查；依赖缓存的拓扑快照，扩缩容后可能滞后；后端留空不检查 | 后端按 IP 登记；点横幅「立即刷新」 |
| 登记的修改历史 | 没有版本历史，只有审计；并发编辑「最后保存者胜」 | 改之前先点「刷新」；追溯看审计日志 |

- [TiProxy 简介](https://docs.pingcap.com/zh/tidb/stable/tiproxy-overview/)：TiProxy 能自动发现 TiDB server 列表；TiDB 缩容、滚动升级、滚动重启时迁移连接；TiDB 需配置 `graceful-wait-before-shutdown`（比应用最长事务时长大 10 秒以上）；限制（如 TiDB 意外故障时无法保持连接）。
- [TiProxy 部署拓扑](https://docs.pingcap.com/zh/tidb/stable/tiproxy-deployment-topology/)：拓扑文件里的 `tiproxy_servers`，示例 `port: 6000`、`status_port: 3080`；实例的 `host` 目前只支持 IP。
